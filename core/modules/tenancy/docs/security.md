# tenancy: security

Read before changing the module ([security §8](../../../../docs/rules/security.md#8-conduct)); two reviews.

- **The four paths** (`domain/store.ts`), the first three on the module's own `app` client and no other, the fourth on the caller's run:
  - `memberships`, a tenant table, inside `withTenant` for one workspace, as the service principal `tenancy`: the tenant client adds `workspace_id` to every query;
  - `users`, `organizations` and `workspaces`, global tables, outside any run through `withoutTenant("tenancy")`, which logs the reason;
  - the one read of a tenant table across workspaces, `membershipsOfUser(userId)`: a user's own memberships, never a workspace's members. `listMemberships` and `resolveMembership` are built on it. It refuses an empty or missing user id, which Prisma would drop from the where, listing every membership. A second such read is a security change, reviewed as one.
  - `oldestOwner(workspaceId)`, for `workspaceOwner` (gamma-p3-030): `memberships` read in the caller's own tenant run, on its client, which adds the run's `workspace_id`, so another workspace's id finds nothing; it answers a user id only, and refuses an empty or missing workspace id.
  - the members commands (gamma-p6-030), `listMembers`, `changeRole`, `removeMember` and `findActiveMembership`, in the caller's run in the same way, the request's run for the routes: its client scopes every `memberships` query to the run's workspace, and reads the members' `users` rows by their ids. The one raw query, the lock, names the run's workspace itself, since the tenant client does not scope raw SQL.
  - `runOrganization()`, for `sharingGroupOf` (gamma-rf-010): the run's own workspace's row of `workspaces`, read on the caller's run by the run's workspace id (`currentTenant()`), never an id a caller passes, so a run learns its own organization only and contacts never takes a group's id from a caller.
- **Isolation**: `tests/tenancy.test.ts` registers `memberships` in the two-workspace harness.
- **Personal data**: `users.email` and `users.display_name`, the account holder's own. `users` is global, so the `/// pii` marking, which needs a tenant table, is not used (an Open question of alpha-p3-010). `GET /v1/me` answers them to their owner only; no log line carries them.
- **The feedback link**: `FEEDBACK_URL`, the operator's, reaches every signed-in user through `GET /v1/me` and every page's header. It must be `https:`, checked at start, so the link is never `javascript:`, `data:` or plain http; the web opens it in a new tab with `rel="noopener noreferrer"`, so the page it opens gets neither the app's window nor its address.
- **Who may do what**: `GET /v1/me` needs a session and returns the caller's own data. `workspace.read` is every role's; the roles are enforced from alpha-p3-030. `members.manage` (Owner) changes a role and removes a member; listing the members is `workspace.read`. The caller is the run's principal, never a value of the request: no one changes their own role or removes themselves (`member_is_self`).
- **Removal ends access on the next request**: identity's resolver reads the membership on every request, with no cache, and every read of memberships skips a removed one, so the member's next request to the workspace is refused (403) as a stranger's; their session lives on for their other workspaces. A role change holds from the next request the same way.
- **The last Owner**: `changeRole` and `removeMember` lock the target and the workspace's active Owner rows (`SELECT … FOR UPDATE`, in id order, so two changes never deadlock) before they count the Owners, so two Owners demoting or removing each other at once leave one Owner (`last_owner`); a test runs the two on two connections.
- **Input**: every command parses its input with Zod (`domain/rules.ts`); an error names the fields at fault, never a value. The email CHECK refuses an address not lowercased, whoever writes it.
