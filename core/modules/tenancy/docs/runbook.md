# tenancy: runbook

- **Settings**: `ORGANIZATION_NAME`, `WORKSPACE_SLUG`, `FEEDBACK_URL` (README "Settings"); a value off the rules stops the api's start with `config_invalid`, `details.block` `modules/tenancy`, `details.variables` naming the variable. No "Give feedback" link in the header: `FEEDBACK_URL` is unset.
- **Logs**: every read of the global tables logs `tenant: running without a tenant context` with `reason: "tenancy"`.
- **Failure modes**: `organization_exists` (409) when the bootstrap slug is taken: pick another `WORKSPACE_SLUG`; `workspace_exists` (409) from `createWorkspace`: the organization has a workspace with the slug, pick another; `organization_not_found` (404): no organization has the id; `user_not_found` (404) on `GET /v1/me` when the session's user has no row: the authentication adapter and `users` disagree.
- **Members** (README "Members"): `membership_not_found` (404), the workspace holds no such membership, or it was removed (a role change); `member_is_self` (409), the caller's own row: another Owner changes it; `last_owner` (409), the change would leave the workspace with no active Owner: make another member an Owner first.
- **A removed member still sees the workspace**: the screen they have open shows what it read until its next request, which is refused. If the next request still answers, their membership is active: the removal did not commit (its DELETE did not answer 204), or they were invited again and signed in, which makes it active. Read it with `SELECT role, removed_at, removed_by FROM memberships WHERE workspace_id = '<id>' AND user_id = '<id>'` as the owner role; there is no cache to clear.
- **Restoring a removed member**: invite them again; their next sign-in accepts the invite through `addMember`, which makes the same membership active with the invite's role and clears `removed_at` and `removed_by`. Inviting an email invited before renews its accepted invite (identity's README "Invites").
