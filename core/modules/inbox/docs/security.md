# inbox: security

- **Only the platform's threads:** the receiver keeps a message only when an outreach row of the account matches it (beta-p0-060), so `threads` never holds a personal conversation (RB-13.1.3).
- **The text's path:** the provider's webhook, the receiver's file under the workspace's raw/ (72 hours), the store's read, `messages.body`, and a member's read of the thread (beta-p5-040). Never an event, a workflow input or history, an activity's answer, a metric label or a log line; the store deletes the file once its run committed.
- **No model:** the stop and the opt-out are code and a phrase list; the module does not depend on `@whytide/ai`, and the store calls no model (`tests/safety/reply-hold.test.ts`).
- **Toward the stop:** the hold runs first, also without the file, and the receiver's `last_inbound_at` blocks the person's next step at the gate before the store runs. A false positive suppresses: an opt-out is never removed.
- **The tester's own messages** (beta-p5-020): a message typed on LinkedIn on a platform thread records the person's touch in the run that stores it, so the gate sends no follow-up that local day (`tests/safety/tester-touch.test.ts`). A campaign message's text is the one approvals froze, never the provider's copy; its provider refs come from linkedin's `sentMessageRef` and stay in `messages`, and the unmatched line names the step's id only.
- **Who reads:** the routes' permissions (beta-p5-040), `inbox.read` (the list and a thread) and `inbox.label` (a reply's label), Owner, Admin and Member: every member reads every thread of the workspace and labels any reply, since only the platform's threads exist (above) and beta has one sender per workspace. The routes read inbox's tables and contacts' `getLead`, call no provider and send nothing; the screens have no reply box. Workspace isolation as every tenant table, `reply_labels` included (`tests/tenancy.test.ts`); another workspace's thread is not found.
- **Erasure:** `erasePerson`, through privacy's deletion script, whose run locks the lead before any of inbox's rows go, as the store's hold does, so a store during the erasure waits for it. A reply stored after it writes nothing back: the store asks contacts whether it still knows the person, and deletes the file. A reply mail after it sends nothing (`gone`).
- **The reply mail** (beta-p5-030): one mail per reply, to the sender account's owner only, the address tenancy holds for that user; none to a disabled user or an id that is no user. It holds the person's first name, folded to one line and at most 50 characters, else "a lead", and the thread's link, which opens behind sign-in: never the reply's text, the person's other names, the company or the account's label, so a forwarded or leaked mail tells little. Its workflow input, history and answer carry ids and codes only, and its log line ids.
- **The reply golden set** (beta-p7-030): a way for data to leave, to a member with `inbox.read` (the route) or the operator on the machine (`pnpm inbox:export-labels`), with the workspace's own replies only, read in its tenant runs (the api's `tests/inbox-exports.test.ts`, two workspaces). A line holds the conversation's texts, which are personal data: the person's first and last names masked, the person and the thread as the sha256 of their ids, no other id and no member. Another name in a text, a colleague's or the sender's, stays: the operator reads the file before it leaves the machine. The file lives under the workspace's `exports/`, 7 days at most: an erasure leaves a file already written until it expires, as it does qualification's golden set. Nothing logs a line, and the command prints counts, keys and codes only.
