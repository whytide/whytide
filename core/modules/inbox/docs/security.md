# inbox: security

- **Only the platform's threads:** the receiver keeps a message only when an outreach row of the account matches it (beta-p0-060), so `threads` never holds a personal conversation (RB-13.1.3).
- **The text's path:** the provider's webhook, the receiver's file under the workspace's raw/ (72 hours), the store's read, `messages.body`, and a member's read of the thread (beta-p5-040). Never an event, a workflow input or history, an activity's answer, a metric label or a log line; the store deletes the file once its run committed.
- **No model in the stop:** the stop and the opt-out are code and a phrase list, and the store calls no model; the classifier (gamma-p4-040) is the module's only caller of `@whytide/ai`, after the stop in its own workflow, and nothing the store's run imports reaches it (`tests/safety/reply-hold.test.ts`).
- **What the model sees** (gamma-p4-040; README "The classifier"): the reply and its thread's last 6 messages before it, each with its author (`lead` or `seller`) and day, in data blocks, with the person's and the thread owner's names, email addresses, phone numbers and links masked first (`domain/classify/mask.ts`; the input's schema masks the last three again, whatever a caller sends); another name a reply holds stays. No tool: the answer is a label, a confidence and a date, and code picks every action, so an instruction in a reply changes no action but its own label. A model's `opt_out` suppresses at any confidence, a phrase's stands whatever the model answers, and a failed classification acts on nothing (`tests/safety/classify-opt-out.test.ts`). The masked texts are in the decision record's raw prompt only, purged after 30 days; the event, the workflow's input, answer and history and the log lines hold ids, statuses and the label.
- **Toward the stop:** the hold runs first, also without the file, and the receiver's `last_inbound_at` blocks the person's next step at the gate before the store runs. A false positive suppresses: an opt-out is never removed.
- **The tester's own messages** (beta-p5-020): a message typed on LinkedIn on a platform thread records the person's touch in the run that stores it, so the gate sends no follow-up that local day (`tests/safety/tester-touch.test.ts`). A campaign message's text is the one approvals froze, never the provider's copy; its provider refs come from linkedin's `sentMessageRef` and stay in `messages`, and the unmatched line names the step's id only.
- **Who reads:** the routes' permissions (beta-p5-040), `inbox.read` (the list and a thread) and `inbox.label` (a reply's label), Owner, Admin and Member; and each member their own senders' threads only, whatever their role (gamma-p6-060): every read of threads and messages filters on `owner_user_id`, the principal's user id, and every route that takes a thread or message id answers the thread's owner only. Another member's thread is `thread_not_found` and their message `inbox_message_not_found` (404, not 403), as another workspace's, so the answer says nothing of whose it is. No cross-user view, an Owner's included: each would need the audit log (RB-13.1.3), which comes later; a removed member's threads stay, read by no one. A reply's label is its thread owner's alone since gamma-p4-055, since the label runs the reply's default action, an opt-out among them (`tests/label.test.ts`, the api's `tests/inbox-threads.test.ts`). The routes read inbox's tables and contacts' `getLead` and call no provider; the reply route only writes the row and its event (below). Workspace isolation as every tenant table, `reply_labels` included (`tests/tenancy.test.ts`); another workspace's thread is not found.
- **Erasure:** `erasePerson`, through privacy's deletion script, whose run locks the lead before any of inbox's rows go, as the store's hold does, so a store during the erasure waits for it. A reply stored after it writes nothing back: the store asks contacts whether it still knows the person, and deletes the file. A reply mail after it sends nothing (`gone`).
- **The reply mail** (beta-p5-030): one mail per reply, to the sender account's owner only, the address tenancy holds for that user; none to a disabled user, an id that is no user, or a user who is no longer an active member of the thread's workspace (gamma-p6-060), since a removed member keeps their user and their session for other workspaces and hears nothing more about this one. It holds the person's first name, folded to one line and at most 50 characters, else "a lead", and the thread's link, which opens behind sign-in: never the reply's text, the person's other names, the company or the account's label, so a forwarded or leaked mail tells little. Its workflow input, history and answer carry ids and codes only, and its log line ids.
- **The reply golden set** (beta-p7-030): a way for data to leave, to an Owner or an Admin with `inbox.export` (the route, the replies of the caller's own threads only, gamma-p6-060; a Member refused `forbidden` since gamma-p7-060, as exports are Owner only) or the operator on the machine (`pnpm inbox:export-labels`, every member's), with the workspace's own replies only, read in its tenant runs (the api's `tests/inbox-exports.test.ts`, two workspaces). A line holds the conversation's texts, which are personal data: the person's first and last names masked, the person and the thread as the sha256 of their ids, no other id and no member. Another name in a text, a colleague's or the sender's, stays: the operator reads the file before it leaves the machine. The file lives under the workspace's `exports/`, 7 days at most: an erasure leaves a file already written until it expires, as it does qualification's golden set. Nothing logs a line, and the command prints counts, keys and codes only. Since gamma-p7-060 a line also holds the thread's channel, the owner's class, the phrases' match and the classification's label, confidence, suggestion, origin and prompt version: words and numbers, no text or id.
- **The report** (gamma-p7-060; README "The report"): the operator's command, with no route, run as the service `inbox` in each workspace's own tenant run; it reads ids, labels and instants, never a text, writes nothing, calls no provider, and prints workspace ids, ISO weeks, counts and shares only (`tests/report-cli.test.ts`).
- **Replies from the inbox** (gamma-p4-060; README "Replies from the inbox"): a send path. `inbox.reply`, Owner, Admin and Member, and the caller's own thread only: another member's, like another workspace's, is `thread_not_found`, and the row keeps the member (`created_by`). Contacts' suppression is asked at the press and again in the run before the reservation, under the lead's lock; linkedin's `reserveSend` and its send activity read the platform's, the workspace's and the account's switches, the account's health, hours and budgets, and the gate again before the call, so a reply is one of the account's 200 actions a day and the closed switch of an instance that never opened sending refuses it. One `Idempotency-Key` per press, one workflow per message, one slot per message id: a press twice sends once. An unknown outcome is only checked, never sent again. The text goes from the row to the request file under the workspace's raw/, which linkedin's activity reads: never an event, a workflow input, answer or history, or a log line; the file is deleted once the reply settles. No model in the path (`tests/safety/reply-from-inbox.test.ts`).
- **The reply draft** (inbox-reply-draft; README "The reply draft"): `inbox.reply` and the caller's own thread only, with the reply's checks at the request (the channel, contacts' suppression under the lead's lock), so no draft is written for a person Whytide must not contact; another member's thread, like another workspace's, is `thread_not_found`. The draft sends nothing: Use draft fills the reply box, and Send's route, checks and run are unchanged (`pnpm -F inbox test:safety`). The writer is messaging's `writeReply`: the dossier built as the requester, the conversation and the brief as untrusted data blocks, the answer checked by messaging's gates (no invented name, number or date, no placeholder, no red-line phrase, no colleague's signal) and written again once, else `gates_failed`. The brief, the conversation and the draft cross only inside the worker's process: the event and the workflow's input carry the draft's id, its answers and history statuses and codes, the log lines ids, and the GET never answers the brief. The rows are workspace-isolated (`tests/tenancy.test.ts`) and go with their thread, so with the person at an erasure.
