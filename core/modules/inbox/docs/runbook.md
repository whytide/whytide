# inbox: runbook

One setting, `AI_MODEL_INBOX_CLASSIFY_REPLY` (README "The classifier"). Logs: the worker's lines for the activities `inbox_store`, `inbox_mail_reply`, `inbox_reply_begin`, `inbox_reply_settle`, `inbox_write_reply_draft`, `inbox_reply_draft_failed`, `inbox_sweep_reply_drafts`, `inbox_classify` and `inbox_classify_failed`, ids only; this module logs two lines itself, `inbox: no reply mail, the owner is unavailable`, with ids, and `inbox_sent_message_unmatched` (below).

- **A reply not stored:** find `linkedin.message_received` in `outbox` by `payload.person_id`. None: the receiver dropped or never got it (linkedin's runbook, `linkedin_event_receipts`). Not delivered: the worker's outbox. Delivered: the workflow `inbox.message:<workspaceId>:<event id>` in Temporal, whose activity's last failure names the code.
- **`inbox_file_invalid`:** the file did not parse, or its direction is not the event's. An inbound message's steps are held; the file stays under `raw/linkedin/messages/` for 72 hours. Read it through the files port, never into a log.
- **A missing file:** the steps are held and nothing is stored: the worker was down past raw/'s 72 hours. The message is lost to the inbox; the gate's `last_inbound_at` stays.
- **A failed run** (`sender_account_not_found`, the database): the run rolls back with its hold, and Temporal tries it again; the receiver's `last_inbound_at` keeps the gate blocking the person's next step meanwhile.
- **A wrong opt-out:** an opt-out is never removed (contacts).
- **`inbox_sent_message_unmatched`** (beta-p5-020): a sent message step whose `campaigns.step_sent` found no `succeeded` step, no approved text (approvals' `approvedContent`) or no refs (linkedin's `sentMessageRef`, the outreach row's last send), or whose ref another step's row holds. The line names the step's id: read the step, its approval item and the person's `sender_outreach` row. Its message stays out of the thread; the echo, if it came, stays the user's.
- **A reply mail not received** (beta-p5-030): find the reply's message, its `owner_notified_at`. Set: the mail went; in development it is in Mailpit (the shared stack's inbox), else the owner's mail server has it. Unset: the workflow `inbox.reply_mail:<workspaceId>:<messageId>` in Temporal. None: `inbox.reply_received` was not delivered (the worker's outbox). Ended: its answer's `reason`, `owner_unavailable` for an owner who is no user or is disabled (the worker's `info` line names the ids), `gone` for a reply erased since. Failed: the activity's last failure names the code: the port's `mail_unreachable` (the SMTP settings, `PROVIDER_APP_MAIL`) after five attempts; `mail_rejected` (the server refused the mail for good: the owner's address, the sender, the content) or `mail_input_invalid` (an address the port refuses) after one, since a second would get the same answer (gamma-p0-085). A mail without a link: `APP_PUBLIC_ORIGIN` is empty in the worker's environment.
- **The reply golden set** (README "The reply golden set"): `pnpm inbox:export-labels [--workspace <id or slug>] [--week 2026-W44]` on a laptop; on the production machine, from `deploy/`, `docker compose exec -e LOG_LEVEL=warn api node ../../modules/inbox/dist/cli/export-labels.js [options]` (`LOG_LEVEL=warn` hides the platform's JSON log lines). The last line, `reply_labels_total`, gives beta's two numbers: the replies labeled, and the testers with a positive reply. `files_too_large`: a workspace's set passed 25 MiB, export it by week. `week_invalid`: a week its year does not have, or one not started. A file stays 7 days under `exports/`; read it before it leaves the machine.
- **A reply left "Sending"** (gamma-p4-060): the message's `send_status` is still `sending`, and its thread shows it Sending (gamma-p4-061: the page reads the thread again every 3 seconds for two minutes, then at a reload). Find the workflow `inbox.reply:<workspaceId>:<messageId>` in Temporal. None: `inbox.reply_requested` was not delivered (the worker's outbox). Running: it waits between checks, up to 12 hours each (the account's `retry_at`, a switch, a disconnection); the history names the last activity. Ended with `{ status: "sending" }`: three checks found no answer. Read linkedin's `sender_action_log` rows whose `object_ref` is the message's id and its `sender_quota_reservations` row by `idempotency_key`: a committed slot with an `ok` log row went out, and its echo, once it came, is in the thread as typed on LinkedIn; a released one did not, and the member can send again. Never start a second send of the same message: a new press is a new row. The request file under `raw/inbox/<messageId>/` expires after 72 hours.
- **A reply "Not sent"**: the thread shows the reason in words, never the code (README "Replies from the inbox"); the row's `error_code` says why, linkedin's refusals (`sending_closed`, a stop or a pause, `outside_working_hours`, the day's caps) or the port's code after the call (linkedin's runbook); `person_suppressed` and `reply_channel_unavailable` are inbox's checks. Nothing to repair: the member sends again once the cause is gone.
- **A reply draft left "Drafting"** (inbox-reply-draft): the thread's `reply_drafts` row is still `drafting`, and the screen, after 10 minutes of reads, says it takes longer than usual. Find the workflow `inbox.reply_draft:<workspaceId>:<draftId>` in Temporal. None: `inbox.reply_draft_requested` was not delivered (the worker's outbox). Running: the writer's activity, two model calls at most, three attempts of 3 minutes. Failed: the draft is `failed` with the code (a provider's, as `llm_provider_error` or `llm_error_unmapped` when the model's credits ran out, else `write_failed`). The sweep (`inbox.reply_draft_sweep`, every 15 minutes) fails a draft still drafting 30 minutes after its request, `draft_stuck`; the member asks again. Nothing to repair: a new request replaces the draft.
- **A reply draft "failed"**: the row's `error_code` says why, and the screen says it in words: `gates_failed` or `ai_failed` (the model's answers broke the checks twice: an invented name or number, a placeholder; the brief can name what the reply should say), `dossier_lead_not_found` or `conversation_empty` (the lead or the conversation unreadable), `draft_requester_not_member` (the member left the workspace). The decision record (`decision_record_id`) holds the call; the model's setting is messaging's `AI_MODEL_MESSAGING_WRITE_REPLY`.
- **A reply without a classification** (gamma-p4-040): find the workflow `inbox.classify:<workspaceId>:<messageId>` in Temporal. None: `inbox.reply_received` was not delivered (the worker's outbox). Failed attempts of `inbox_classify` name the code: the LLM port's (`llm_provider_error`; `llm_error_unmapped` when the model's credits ran out) or `classifier_agent_not_loaded` (the worker did not load the agents). Past three, `inbox_classify_failed` stores `other`, suggested, origin `fallback`, which acts on nothing: the person stays held, and the thread's owner decides. Nothing to repair: the stop never waited for it.
- **The reply numbers** (gamma-p7-060, README "The report"): `pnpm inbox:report [--workspace <id or slug>] [--since 2026-11-01]` on a laptop; on the production machine, from `deploy/`, `docker compose exec -e LOG_LEVEL=warn api node ../../modules/inbox/dist/cli/report.js [options]`. It writes nothing and calls no provider. Read it against gamma's targets, printed on each line: `reply_rate_linkedin` ≥ 0.06 (signal-sourced leads touched on LinkedIn, `touched`, and those with a human reply, `replied`); `positive_conversations` ≥ 1, the mean of the `positive_week` lines above it, one per workspace-week with a send; `classifier_agreement`, the F1 of `interested` ≥ 0.93 and the opt-out share ≥ 0.99, on the replies the threads' owners labeled and the classifier classified. `none`: nothing to count yet (no touch, no active week, no owner's `interested` or `opt_out`). `too_few`: under 30 such pairs; the owners have to label more replies, and gamma-p7-065's synthetic set is the check meanwhile. A low agreement: export the golden set (`pnpm inbox:export-labels`) and compare `class_label` with `classification` line by line, before changing the prompt or the classifier's constants (the 6 earlier messages, the 90 days of a return date). `workspace_not_found` (exit 1): the id or slug names no workspace.
