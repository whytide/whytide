# inbox

The replies of the persons Whytide contacted (beta-p5-010): each message linkedin's receiver kept is stored in its thread, and in the same transaction every pending step of its person is held, so the sequence stops. A reply that asks to stop also suppresses the person. No model is in this path. The account's own messages are in the thread too (beta-p5-020): the platform's, once each, with who approved them, and the ones the tester typed on LinkedIn, as theirs, each that day's touch. The thread's owner replies from the thread too, on the thread's own channel, LinkedIn's for now (gamma-p4-060, "Replies from the inbox"), and can ask the AI for a draft of the reply first, which only fills the reply box (inbox-reply-draft, "The reply draft"). Each stored reply is then classified, after the stop and outside its path, into one of 7 labels whose default action campaigns runs (gamma-p4-040, "The classifier").

- **Owns:** `threads`, `messages`, `reply_labels`, `reply_drafts` and `reply_classifications` ([docs/data.md](docs/data.md)); the events `inbox.reply_received`, `inbox.reply_requested`, `inbox.reply_draft_requested` and `inbox.reply_classified`; subscribers to `linkedin.message_received`, `campaigns.step_sent` and its own events; the agent `inbox.classify-reply` (`agents/classify-reply/`); the workflows `inbox_store_message`, `inbox_reply_mail`, `inbox_send_reply`, `inbox_draft_reply`, `inbox_reply_draft_sweep` and `inbox_classify_reply`, and the schedule `inbox.reply_draft_sweep`; the routes under `/v1/workspaces/{workspaceId}/inbox` and the "Inbox" screens (beta-p5-040, "API" and "Screen" below).
- **Public interface:** `index.ts` (below).
- **Depends on:** `platform`, `db`, `providers` (the files port); `ai` (`defineAgentTask`, `callAgent`, `agentModel` and `registeredAgentTasks`), for the classifier only; approvals' `approvedContent`; campaigns' `events`, `holdForReply`, `sentStep`, and `applyReplyLabel` and `REPLY_ACTION_LABELS` for the classifier; contacts' `addOptOut`, `getLead`, `getPerson`, `lockLeadStatus`, `recordTouch`, `suppressionOf` and `errors`; linkedin's `events`, `findSenderAccount`, `messageFile`, `sentMessageRef`, `sendLogRows` for the report ("The report"), and for a reply `reserveSend`, `releaseSend`, `findSendReservation`, `sendRequestFile` and its send activities by name; messaging's `writeReply` and `REPLY_CHAT_MAX` for the reply draft; `tenancy` (`listWorkspaceIds` for the drafts' sweep, `findUser` for the classifier's mask and the reply mail, `resolveMembership` for the reply mail); `ui` for the screens. Nothing imports inbox but privacy.
- **Reviewers:** the owners of this module.

## Public interface

| Export | What it does |
|---|---|
| `erasePerson(personId)` | Deletes the person's messages and every message of their threads, then their threads, in the caller's tenant run; `{ messages, threads }`. privacy registers it. |

Also `events` (`inbox.reply_received { messageId, threadId, personId }`, for a newly stored reply only; `inbox.reply_requested { messageId }`, a reply from the inbox; `inbox.reply_draft_requested { draftId }`, a reply draft; `inbox.reply_classified { classificationId, messageId, threadId, personId, label }`, a reply classified, "The classifier"), `ids` (`thr`, `msg`, `rlb`, `rdr`, `rcl`), `errors` (`inbox_file_invalid` and `classifier_agent_not_loaded`, 500, and the routes' codes, "API"), `permissions` (`inbox.read`, `inbox.label`, `inbox.reply`, and `inbox.export`, Owner and Admin, the golden set's route, gamma-p7-060) and `api`, the routes the api host mounts.

## The store

`linkedin.message_received` starts `inbox_store_message` by the id `inbox.message:<workspaceId>:<event id>`, so a second delivery starts none. Its one activity, `inbox_store` (kind `provider`), reads the message's file outside any run; for an inbound message, one tenant run holds the person's steps first, always, then, with the file and a person contacts still knows, stores the thread and the message, suppresses the person on an opt-out phrase and publishes `inbox.reply_received`; for the account's own message, one tenant run stores it (below). The file is deleted once the run committed. The order: [docs/flows.md](docs/flows.md).

## The platform's own messages

beta-p5-020. A sent message step: `campaigns.step_sent` (`actionType = message`; an invite stores nothing) reaches a subscriber that writes in the delivery's own run (`domain/store/sent.ts`), from rows only: campaigns' `sentStep`, approvals' `approvedContent` and linkedin's `sentMessageRef`, the provider's refs linkedin's alone. Its message joins the chat's thread as `sent_by = campaign`, with the step, the approved text, `approved_by` and `approved_at`. The account's own message as the receiver keeps it, the echo (`direction = out`, `domain/store/echo.ts`): a row holding its `provider_message_ref` is the platform's, and nothing changes; any other is the tester's, typed on LinkedIn, stored as `sent_by = user` with contacts' `recordTouch(personId, sentAt)`. Whichever of the two comes first, one row stays: the step's event makes an echo stored first the campaign's. Each run locks the person's lead first; the step's event logs `inbox_sent_message_unmatched` with the step's id when one of the three reads answers null, a defect.

## Decided here

- Every inbound message the receiver kept holds, whatever the lead's status: the receiver keeps only messages on an outreach the platform started, so the person is in a campaign or past one. `holdForReply` leaves a suppressed lead suppressed.
- The store's order: the hold, then the account's owner, the thread, the message, the opt-out and the event, in one run. A missing file (raw/'s 72 hours) still holds and stores nothing. An invalid file, or one whose direction is not the event's, holds, stays for the runbook and fails `inbox_file_invalid`.
- The account's messages are stored once by `provider_message_ref`, in either order: the step's event finds an echo stored first as the user's and makes it the campaign's, with the approved text (the provider's copy is used only for a message no step sent) and the echo's `sent_at`, the provider's time; an echo that finds a row changes nothing (beta-p5-020).
- A message the tester types is a touch, not a hold: contacts' `last_touch_at` moves to its time, so the gate's one touch a day (`touched_today`) keeps a follow-up planned that day for the next; the steps stay as they are. A platform message's echo records no touch: the sender's commit did. An echo that comes before the step's event cannot tell the two apart and records one, seconds from the send's own, the same day.
- The step's event and the echo lock the person's lead before anything else, as privacy's erasure does before it deletes their rows: one that waits on an erasure then finds the person gone and writes nothing. The echo records its touch before its rows, so a person erased mid-run, one without a lead to lock (contacts' `person_not_found`), gets neither.
- The provider's refs come from linkedin's `sentMessageRef`, never from campaigns, and none crosses an event, a workflow input or an activity's answer. The step's event checks for a row holding its step before it reads them, since `sentMessageRef` answers the outreach row's last send only.
- A step without its send, its approval or its refs stores nothing and logs `inbox_sent_message_unmatched` (`error`) with the step's id: every `succeeded` message step has all three. So does a ref another step's row holds. The line goes through the host's logger, which `onWorkerStart` (`workflows/index.ts`) keeps.
- A person erased since the reply (contacts' `getPerson` answers `person_not_found`): nothing stored or published and the file deleted, as campaigns' enrollment does for `person_gone`, so the erasure sticks. The store reads it after the hold's lock on the lead, which an erasure that deleted the lead holds until it commits.
- The phrase list decides, no model: whole words, any case, after folding curly apostrophes to straight ones and every run of other characters to one space. "stop" counts only as the reply's first word, the whole reply included ("STOP.", "Stop, please"): elsewhere it is rarely a request, and an opt-out is never removed, so "can't stop thinking about it" and "non-stop" do not suppress. A request mid-reply counts through its own phrases, "stop messaging me", "stop contacting me" and "stop sending me", and "please stop" counts as the whole reply only, so "Please stop by our booth" does not suppress (beta-p5-010's review, beta-p5-030). The other phrases count anywhere, and a hyphen parts words ("opt-out").
- A repeat is a row already holding the message's `provider_message_ref`: the run ends there, with no event.
- The activity is `inbox_store`: the worker refuses a workflow and an activity of one name (`worker_duplicate_registration`).
- The eraser deletes every message of the person's threads too: the messages' foreign key holds a thread. It takes no lock: privacy's run locks the lead before it, after the platform's step, as the store's hold does (contacts' `lockLeadStatus`), so a store that runs during the erasure waits for it, then finds the person gone and writes nothing back (beta-p5-030; the race on the real erasure: `core/apps/worker/tests/inbox-store.test.ts`).
- Grants as alpha's tenant tables have them, the owner's default privileges; no row-level policy.
- `inbox_file_invalid` has a message key, though no screen shows it: messages:check asks one of every code.
- A reply's label lives in inbox's own `reply_labels`, one row per inbound message, changed in place and never removed: not the data model's reply classification, which gamma's own table holds apart (beta-p5-040). beta-p7-030's export reads it. Since gamma-p4-055 the row holds the thread owner's class too, one of the 7 (`class_label`), and `label` follows it, `positive` for `interested` and `not_positive` for the six others (the CHECK `reply_labels_class_label`), so the export keeps its two words; beta's rows have no class.
- No unread state, no views or filters (RB-13.1.1 reduced): the list is the caller's own threads, newest first, those of their own senders, whatever their role (gamma-p6-060, below). Replies from the app since gamma-p4-060, the thread's owner's only ("Replies from the inbox").
- The label's not-found code is `inbox_message_not_found`: the platform's i18n registers `message_not_found`, and the registry refuses a code twice.
- The label is a PUT that sets a state, so it takes no `Idempotency-Key`: the same label again changes nothing, its time and member included.
- The list's cursor is the last row's `last_message_at` and id, base64url, the keyset of its order; the screen reads 20 threads at a time (`ui/inbox/constants.ts`), the api 50 at most.
- The thread's page is `ui/inbox/thread-page.tsx`, beside the list's: `ui/thread/page.tsx` re-exports it, since web:routes mounts a page from `ui/<screen>/page.tsx`.
- One mail per reply, to the sender account's owner, the thread's `owner_user_id` (beta-p5-030): the workflow's id makes a second delivery start nothing, and `owner_notified_at` stops a retry once the mail went. It never carries the reply's text: the person's first name, "a lead" without one, and the thread's link. An opt-out reply gets its mail too, so the owner knows.
- The mail's first name is folded to one line, its direction marks dropped; a blank one, or one longer than 50 characters (`MAIL_NAME_MAX`), is "a lead" (beta-p5-030).
- No mail for a reply erased since its event (`gone`), nor for an owner who is no user, is disabled (beta-p5-030) or is no longer an active member of the thread's workspace (gamma-p6-060) (`owner_unavailable`): the workflow ends without an error, the latter logged with ids.
- The label is the thread owner's alone (gamma-p4-055), as gamma-p6-060 rules a thread's: another member's message answers `inbox_message_not_found`, as another workspace's does. The screen shows the label with nothing to choose where the reply state's `own` is false, which a thread the caller reads is not while no transfer of an account exists. Its run locks the person's lead before any write, then writes the row, then campaigns' `applyReplyLabel` takes the enrollments: the classifier's order.
- The owner's label acts as a confident one: `applyReplyLabel` with `suggested: false`, the reply's `sent_at` as `repliedAt` and, for `out_of_office`, the classification's return date. A label the row holds already writes nothing and acts on nothing; the owner's label equal to a confident classification already acted on is campaigns' repeat, so no second notice.
- The classifier acts only for a reply its thread's owner has not labeled: a label chosen before the model answers is the one that acts, and the classifier's row keeps `actions_taken` empty, but an `opt_out`, which suppresses whatever the owner chose (RB-13.2.2: when in doubt, suppress).
- An older reply's label is recorded and acts on nothing, as the classifier's newest-reply rule has it, but its `opt_out`: the owner's suppresses the person as the classifier's does (`optOutOnly`), since a label that says "opted out" with the person still contacted would mislead. Nothing lifts an opt-out: a label moved away from `opt_out` leaves the person suppressed, and the screen says so.
- The label shown is the owner's, not suggested, else the classification's with its `isSuggested`; a beta row, with no class, shows the classification. The list's `classification` follows the same rule, and a beta row still counts as labeled in `toLabel`.
- The control is a menu of buttons, not a select: a select changes on the arrow keys, which would label, and act, while a keyboard user browses. The suggestion's Confirm is one click; `opt_out` asks first.
- Each member reads their own senders' threads only (gamma-p6-060; RB-13.1.3 reduced): every read of threads and messages filters on `owner_user_id`, the principal's user id, which the store writes from the sender account's owner, so no column or backfill; another member's thread is `thread_not_found` (404) and their message `inbox_message_not_found`, as another workspace's: the answer says nothing of whose it is. No cross-user view, an Owner's included, until the audit log; a removed member's threads stay, read by no one, until a transfer exists. A service principal (`service:<name>`) owns no thread, so the routes' reads answer it none; the operator's command reads through its own function.
- Every later route that takes a thread or message id answers the thread's owner only, 404 for anyone else (`AGENTS.md`). The reply's and the reply draft's routes read the thread by its id and the caller's `owner_user_id`, and keep the reply state's `own` (the account's owner, as linkedin's `not_account_owner` reads it) beside: both must hold.
- The golden set's route passes the caller as the export's `owner`: the tenant client refuses a relation in a where, so the owner's replies' ids are read first, from their threads, then their labels. The file's name stays the day's or the week's, so two Owners or Admins exporting the same day replace each other's file under `exports/`; each answer holds the caller's own.
- The reply mail's check reads tenancy's `findUser`, then `resolveMembership` of the thread's workspace, both outside any run, as campaigns' reply notice does; its `owner_unavailable` line goes through the host's logger, which `onWorkerStart` keeps.
- The list's empty state reads linkedin's `GET …/accounts` beside the threads, as contacts' lead page does: no connected account of the member's own (`mine`) says to connect one; an accounts read refused leaves the plain empty state. The keys are `inbox.empty.no_sender` and `inbox.empty.connect`: the key check takes lower-case segments only, and the button has its own words, as approvals' empty state does.
- The CHECK `reply_labels_class_label` is expand-compatible: the previous release writes no class, so its rows and writes stay valid. During a deploy, the previous release changing a row the new one gave a class is refused by the CHECK (its PUT answers 500) until the new release is up.

## Open questions

- An invalid file fails all five attempts of a `provider` activity: a module cannot mark its own code not retried (the worker's `NOT_RETRIED`).
- Whether a message the tester types should also hold the person's pending steps (beta-p5-020; a Finding): here it is a touch only, and the tester can skip the next step in "Up next".
- A reply that begins "Stop by Tuesday" still suppresses for good: "stop" counts as the first word. Any reply holds the sequence all the same.
- Replies from the inbox (gamma-p4-060): campaigns' report counts a reply's log rows as `send_step_missing`, its `sendLogRows` mapping `sx_` refs only (gamma-p7-050); linkedin's `recordSend` moves the outreach row's last send to the reply, so a campaign's `campaigns.step_sent` handled after a reply finds no refs in `storeSent` (unmatched); the went-out check counts any message of the account's in the chat since the first reservation; linkedin's `rate_limited` is no registered code, so such a refusal keeps no code and the screen shows the generic reason. (The working hours and the email-only entry: the owner's decisions of 2026-11-02, under "Replies from the inbox".)
- The classifier (gamma-p4-040): a suggested label waits for the thread owner's confirmation (RB-13.2.2), gamma-p4-055's; until then only `opt_out` acts below `INBOX_CLASSIFY_SUGGEST_BELOW` (0.7 unset). The 6 earlier messages and the 90-day ceiling on a return date are constants to tune on gamma-p7-060's set. The masker knows the person's and the thread owner's names only: another name a reply holds, a colleague's, reaches the model.

## The reply mail

beta-p5-030: when a reply is stored, the owner of its sender account gets one email saying who replied, with a link to the thread, never the reply's text ([docs/flows.md](docs/flows.md#the-reply-mail), [docs/security.md](docs/security.md)).

- **The start:** the module's own subscriber to `inbox.reply_received` (`events.ts`) starts the workflow `inbox_reply_mail` with `{ workspaceId, messageId }` by the id `inbox.reply_mail:<workspaceId>:<messageId>`: a second delivery starts none.
- **The activity** `inbox_mail_reply` (`workflows/index.ts`, kind `provider`, five attempts, one for the two codes below) runs `mailReply` (`domain/mail.ts`): a tenant run reads the inbound message, its thread and the person's first name (contacts' `getPerson`); tenancy's `findUser` reads the owner, and `resolveMembership` their active membership of the thread's workspace (gamma-p6-060), outside any run; `renderMail("inbox.mail.reply", …)` in the owner's locale or the default, then the app-mail port's `send`; a second run sets `owner_notified_at` where it is still null.
- **The answer:** `{ sent: true }`, or `{ sent: false, reason }` with `already_sent` (the marker is set), `owner_unavailable` (no user, a disabled one, or one no longer an active member of the workspace: a removed member hears nothing more about it) or `gone` (the message, its thread or its person erased since). - **`reply_rate_linkedin: <share> touched=<n> replied=<n> target=0.06`:** among signal-sourced leads, those with a human reply on a LinkedIn thread from `--since` ÷ those with a LinkedIn touch from `--since`.
- **`positive_week: <workspaceId> <ISO week> <n>`**, one line per active workspace-week, by workspace then week: the leads whose first positive event falls in the week, each lead counted once in 90 days (`POSITIVE_REPEAT_DAYS`, rolling: the next counted event is 90 days or more after the last counted). A positive event is the owner's `interested` (beta's `positive` on a row with no class), or, where no owner labeled the reply, the classifier's `interested` when not suggested: an owner's other label cancels the model's (requirements/11 §2.1). Its time is the reply's `sent_at`. A workspace is active in a week with at least one touch from `--since`.
- **`positive_conversations: <mean> workspace_weeks=<n> positives=<n> target=1`:** the mean of `positive_week` over the active workspace-weeks; a week with no touch leaves the workspace out of the mean, its positives too.
- **`classifier_agreement: f1_interested=<share> opt_out_share=<share> pairs=<n> target_f1=0.93 target_opt_out=0.99`,** on the replies from `--since` with both an owner's label and a classification, whatever its origin: the F1 of the classifier's `interested` against the owner's `interested` (or beta's `positive`), and the share of the owner's `opt_out` replies classified `opt_out`. Under 30 pairs (`AGREEMENT_MIN_REPLIES`), `classifier_agreement: too_few pairs=<n>`.
- **Shares** have three decimals; `none` where nothing was counted. Weeks are ISO weeks in UTC. Without `--since`, every row.
- **Exit:** 0 printed; 1 `workspace_not_found: <id or slug>`; 2 the usage (an unknown option, a positional, a value missing, a day that is no calendar day).
- **Lines** hold workspace ids, ISO weeks, counts and shares only: never a text, a name or a person's id.
- **Decided here:** a human reply follows the owner's label before the classification's, as requirements/11 §3.2's notes count a reply the user marks as automatic out; a reply counts in the rate from `--since`, as the touches do, and only for a lead touched in the period; a positive event's week is the reply's `sent_at`'s, and the 90 days look at every reply, before `--since` too; activity is read from the same touches, the campaigns' invites and messages; the run's instant is not read: `--since` and the rows decide every figure. `reply_rate_email` waits for the email phase (gamma-p7-060's LinkedIn part): no email reply exists before gamma-p4-020's poller.
- **Tests:** `tests/report.test.ts` (on the worktree's database: the rate, the positive rules, the 90 days, the active weeks, the agreement and `too_few`), `tests/report-cli.test.ts` (the command's lines and exit codes); rows in `tests/report-fixtures.ts`.

## Addresses a person gave

gamma-en-085. `addressesGivenBy(personId)` (`domain/addresses/given.ts`), exported from `index.ts` and given to enrichment's `reply` source by `onWorkerStart` (enrichment's `useAddressesGiven`), in the caller's tenant run: of the person's own inbound messages (`direction = in`) in their LinkedIn threads (`GIVEN_CHANNELS`) that hold an email address, newest first, at most 5 (`GIVEN_MESSAGES`, read among the newest 50 holding an `@`), the addresses in each, lower case, each once, at most 10 a message. Never an address of the workspace's own messages to them, and never a text: the body is read and dropped in the function. Each `@` is read outwards within an address's bounds, so the scan is linear; a run longer than an address's part is no address. Inbox imports enrichment for that slot, never the reverse: enrichment never imports inbox, which imports campaigns. Tests: `tests/addresses-given-by.test.ts`. LinkedIn threads only for now: an email reply quotes the thread ("… <sender@ourco> wrote:"), so gamma-p4-020, which stores email replies, drops quoted text before it adds `email` to `GIVEN_CHANNELS`.

## Settings

The `modules/inbox` block of `deploy/.env.example`, `settings.ts`:
- `AI_MODEL_INBOX_CLASSIFY_REPLY`: the classifier's model ("The classifier").
- `INBOX_CLASSIFY_SUGGEST_BELOW` (0.7, a number above 0 and at most 1; the default `SUGGEST_BELOW` in `domain/classify/constants.ts`; env-settings-a): a label the model gives with less confidence is stored suggested, and campaigns acts on it only for `opt_out`. Raising it leaves more labels for the member to confirm. Unset or empty, 0.7; a value off its range stops the api's and the worker's start with `config_invalid` naming it. It is read once, as the module loads: **a changed value needs an api and worker restart**. `tests/settings.test.ts` sets 0.8 and tries the values off its range.
