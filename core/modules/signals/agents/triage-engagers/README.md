# signals.triage-engagers

The triage agent (signals-triage-ai): up to 25 of a run's candidates against the ICP's targeting, before their profiles are read, each skipped as a recruiter or a job seeker the ICP does not target, read first, or read. [README.md "Triage"](../../README.md#triage) says how a run uses it, [docs/security.md](../../docs/security.md) what the model may see.

- **Task:** `task.ts`: `kind: classification`, no tools, prompt version 1, a budget of 24,000 input tokens (the largest ICP and 25 headlines in a non-Latin script fit) and 2,000 output tokens, and no credits, as the triage has no price. A batch over the budget is refused before the model is asked and decided by the rules, as an `ai_failed` one is. The model is `AI_MODEL_SIGNALS_TRIAGE_ENGAGERS`, else the LLM port's first. The task file imports none of the module's registries (index, events, ids, errors), and the module never imports it: hosts load it from the sources (core/packages/ai README "Declaring a task"), and `triageCandidates` takes it from the agent registry.
- **Prompt:** `prompt.v1.md`, the system prompt. The data blocks, in order: `<icp>` (the ICP's `titles`, `seniorities`, `industries` and `mustHaves`, icp's `readIcpForScoring`; never its countries, sizes or disqualifiers) and `<candidates>` (up to `TRIAGE_BATCH_SIZE`, 25, each `{ index, role, headline }`: `role` `author`, `comment` or `reaction`; `headline` the staged headline scrubbed by rating's `domain/rate/scrub.ts`: links, emails, phone numbers and the engager's name as placeholders). Never a name, a profile URL, a company or a member reference. Its rules follow qualification's assess-fit prompt v2: a skip only when the headline clearly shows the kind and the ICP's titles, seniorities, industries or must-haves do not name it; an agency's owner is never a recruiter; `read_first` reads combined and shortened roles as `title_function` does. A changed prompt is a new file, `prompt.v2.md` with `promptVersion: 2`, and runs the evals.
- **Schemas:** `schemas/triage-engagers.ts`. The output: `decisions`, each `{ index, decision, code }`: `decision` `skip`, `read_first` or `read`, `code` `recruiter` or `job_seeker` for a skip, else null. A value off the lists fails the schema.
- **Gate:** `decisions` (`domain/triage/checks.ts`): each candidate of the input decided exactly once, no other index, and a code exactly for a skip. A failed schema or gate is retried once, the failure in `<validation_error>`, then the call is `ai_failed`, and the batch is decided by the rules.
- **Evals:** `core/packages/ai/evals/signals.triage-engagers/`, eight synthetic batches: a recruiter skipped against an ICP without recruiters and read against one whose titles hold "Recruiter", "#OpenToWork" skipped and read for an ICP that targets job seekers, "Founder, XYZ Staffing" kept for an ICP with "Agency Owner", "RevOps & GTM Lead" `read_first` for "Revenue Operations Manager", "Barista" read and never skipped, and an injection in a headline: `pnpm -F ai eval signals.triage-engagers`. Each case expects, per candidate, what a good model answers (`skip:<code>`, `read_first`, `read`, or `kept`, either read), so the same cases run live (`EVAL_LIVE=1`, by hand) after a prompt change. `outcome` 1 and `fails_safe` 1 (the injection: every decision as expected, or `ai_failed`), `skips` 1 (no candidate skipped that a good model reads), `decisions` 0.8, their share. On the fake, one case answers invalidly first (a skip without its code: the gate), to test the retry.
