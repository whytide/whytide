# signals

Where leads come from: a workspace's signal sources, each of a kind, the runs that read them into staged candidates, and the processing that makes those people, leads, events and evidence, or a salted hash. A kind is a folder under `sources/` that declares its config, its schedule, its reader, its event and its evidence; alpha ships one, `post_engagers`.

- **Owns:** `signal_sources`, `signal_runs`, `signal_candidates`, `signal_events` and `evidence` in `core/packages/db/prisma/schema/signals.prisma` ([docs/data.md](docs/data.md)), the registry of source kinds, the workflow `signals_run` and each source's schedule `signals-<sourceId>`, the evidence reduction (`signals_evidence_reduction`, its daily tick and the schedule `signals.evidence_reduction`) and `pnpm evidence:reduce`, the screen `ui/sources` and the lead page's evidence panel `ui/lead-evidence`.
- **Public interface:** `index.ts`: `api`, which the api host mounts; `events`; `erasePerson(personId)`, in the caller's tenant run, which deletes the person's events and evidence and returns the rows deleted by table, the deletion script's step (core/modules/privacy); `listEvidence(personId)`, in the caller's tenant run, the person's events, newest first, each with its evidence row or null, or contacts' `person_not_found` (the evidence route's read, and messaging's dossier's); `personReads(personId)`, in the caller's tenant run, the runs the person has events from, by run id, each `{ runId, candidates, personCandidates, candidateIds }`: the candidates the run staged (its counts' `staged`, never fewer than the person's), the person's events from it, and their candidates' ids, an event's id carrying its candidate's ULID since beta-p1-090 (credits' cost counter, alpha-p10-010); the registries `errors`, `ids` (`src`, `run`, `cand`, `sev`, `evd`), `permissions` (`signals.read`, `signals.write`, `signals.run`), `prices` (`signals.engager`, `signals.engager_read`) and `settings`; `workflows/` for the worker.
- **Depends on:** `platform`, `db`, `providers` (files); `linkedin` (its accounts, its read quota and its activities `linkedin_read_post_engagers` and `linkedin_read_profile`); `contacts` (persons, companies, leads, hashes, `countryOf`), `icp`, `qualification` (its hard filters, its batch and its re-score request), `onboarding` (the company's domain) and `tenancy` (its names); credits through the platform's port; the screen on `@whytide/ui` and the web's API client, through which it reads linkedin's accounts and an account's usage.
- **Reviewers:** the owners of this module.

## API

Under `/v1/workspaces/{workspaceId}/signals`; requests in `api-calls/alpha-p8-010-source-kind-registry.http`, `api-calls/alpha-p8-020-signal-run.http` (Run now and Stop) and `api-calls/alpha-p8-030-evidence.http`. A source is answered as its row, without `workspace_id` and the reader's `watermark`.

| Route | Permission | Does |
|---|---|---|
| `POST /sources` `{ kind, config, label, senderAccountId }` | `signals.write` | 201 with the source, enabled; publishes `signals.source_created`. `signal_kind_unknown` (400, `details.fields: ["kind"]`), `signal_config_invalid` (400, `details.fields`: `config.postUrl`), `signal_post_link_unreachable` (502, a short link's request failed), `signal_sender_account_invalid` (400, `details.fields: ["senderAccountId"]`), `signal_sources_limit` (400, `details.limit`) |
| `GET /sources` | `signals.read` | `{ sources }`, newest first, each with its next fire times, `runOpen` and `openRun` |
| `PATCH /sources/{id}` `{ enabled?, label? }` | `signals.write` | 200 with the source; enabling one counts against the limit; publishes `signals.source_updated` when `enabled` changes; `signal_source_not_found` (404) |
| `DELETE /sources/{id}` | `signals.write` | 204; deletes the source and its runs, publishes `signals.source_deleted` with its open runs' workflow ids, which the worker cancels |
| `GET /sources/{id}/runs` | `signals.read` | `{ runs }`: those not started yet first, then by `startedAt`, newest first |
| `POST /sources/{id}/run`, `Idempotency-Key` | `signals.run` | 202 with the run, `scheduled`; publishes `signals.run_requested`, from which the worker starts it; `@Idempotent()`; `signal_source_not_found` (404); `signal_run_open` (409) while one of its runs is `running` or `waiting` |
| `POST /sources/{id}/runs/{runId}/stop`, `Idempotency-Key` | `signals.run` | 202 with the run, its `stopRequestedAt` set (a second stop keeps the first's); publishes `signals.run_stop_requested`, on which the worker cancels it; `@Idempotent()`, a second stop 202 and published again; `signal_run_not_open` (409) once it is `done`, `failed` or `cancelled`; `signal_source_not_found` (404), for another source's run too |
| `GET /leads/{personId}/evidence` | `leads.read` (contacts') | `{ events, attribution }`: the person's events, newest first, each `{ id, kind, sourceId, sourceLabel, runId, occurredAt, evidence }`, the evidence `{ url, excerpt, commentText, reaction, author, capturedAt, reducedAt }` or null; the lead's sources in contacts' order (`getLead`), `{ first, others }`, each `{ kind, label }` (`signal` or `imported`; a signal source's label, null once deleted), null for a person without a lead; `person_not_found` (404) |

- The kind is checked against the registry on every write, the config against the kind's schema at the create, and the stored config is what the schema returns.
- Every source answered carries `fireTimes`, its kind's fire times from the save that come after its `lastRunAt` (all of them before its first run), oldest first, and `nextRunAt`, the first of them or null; a disabled source has `[]` and null (`domain/fire-times.ts`). alpha-p8-020 sets `lastRunAt` when a run starts.
- Every source answered carries `runOpen`: one of its runs is `running` or `waiting`, and run now answers `signal_run_open` until it ends; a `scheduled` run is not open. And `openRun`, that run as `{ id, status, stopRequestedAt }`, null when none is open; a scheduled run starts whatever is open, so of two, the running one, else the newest. A run answered carries `stopRequestedAt`, null until a stop is asked.
- `senderAccountId` must name a sender account of the workspace (linkedin's `findSenderAccount`), connected or not; a run checks that it is connected.
- At most `SIGNALS_MAX_ENABLED_SOURCES` are enabled per workspace. A create or an enable takes a transaction-level advisory lock on the workspace before it counts, so two at once cannot both pass.
- Events, ids only, in the transaction of the change: `signals.source_created`, `signals.source_updated` and `signals.source_deleted`, `{ source_id }`, the deleted one with `workflow_ids` when it had open runs; `signals.run_requested`, `signals.run_stop_requested` and `signals.source_blocked`, `{ source_id, run_id }`; `signals.person_found`, `{ workspaceId, personIds }` (below).

## Kinds

`post_engagers`: the people who reacted to, commented on or reposted one LinkedIn post. Config `{ postUrl }`: https on `linkedin.com` or `www.linkedin.com`, `/posts/<author>_<words>-activity-<id>-<code>` or `/feed/update/urn:li:activity:<id>`, with `share` or `ugcPost` in place of `activity` too; stored as `https://www.linkedin.com<path>`, without the query or the fragment. A short link from the Share button, `https://lnkd.in/p/<code>` or `https://lnkd.in/<code>`, is resolved at the create: one GET to it through `fetchSafe`, whose redirect is answered unfollowed, and its `Location`, when it is one of those post links, is stored the same way (`sources/post_engagers/post-url.ts`, its bounds in `constants.ts`). It runs at save, then three and seven days later, reading back `SIGNALS_POST_ENGAGERS_LOOKBACK_DAYS`. Its reader is linkedin's `linkedin_read_post_engagers`, 25 engagers a page.

## Adding a kind

1. A folder `sources/<kind>/` whose `index.ts` calls `defineSourceKind({ kind, configSchema, labelKey, lookbackDays, schedule, reader, event, evidenceOf }, import.meta.url)` (`sources/_contract.ts`); its settings in a `config.ts` of the folder, in the `modules/signals` block. The `reader` names a provider activity that writes a page to the files port and answers `{ key, count, nextCursor }`, the activity's input from the config, the page size, and `page(file, config, cut)`, the candidates of a page file; the `event` is `{ kind, objectOf(config) }`, the event's kind and what the candidates engaged with.
2. `pnpm -F @whytide/signals build`: `scripts/kinds-generate.ts` writes `sources/registry.generated.ts` (git-ignored), which imports every `sources/*/index.ts`; `build`, `typecheck` and `test` run it first, and so do the api's and the worker's `generate`. No other file changes.
3. Loading the module registers each kind. A name off snake_case fails the start with `signal_kind_invalid`; a name two folders declare with `signal_kind_duplicate`, `details.sources` naming both files.

## Runs

`signals_run` (`workflows/`), on the worker; [docs/flows.md](docs/flows.md) has the steps.

- **Schedules:** a source's own Temporal schedule `signals-<sourceId>`, made on `signals.source_created` with its kind's fire times and one run at once when the first has passed, paused while the source is disabled, deleted with it, through the platform's `createSchedule`, `pauseSchedule` and `deleteSchedule` (bound by the worker). An enable that finds no schedule (a source saved before alpha-p8-020, or whose created event failed) makes it, with one run at once when a fire time has passed since the last run.
- **By hand:** `POST …/run` writes the run, unless one of the source's is open (`signal_run_open`); the worker starts `signals.run:<workspaceId>:<runId>` in the delivery's workspace, so a second delivery starts none.
- **Stop:** `POST …/runs/{runId}/stop` sets the run's `stop_requested_at`; on `signals.run_stop_requested` the worker cancels its workflow by the id its start recorded (`workflow_id`, a schedule's run's too), else Run now's, and the run ends `cancelled` as any cancellation ends it (below). The worker cancels a `running` or `waiting` run only: one not started yet is left to its start (`signals_run_start`), which finds the stop, ends it `cancelled` and starts nothing; one that ended meanwhile needs nothing. A run the schedule started before fix-run-stop has no recorded workflow id, so Stop reaches it only through the derived id, Run now's, which a schedule's run does not have: cancel such a run in Temporal ([docs/runbook.md](docs/runbook.md)).
- **Deleting a source** stops its open runs: `deleteSource` reads their workflow ids before the delete takes the rows, `signals.source_deleted` carries them, and its subscriber cancels each after the schedule's delete.
- **A run:** per page one read of linkedin's quota and no credits; the kind's reader writes the page to `raw/signals/<runId>/<page>.json` under the workspace's prefix (72 hours); the engagers from the cut on (the watermark's `engagedAt`, else the lookback) are staged, once per member, reaction and run. The reading stops at a page that reaches the cut, or at the last; the processing (below) follows. The run ends `done`; `failed` with a code (`insufficient_credits` when a candidate's credit was refused, after the profiles read and paid for are processed); or `cancelled`. Only a done run, which read down to its cut, moves the watermark, to the newest engager it read; a run that ends early keeps it. Every end empties the run's `signal_candidates` and deletes its files under `raw/signals/<runId>/`. `counts`: `{ pages, read, staged, created }` and the processing's.
- **The price per engager** (beta-p1-090): each profile read costs `signals.engager`, unit `engager`, `SIGNALS_CREDITS_PER_ENGAGER` credits (Settings); the pages, and a candidate the cheap drops take before its read, cost nothing. Per candidate, in order: its read slot (`signals_reserve_read`, which may wait for the cap or the hours), its credit (`signals_reserve_engager_credit`: quantity 1, key `sigprof:<runId>:<candidateId>:<n>`, its subject the candidate's `cand_` id, the 24-hour lease), the read, then the slot settled and the credit (`signals_settle_engager_credit`), committed when the profile came back and released otherwise: a profile gone or unreadable, a failed step, a cancellation. The credit comes after the slot, so none is held through a wait. `n` counts the candidate's reservations in the run from 1: credits answers a used key with its old row, so a released one is never reserved again. A refused credit releases the slot and stops the reading: the profiles read are processed, then the run ends `failed`, `insufficient_credits`, keeping the watermark, and the next run reads those pages again for nothing.
- **A run started before beta-p1-090** replays and ends on its old path: `patched("engager-price")`, asked once at the workflow's start, is false in its history. It reserves a block of `signals.engager_read` (unit `engagers_30`), the price of `SIGNALS_ESTIMATED_PAGES` pages, before the first read and again whenever the next page could pass what the blocks pay for (`sigrun:<runId>`, then `:<n>`); a refused block stops the reading as a refused credit does; every end and every wait settle the open block, the engagers read committed (1 per 30, rounded up) and the rest released. The price stays declared for those runs and for lead costs; no new run reserves it.
- **Waiting:** a read refused for the cap or the working hours makes the run `waiting` until the refusal's `retryAt`, with no credit held (a run before beta-p1-090 settles its open block first and reserves a new one after). A disconnected account ends it `failed`, `linkedin_account_disconnected`, and publishes `signals.source_blocked`. A kill switch of linkedin's (beta-p1-040), the account's pause or the workspace's or the instance's stop, ends it `failed` with its code, `account_stopped`, `workspace_stopped` or `platform_stopped`, the profiles read so far processed, and publishes nothing: a stop is not a disconnect, and the runs panel says which stop to lift.
- **Metrics:** `signals.runs` (`outcome`, `code`) and `signals.candidates` (`kind`); the dashboard `deploy/observability/dashboards/signals.json`.

## Processing

`domain/process/`, after the reading, in the run's steps ([docs/flows.md](docs/flows.md)):

1. **The cheap drops**, before any read, each counted: a company page (`dropped_company`, no hash: no person); the workspace's own staff by the headline (`dropped_own`): onboarding's company domain and the organization's name, else the workspace's, as whole words in any case; an erased or rejected hash (`dropped_hashed`, contacts' `isHashed`); an engagement the workspace knows by its dedupe key (`dropped_known`).
2. **A profile read** for each candidate left: one read of linkedin's quota (`read_profile`, waiting on the cap and the hours as a page does), linkedin's `linkedin_read_profile`, its request and the profile as files in the run's folder. A profile the provider cannot read (the refusal `linkedin_provider_error`, on the read's third attempt) is settled as read and dropped as a gone one, `dropped_unread`. Three such in a row (`UNREADABLE_IN_ROW_MAX`, `domain/process/keys.ts`; any other answer resets the count) stop the reading: the profiles read are processed, and the run ends `failed`, `linkedin_provider_error`, keeping the watermark, so that an outage drops no more. A read refused for its account (`READING_ENDS`: disconnected, or since beta-p6-020 `account_paused` or `linkedin_rate_limited`, the account paused or held by its `retry_at` after the read was reserved, as linkedin's third error within the hour does, or since beta-p6-040 `platform_stopped`, `workspace_stopped` or `account_stopped`, a kill switch thrown after it) stops the reading the same way, with that code; the next run waits at its reservation. Within the hour that third error comes before the count in a row: the third profile the provider cannot read pauses the account on its first attempt, and its next attempt is refused `linkedin_rate_limited`.
3. **The profiles, 25 at a time**, in one step each: the own staff again by the profile's headline, company and company page (`dropped_own`); qualification's hard filters, prepared once per step, on the title and the country (contacts' `countryOf`), the size unknown and passing; a miss leaves contacts' salted hash with its reason and nothing else (`dropped_filtered`). A pass: the person (`linkedin`), the company, the lead (`signal`, at the engagement, with the source's label and post URL, which contacts' lead list shows), the event and its evidence; `created` for a new lead, `attached` for a known person, `dropped_known` for an event the workspace has. `profiles_read`, and `dropped_unread` for a profile gone.
4. **The hand-off:** a step's new leads go out as `signals.person_found` `{ workspaceId, personIds }`, whose subscriber, signals' own, starts qualification's batch; its known persons as qualification's re-score request.

## Reduction

Evidence text is kept for its kind's lookback, then reduced (security §2, RB-4.4.3; `domain/reduce/`, [docs/flows.md](docs/flows.md)).

- **The rule:** an `evidence` row not reduced whose `captured_at` is older than its kind's lookback (the kind that declares its event's kind; post engagers: `SIGNALS_POST_ENGAGERS_LOOKBACK_DAYS`, 30 days) keeps `url`, `author`, `reaction`, `captured_at` and its event; `excerpt` and `comment_text` become null and `reduced_at` is set. No summary is stored: the lead page's panel words the line from `signals.evidence.reduced` with the reaction and the date (alpha-p8-050). `captured_at` is set once, with the event (`domain/process/`): a second engagement is an event of its own, the same one seen again is dropped, a re-import writes no evidence.
- **Daily:** the global schedule `signals.evidence_reduction`, 03:00 UTC, runs `signals_evidence_reduction_tick`; its activity lists the workspaces through tenancy's `listWorkspaceIds` and starts each one's `signals_evidence_reduction { workspaceId }` as `signals.evidence_reduction:<workspaceId>:current`, one run at a time; a start that fails leaves the others started and fails the tick. A reduction is one activity, `signals_reduce_evidence`: 500 rows a batch by id, each batch its own tenant run, until one is short, then one line `signals: evidence reduced` with `reduced_count`.
- **By hand:** `pnpm evidence:reduce --workspace <id or slug>` reduces the same rows at once and prints `evidence_reduced: <count> in <workspaceId>`; `workspace_not_found` for a slug no single workspace has. The command exits 0, 1 refused, 2 a usage error; through `pnpm`, any failure is 1.

## Decided here

- `kind` is a string, not the data model's enum; the run status is an enum of the six states.
- A kind's settings live in its folder; the registry is a module-level map filled as each kind's file loads, like the platform's registries.
- DELETE removes the source and its runs (`ON DELETE CASCADE`), not the data model's soft delete: nothing else refers to a source yet.
- The post URL is stored canonical, without the query: share links carry tracking ids.
- A short link is resolved once, at the save, so a run never sees one: one GET to lnkd.in, its path without the query, whose `Location` is read and never followed, since the app reads no LinkedIn page outside the person's connected account. A failed request is `signal_post_link_unreachable`, any other answer `signal_config_invalid`.
- The create is a `whytide:own-runs` route (`addSource`): the kind's schema, which may call lnkd.in, runs outside any run, which waits on no call and ends after 5 seconds (core/packages/db README "One run at a time"); `createSource` then reads the canonical config again in its own run, with no request.
- The next fire times count from the last run, not from the clock: right after a save, the three fire times are all still to come, the run at save first (alpha-p8-040).
- A waiting run's resume time is its sender account's next window start, linkedin's `nextWindowAt`, read by the runs panel: a refusal for the hours waits for it, and one for the cap wakes at the next quota day and waits for it then; no column holds the refusal's `retryAt` (alpha-p10-110).
- The runs panel opens by `?runs=<id>`; the screen and the evidence panel read in the browser, so that their loading and error states show and a retry asks again; the times are in next-intl's zone (the server's until a user setting exists), named, a resume time in the account's.
- Run now is refused only while a run is `running` or `waiting` (decided with alpha-p8-020): a `scheduled` one is about to start, and the 409 is a code of signals', `signal_run_open`.
- Stop (fix-run-stop) cancels by the workflow id the run's start records, the only place a schedule's run's id is known. A `scheduled` run is not cancelled but ended by its start: a cancel could reach its workflow before that first step, which would leave the row `scheduled`. The start sets `running` only while no stop is asked, so a stop that commits meanwhile is seen. A stop of another source's run is `signal_source_not_found`, as the path names nothing; a second stop keeps the first time.
- Deleting a source stops its open runs through `signals.source_deleted`, which carries their workflow ids (`workflow_ids`, absent without one, so an event written before the change still reads): one event, whose subscriber already removes the source's schedule, rather than a stop event per run, which would need the id as well, as the rows are gone.
- The line under Run now (fix-run-wait) takes the run's status from the list and the reason from linkedin's usage, no new column: an account not connected first, since no resume time holds then; then the cap; then the hours; neither (a wait about to end), the runs panel's "Waiting until". A usage read that fails leaves the line at "Waiting" rather than failing the screen.
- A page reaches the workflow as a file's key, never as engagers: the history holds ids, the post URL, keys and counts.
- A read that answered, a page or a refusal, is committed as one read, in a cancelled run too; a read whose activity failed, or that a cancellation found not yet made, is released.
- Credits go in blocks, each settled before a wait, before the next block and at the end, so no wait outlives a lease and a run past the estimate pays for every 30 engagers it reads (alpha-p8-030).
- A cancelled run settles like a failed one: the engagers it read are paid, the rest released. Its steps wait for the one under way (`WAIT_CANCELLATION_COMPLETED`), so it knows what it holds.
- A scheduled run makes its id in the workflow; its first step writes the row. Sources saved before alpha-p8-020 have no schedule until an enable makes it (alpha-p10-110).
- A refused block ends the reading, not the run: the pages read and paid for are processed, then the run ends `insufficient_credits` and keeps the watermark (alpha-p8-030): pages come newest first, so a watermark moved to them would skip the older engagers never read. The next run reads and pays for those pages again; its dedupe keys and hashes drop what this one processed before any profile read, so only the page reads repeat (and the profile reads of own staff known only by their profile, and of profiles gone).
- An event's dedupe key is the SHA-256 of its kind, the engager's member reference, the post and the reaction. The cut keeps the watermark's own engager, so a known key drops it before its profile read.
- Every candidate left after the cheap drops gets a profile read, the cap showing the cost; its profile goes through a file, never the history, and every end deletes the run's folder (raw/'s 72 hours catch a miss).
- The excerpt is the person's own words, the first 500 characters of the comment, null for a reaction: the reader has no post text, and other people's words would reach the model (qualification's anonymizer).
- `signals.person_found`, the module's prefix, carries a step's new leads' person ids; the re-score request carries the known persons' with a new event. Its subscriber is signals': qualification imports nothing of signals (decisions.md, 2026-10-22).
- An event keeps its source and run by id, `ON DELETE SET NULL`: deleting a source keeps the person's events and evidence. Persons and companies from a profile have `provider` null.
- The reduction (alpha-p10-020): one global daily tick that starts a run per workspace, not a schedule per workspace (decisions.md, 2026-10-27); the workflow carries the module's prefix, `signals_evidence_reduction` for the task's `evidence_reduction`. No summary text is stored (decisions.md, 2026-10-27).
- A row's clock is `captured_at`, as the task says; its lookback is its event kind's: two kinds of one event kind take the shorter, an event kind no kind declares (a folder removed) the shortest of all, so a new kind changes nothing here.
- A reduction is one activity that loops its batches, each batch its own run, so a retry goes on from what committed and a run logs one count; the command calls the same function in runs of its own.
- The evidence route answers the attribution and the sources' labels too (alpha-p8-050), so that the panel reads once: contacts' lead holds the sources' ids, signals their labels. Contacts never imports signals, so the processing gives contacts the source's label and post URL with the lead's source (fix-lead-source-post), which the lead list shows; the panel reads the sources' labels as they are now.
- A candidate's credit has the candidate as its subject, the person being known only after the read (beta-p1-090); since the staging row goes with the run, the event a candidate becomes carries its ULID in its id (`sev_` and the candidate's ULID, `ids.ts`), so `personReads` finds a person's candidates with no new column or table. An event made before has an id no candidate had, which matches no credit.
- `patched("engager-price")` is asked once, at the start of `signals_run`, and kept: in a replay without the marker it answers false, but once the replay is over a later ask would answer true and switch an old run to the new path mid-run.
