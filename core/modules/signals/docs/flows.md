# signals: flows

- **The start**: loading the module imports `sources/registry.generated.ts`, which imports each `sources/<kind>/index.ts`; each calls `defineSourceKind`, which registers the kind or fails the start (`signal_kind_invalid`, `signal_kind_duplicate`).
- **POST /sources**: after the host's guards (session, workspace, `signals.write`, origin), on a `whytide:own-runs` route: the kind from the registry and the config through the kind's schema, outside any run (a short link: one GET to it through `fetchSafe`, its `Location` read and never followed); then, in a run of its own, the config again, canonical, the sender account, the advisory lock `signals.enabled_sources:<workspace>`, the count of enabled sources, the insert, and `signals.source_created` into the outbox; one transaction.
- **PATCH /sources/{id}**: an enable takes the same lock first; the source, its kind checked against the registry, the count when it was disabled, the update.
- **DELETE /sources/{id}**: the source, its open runs' workflow ids (recorded, else Run now's), its delete (its runs by the cascade) and `signals.source_deleted` with those ids into the outbox; one transaction.
- **GET /sources** and **GET /sources/{id}/runs**: reads in the tenant run; a source of another workspace is not found (404). Each source answered carries its next fire times (`domain/fire-times.ts`): the kind's schedule from the save, after the last run.
- **The sources screen** (`/w/{workspace}/sources`): the page renders its title on the server; in the browser, `ui/sources/sources.tsx` reads the sources and linkedin's `GET …/linkedin/accounts` through the web's API client, loading, then the screen or the error with a retry; the runs panel reads the source's runs when `?runs=<id>` names it, and linkedin's `GET …/accounts/{id}/usage` of its sender account when one is waiting (`nextWindowAt`). The form `POST`s a source and the switch `PATCH`es `enabled`, then the screen reads again; Delete opens a confirmation, then `DELETE`s. Run now `POST`s `…/run` with a new `Idempotency-Key`, then opens the source's runs panel, `?runs=<id>` set in place. A refusal shows in words: `signal_config_invalid` under the URL, any other code in the form or above the list, `signal_run_open` with the list read again.
- **The schedule** (worker, from the outbox): `signals.source_created` creates `signals-<sourceId>` with the kind's fire times, paused when the source is disabled, one run at once when the first time has passed; `signals.source_updated` pauses or resumes it as `enabled` is, and an enable that finds none creates it, one run at once when a fire time has passed since the last run; `signals.source_deleted` deletes it, then cancels each workflow its payload names (`cancelWorkflow`), one line each, ids only.
- **POST /sources/{id}/run**: `signals.run`, `@Idempotent()`; the source, `signal_run_open` (409) when one of its runs is `running` or `waiting`, a run row `scheduled` and `signals.run_requested`, one transaction; the worker starts `signals_run` as `signals.run:<workspaceId>:<runId>`.
- **POST /sources/{id}/runs/{runId}/stop**: `signals.run`, `@Idempotent()`; the source, its run (another source's is `signal_source_not_found`), `signal_run_not_open` (409) once ended, `stop_requested_at` set unless set, and `signals.run_stop_requested`, one transaction. The worker's subscriber reads the run and cancels a `running` or `waiting` one only, by `workflow_id`, or `signals.run:<workspaceId>:<runId>` when none was recorded, `{ cancelled: false }` meaning no open workflow had that id; one line, ids only. A `scheduled` run is left to its start; one that ended meanwhile, or went with its source, needs none.
- **The run** (`workflows/workflows.ts`), each step an activity in the run's tenant: `signals_run_start` (the row with the workflow's id from the activity's context, `running` unless a stop was asked, else `cancelled` with `finished_at` and the answer `gone`, on which the workflow ends; `lastRunAt`, the account connected or the run blocked); per page `signals_reserve_read` and no credits (a run started before beta-p1-090, without the patch `engager-price`: before the first read, and whenever the next page could pass what the blocks pay for, `signals_settle_credits` for the open block and `signals_reserve_credits` for a new one, `sigrun:<runId>`, then `:<n>`; refused, the reading stops); the kind's reader, `linkedin_read_post_engagers` (the reference opened in the worker, one vendor call, the page to the files port, an action-log row); `signals_settle_read`; `signals_stage_page` (the file read back, the candidates from the cut on inserted, the counts); the processing (below); `signals_run_end` (the run's files deleted, outside the run, a failure logged by code; an old run's open block settled, the engagers read committed and the rest released; the run's candidates deleted, the status, the watermark for a done run, `signals.source_blocked`, the metric).
- **The processing** (`domain/process/`): `signals_select_candidates` (the names read outside the run: onboarding's domain, the organization's name, else the workspace's; in the run, the cheap drops in order, company page, own staff by the headline, a hash, a known dedupe key, each deleted and counted; after it, each candidate's request file `raw/signals/<runId>/profiles/<candidateId>.request.json`, its profile URL); per candidate `signals_reserve_read` (`read_profile`), then `signals_reserve_engager_credit` (credits' `reserve` of one `signals.engager`, key `sigprof:<runId>:<candidateId>:<n>`, subject the candidate, lease `async`; refused, `insufficient_credits`), linkedin's `linkedin_read_profile` (the request file read, the reference opened, one vendor call, the profile written beside it, an action-log row with no object), `signals_settle_read`, then `signals_settle_engager_credit` (commit when the profile came back, else release); `signals_process_candidates` for every 25 read, before a wait and at the end (the profile files read outside the run; in it, the ICP's hard filters prepared once, then per candidate the drops, contacts' `recordHash`, `upsertPersonFromSource`, `upsertCompany`, `linkPersonToCompany`, `createLeadForPerson`, the event, inserted unless its dedupe key exists, and its evidence; the chunk's staging rows deleted, `signals.person_found` into the outbox, qualification's `requestRescore` for the known persons, the counts). A refused credit releases the candidate's slot and stops the reading, as an old run's refused block does; the processing runs, then the run ends `insufficient_credits` with the watermark kept, so the next run reads those pages again.
- **signals.person_found** (worker, from the outbox): signals' subscriber starts qualification's `batchStart` workflow for the delivery's workspace, `qualification.batch:<workspace>:current`, one at a time: a start while one runs starts none, and those leads wait for qualification's next tick.
- **GET /leads/{personId}/evidence**: contacts' `leads.read`; in the request's tenant run, contacts' `getPerson` (another workspace's person is not found, 404), then the person's events, newest first, and their evidence, in two reads (the tenant guard refuses a relation in a query).
  Then contacts' `getLead` for the lead's sources (none, and no attribution, without a lead) and one read of the labels of the sources they and the events name (`domain/attribution.ts`).
- **The evidence panel** (`ui/lead-evidence`, in contacts' lead page): its loading state renders with the page, inside the slot's boundary; then, in the browser, one call of the route above, as the member, through the web's API client, and its error state with a retry; each line's words come from the module's keys, with the answer's label, author, comment and time; a reduced event's line, from `signals.evidence.reduced`, the reaction and the date, as no summary is stored.
- **Erasure**: `erasePerson(personId)`, in the deletion script's run (core/modules/privacy), deletes the person's evidence, then its events, and returns the rows deleted by table.
- **The reduction** (worker, daily; README "Reduction"): the schedule `signals.evidence_reduction`, 03:00 UTC, runs `signals_evidence_reduction_tick`; `signals_start_reductions`, global, lists the workspaces (tenancy's `listWorkspaceIds`) and starts each one's `signals_evidence_reduction` as `signals.evidence_reduction:<workspaceId>:current`, one run at a time. Its one step, `signals_reduce_evidence`, loops batches, each a tenant run: the next 500 rows by id not reduced and captured before the shortest lookback's cut, their events' kinds in a second read, and one update of those past their own kind's cut (`excerpt` and `comment_text` null, `reduced_at` now), until a batch is short; then the count in its log line. `pnpm evidence:reduce` calls the same loop in runs of its own and prints the count.
- **Waiting**: `read_cap_reached` or `outside_working_hours` sets the run `waiting`, settles an old run's open block (a new run holds no credit then), processes the profiles read so far, and sleeps a Temporal timer to the refusal's `retryAt` (one second at least), then asks again. `linkedin_rate_limited` fails the reader's attempt, retried after the vendor's `retryAfterSec`.
- **A run ended by a stop**: a read refused with `retryAt` null opens no wait: linkedin's kill switches (`platform_stopped`, `workspace_stopped`, `account_stopped`; beta-p1-040) and `linkedin_account_disconnected`. At a page's read the run ends at once; at a profile's, the profiles read so far are processed first. A stop thrown after a profile's read was reserved ends it the same way: `linkedin_read_profile` answers it before its call (`READING_ENDS`, beta-p6-040). `signals_run_end` ends it `failed` with the refusal's code, and publishes `signals.source_blocked` for `linkedin_account_disconnected` alone: a stop is not a disconnect. The next run after the lift reads on from the watermark, which a failed run keeps.
- **Failing and cancelling**: a refusal or a failed step ends the run through `signals_run_end` with the code, a failed step's read and credit released first; a cancellation waits for the step under way, releases a read reserved and not made and a credit not settled, then ends the run `cancelled` through `signals_run_end`, outside the cancellation, and the workflow ends cancelled.
