# signals: flows

- **The start**: loading the module imports `sources/registry.generated.ts`, which imports each `sources/<kind>/index.ts`; each calls `defineSourceKind`, which registers the kind or fails the start (`signal_kind_invalid`, `signal_kind_duplicate`).
- **POST /sources**: after the host's guards (session, workspace, `signals.write`, origin), on a `whytide:own-runs` route: the kind from the registry and the config through the kind's schema, outside any run (a short link: one GET to it through `fetchSafe`, its `Location` read and never followed); then, in a run of its own, the config again, canonical, the sender account, the advisory lock `signals.enabled_sources:<workspace>`, for a tracked kind (an author's posts) the count of the sender account's enabled tracked sources, the count of enabled sources in no agent (playbooks' links read, gamma-p5-045), the insert, and `signals.source_created` into the outbox; one transaction.
- **PATCH /sources/{id}**: an enable takes the same lock first; the source, its kind checked against the registry, the counts when it was disabled (the tracked, then the enabled of its group: its agent's sources, or those in no agent), the update.
- **DELETE /sources/{id}**: the source, its open runs' workflow ids (recorded, else Run now's), its delete (its runs by the cascade), playbooks' `detachSource` (its agent's link) and `signals.source_deleted` with those ids into the outbox; one transaction.
- **GET /sources** and **GET /sources/{id}/runs**: reads in the tenant run; a source of another workspace is not found (404). Each source answered carries its next fire times (`domain/fire-times.ts`): the kind's schedule from the save, after the last run; and its agent, from playbooks' `listPlaybooks` and `sourcesOf`, read once per answer (gamma-p5-045).
- **The sources screen** (`/w/{workspace}/sources`): the page renders its title on the server; in the browser, `ui/sources/sources.tsx` reads the sources and linkedin's `GET …/linkedin/accounts` through the web's API client, loading, then the screen or the error with a retry; the runs panel reads the source's runs when `?runs=<id>` names it, and linkedin's `GET …/accounts/{id}/usage` of its sender account when one is waiting (`nextWindowAt`). The form `POST`s a source and the switch `PATCH`es `enabled`, then the screen reads again; Delete opens a confirmation, then `DELETE`s. Run now `POST`s `…/run` with a new `Idempotency-Key`, then opens the source's runs panel, `?runs=<id>` set in place. A refusal shows in words: `signal_config_invalid` and `signal_topic_blocked` under each field they name, any other code in the form or above the list, `signal_run_open` with the list read again.
- **The schedule** (worker, from the outbox): `signals.source_created` creates `signals-<sourceId>` with the kind's fire times, paused when the source is disabled, one run at once when the first time has passed; `signals.source_updated` pauses or resumes it as `enabled` is, and an enable that finds none creates it, one run at once when a fire time has passed since the last run; `signals.source_deleted` deletes it, then cancels each workflow its payload names (`cancelWorkflow`), one line each, ids only.
- **The daily tick** (worker; README "Runs", gamma-p5-040): the schedule `signals.daily_runs`, every `DAILY_RUNS_TICK_MINUTES` minutes, skipped while one runs, starts `signals_daily_runs_tick`; its one step, `signals_start_daily_runs`, global, lists the workspaces (tenancy's `listWorkspaceIds`) and, per workspace, in a run of its own as the service `signals`: the enabled sources of a daily kind, less a paused agent's (playbooks' `listPlaybooks` and `sourcesOf`; paused-agent-sources); once per sender account, linkedin's `readsLeftToday` (the quota day, the reads left, the window; a gone account skips its sources); the sources' runs not over or of those quota days; then, for each source due, the run row `scheduled` and `signals.run_requested` into the outbox, as Run now writes them, whose subscriber starts `signals.run:<workspaceId>:<runId>`. A workspace that fails rolls back alone and the others' runs stay; the step then throws the first failure, which fails the tick. It answers `{ workspaces, started }`, counts only.
- **POST /sources/{id}/run**: `signals.run`, `@Idempotent()`; the source, `signal_agent_paused` (409) while its agent is paused (playbooks' `playbookOfSource` and `getPlaybook`; paused-agent-sources), `signal_run_open` (409) when one of its runs is `running` or `waiting`, a run row `scheduled` and `signals.run_requested`, one transaction; the worker starts `signals_run` as `signals.run:<workspaceId>:<runId>`.
- **POST /sources/{id}/runs/{runId}/stop**: `signals.run`, `@Idempotent()`; the source, its run (another source's is `signal_source_not_found`), `signal_run_not_open` (409) once ended, `stop_requested_at` set unless set, and `signals.run_stop_requested`, one transaction. The worker's subscriber reads the run and cancels a `running` or `waiting` one only, by `workflow_id`, or `signals.run:<workspaceId>:<runId>` when none was recorded, `{ cancelled: false }` meaning no open workflow had that id; one line, ids only. A `scheduled` run is left to its start; one that ended meanwhile, or went with its source, needs none.
- **An agent paused** (worker, from the outbox; paused-agent-sources): on playbooks' `playbooks.playbook_updated`, in the delivery's tenant run, the agent (`getPlaybook`); while it is paused, its sources (`sourcesOf`) and their `running` and `waiting` runs whose stop is not asked, each one's `stop_requested_at` set where still null and `signals.run_stop_requested` into the outbox, one transaction; the stop's subscriber then cancels each workflow as Stop's does. Delivered while the agent is active, resumed or renamed, it reads no run.
- **The run** (`workflows/workflows.ts`), each step an activity in the run's tenant: `signals_run_start` (the source's agent first, playbooks' `playbookOfSource` and `getPlaybook`: while it is paused, a row not ended `cancelled` with `finished_at`, none made, and the answer `gone`, paused-agent-sources; else the row with the workflow's id from the activity's context, `running` unless a stop was asked, else `cancelled` with `finished_at` and the answer `gone`, on which the workflow ends; `lastRunAt`, the account connected or the run blocked; since gamma-p5-040, behind `patched("read-budget")`, the run's quota day and read budget from linkedin's `readsLeftToday` and the account's sources and runs, split by their agents since gamma-p5-045, written to the row once, a retry reading them back; since gamma-p5-045 the source's agent, playbooks' `playbookOfSource`, whose id the workflow hands to the select, the triage and the processing); per page `signals_reserve_read` and no credits (a run started before beta-p1-090, without the patch `engager-price`: before the first read, and whenever the next page could pass what the blocks pay for, `signals_settle_credits` for the open block and `signals_reserve_credits` for a new one, `sigrun:<runId>`, then `:<n>`; refused, the reading stops); the kind's reader, `linkedin_read_post_engagers` (the reference opened in the worker, one vendor call, the page to the files port, an action-log row); `signals_settle_read`; `signals_stage_page` (the file read back, the candidates from the cut on inserted, the counts); the processing (below); `signals_run_end` (the run's files deleted, outside the run, a failure logged by code; an old run's open block settled, the engagers read committed and the rest released; the run's candidates deleted, the status, the watermark for a done run, `signals.source_blocked`, the metric).
- **A posts kind's run** (gamma-p5-020, behind `patched("posts-reader")`): after `signals_run_start`, per page of posts `signals_posts_request` (the request file `raw/signals/<runId>/posts/<page>.request.json`: the kind's source, the lookback's start, the page's size, `after` the previous page's file), `signals_reserve_read` (`read_posts`), linkedin's `linkedin_read_posts` (the request read, the reference opened, one vendor call, the page to `…/posts/<page>.json`, an action-log row with no object), `signals_settle_read`, and `signals_stage_posts` (the page read back: each post's unnamed URL and its cut, its watermark entry else the lookback's start, the authors the kind keeps from their post's cut on staged, `post_pages` and `posts`), until a page has no next; then per post, newest first, per page `signals_reserve_read` (`read_engagers`), `linkedin_read_post_engagers` by the unnamed URL to `…/posts/<n>/<page>.json`, `signals_settle_read`, and `signals_stage_page` with the post and its posts file (the post's excerpt, the undated dated at the later of the post's date and the last done run's start), until the cut or the last page; then the processing, as below. `signals_run_end` writes a done run's watermark, `{ posts: { <unnamed URL>: <newest> } }`.
- **The processing** (`domain/process/`): `signals_select_candidates` (the names read outside the run: onboarding's domain, the organization's name, else the workspace's; in the run, the run's audience's titles and must-haves (its agent's by the id, else the default: `domain/agents.ts`; the triage and the processing read it the same way) and the competitors of the workspace's `competitor_engagement` sources read once, then the cheap drops in order, company page, own staff by the headline, the noise rules by the headline (a competitor's staff; a recruiter and a job seeker too in a run started before signals-triage-ai), a hash, a known dedupe key, each deleted and counted; a triaged run answers the ids left, oldest staged first, for the triage (below); a run before it, the rest in the read order (gamma-p5-040), qualification's title rule (`titleFits`) read once from the same ICP for the title's rank, and after it each candidate's request file `raw/signals/<runId>/profiles/<candidateId>.request.json`, its profile URL); in a triaged run, the triage; per candidate `signals_reserve_read` (`read_profile`), then `signals_reserve_engager_credit` (credits' `reserve` of one `signals.engager`, key `sigprof:<runId>:<candidateId>:<n>`, subject the candidate, lease `async`; refused, `insufficient_credits`), linkedin's `linkedin_read_profile` (the request file read, the reference opened, one vendor call, the profile written beside it, an action-log row with no object), `signals_settle_read`, then `signals_settle_engager_credit` (commit when the profile came back, else release); `signals_process_candidates` for every 25 read, before a wait and at the end (the profile files read outside the run; in it, the ICP's hard filters and the noise rules prepared once, then per candidate the drops (own staff, a competitor's staff by the headline, the company and its page, no recruiter or job seeker since signals-triage-ai, the hard filters on the country, the title being the assessment's since title-check-ai), contacts' `recordHash`, `upsertPersonFromSource`, `upsertCompany`, `linkPersonToCompany`, `createLeadForPerson`, the event, inserted unless its dedupe key exists, and its evidence; the chunk's staging rows deleted, `signals.person_found` into the outbox, qualification's `requestRescore` for the known persons, the counts). A refused credit releases the candidate's slot and stops the reading, as an old run's refused block does; the processing runs, then the run ends `insufficient_credits` with the watermark kept, so the next run reads those pages again.
- **The triage** (signals-triage-ai, behind `patched("headline-triage")`, asked once at the start; README "Triage"): the selected ids, 25 a batch (`TRIAGE_BATCH_SIZE`) in the staged order, each through `signals_triage_candidates` (kind `ai`: in a tenant run, the ICP's titles, seniorities, industries and must-haves, the batch's candidates still staged and the noise rules; outside any run, `callAgent` of `signals.triage-engagers` with each candidate's role and headline, scrubbed, its subject the workspace, which writes the decision record and the cost event in its own run; the request file of each candidate read, outside any run; then, in another run, the skips deleted and counted `dropped_triage`). An `ai_failed` answer and a batch over the agent's budget are decided by the rules in the same step; a step failing past its three attempts, or with `signal_triage_agent_not_loaded`, never retried, by `signals_triage_fallback` (kind `db`: the same read, the recruiter and job-seeker terms on the headline dropped with their counts, the rest in the title rule's ranks, the request files, the deletions). Each step answers its ids in three ranks; the workflow reads every batch's authors and commenters first, then the ones read first, then the rest, the staged order within each. A cancellation ends the run as below. The history holds candidate ids only.
- **The rating** (gamma-p5-030, behind `patched("rate-engagement")`, asked once at the start): after the last processing of a run that read to its end, or to the end of its day's reading (gamma-p5-040), `signals_select_ratings` (in the run: Company Knowledge's offer, nothing picked while it is empty; the source's oldest unrated events with words or a post not reduced, 100 at most, one query), then per ten `signals_rate_events` (kind `ai`: the events and their evidence read in a tenant run and scrubbed; `callAgent` outside any run, which writes the decision record and the cost event in its own; the ratings written while unrated, a rationale nulled when its evidence was reduced meanwhile, and qualification's `requestRescore` for the rated persons, in another run), then `signals_count_ratings` (`rated`, `unrated`). A batch failing past its three attempts stops the loop, and the run ends as it would have; a cancellation ends it as below. The history holds event ids and `{ rated }`.
- **The signal reader** (gamma-p5-030): loading `index.ts`, `events.ts` or `workflows/index.ts` registers it with qualification once per process; qualification calls `intentInputs` and `excerpts` in its own tenant run, and the reader reads there: the events of the persons, their evidence's reactions and their sources' creators in three reads, then the collapse in code; the excerpts in two.
- **The source checker** (gamma-p5-045): loading `index.ts`, `events.ts` or `workflows/index.ts` registers it with playbooks once per process (`defineSourceChecker`); playbooks' `PUT …/playbooks/{id}/sources` and its check call it in their tenant run: one read of the ids' rows, `FOR SHARE`, then linkedin's `findSenderAccount` once per account.
- **signals.person_found** (worker, from the outbox): signals' subscriber starts qualification's `batchStart` workflow for the delivery's workspace, `qualification.batch:<workspace>:current`, one at a time: a start while one runs starts none, and those leads wait for qualification's next tick.
- **GET /leads/{personId}/evidence**: contacts' `leads.read`; in the request's tenant run, contacts' `getPerson` (another workspace's person is not found, 404), then the person's events, newest first, and their evidence, in two reads (the tenant guard refuses a relation in a query).
  Then contacts' `getLead` for the lead's sources (none, and no attribution, without a lead) and one read of the labels of the sources they and the events name (`domain/attribution.ts`).
- **The evidence panel** (`ui/lead-evidence`, in contacts' lead page): its loading state renders with the page, inside the slot's boundary; then, in the browser, one call of the route above, as the member, through the web's API client, and its error state with a retry; each line's words come from the module's keys, with the answer's label, author, comment and time; a reduced event's line, from `signals.evidence.reduced`, the reaction and the date, as no summary is stored.
- **Erasure**: `erasePerson(personId)`, in the deletion script's run (core/modules/privacy), deletes the person's evidence, then its events, the decision records their ratings name and every triage record of the workspace (signals-triage-ai); then, when contacts still has the person, the scrub by their public id: each source whose kind's `scrub` names them disabled through `updateSource` (`signals.source_updated`), its config and label emptied, its open runs stopped through `stopRun` (`signals.run_stop_requested`); others' evidence whose `/posts/` URL names them (`url` from `https://www.linkedin.com/posts/`, the index) rewritten to the unnamed URL, its `post_excerpt` null. It returns the rows deleted by table.
- **The reduction** (worker, daily; README "Reduction"): the schedule `signals.evidence_reduction`, 03:00 UTC, runs `signals_evidence_reduction_tick`; `signals_start_reductions`, global, lists the workspaces (tenancy's `listWorkspaceIds`) and starts each one's `signals_evidence_reduction` as `signals.evidence_reduction:<workspaceId>:current`, one run at a time. Its one step, `signals_reduce_evidence`, loops batches, each a tenant run: the next 500 rows by id not reduced and captured before the shortest lookback's cut, their events' kinds in a second read, and one update of those past their own kind's cut (`excerpt`, `comment_text` and `post_excerpt` null, `reduced_at` now), then their events' `relevance_rationale` null, until a batch is short; then the count in its log line. `pnpm evidence:reduce` calls the same loop in runs of its own and prints the count.
- **A budgeted run's reads** (gamma-p5-040): each `signals_reserve_read` carries `{ readBudget, used }`, `used` the reads settled as made, and reserves through linkedin's `reserveReads` with `keep` `SIGNALS_READS_KEPT_FOR_SENDS`; linkedin's refusal answers as it is; a slot granted once `used` reached the budget is released (`releaseReads`) and answered `read_budget_reached`. That, `read_cap_reached` or `daily_actions_cap_reached` leaves the run `running` and ends its reading: at a page, nothing is selected; at a profile, the profiles read are processed; `signals_run_end` then ends it `done`, sets `counts.budget_reached` to 1 and leaves the watermark. Before each page read, posts' or engagers', the workflow stops the paging once its reads made reach the page limit, `pageLimitOf(readBudget)`, half the budget, one at least: no step is called, the candidates staged are selected and their profiles read with the rest of the budget, and the end is the same, `done` with `counts.budget_reached` 1 and the watermark left.
- **Waiting**: `read_cap_reached` (a run started before gamma-p5-040) or `outside_working_hours` sets the run `waiting`, settles an old run's open block (a new run holds no credit then), processes the profiles read so far, and sleeps a Temporal timer to the refusal's `retryAt` (one second at least), then asks again. `linkedin_rate_limited` fails the reader's attempt, retried after the vendor's `retryAfterSec`.
- **A run ended by a stop**: a read refused with `retryAt` null opens no wait: linkedin's kill switches (`platform_stopped`, `workspace_stopped`, `account_stopped`; beta-p1-040) and `linkedin_account_disconnected`. At a page's read the run ends at once; at a profile's, the profiles read so far are processed first. A stop thrown after a profile's read was reserved ends it the same way: `linkedin_read_profile` answers it before its call (`READING_ENDS`, beta-p6-040). `signals_run_end` ends it `failed` with the refusal's code, and publishes `signals.source_blocked` for `linkedin_account_disconnected` alone: a stop is not a disconnect. The next run after the lift reads on from the watermark, which a failed run keeps.
- **Failing and cancelling**: a refusal or a failed step ends the run through `signals_run_end` with the code, a failed step's read and credit released first; a cancellation waits for the step under way, releases a read reserved and not made and a credit not settled, then ends the run `cancelled` through `signals_run_end`, outside the cancellation, and the workflow ends cancelled.
- **POST /sources/imports/check** and **POST /sources/imports** (sources-csv-import; README "Importing sources"): after the host's guards (`signals.write`, origin), on a `whytide:own-runs` route with its own body limit: the base64 decoded, the file read (`domain/import/csv.ts`), the sender account in one run, each row through its kind's `csv` and schema outside any run, one at a time, then the workspace's sources in one run for the repeats. The import then writes the import's row, creates each valid row in the file's order through `createSource` in a run of its own, created disabled past a limit (`signals.source_created`, so its schedule is made paused), and writes the counts.
- **A research source** (gamma-wr-030; README "Runs"): `POST /sources` for a kind with `readsThroughAccount: false` takes no account, writes `sender_account_id` null and skips the account's tracked count; `PATCH /sources/{id}` with `config` runs the kind's schema again, for a kind that allows it. `signals.source_created` makes no schedule for it (`schedule()` is empty). The tick (`signals_start_daily_runs`) writes its run when it is due: enabled, in an active agent, no run scheduled, running or waiting, none started within `SIGNALS_RESEARCH_EVERY_DAYS` days. `signals.run_requested` starts `signals_research_run` for it: `signals_research_start` (`openRun`: a gone source or a stop asked before the start ends it; a paused agent's run ends as `signals_run_start` ends it; then the audience's countries are counted), then `signals_research_end`, `endRun` with `research_no_country` and `failed` for none, else `done` with empty counts. A stop or a delete cancels the workflow as for any run.

- **A research run's plan** (gamma-wr-040; README "Web research"): after `signals_research_start` (a run started since the patch `research-plan`), `signals_research_plan` (kind `ai`, retried as every model call; `signal_research_agent_not_loaded` is not retried): one tenant run reads the source's config, Company Knowledge, the run's audience (its agent's, by the id the start named, else the default) and the queries the source asked within `SIGNALS_RESEARCH_RECHECK_DAYS`; the agent `signals.research-plan` is asked outside any run, between two runs, with the member's texts scrubbed in labelled blocks; the answer goes through the gates (`domain/research/checks.ts`) and another tenant run writes the plan, its queries and the counts `queries_planned` and `queries_refused`. The step answers `planned` with two counts, `failed` with `research_plan_failed`, or `gone`. The run then ends `done`, or `failed`.

- **A research run's search** (gamma-wr-041; README "Web research"): after the plan, in a run started since the patch `research-search`, the workflow calls `signals_research_search` (kind `provider`) once for each of the plan's queries, from position 1 to the count the plan step answered, stopping at `budget` or `spent`, failing the run at `unavailable`. One step: a tenant run reads the query, the run's counts and the source; before the search it skips an asked query, ends at the searches' limit and refuses a query that holds an email address, a link or a phone number; the search is enrichment's counted `searchWeb`, outside any tenant run, with the query's country and language, 10 results, page 1; its answer is written to `raw/signals/<runId>/search/<position>.json`; another tenant run marks the query `asked_at` and `result_count` and adds the counts. The history holds the step's status, never a query or a result.
- **The route and the card** (gamma-wr-041): `GET /sources/{id}/research-plan` reads the source's newest plan; the card of a Web research source reads it again when its run changes.

- **A research run's pick, queue and pages** (gamma-wr-045; README "Web research"): after the searches, in a run started since the patch `research-pages`, `signals_research_pick` (kind `ai`, the plan's positions from 1; `signal_research_pick_agent_not_loaded` is not retried), then `signals_research_queue` (kind `db`), then `signals_research_page` (kind `provider`, a 3-minute timeout) for each place of the queue, told how many pages were read before it, stopping at `budget`. The pick reads the search's answer file, drops LinkedIn and social results in code, asks the agent outside any run and keeps the picks as `pick/<position>.json`; the queue is the start pages, then the picks round by round, three pages of a host at most, in `pages/queue.json`; a page is read through platform's `readPage` (robots.txt once a host a run, the `browser` port for a thin page) and kept as `pages/<n>.json`. The steps answer statuses and counts; every file is read by its key.


- **A research run's pages understood and candidates** (gamma-wr-046; README "Web research"): after the pages, in a run started since the patch `research-candidates`, `signals_research_carry` (kind `db`, once: pending candidates of earlier runs checked again), then for each page read `signals_research_read` (kind `ai`, 5 minutes; `signal_research_read_agent_not_loaded` is not retried) and `signals_research_candidates` (kind `provider`: a company named with no link is searched once by name through the counted search, then own company, never-contact and re-check drops, then the row). A page read gone answers `gone` and the run ends. The steps answer statuses and counts; the files are `candidates/<n>.json`.
- **A research run's judging** (gamma-wr-050; README "Web research"): after the candidates, in a run started since the patch `research-judge`, `signals_research_judge_queue` (kind `db`, once), then for each company of the queue `signals_research_site` (kind `provider`, 3 minutes: the site read, or its candidate dropped) and `signals_research_judge` (kind `ai`, 5 minutes; `signal_research_judge_agent_not_loaded` is not retried), until the companies' limit (`counts.budget_reached`). The steps answer statuses and a verdict; the files are `judge/queue.json`, `site/<n>.json` and `verdict/<n>.json`. Since gamma-wr-051 (patch `research-price`) the site step reserves a company's credit before its read (a refusal ends the run `failed`, `insufficient_credits`), the judge step commits it with the verdict, and `signals_research_end` releases an open one.
- **A research run's people** (gamma-wr-060; README "Web research"): after the judging, in a run started since the patch `research-people`, `signals_research_people_queue` (kind `db`, once: the source's found companies judged `fit` whose people were not taken, the oldest first, at most the companies' limit, as ids in `people/queue.json`), then for each company `signals_research_people` (kind `ai`, 10 minutes; `signal_research_people_agent_not_loaded` is not retried): the company's pages are read from the run's files or anew, the read agent names the people with a role, code gates the answer against the pages, the pick agent chooses among the roles alone, and each picked person with a key the page printed is made a lead with its research event, then `signals.person_found`. The step answers a status and a count; the company's `people_taken_at` is set in the same tenant run that makes its people, so a step run again adds nobody and a run cut short takes the company up at the next run.


- **Not a fit** (gamma-wr-110; README "Web research"): `POST /found-companies/{id}/not-fit` marks the row in the request's tenant run, no event, no workflow. The next run of the source, in `signals_research_candidates` and the carried candidates (`signals_research_carry`), drops the company's domain before any read or credit (`dropped_not_fit`), and the plan of that run (`signals_research_plan`) reads the source's marked companies in its `not_fit` block.
- **A company's managers by search** (gamma-wr-090; README "Web research"): inside the people step, no new activity. After the pages' pick, when it took fewer people than `SIGNALS_RESEARCH_PEOPLE_PER_COMPANY` and the run's plan has role words, one counted web search on linkedin.com (the company's name and the role words), code keeps the results that are a profile's and name the company, the agent `signals.research-read-result` reads the name and the role of each, code gates the answer, and the pick judges the roles for the places left. In a run started since the patch `research-managers` the step has 20 minutes, not 10. The step answers a status and a count; the results are the file `managers/<found company>.json`.
