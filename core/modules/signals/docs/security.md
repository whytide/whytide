# signals: security

- **Personal data:** a source's config holds a LinkedIn post's URL, which names its author: business contact data, typed by a member, stored without the link's query (tracking ids, the sharer's among them); a short link is not stored, the post's URL it redirects to is. A run's candidates hold the engagers' business fields only (no field beyond those, checked by `tests/tenancy.test.ts`); its raw pages and profiles live in the files port under the workspace's prefix until the run's end deletes them (72 hours at most), never in the database or in Temporal's history, which carries ids, the post URL, keys and counts.
- **What a run keeps:** a rejected candidate (the hard filters) leaves contacts' salted hash with its drop reasons, kept 90 days, and nothing else; a company page and the workspace's own staff leave nothing; no table holds their name, URL or headline after the run (the worker's `tests/signals-process.test.ts` scans every table). A kept candidate becomes a person with business fields only, its lead, an event and its evidence: the post, the person's own comment and its first 500 characters, the reaction and the person's name; the post's text and other people's comments are never fetched. The excerpt and the comment are kept for the kind's lookback from `captured_at` (30 days for post engagers), then the daily reduction nulls them (README "Reduction"); the URL, the author's name and the reaction stay. No refresh, second engagement or re-import moves `captured_at`. `erasePerson` deletes a person's events and evidence.
- **Who may do what:** `signals.read` lists sources and runs, `signals.write` creates, changes and deletes them, `signals.run` (Owner, Admin) runs one now or stops one, once per `Idempotency-Key`; `leads.read` (contacts') reads a person's evidence; every query runs in the request's or the activity's tenant run, scoped to its workspace, and the five tables pass the two-workspace isolation test. The worker starts a run in the delivery's workspace, never the payload's.
- **Bounds:** at most `SIGNALS_MAX_ENABLED_SOURCES` enabled per workspace, counted under an advisory lock. A source reads only through its sender's own account, which must be the workspace's at the create and connected at each run; each read, a page's or a profile's, is reserved from the account's daily cap inside its working hours first (security §1), and a profile's credit after its slot, before the read (a run started before beta-p1-090: its block of credits before the first read).
- **The screen:** members with `signals.read` see each source's post link (opened in a new tab with `rel="noreferrer"`, so LinkedIn gets no address of ours) and the label and status of its sender account, from linkedin's list, and for a waiting run, in the list and the runs panel, its account's reads today and next window from linkedin's usage route (`linkedin.read`: counts and times only); the browser reads them through the web's API client with the member's session, and writes go through the same routes and checks as the API.
- **The evidence panel:** members with `leads.read` see, on a lead's page, read in the browser through the web's API client with the member's session, its events' evidence (the person's comment, their name, the reaction) and the labels of its sources; the post opens in a new tab with `rel="noopener noreferrer"`, and only for an `http(s)` URL.
- **Leaving the system:** the reads go to LinkedIn through linkedin's adapter, the reference opened in the worker only; a create with a short link sends one GET to `lnkd.in` from the api through the platform's `fetchSafe` (its path only, no cookie, five seconds, a kilobyte), whose `Location` is read and never fetched, and no log line, error or span carries the link, the `Location` or the post's URL (the span: the host only); events carry ids only; qualification's batch sends the kept persons' business fields, anonymized, to the model.
