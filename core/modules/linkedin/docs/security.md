# linkedin: security

- **Red lines**: only the user's own account, through the provider's hosted page; never a password, a cookie or a second factor in Whytide; never a shared, rented or fake account. The disclosure is acknowledged before the link is made, by the screen and by the api (`disclosure_required`). Every read is reserved first: refused outside the working hours and past the daily cap, both in the account's zone, and for an account not `connected`; reservations of an account queue on the day's usage row, so concurrent runs cannot pass the cap together.
- **The reference**: sealed with the platform's envelope encryption under `APP_MASTER_KEY`, the context the workspace's organization and the purpose `linkedin_account`; a row copied to another organization does not open. The api seals it in the webhook and never opens it; `withDecryptedRef` in `workflows/` opens it and zeroes the buffer after. The lint's `decrypt-in-worker-only` refuses `@whytide/platform/secrets/worker` outside the worker host and a module's `workflows/`, and a module's `workflows/` outside the worker host, itself and the module's tests. The answers, the events, the logs and the OpenAPI document never carry it, sealed or not.
- **The webhook route**: public, no session. It is limited per address, reads at most 64 KiB, refuses a compressed body, and changes nothing before the adapter checks the vendor's signature (401). It finds the account by the reference's hash across workspaces, then writes in that account's workspace only. Only the webhook (or the worker's refresh) sets `connected`: the return visit is not trusted, it shows the status.
- **Pairing**: on the fake, the pending account by the link's `providerRef`. On Unipile, open (README "Open questions"): never by anything the browser sends.
- **Who may do what**: `linkedin.read` lists the workspace's accounts, `linkedin.connect` connects one's own, `linkedin.manage` (Owner, Admin) changes, refreshes and disconnects one; its daily read cap too, within `LINKEDIN_DAILY_READ_CAP_MAX`, the operator's bound. The screen shows the cap's field to whom the account's `canManage` says, the api's `can()`, and the api refuses the rest (403). Every query runs in a tenant run scoped to the workspace; the table passes the two-workspace isolation test.
- **The action log**: `object_ref` is a post's URL or a person's id, checked by `isObjectRef` (schemas/quota.ts): never a profile's URL, which names someone who may not be a person of ours (security §1). No log line, error detail or metric label carries it: `linkedin.actions` has `kind` and `outcome` only.
- **Refresh status**: `linkedin.manage`, the account in the caller's workspace (404 otherwise), the origin check and `@Idempotent()`; the event carries the account's id only, and the subscriber takes the workspace from the delivery's tenant run, never from the payload. Each press asks the provider once (README "Open questions"). The hourly refresh reads no tenant table across workspaces: the workspaces' ids come from tenancy's global tables (`listWorkspaceIds()`), and each workspace's accounts are listed and refreshed in that workspace's run; the webhook's lookup stays the one read across workspaces. Workflow inputs, results and the replay histories hold ids and statuses only.
- **Leaving the system**: the provider calls (the hosted link, the account's status) go through the LinkedIn port's adapter; events carry ids only.
