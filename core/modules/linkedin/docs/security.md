# linkedin: security

- **Red lines**: only the user's own account, through the provider's hosted page; never a password, a cookie or a second factor in Whytide; never a shared, rented or fake account. The disclosure is acknowledged before the link is made, by the screen and by the api (`disclosure_required`), and its sending version, with the confirmation that the account is the owner's own personal one, before any send: `sendStateRefusal`, which beta-p1-050 asks again before the call. Every read is reserved first: refused outside the working hours, past the day's read limit (the smaller of its allowance and the cap) and past the day's 200 actions, all in the account's zone, and for an account not `connected`; reservations of an account queue on the day's usage row, so concurrent runs cannot pass the cap together, nor the reads a `keep` leaves.
- **Budgets**: every send is reserved first, under its step's key, the account read from Postgres in the reservation's run: refused for an account not `connected`, while its `retry_at` lies ahead, outside its window and on Saturday and Sunday in its zone whatever days it lists, past the month's three notes, the day's limit of its type, the week's 100 connection requests and the day's 200 actions. One live reservation per key (the partial unique index), so a retry takes no second slot; a send that went out is counted, after a release or past its hold too. A zone change takes effect from the next local day, so no move opens a second day's budgets within 24 hours. `tests/safety/` checks these on concurrent reservations and seeded sequences.
- **Hard maximums**: 25 connection requests, 80 messages, 15 withdrawals, 100 reads and 200 actions a day, 200 connection requests a week: `domain/quota/constants.ts`, frozen, and the CHECKs of `linkedin_send_quotas`, never a setting; no setting, route, script or operator raises them. `LINKEDIN_DAILY_READ_CAP_MAX` is bounded by `READS_PER_DAY_MAX`, so a value above 100 stops the start; `tests/safety/` checks the CHECKs, the bound and that no other file declares a maximum.
- **The reference**: sealed with the platform's envelope encryption under `APP_MASTER_KEY`, the context the workspace's organization and the purpose `linkedin_account`; a row copied to another organization does not open. The api seals it in the webhook and never opens it; `withDecryptedRef` in `workflows/` opens it and zeroes the buffer after. The lint's `decrypt-in-worker-only` refuses `@whytide/platform/secrets/worker` outside the worker host and a module's `workflows/`, and a module's `workflows/` outside the worker host, itself and the module's tests. The answers, the events, the logs and the OpenAPI document never carry it, sealed or not.
- **The webhook route**: public, no session. It is limited per address, reads at most 64 KiB, refuses a compressed body, and changes nothing before the adapter checks the vendor's signature (401). It finds the account by the reference's hash across workspaces, then writes in that account's workspace only, the receiver included. Only the webhook (or the worker's refresh) sets `connected`: the return visit is not trusted, it shows the status.
- **Pairing**: only by the vendor's notify of the hosted link, which names the link's `providerRef` (on Unipile in its `name`, with the pairing token the adapter verifies: core/packages/providers/linkedin/unipile/README.md "Pairing"); never by anything the browser sends, nor by a status, which sets an account's status only once it is paired. A second user of a workspace pairing a LinkedIn account connected there already gets `sender_account_in_use` (409), checked in the pairing's run: their pending account ends `disconnected` with its link cleared, so the vendor's retries find none (204), and the unique hash never answers a 500.
- **Personal conversations** (RB-13.1.3): a person event is kept only when an outreach row of its account names the person: an acceptance by the member; a message by its chat, or by its sender (inbound) or attendees (the account's own). Anything else, a friend's message or the account's own to that friend, is dropped before it is stored: no row, no receipt, no file, no log line, `linkedin.events_dropped` by kind alone. The filter reads refs only. A kept message's text goes to a raw file (refs, no person id, 72 hours) for its subscriber; the events carry ids; `provider_member_ref` is personal data, never logged or a label.
- **Who sees which account** (gamma-p6-070): `linkedin.read` lists the accounts the caller sees, a Member's own, every member's for a holder of `linkedin.manage` (Owner, Admin), and reads their usage and health; `linkedin.connect` connects one's own, and its owner alone, whatever their role, changes, refreshes, resumes and disconnects it, its daily read cap too, within `LINKEDIN_DAILY_READ_CAP_MAX`, the operator's bound, itself at most 100, and accepts its disclosure. Anyone else is refused `not_account_owner` (403), an Owner included: the domain checks the account's `owner_user_id` (`domain/access.ts`), whatever the route declares. The screen shows the cap's field to whom the account's `canEdit` says, and the api refuses the rest. Every query runs in a tenant run scoped to the workspace; the table passes the two-workspace isolation test.
- **The action log**: `object_ref` is a post's URL or a person's id, checked by `isObjectRef` (schemas/quota.ts), or, alone on a send's row, the step execution (`sx_`) or inbox's reply (`msg_`) it records: never a profile's URL, which names someone who may not be a person of ours (security §1), and never a person on a send's row. No log line, error detail or metric label carries it: `linkedin.actions` has `kind` and `outcome` only. `app` cannot update a row (`REVOKE UPDATE`, 42501): it inserts and reads them, and deletes them through `erasePerson` and the 90-day purge only; the `outcome` is a closed list, `ACTION_OUTCOMES`, which the database's CHECK holds too.
- **Refresh status**: `linkedin.manage`, the account in the caller's workspace (404 otherwise), the origin check and `@Idempotent()`; the event carries the account's id only, and the subscriber takes the workspace from the delivery's tenant run, never from the payload. Each press asks the provider once (README "Open questions"). The hourly refresh reads no tenant table across workspaces: the workspaces' ids come from tenancy's global tables (`listWorkspaceIds()`), and each workspace's accounts are listed and refreshed in that workspace's run; the webhook's lookup stays the one read across workspaces. Workflow inputs, results and the replay histories hold ids and statuses only.
- **The member id**: the account's own LinkedIn member id is never stored, logged, published or put in a workflow input: only its keyed hash, HMAC-SHA-256 of `linkedin:<member id>` under `LINKEDIN_HASH_KEY`, a secret of 32 characters or more, as contacts' `HASH_SALT` is for persons; the receipts' event key hash is keyed with it too. The partial unique index, which the database checks on every row whatever a run sees, keeps one LinkedIn account on one connected row in every workspace, with no read across them; until the hash is stored, after each connect until the refresh has read the member id again, and while `LINKEDIN_HASH_KEY` is empty, whatever hash is stored, the account sends nothing (`member_id_unknown`), so a reconnect sends neither under the previous LinkedIn account's targets nor from a second row. `tests/safety/disclosure.test.ts` checks these.
- **Leaving the system**: the provider calls (the hosted link, the account's status) go through the LinkedIn port's adapter; events carry ids only.
- **The kill switches**: read from Postgres in each reservation's own run, reads included, with no cache, so a switch holds from the next reservation; beta-p1-050's activity asks again before the port call. Who may lift a pause (gamma-p6-070): the checks compare user ids and ask platform's `can()` for `linkedin.manage`, in the domain, so the routes and the safety cases meet one rule: a pause, the account's owner or a holder of `linkedin.manage`; a tester's pause lifted by the same; a removed member's (`member_removed`, written by the removal's subscriber) by its owner alone, once invited again, never an Owner; the workspace's stop, a holder of `linkedin.manage` alone (`forbidden`, 403); anyone else `not_account_owner` (403). No route lifts a stop the operator holds (`stopped_by_operator`, 409) or writes the instance's row. The CHECKs keep a stop's source set exactly when it is on and the instance's row single; `app` cannot delete that row, nor update or delete a control event (42501). Sending is closed until the operator opens it. `tests/safety/kill-switches.test.ts` checks these.
- **The control command** (`pnpm linkedin:control`, README "The control command"): the operator's way to the switches, run on the machine as `app` by whoever holds its shell and its environment; no route or page reaches it. Every change names its operator: `--operator`, a name matching `^[a-z0-9][a-z0-9._-]{0,63}$`, never free text, is the control event's `actor`, `actor_type` `operator`, written in the change's own transaction, so no change goes unrecorded and no event records a change that did not happen. Who lifts what: the instance's stop and its sending, the command alone; the fleet breaker's pause of the connection requests, the command's `breaker reopen` alone, never a route, a tester's switch, the operator's other switches, a reconnect or the owner's resume; the operator's pause or stop of a workspace or an account, the command alone, the routes answering `stopped_by_operator`; a tester's pause or stop, the tester, the command answering `paused_by_tester`; the operator's pause takes a tester's over. It changes the switches through `domain/controls/` only, calls no provider and prints ids and codes only. `tests/safety/operator-stop.test.ts` checks these.
- **The posts read** (gamma-p5-015): the phrase or the author's link comes in a request file under `raw/`, the page goes out in a file there with the vendor's cursor, which may carry the author's vendor id or the phrase; the next page's request names the previous page's file. The workflow's input, its answer and so its history hold ids, file keys, counts and a boolean only. No `read_posts` row names an object; the excerpts and names stay in the file, which raw/'s 72 hours expire.
- **Sends** (beta-p1-050): only `workflows/send.ts` calls the port's send side, each call under an open reservation and after the switches and the account are read again, in the activity's run, from Postgres. Provider refs stay in linkedin: the caller's request file under `raw/` holds the member ref and the words, never a chat or invitation ref, which the activity reads from the outreach row and writes back there. An answer, and so the workflow history, holds ids, codes, booleans, numbers and instants only; a thrown failure reaches it as its code. The send's `ok` row names its step execution, never a person.
- **Account health** (beta-p6-010): any warning from LinkedIn pauses the account in the transaction that learns it, its row locked first: the webhook's restriction or checkpoint, LinkedIn's limit, a lost session, a send's, a check's or a read's typed error. The next send and read reservation is refused `account_paused` (read from Postgres, no cache), the open send slots are released but one held for a send whose outcome is unknown, so that its late commit after a reconnect the same day never passes the day's limit, and a cool-down ends no earlier than 72 hours after the last warning; a disconnect and a reconnect never cut it short. The third call answered by a rate limit or a provider error in an hour, the attempts of one call counting once, pauses sends and reads until the next working day.
- **The health mail**: only to the account's owner, an enabled user and an active member of the workspace (gamma-p6-070), through the app-mail port from the worker, never from a run or a subscriber; at most one per event (the workflow's id, then `owner_notified_at`). It holds the state, the trigger's words, the pause's end in the account's zone and the LinkedIn page's link: never a person's data, a member id, the account's reference, a provider's message or an error's details. A health event's `metrics` hold numbers and codes only.
- **The fleet breaker** (beta-p6-030; RB-11.3.2, reduced for beta): a restriction or a checkpoint on any account pauses every account's connection requests on the instance, in the warning's own transaction, so the account's pause and the instance's commit together; messages, withdrawals and reads go on. The trip writes one control event, `actor_type` `system` and actor `fleet_breaker`, and is a compare-and-set, so two warnings at once record it once. Only the operator lifts it, with `breaker reopen`, whose event names them. `tests/safety/fleet-breaker.test.ts` checks these.
- **The operator's mail**: only to `LINKEDIN_ALERT_EMAIL`, through the app-mail port from the worker, never from a run or a subscriber; at most one per trip (the workflow's id, then `operator_notified_at`). It holds the workspace's and the account's ids, the trigger, the time and the reopen command: never the account's label or reference, a person's data, a member id, a provider's message or an error's details. With the address empty, no mail goes and the worker logs `linkedin_alert_email_missing` with the event's id.
- **Pending invitations** (beta-p4-070, RB-11.2.5): no connection request while more than 400 of the account's invitations are pending, or while the count is unknown or older than 48 hours, failing closed: `sendStateRefusal`, in the reservation's run and again before the call, and `remainingToday`. Each committed invite raises the count until the next check, under the account's row lock, but one LinkedIn refused as already connected, which leaves no invitation and no outreach row (connect-already-connected). The check's calls are reads under the quota, once a day at a random time, never on a fixed schedule (RB-11.2.4); the activity answers counts and codes only, and the provider refs stay in linkedin's tables. `tests/safety/pending-invites.test.ts` checks these.
- **The resume** (beta-p6-040): only the account's owner resumes it after a cool-down, whatever their role since gamma-p6-070 (`not_account_owner`, 403, for any other member; the check compares user ids, as the unpause's does), and only once the cool-down is over, after a checkpoint only once the owner has connected the account again, and only on the worker's status read after the cool-down's end and at most 10 minutes before: the api never opens the reference, so it never asks the provider itself, and no decryption reaches the api for this route. The resume restarts the account at half its targets and never raises today's limits; it leaves the fleet breaker, which only the operator reopens, and the switches as they are. The health route answers numbers and codes only: no reference, no member id, no person.
- **Company pages** (gamma-en-060): `readCompany` reads a company page's business facts only (the port's `LinkedinCompany`: no person, follower, employee, post or phone), through any connected account of the workspace, each read reserved as `read_company` within the account's daily reads, window, pauses and switches, and within `LINKEDIN_COMPANY_READS_PER_DAY`. The reference is opened only by the worker's decrypt entry, which `workflows/index.ts` registers as it loads (`useRefOpener`); `domain/` holds a function handle, never a key, and the api, which never loads `workflows/`, has none (`company_read_unavailable`). The page's link and its facts reach no log line, span, metric label or action-log row.
- **Contact info** (gamma-en-087; the owner's exception of 2026-11-13 to security §1, behind `LINKEDIN_CONTACT_INFO_ENABLED`, off by default): `readContactEmails` reads a lead's "Contact info" email addresses only, never its phones, addresses, birthday, messengers or websites, and only through a connected account of the workspace whose invitation the person accepted, each read reserved as `read_profile` within the account's daily reads, window, pauses and switches. Off, nothing is reserved or called. The reference is opened only by the worker's decrypt entry (`contact_read_unavailable` elsewhere). It is the port method's only caller (the providers' never-list safety case). The addresses reach no log line, span, metric label, action-log row or event; the rows name the person's id, erased with the person. Off stops new reads only: nothing is deleted.
