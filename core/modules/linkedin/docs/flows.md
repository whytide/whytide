# linkedin: flows

- **POST /accounts/connect**: after the host's guards (session, workspace, `linkedin.connect`, origin), on a `whytide:own-runs` route: the acknowledgment of `DISCLOSURE_VERSION` and the personal-account box, the zone; a run that refuses a connected account; the provider's `createHostedAuthLink` with the return URLs, 30 minutes, outside any run; a run that upserts the user's row as `pending` with the link's `providerRef`, the version and the confirmation's time. The browser goes to the link.
- **The provider's page**: the user signs in at the provider, which sends the browser back to the screen and posts `account.connected` to the webhook route. On the fake, the link is the test-mode route `connectOnVisit` (served under `APP_ENV=test` only, on the web's origin through its `/api/linkedin/*` rewrite), which posts the webhook before it redirects.
- **POST /v1/linkedin/webhooks/{provider}**: the host's limit per address (open when Redis does not answer), the raw body read, then `handleWebhook`: the adapter's `parseWebhook` checks the signature (401 otherwise), then by kind. An account event reads as one status. `connected` with the link's `providerRef`, the vendor's notify of the owner's connect: the rows by `providerRef`, across workspaces, on the module's client; for each, the workspace's organization, the reference sealed, then one run in that workspace that pairs a pending account: when another account of the workspace has the hash, it ends `disconnected`, its link cleared, and the answer is `sender_account_in_use` (409); otherwise `connected`, the sealed reference, its hash, `connected_at` and `linkedin.sender_account_connected`, paired as replaced, its kept member id cleared, when another connected row holds that id. Any other status, `connected` without the link's `providerRef` too (Unipile's `OK`, `SYNC_SUCCESS`): the rows by hash, one run each, a pending one left as it is, the status and `status_checked_at`, the event when it crosses into `connected` or `disconnected`. `checkpoint`, `restricted`: `linkedin.account_warnings` only. `ignored`: `linkedin.events_dropped` only. `invite.accepted`, `message.received`: the receiver. 204 once it resolves.
- **The receiver** (`domain/receiver/`): verify, filter, file, one transaction. The accounts by the reference's hash, across workspaces; for each in turn, a run in its workspace reads the account's outreach rows the event's refs name, and picks the one it concerns; none in any: `linkedin.events_dropped`, nothing stored or logged. A kept message: nothing when the event has its receipt already, a redelivery, whose file inbox's store may have deleted (beta-p5-010); else its file through the files port, outside any run, at `raw/linkedin/messages/<event_key_hash>.json`; then one run: the row read again, the receipt (`ON CONFLICT DO NOTHING`: a repeat, or a delivery at the same time once the first commits, ends there), for an inbound message `last_inbound_at` when later and `provider_chat_ref` when null, and `linkedin.message_received`. A kept acceptance: one run: the row, the receipt, then, when `accepted_at` is null, `accepted_at` and `accepted_detected_at` and `linkedin.invite_accepted`. The receipt, the row's change and the event commit together; a failed run leaves at most the orphan file, which raw/'s 72 hours expire. The subscribers run in the worker, from the outbox.
- **GET, PATCH, DELETE /accounts…**: in the request's tenant run; another workspace's account is not found (404). DELETE writes the event in the same transaction.
- **POST /accounts/{id}/refresh**: after the host's guards and `@Idempotent()`, in the request's tenant run: the account (another workspace's is 404), then `linkedin.status_refresh_requested` written to the outbox in the same transaction; 202 with the account. In the worker, the event's delivery runs in that workspace's tenant run; the subscriber (`events.ts`) takes the workspace from it, `currentTenant()`, and starts `linkedin_refresh_account` with `startWorkflow`, by the event's id, so a second delivery starts none. The screen asks for the account every two seconds until its status changes, thirty seconds at most.
- **linkedin_status_refresh** (worker, hourly): `linkedin_list_workspaces`, global, the workspaces' ids from tenancy's `listWorkspaceIds()`, outside any run; for each workspace, `linkedin_list_referenced_accounts` in that workspace's run, its accounts with a reference, ids only; then `linkedin_refresh_status` for each account in turn and, behind the patch `pending-invites`, `linkedin_check_invites` after it ("The pending invitations' check").
- **linkedin_refresh_status** (worker): the row and its reference in the activity's run; `withDecryptedRef` opens it; `getAccountStatus` outside any run; then a run that stores the status and the member id's hash (below) and writes the event on a crossing, and one that logs the `status_check`. A typed port error but `linkedin_not_found` (beta-p6-020): one run logs the `status_check` with its code, sets `retry_at` as the error map says and applies the error's health ("Health"); the activity answers `{ status, failed }`, the status as it was, never thrown, so Temporal does not call again; any other error throws. While the account's `retry_at` lies ahead, no call, no run and no row: `{ status, held: "rate_limited" }` (beta-p6-040). A read of `connected` with the status `connected` already is still a reconnect for the health: a `disconnected` account, which a send's or a read's lost session left, goes `healthy`.
- **The member id after a connect**: `linkedin.sender_account_connected`'s subscriber starts `linkedin_refresh_account` by the event's id, as a Refresh status press does. The pairing clears `member_id_checked_at`, so the account sends nothing (`member_id_unknown`) until a refresh reads a member id and sets it in the run that stores the hash: a reconnected row still holds the previous LinkedIn account's hash. The refresh hashes the member id `getAccountStatus` answers (no key: nothing stored, `linkedin_hash_key_missing` logged once per run). The write names the pairing the activity read (`connected_at`): after a reconnect during the call, it stores no member id and leaves `member_id_checked_at` null for the next refresh. A row without a hash takes it; the same hash changes nothing; another replaces the account in the same run: the targets 5 and 10, `ramp_updated_on` null, `disclosure_version` 1, `personal_account_confirmed_at` null, `linkedin.account_replaced`. When the unique index refuses the hash, another connected row holds it: the run is lost, and a second run ends the account as a disconnect does, with a `status_check` row `sender_account_in_use` and `linkedin.sender_account_disconnected`; the activity answers that as its result, so nothing retries.
- **POST /accounts/{id}/disclosure**: after the host's guards and `@Idempotent()`, in the request's tenant run: the account (404), its owner (`not_account_owner`), the version (`disclosure_version_invalid`), the box (`personal_account_required`), nothing stored before all four pass; then, unless accepted already, the version, `disclosure_acknowledged_at` and `personal_account_confirmed_at`, now; the account answered.
- **The daily job** (worker, `linkedin_daily`, daily at 00:30 UTC by the schedule `linkedin.daily`): `linkedin_daily_tick`, global, takes the workspaces' ids from tenancy's `listWorkspaceIds()` and starts each one's `linkedin_daily_workspace` by the id `linkedin.daily:<workspaceId>:<UTC date>`, one run of the id at a time (a start while it runs starts none; one after it closed runs it again, which changes nothing more that day); then `linkedin_purge_receipts`, global, deletes the receipts past 7 days outside any run, 5000 per transaction on the global client (`inGlobal`). A workspace's run: `linkedin_ramp_accounts`, each account in a run of its own: its row locked (`SELECT … FOR UPDATE`, so two runs at once give one step), then under the lock the switches, the account and its committed sends of the 14 quota days before today and today (before them, the first day of each type since its last step), its quota day in its zone (platform's `quotaDay`), `rampStep` (docs/concepts.md "Ramp") and the write; `linkedin_expire_holds`, the reservations past their hold of a day no reservation swept (the sweep covers the day in use only), each day's row locked first in a run of its own and swept as a reservation sweeps it; `linkedin_purge_action_log`, the workspace's log rows past 90 days, 5000 per run until none is left. A failed account, start or workspace leaves the others going on and the purges still run; the activity, then the run, fails with the first failure's code.
- **The day in use** (the reservations, remainingToday, the usage route): the account's latest row whose date has begun in the zone it was made in and is not over there or in the account's zone now (`dayEndsAt`); else the account's date now, its row made in that zone.
- **reserveReads** (the caller's run): the account; refused, and logged, when a kill switch is on, when it is not `connected`, its health pauses it (`account_paused`), its `retry_at` lies ahead or its window is closed; then the day's usage row (the day in use), locked (`SELECT … FOR UPDATE`) before it is read, so concurrent reservations of the account wait here; when the lock finds none, the row is inserted with its limits drawn (`ON CONFLICT DO NOTHING`, which waits for another run's uncommitted insert of the day and keeps the first draw) and locked again; the sweep; reads reserved plus committed plus `count` checked against the smaller of the allowance and the cap (`read_cap_reached`), then the day's actions against the 200 (`daily_actions_cap_reached`); the reservation, the day's `reads_reserved` moved by an increment, and the log row, or the refusal's log row. The run's commit releases the lock.
- **Sends** (the caller's run). reserveSend: the account; a repeat of the key answered first, with no row; `sendStateRefusal`, refused and logged; the key's reservations past their hold expired, each on its own day's row, locked first; the day's row locked as for reads, the key asked again under the lock, the sweep; the note budget (an invite with a note), the type's limit, the week (an invite) and the 200, refused and logged in that order; the reservation inserted (`ON CONFLICT DO NOTHING` on the key's index: a conflict answers the holder), the type's reserved counter moved by an increment, and the `reserved` log row. Then beta-p1-050's activity: `sendStateRefusal` again, the port call outside any run, and the settle the error map names. commitSend, releaseSend: an invite's account row locked first (commitSend), then the reservation's day row, the reservation read again, then its status and its type's counters, and for a committed invite one more on the account's pending invitations when the count is known; a commit after a release or the hold's end while another reservation holds the key is `committed_late`.
- **Reservations**: the sweep, in each reservation of a day: the day's reservations past their hold, of every type, expire in one statement that names the run's workspace, and what they held comes off each type's reserved counter. commitReads, releaseReads (the caller's run): the reservation's day row locked first, the reservation read again, then its status and the day's counters; a settled one answers as before.
- **The error map** (`SEND_ERROR_MAP`): success commits the slot and the credits, the step `succeeded`. `linkedin_rate_limited` releases both, reschedules the step after `retryAfterSec` and sets `retry_at` that far. An unknown outcome (`linkedin_provider_error`, `linkedin_output_invalid`, `linkedin_error_unmapped`) keeps the slot until `linkedin_check_sent` answers, the credits as the slot, the step `executing` until that check after the pause, never retried in a loop; `retry_at` an hour on, the session ended. `linkedin_send_refused` and `linkedin_not_found` commit the slot, release the credits and fail the step, the enrollment `exited` with `send_refused`. `linkedin_limit_reached` commits the slot, releases the credits, waits for the resume, the account `restricted` (trigger `limit_reached`) for 72 hours. `linkedin_account_disconnected` releases both and reschedules, the account `checkpoint` or `restricted` for 72 hours by its reason, else `disconnected`. `linkedin_input_invalid` releases both and fails the step, a defect. A refusal before the call releases both and waits for its `retryAt`, or the resume. A repeat answered `committed` is a success, its credits settled as sent through the check.
- **linkedin_read_post_engagers** (worker): a run reads the switches and the account again, on every attempt (beta-p6-020, beta-p6-040), in the reservation's order: a stop, its code; not `connected`, `linkedin_account_disconnected`; paused by its health, `{ refused: "account_paused" }`; its `retry_at` ahead, `{ refused: "linkedin_rate_limited" }`; each answered with no call and no row. Then `withDecryptedRef` opens the reference; `listPostEngagers` outside any run; a run that logs `read_engagers` with the outcome, and a port error's health ("Health"); the page to the files port at the given `raw/` key; the key, the count and the next cursor back. The caller's run holds the read's reservation.
- **linkedin_read_profile** (worker): the request file at the given `raw/` key read; the account read again as for the engagers; `withDecryptedRef` opens the reference; `getProfile` outside any run; a run that logs `read_profile` with the outcome and no object, and a port error's health; the profile to the files port at the given `raw/` key; the key back. The caller's run holds the read's reservation.
- **GET /accounts/{id}/usage**: in the request's run, the account, its quota day and window from the clock, the day's row (the day in use), made with its draw if missing, unlocked; the connection requests of the six quota days before, for the week.
- **remainingToday** (the caller's run): the account; the switches, nothing while sending is closed, a kill switch is on, the account's health pauses it, its `retry_at` lies ahead, its disclosure for sending is not accepted or its member id is unknown (`windowEnd` null), no invite while the invites are paused, the account is `at_risk` or its pending invitations' count refuses one; no send on Saturday or Sunday in its zone, nor for an account of the weekend alone, answered before any row; else the day's row (the day in use), made with its draw if missing, unlocked; the connection requests of the six quota days before; `limitsFor`, and the end of what is left of today's send window. **senderOf**: the user's `connected` account in the run's workspace.
- **A switch and the next reservation**: reserveSend, reserveReads and remainingToday read the switches in the caller's run, from Postgres (`readControls`: the instance's row, the workspace's, and the account's `kill_switch` with the account), so a change holds from the next reservation. A send is refused, first and in this order, `sending_closed`, `platform_stopped`, `workspace_stopped`, `account_stopped`; after the account's status, `account_paused`, `invites_paused` for an invite, then `disclosure_required`, an invite's `pending_invites_unknown` and `pending_invites_over_limit` (the count with the account's open invite reservations, the gate's own aside), and `member_id_unknown`. A read is refused the three stops only. A repeat of a reserved key answers its hold before any refusal: beta-p1-050's activity asks `sendStateRefusal` again just before the port call, so a send reserved before the switch does not go out.
- **POST /accounts/{id}/pause, …/unpause, PUT /controls** (the request's tenant run, the two POSTs `@Idempotent()`): the account, or the workspace's row, read; unpause checks the owner first; then a compare-and-set from the state read (`updateMany` whose `where` names it; the workspace's first stop inserts its row, `ON CONFLICT DO NOTHING`) and, when a row changed, the control event in the same run, so two presses at once change it, and record it, once. A lift that finds the operator's stop changes nothing and answers `stopped_by_operator`. The operator's variants run in the named workspace's run; the instance's switches in a transaction on the global client outside any run (`withoutTenant`), so the change and its event commit together.
- **`pnpm linkedin:control`** (the machine, README "The control command"): the arguments parsed, `--workspace` resolved through tenancy's `findWorkspace` or `findWorkspaceBySlug`; a change calls the operator's variant above and prints `changed`, `unchanged` or the refusal; `status` reads the platform's row on the global client, then, for each id of tenancy's `listWorkspaceIds()` (or the one named), the workspace's slug from tenancy and its stop and accounts in that workspace's run, one run each.
- **The send activities** (worker, `workflows/send.ts`; beta-p1-050): `linkedin_send_invite`, `linkedin_send_message`, `linkedin_withdraw_invite`. The request file at `requestKey` (`sendRequestFile`) read, outside any run: one that is no send of the activity's is `linkedin_input_invalid`, its slot released, no call; one the files port cannot read throws, retried, its slot kept. On a retry (the step's `stepAttempt` or the Temporal attempt above 1, or an earlier call of the step whose outcome is unknown), the check below first: went out, settled as sent, no call; a refused read answers its refusal and holds the slot. Then one run, the gate: a reservation of the key already counted, late included, answers sent with no call, the live one released; else the activity's reservation must be `reserved`, of the step's account, type and key, with `SEND_CALL_MARGIN_MS` left on its hold (one shorter is released), and carry the note's budget when the file has a note; `sendStateRefusal` read again (sending closed, the switches, the status, the health, invites paused, the disclosure, the member id, `retry_at`, the window); a withdrawal needs the outreach row's invitation ref. A refusal releases the slot and logs the code. `withDecryptedRef` and the port call, with the step's key and the outreach row's chat ref, outside any run; an attempt with less than `SEND_CALL_MIN_LEFT_MS` (45 s) of `SEND_CALL_MARGIN_MS` left by its own monotonic clock makes no call and throws `send_attempt_late`, retried with the slot kept, since Temporal may have started the next attempt, which checks first. Then one run: success commits the slot, writes the `ok` row once per step (`with_note` for a note) and upserts the outreach row (the member ref, the invitation ref and `invited_at`, the chat ref, `last_message_ref` and `last_sent_at`, or `withdrawn_at`, and `last_step_execution_id`); a typed port error settles by `SEND_ERROR_MAP`: the slot committed, released, or held until `retry_at` plus `SEND_RESERVATION_MS` while the outcome is unknown; `retry_at` moved to now plus `retryAfterSec` (a 429) or `PROVIDER_ERROR_PAUSE_MS` (an unknown outcome), never earlier; the code logged, then the error's health in the same run ("Health"); answered, never thrown. `linkedin.actions` after each run.
- **linkedin_check_sent** (worker): the request file; none of the key's reservations, `not_sent` with no read. Else a run reserves one `send_check` read naming the step (refused: the answer, nothing else changes); `getRelation` (an invite went out when pending or connected, a withdrawal when no longer pending) or `listRecentMessages` since the key's first reservation less `SEND_CHECK_SKEW_MS` (a message of the account's), outside any run (`domain/send/went-out.ts`); a run commits the read and logs it, then went out: the key's latest reservation committed unless one is counted, the `ok` row once, the outreach row; not: the key's open reservation released. A port error: the read committed, the code logged, `retry_at` as for a send, the error's health ("Health"), and the key's open reservations held until the later `retry_at` plus `SEND_RESERVATION_MS`. **linkedin_check_reply**: the outreach row; no chat, member or send known, no read; else one `send_check` read naming the person, `listRecentMessages` since `last_sent_at`, and the person's latest message after it sets `last_inbound_at`, never earlier.
- **Health** (`domain/health/`, beta-p6-010): the cause's run (the webhook's warning, `setStatus`, `completeConnect`, the run that logs a send's, a check's, a status check's or a read's port error, the day's acceptance rule) calls `applyHealth`: the account's row locked (`SELECT … FOR UPDATE`), `transitionOf` the state and the signal; a signal the state ignores changes nothing, and a warning in a cool-down only moves `paused_until` later. Else the state, `health_changed_at` and `paused_until` written, one `sender_health_events` row, `linkedin.health_changes`, and into `restricted`, `checkpoint`, `disconnected` or `at_risk` `linkedin.account_paused` in the outbox; into `restricted` or `checkpoint`, the fleet breaker (below); into the first three, each open send reservation of the account released under its day's lock, taken after the account's and the platform's, but one held past its two hours for a send whose outcome is unknown (`holdSendUntil`), which its check settles, and one settled since it was listed. A rate limit or a provider error, logged, takes the same lock and counts the distinct calls among the account's rows of the two codes in the last 60 minutes (`call_ref`, a row without one its own call): at the third, `retry_at` moves to the next working day's start, never earlier, with an event and `linkedin.account_paused`. The subscriber starts `linkedin_notify`; `linkedin_mail_health` reads the event and the account's owner in a run, the owner through tenancy's `findUser` outside any run, renders `linkedin.mail.account_paused` in the owner's locale and sends it through the app-mail port outside any run, then a run sets `owner_notified_at` where it is still null.
- **The fleet breaker** (`domain/health/breaker.ts`, beta-p6-030): in `applyHealth`'s run, after the health event, `tripBreaker` updates the platform's row where `invites_paused` is false, or makes it (`createMany … skipDuplicates`), so of two warnings at once the second waits on the row's lock and then changes nothing; only the run that changed it writes the control event and `linkedin.invites_paused`, in the same commit. Its subscriber starts `linkedin_notify` with `recipient` `operator`; `linkedin_mail_health` answers `no_address` with the warn line while `LINKEDIN_ALERT_EMAIL` is empty, reads the event in a run (`already_sent` once `operator_notified_at` is set), renders `linkedin.mail.invites_paused` in the default locale, sends it outside any run, then a run sets `operator_notified_at` where it is still null. `breaker reopen` updates the row where `invites_paused` is true, on the global client outside any run, with its event in the same transaction.
- **The pending invitations' check** (worker, `linkedin_check_invites`; beta-p4-070): in a run, the account and today's row (the day in use, made with its draw if missing): due when the account is `connected`, `check_after` has passed and `checked_at` is null; else `{ due: false }`, no read and no call. Page by page: a run reserves one `pending_invites` read (refused: the answer, nothing written); `withDecryptedRef` and `listPendingInvites` outside any run; a run commits the read and logs `ok`. After the last page, or past 400 listed, one run locks the account's row, counts the invites committed since the check began, of any day's reservation, and writes `pending_invites`, the invitations listed plus those, and `pending_invites_checked_at`, where the account is `connected` with the `connected_at` the check began with, then the day's `checked_at`; no row written answers `linkedin_account_disconnected`. With the whole list: the account's outreach rows invited since its `connected_at` (all of them while it is null), not accepted, withdrawn or asked, oldest first, whose invitation ref and member ref are both off the list, a row without a member ref left; for each, a run reserves one `relation_check` read naming the person (refused: the pass ends), `getRelation` outside any run, and a run commits the read and logs it: connected, `accepted_at`, `accepted_detected_at` and `relation_checked_at` where `accepted_at` is still null, and `linkedin.invite_accepted` in the same run; neither connected nor pending, `relation_checked_at`; pending, nothing. A port error: its row, `retry_at` as the error map says, the error's health ("Health"), the read committed, and the check ends; a person's own (`linkedin_not_found`) also sets that row's `relation_checked_at`, and the pass goes on. Last, the acceptance rule (beta-p6-020): one run measures the account's newest 100 invites at least 7 days old in one query (`acceptanceOf`) and, with a rate, calls `applyHealth` with `at_risk` under 20 percent or `recovered` at it or over, trigger `acceptance_rate`, which moves a `healthy` account or an `at_risk` one only. `linkedin.actions` after each run.
- **Check status, then resume** (beta-p6-040; README "Health"): the card's "Check status" posts `/accounts/{id}/refresh` (above), and the worker's `linkedin_refresh_status` writes `status_checked_at` with the status; the card asks `GET /accounts/{id}/health` every three seconds until `statusCheckedAt` moves, a minute at most. `POST /accounts/{id}/resume`, after the host's guards and `@Idempotent()`, in the request's tenant run: the account's row locked (`lockAccount`, 404 for none), then read; `resumeRefusal` in its order (`not_account_owner`, `account_not_paused`, `cooldown_active` with `details.pausedUntil`, `linkedin_account_disconnected`, `reconnect_required`, `status_check_required`), refused with nothing written; else the targets halved and `ramp_updated_on` today, today's row (the day in use) locked after the account's and its send limits lowered to the smaller of the stored ones and a new draw, `applyHealth` with `resumed` (trigger `manual`, acknowledged by the owner: `healthy`, the event, the metric, no outbox row, the breaker untouched), and the account's events still to acknowledge acknowledged by the owner; the health read in the same run answers it (200). The card then shows `healthy`; a second press, or a press of the same key, changes nothing more.
