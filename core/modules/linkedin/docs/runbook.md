# linkedin: runbook

- **Settings**: `LINKEDIN_DAILY_READ_CAP_MAX` (README "Settings"), read at the start, at most 100: above, the start stops with `config_invalid`; an `.env` from before beta-p1-020 (250) comes down to 100 before the upgrade. An unset `PROVIDER_LINKEDIN` makes connect and the webhook fail with a 500; an unset `APP_PUBLIC_ORIGIN` (and `WEB_DEV_ORIGIN`) makes connect fail with a 500. `LINKEDIN_HASH_KEY` (`openssl rand -base64 32`): set it once, the same value in the api's and the worker's environment, and never change it. Empty, no account can send (`member_id_unknown`, a hash stored before included) and a kept person event answers 500 `linkedin_hash_key_missing`, which the vendor retries; changed, every account looks replaced at its next refresh: its owner accepts the disclosure again, its pending invitations' count is unknown until its next check, its enrollments end once campaigns reads `linkedin.account_replaced` (beta-p4-040), and a redelivered event is kept twice, the receipts kept under the old key no longer matching. `LINKEDIN_ALERT_EMAIL`: the operator's address for the fleet breaker's mail, set before sending opens; empty, the breaker still trips and the worker logs `linkedin_alert_email_missing` (warn, with `health_event_id`) instead of mailing.
- **Logs**: the api's request log names the route and the code; nothing of the reference or the webhook's body is logged.
- **Removing an account at the vendor**, which Disconnect does not do in alpha: in the Unipile dashboard, under Accounts, find the account by the user's LinkedIn name and delete it. Whytide's row stays `disconnected`; a webhook for it changes nothing more.
- **Reading the action log**: `SELECT at, kind, count, outcome FROM sender_action_log WHERE workspace_id = '<workspace>' AND sender_account_id = '<account>' ORDER BY at DESC LIMIT 100;` as the owner. `object_ref` is personal data: read it only for the case at hand, never copy it into a ticket; a send's row names its step execution (`sx_…`). The day's numbers: `sender_quota_usage` by account and `quota_day`, its drawn limits, the zone it was made in and its counters per action type; open reservations: `sender_quota_reservations` with `status = 'reserved'`, a send's with its `action_type` and `idempotency_key`. A `committed_late` reservation is a send that went out after its slot was freed: counted, nothing to do.
- **Reading the switches**: as the owner, `SELECT * FROM linkedin_platform_controls;` (no row: sending closed and nothing stopped), `linkedin_workspace_controls` by `workspace_id`, and `sender_accounts.kill_switch` and `kill_switch_source`. Their history: `SELECT at, scope, control, target_workspace_id, sender_account_id, from_state, to_state, actor_type, actor FROM linkedin_control_events WHERE target_workspace_id = '<workspace>' ORDER BY at DESC LIMIT 100;` (`scope = 'platform'` for the instance's: the breaker's events name the workspace and the account that tripped it).
- **The control command** (README "The control command"): `pnpm linkedin:control <subcommand>` on a laptop, from the repository root; on the production machine, from `deploy/`, `docker compose exec api node ../../modules/linkedin/dist/cli/control.js <subcommand>`. Every change takes `--operator <name>`, your own name in lowercase letters, digits, `.`, `_` and `-`, which its control event records. A change holds from the next reservation, well within the 60 seconds; `unchanged` means it was so already; exit 1 prints the refusal's code, exit 2 the usage. The JSON `info` lines among the output are the platform's log: `LOG_LEVEL=warn` before the command (`docker compose exec -e LOG_LEVEL=warn api …`) hides them.
  - `status`, first and after each change, `--workspace acme` for one: `platform: sending=closed stop=off invites_paused=off reason=none`, then each workspace, `workspace: wsp_… slug=acme stop=off source=none`, followed by its accounts, `account: sac_… workspace=wsp_… owner=usr_… status=connected switch=on source=operator`. Ids and codes only.
  - `sending open --operator anna`, `sending close --operator anna`: sends only; reads go on. Open sending only once every task under "Turning sending on" in the beta index is merged and the owner says so: the command checks nothing.
  - `stop --platform --operator anna`, `start --platform --operator anna`: every LinkedIn action on the instance, reads included. Stop the platform when nothing may touch LinkedIn: a wave of restrictions or checkpoints, a provider incident, a doubt about the accounts themselves. Close sending when only what goes out must stop, a send defect or a review of the messages, so that the signal runs keep reading.
  - `breaker reopen --operator anna`: the connection requests the fleet breaker paused open again, the only way to lift it ("The fleet breaker has tripped").
  - `pause --workspace acme --operator anna`, with `--account sac_…` for one account; `unpause` the same. The operator's pause takes a tester's over, and the screen cannot lift it (`stopped_by_operator`). The operator's unpause lifts the operator's only: a tester's answers `paused_by_tester`, and the tester lifts it on the screen; a removed member's (`source=member_removed`) answers `paused_by_member_removed`, and only the account's owner lifts it ("A removed member's account"). Before an unpause, read `status` and ask the workspace's tester: an account the operator paused over its tester's pause runs again once the operator unpauses it.
- **The hourly refresh**: the schedule `linkedin.status_refresh`, upserted at each start of the worker and paused while `WORKER_SCHEDULES=off`; in the Temporal UI under Schedules, where Trigger runs it at once. A run answers `{ accounts, failed }`; a failed account is the worker's `worker: an activity failed` line with `activity: linkedin_refresh_status` and its code. A status check the provider answered with an error is no failure (beta-p6-020): its `status_check` row holds the code (`linkedin_provider_error`, `linkedin_rate_limited`, …), the account's `retry_at` holds its reads and sends that long (the third such error in an hour, until its next working day), and the next hourly run asks again: `SELECT at, outcome FROM sender_action_log WHERE workspace_id = '<workspace>' AND sender_account_id = '<account>' AND kind = 'status_check' ORDER BY at DESC LIMIT 24;` as the owner.
- **The daily job**: the schedule `linkedin.daily`, 00:30 UTC every day (`DAILY_CRON`, `DAILY_ZONE`), upserted at each start of the worker and paused while `WORKER_SCHEDULES=off`. `linkedin_daily` answers `{ workspaces, started, receiptsDeleted }`, and each workspace's run, `linkedin.daily:<workspaceId>:<date>` in the Temporal UI, `{ accounts, ramped, staleDays, logDeleted }`. A failed run: the workspace's run of the day shows the failed activity and its code, and the worker's log `worker: an activity failed` names the activity; an account whose zone Intl does not know (a row changed by hand) fails its ramp, the workspace's other accounts ramped and its purge ran. A failed `linkedin_daily`: a start refused for one workspace, the others started and the receipts purged. To run it again or by hand: Trigger on the schedule in the Temporal UI, or `temporal workflow start --namespace <namespace> --task-queue whytide --type linkedin_daily --input '{}'`; one workspace: `--type linkedin_daily_workspace --workflow-id linkedin.daily:<workspaceId>:<date> --input '{"workspaceId":"<workspaceId>"}'`. A second run the same day ramps nothing more and deletes only what aged since.
- **Failure modes**:
  - An account stays `pending`: the webhook did not arrive. Check `UNIPILE_NOTIFY_URL` is the public URL of `POST /v1/linkedin/webhooks/unipile`, and the api's log for a 401 `linkedin_webhook_invalid` (a wrong signature or another adapter's path) or a 429 (the limit per address). The user can press Connect again.
  - Refresh status changes nothing: the provider says the same status, or the worker is not running and the event waits in the outbox (`SELECT id, created_at, attempts, last_error FROM outbox WHERE event_name = 'linkedin.status_refresh_requested' AND delivered_at IS NULL;`). The screen stops asking after thirty seconds; a reload shows the status once the worker has it.
  - `secret_context_mismatch` in the worker: the row's sealed reference was written for another organization (a row moved by hand); the user disconnects and connects again.
  - Reads stop for the day: the log's latest rows read `read_cap_reached` (the smaller of the day's read allowance and the cap, reserved plus made), `daily_actions_cap_reached` (the day's 200 actions, reads included, used) or `outside_working_hours` (check the account's zone and hours on the screen); `linkedin_account_disconnected` means the account is not `connected`. A member with `linkedin.manage` may raise the cap on the screen, up to `LINKEDIN_DAILY_READ_CAP_MAX`: a raised cap holds from the next quota day (the day's allowance was drawn with its row), a lowered one from the next reservation; a run already asleep until the next quota day keeps sleeping. A reservation left open by a dead run holds its reads for an hour, then the next reservation frees it.
  - Sends stop: the log's latest send rows read `rate_limited` (`sender_accounts.retry_at` lies ahead: the provider's limit, or the hour's pause after an unknown outcome), `outside_working_hours` (outside the account's hours, or a Saturday or Sunday in its zone, when nothing is sent), `invite_note_budget` (`LINKEDIN_INVITE_NOTES_PER_MONTH` invitations with a note in 30 days, 3 unset), or a cap: `invite_cap_reached`, `message_cap_reached`, `withdrawal_cap_reached`, `weekly_invite_cap_reached`, `daily_actions_cap_reached`. Each answer carries when to ask again; no setting raises a hard maximum. `disclosure_required`: the owner accepts the disclosure for sending on the screen; `member_id_unknown`: the refresh has not read the member id since the latest connect (`LINKEDIN_HASH_KEY` empty, the worker not running, or the refresh failed), which Refresh status asks again. A `status_check` row `sender_account_in_use` means the LinkedIn account is connected on another row, maybe in another workspace: its owner disconnects one. A send reservation left open holds its slot for two hours.
  - `secret_key_unavailable` in the worker: `APP_MASTER_KEY` no longer holds the key the reference was sealed with; keep the old key as `APP_MASTER_KEY_PREVIOUS` while rotating (core/packages/platform README).
  - A switch will not lift: `stopped_by_operator` (409) means the operator holds it (`stop_source` or `kill_switch_source` `operator`), which only the operator's command lifts ("The control command"); `not_account_owner` (403), that the caller is neither the account's owner nor, for a tester's pause, a workspace Owner; a removed member's pause only its owner lifts. A stopped instance shows "Stop everything" locked in every workspace. Every send refused `sending_closed`: the instance's sending is closed, as on a fresh install, until the operator opens it. A signals run a switch ended stays `failed` with its code; the next run after the lift reads on.
  - A step left `executing` (an unknown outcome, or a worker that died mid-call): its send may have gone out. Never send it again by hand: `linkedin_check_sent` with its request file tells, as one read (`send_check` rows naming the step); went out, it commits the slot and writes the `ok` row; not, it releases the slot. The step's rows: `SELECT at, kind, outcome FROM sender_action_log WHERE workspace_id = '<workspace>' AND object_ref = '<sx_…>' ORDER BY at;` as the owner. After an unknown outcome the account sends and reads nothing until `retry_at` (an hour); the reservation stays held until then plus two hours. `send_attempt_late` in a send's history: the attempt ran too long before its call (a slow check or provider) and made none; the next attempt checks first.
- **An account paused** (README "Health"): its health and cool-down, `SELECT health_state, health_changed_at, paused_until, retry_at FROM sender_accounts WHERE id = '<account>';`, and its history, `SELECT created_at, from_state, to_state, trigger, metrics, automatic_action, paused_until, owner_notified_at FROM sender_health_events WHERE workspace_id = '<workspace>' AND sender_id = '<account>' ORDER BY created_at DESC;` as the owner. `restricted` or `checkpoint` wait for their `paused_until` and the owner's resume on the screen (beta-p6-040, "An owner who cannot resume"); `disconnected` for a reconnect, or for a refresh that reads the account `connected` (the card's "Check status"); a `rate_limit_errors` event's account starts again by itself at its `retry_at`. Never set `health_state` or `paused_until` by hand: `applyHealth` alone writes them.
- **An account at risk** (README "Health", the acceptance rule): the owner's mail "Whytide paused the connection requests of your LinkedIn account", the account's invites refused `invites_paused`, `health_state` `at_risk` and an `acceptance_rate` event whose `metrics` hold `{ sample, accepted, rate }` (the queries under "An account paused"): fewer than 20 of its last 100 invites at least 7 days old were accepted. Its messages, withdrawals and reads go on. Nothing lifts it by hand: a later day's check at 20 percent or more sets it `healthy` again (`resumed`, no mail), as the acceptances of its earlier invites come in; never set `health_state` by hand. The check runs once a day ("Connection requests stop, messages go on" says why one may not). A lost session and a reconnect, or a refresh that reads the account `connected`, return it to `healthy` until the next day's check, which applies the rule again (README "Health").
- **The fleet breaker has tripped** (README "Health"): the mail "Whytide paused the connection requests of every LinkedIn account on the instance", or `status` showing `invites_paused=on reason=limit_reached` (or `checkpoint`). Every account's connection requests are refused `invites_paused`; messages and reads go on. First read the trip, `SELECT at, target_workspace_id, sender_account_id, reason FROM linkedin_control_events WHERE scope = 'platform' AND control = 'invites' ORDER BY at DESC LIMIT 5;`, then that account's health ("An account paused") and the others', `SELECT workspace_id, id, health_state, paused_until FROM sender_accounts WHERE health_state <> 'healthy';`, both as the owner, and ask the workspace's tester what LinkedIn showed. Several accounts warned at once: `stop --platform` and find out why first. Once it is safe, `breaker reopen --operator anna`, then `status`: `invites_paused=off reason=none`. The account that tripped it stays paused until its cool-down ends and its owner resumes it. The mail did not come: `LINKEDIN_ALERT_EMAIL` is empty (the worker's `linkedin_alert_email_missing` line), or the workflow `linkedin.notify:<workspaceId>:<healthEventId>:operator` in the Temporal UI shows why; the event's `operator_notified_at` is set once it went.
- **The owner's mail did not come**: the event's `owner_notified_at` is set once it went. Unset: the outbox row (`SELECT id, created_at, attempts, last_error, delivered_at FROM outbox WHERE event_name = 'linkedin.account_paused' ORDER BY created_at DESC LIMIT 20;`), then the workflow `linkedin.notify:<workspaceId>:<healthEventId>:owner` in the Temporal UI: `{ sent: false, reason: "owner_unavailable" }` is an owner missing or disabled; a failure is the app-mail port's (`PROVIDER_APP_MAIL`, the stack's Mailpit in development).
- **Connection requests stop, messages go on** (README "Pending invitations"): `pending_invites_over_limit` means the account's count, with its invites in flight, passed 400; its invites wait for 400 or fewer, which the owner's withdrawals on LinkedIn bring, counted at the next day's check. `pending_invites_unknown` means no count, or one more than 48 hours old: a new or replaced account before its first check, or checks that did not run; while the day's check is still to come, the invite asks again an hour after `check_after`. The count: `SELECT pending_invites, pending_invites_checked_at FROM sender_accounts WHERE id = '<account>';`; the days' checks: `SELECT quota_day, check_after, checked_at FROM sender_quota_usage WHERE sender_account_id = '<account>' ORDER BY quota_day DESC LIMIT 3;`, as the owner; `checked_at` set means that day's check ran. It runs in the first hourly refresh after `check_after`, which lies in the account's working hours, and asks the vendor once a day at most. It does not run while the worker or its schedule is stopped (`WORKER_SCHEDULES=off`) or the account is not `connected`; a refused read stops it, logged as a `pending_invites` row with its code: `account_stopped` or another switch, `account_paused`, `rate_limited` (`retry_at` ahead), `read_cap_reached` or `daily_actions_cap_reached` (the day's reads used), `outside_working_hours` (an hourly run outside the account's hours: `check_after` lies in the window's first two hours, never its last), or a port error's code. `SELECT at, outcome FROM sender_action_log WHERE workspace_id = '<workspace>' AND sender_account_id = '<account>' AND kind = 'pending_invites' ORDER BY at DESC LIMIT 20;`. Trigger on the schedule `linkedin.status_refresh` (Temporal UI) runs a due check at once; never write the count by hand: a wrong count lets invites through.
- **An owner who cannot resume** (README "Health", beta-p6-040): the card's hint, or the press's code, says why; the account as `SELECT health_state, health_changed_at, paused_until, status, status_checked_at, connected_at FROM sender_accounts WHERE id = '<account>';` as the owner. `not_account_owner` (403): only the account's owner resumes it. `account_not_paused`: the account is not `restricted` or `checkpoint`, so nothing is to resume (`at_risk` lifts itself; `disconnected` wants a reconnect). `cooldown_active`: `paused_until` lies ahead, its time in `details.pausedUntil`; wait for it. `details.pausedUntil` null: the row lacks the end every warning writes; report it. `linkedin_account_disconnected`: the status is not `connected`; connect the account again. `reconnect_required`: after a checkpoint, `connected_at` is not after the latest warning (`paused_until` less 72 hours: a second checkpoint moves the end, so it wants a second reconnect); the owner passes LinkedIn's check, disconnects and connects again. `status_check_required`: `status_checked_at` is not after `paused_until` or is more than 10 minutes old; "Check status" asks the worker, whose `linkedin_refresh_status` then sets it, unless the worker is down or the account's `retry_at` lies ahead, which holds the call (the activity answers `held` in the Temporal UI). Never set `health_state`, `paused_until` or `status_checked_at` by hand.
- **A removed member's account** (gamma-p6-070; README "Kill switches"): an Owner's removal of a member pauses each of their accounts in the workspace once the worker delivers `tenancy.member_removed`: `status` shows `switch=on source=member_removed`, and its history one control event, `actor_type` `system`, actor `tenancy.member_removed`. It reads and sends nothing; an Owner's screen shows it as a former member's, locked. No Owner, and no operator's unpause, lifts it. To lift it after a new invite: invite the member again, and they resume it on their LinkedIn screen, the Switch on their own account. An account still running after a removal: the event waits in the outbox (`SELECT id, created_at, attempts, last_error, delivered_at FROM outbox WHERE event_name = 'tenancy.member_removed' ORDER BY created_at DESC LIMIT 20;`), the worker not running or failing it; meanwhile the operator can pause it (`pause --workspace … --account sac_… --operator …`). The removal's pause leaves an operator's as it is, so the account runs again at the operator's `unpause`: unpause it only once its owner is a member again.
