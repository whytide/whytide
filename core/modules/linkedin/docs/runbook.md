# linkedin: runbook

- **Settings**: `LINKEDIN_DAILY_READ_CAP_MAX` (README "Settings"), read at the start. An unset `PROVIDER_LINKEDIN` makes connect and the webhook fail with a 500; an unset `APP_PUBLIC_ORIGIN` (and `WEB_DEV_ORIGIN`) makes connect fail with a 500.
- **Logs**: the api's request log names the route and the code; nothing of the reference or the webhook's body is logged.
- **Removing an account at the vendor**, which Disconnect does not do in alpha: in the Unipile dashboard, under Accounts, find the account by the user's LinkedIn name and delete it. Whytide's row stays `disconnected`; a webhook for it changes nothing more.
- **Reading the action log**: `SELECT at, kind, count, outcome FROM sender_action_log WHERE workspace_id = '<workspace>' AND sender_account_id = '<account>' ORDER BY at DESC LIMIT 100;` as the owner. `object_ref` is personal data: read it only for the case at hand, never copy it into a ticket. The day's numbers: `sender_quota_usage` by account and `quota_day`; open reservations: `sender_quota_reservations` with `status = 'reserved'`.
- **The hourly refresh**: the schedule `linkedin.status_refresh`, upserted at each start of the worker and paused while `WORKER_SCHEDULES=off`; in the Temporal UI under Schedules, where Trigger runs it at once. A run answers `{ accounts, failed }`; a failed account is the worker's `worker: an activity failed` line with `activity: linkedin_refresh_status` and its code.
- **Failure modes**:
  - An account stays `pending`: the webhook did not arrive. Check `UNIPILE_NOTIFY_URL` is the public URL of `POST /v1/linkedin/webhooks/unipile`, and the api's log for a 401 `linkedin_webhook_invalid` (a wrong signature or another adapter's path) or a 429 (the limit per address). The user can press Connect again.
  - Refresh status changes nothing: the provider says the same status, or the worker is not running and the event waits in the outbox (`SELECT id, created_at, attempts, last_error FROM outbox WHERE event_name = 'linkedin.status_refresh_requested' AND delivered_at IS NULL;`). The screen stops asking after thirty seconds; a reload shows the status once the worker has it.
  - `secret_context_mismatch` in the worker: the row's sealed reference was written for another organization (a row moved by hand); the user disconnects and connects again.
  - Reads stop for the day: the log's latest rows read `read_cap_reached` (the cap, reserved plus made) or `outside_working_hours` (check the account's zone and hours on the screen); `linkedin_account_disconnected` means the account is not `connected`. A member with `linkedin.manage` may raise the cap on the screen, up to `LINKEDIN_DAILY_READ_CAP_MAX`: the next reservation reads it, but a run already asleep until the next quota day keeps sleeping. A reservation left open by a dead run holds its reads for an hour, then the next reservation frees it.
  - `secret_key_unavailable` in the worker: `APP_MASTER_KEY` no longer holds the key the reference was sealed with; keep the old key as `APP_MASTER_KEY_PREVIOUS` while rotating (core/packages/platform README).
