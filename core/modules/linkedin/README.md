# linkedin

The tester's own LinkedIn account, connected through the provider's hosted authentication after a risk disclosure: a sender account per user and workspace, with its status, time zone, working hours and daily read cap. The provider's account reference is stored sealed and opened in the worker only. Every read through the account passes the read quota (a reservation inside the cap and the working hours) and the action log; the signal run (alpha-p8-020) reads through them.

- **Owns:** `sender_accounts`, `sender_quota_usage`, `sender_quota_reservations` and `sender_action_log` in `core/packages/db/prisma/schema/linkedin.prisma` ([docs/data.md](docs/data.md)), the screen `ui/accounts`, the workflows `linkedin_refresh_account` and `linkedin_status_refresh` with the schedule `linkedin.status_refresh`, the activities `linkedin_refresh_status`, `linkedin_list_workspaces`, `linkedin_list_referenced_accounts`, `linkedin_read_post_engagers` and `linkedin_read_profile`, the metric `linkedin.actions` (`metrics.ts`: kind, outcome).
- **Public interface:** `index.ts`: `api`, which the api host mounts; `webhooks`, which it mounts at `POST /v1/linkedin/webhooks/{provider}`; `reserveReads`, `commitReads`, `releaseReads` and `logAction` ("Read quota"); `findSenderAccount`; the engager and profile reads' types, `engagersFile`, `profileRequestFile` and `profileFile` ("Worker"); `events`; the registries `errors`, `ids` (`sac`, `squ`, `sqr`, `sal`) and `permissions`. The worker loads `events.ts`, with its subscriber of `linkedin.status_refresh_requested`, and `workflows/` itself.
- **Depends on:** `platform`, `db`, `providers` (the LinkedIn port), `tenancy` (a workspace's organization, and every workspace's id for the hourly refresh); the screen on `@whytide/ui` and the web's API client.
- **Reviewers:** the owners of this module.

## API

Under `/v1/workspaces/{workspaceId}/linkedin`; requests in `api-calls/alpha-p7-030-sender-accounts.http`.

| Route | Permission | Does |
|---|---|---|
| `POST /accounts/connect` `{ timeZone, acknowledged }` | `linkedin.connect` | `{ url }`, the provider's hosted link; the caller's account, created or reused, waits as `pending`. `disclosure_required` (400) unless `acknowledged` is `true`; `working_hours_invalid` (400, `details.fields: ["timeZone"]`) for a zone `Intl` does not know; `sender_account_exists` (409) when it is connected already |
| `GET /accounts` | `linkedin.read` | `{ accounts }`, oldest first: `{ id, label, status, timeZone, workingHours, dailyReadCap, mine, canManage }`, never the reference; `canManage`: the caller holds `linkedin.manage`, as the platform's `can()` answers |
| `PATCH /accounts/{id}` `{ label?, timeZone?, workingHours?, dailyReadCap? }` | `linkedin.manage` | 200 with the account; `working_hours_invalid` (400, `details.fields`) for a start not before the end, a day outside 1 to 7, a repeated day or none; `read_cap_invalid` (400, `details.fields: ["dailyReadCap"]`, `details.max`) for a cap that is not a whole number from 1 to `LINKEDIN_DAILY_READ_CAP_MAX`, a string included; `sender_account_not_found` (404) |
| `POST /accounts/{id}/refresh` | `linkedin.manage` | 202 with the account as it stands; publishes `linkedin.status_refresh_requested`, and the worker asks the provider for the status ("Worker"). `@Idempotent()`: an `Idempotency-Key` per press. `sender_account_not_found` (404). Request in `api-calls/alpha-p10-130-linkedin-polish.http` |
| `DELETE /accounts/{id}` | `linkedin.manage` | 204; deletes the reference and its hash, keeps the row `disconnected`, publishes `linkedin.sender_account_disconnected` |
| `GET /accounts/{id}/usage` | `linkedin.read` | `{ quotaDay, cap, capMax, reserved, committed, windowOpen, nextWindowAt }`: the account's reads today in its time zone (`YYYY-MM-DD`), reserved and made, its cap and the highest it may be given (`LINKEDIN_DAILY_READ_CAP_MAX`), whether its working hours are open now and their next start after now (ISO); `sender_account_not_found` (404). Requests in `api-calls/alpha-p7-040-read-quota.http` |

- `status` is `pending`, `connected`, `credentials_required`, `error` or `disconnected`. alpha-p8-040's sources screen reads this list and warns on a source whose account is not `connected`.
- `workingHours` is `{ start, end, days }`: local `HH:MM` times in `timeZone` (IANA), ISO days (1 is Monday), stored sorted.
- The provider sends the browser back to `APP_PUBLIC_ORIGIN/w/{workspaceId}/linkedin?connect=done` (or `failed`).

## Read quota

Every read through an account is reserved first, then committed or released, each call in the caller's own tenant run (an activity's `context.tenant`), as credits' reserve ([docs/flows.md](docs/flows.md)):
- `reserveReads({ accountId, count, kind, objectRef? })`, `kind` `read_engagers` (an engager-list page counts 1) or `read_profile`, `count` 1 to 1000: `{ reservationId, granted }`, all of `count` or none; or a refusal, `{ refused, retryAt }`: `linkedin_account_disconnected` for an account not `connected` (`retryAt` null), `outside_working_hours` with the next window's start, `read_cap_reached` with the next quota day's start, when the day's reads reserved and committed plus `count` pass `dailyReadCap`. A refusal is returned, not thrown, so the run commits its log row. `sender_account_not_found` for an account not in the run's workspace.
- `commitReads(reservationId, actual)`: `{ reservationId, committed }`, the reads made, counted as made, also after the reservation's hour or above its count; `releaseReads(reservationId)`: the reads freed. A repeat answers as the first; the other settlement, or an unknown id, is `reservation_not_open` (409).
- A reservation holds an hour; the next reservation of its account and day frees those past it (the lazy sweep).
- Each reservation reads the account's cap as it stands, so a cap changed on the screen holds from the next reservation, on the same quota day. A run already waiting for a refusal's `retryAt` keeps sleeping until then.
- `logAction({ accountId, kind, objectRef?, count, outcome })`: a read made (`outcome` `ok` or the port's code) or a status check. `objectRef` is a person's id (`per_…`) or a post's URL without query, never a profile's URL; anything else is `read_input_invalid` (`details.fields`). reserveReads logs each answer itself.

## The webhook

`POST /v1/linkedin/webhooks/{provider}`, the api host's route for a module's `webhooks` (core/apps/api/README.md "Modules"): no session, no workspace, `RATE_LIMIT_WEBHOOK_PER_IP_PER_MIN` per address, the raw body at most 64 KiB. A `provider` other than `PROVIDER_LINKEDIN`, or a signature or body the adapter refuses, is `linkedin_webhook_invalid` (401) and changes nothing. `account.connected` pairs the pending account by the link's `providerRef` and seals the reference: only the webhook sets `connected`. `account.disconnected` and `account.credentials_required` find the account by the reference's hash. 204 otherwise, also for an account none of ours.

## Screen

`/w/{workspace}/linkedin` (`ui/accounts`): the header, with the screen's description, and the provider's failed return, in a danger box, come from the server; the account loads in the browser, with the kit's loading state over the cards' shimmering lines, its error state with a retry, and the empty state, the sentence that no account is connected heading the connect card (`linkedin.accounts.*`). Without a connected account, the connect card: the disclosure (what is read, the cap, the working hours, the account is the tester's own) and its box; Connect, off until the box is ticked, sends the browser's time zone. The account's card: its label, with Refresh status; its status as a badge in its colour, its zone and its cap's value, side by side where the card is wide; the working-hours editor; Disconnect, at its foot, with a confirmation. From 1280px (xl) the reads today stand beside the card, in a column of their own; under it otherwise, and for an account not connected, after the connect card that follows it. A connected card shows the disclosure again on demand; one at `credentials_required` says to reconnect with Connect. Refresh status (`connected`, `credentials_required`, `error`) asks the worker; the screen then asks for the account every two seconds until its status changes, thirty seconds at most, as it does for a pending account, two minutes at most. The reads today have their own states again: the reads (reserved and made) over the cap, in words and on a meter that turns warm at the cap, the reads left, and whether the window is open, else when it opens next, in the account's zone; then, when the account's `canManage` says so, the daily read limit: its field with the bound (`capMax`), the warning, its own Save, the api's `read_cap_invalid` under the field, and a toast once saved. A failed action shows its code in words, with a retry.

## Worker

Two workflows, both through the activity `linkedin_refresh_status`. `linkedin_status_refresh`, global, every hour by the schedule `linkedin.status_refresh` (paused while `WORKER_SCHEDULES=off`): `linkedin_list_workspaces`, global, takes every workspace's id from tenancy's `listWorkspaceIds()`, and nothing else; then, workspace by workspace, `linkedin_list_referenced_accounts` lists the workspace's accounts with a reference, ids only, in its run, and each account is refreshed in turn, an account whose refresh fails past its attempts counted and the others refreshed (`{ accounts, failed }`). `linkedin_refresh_account` `{ workspaceId, accountId }`: one account, started by `events.ts`'s subscriber of `linkedin.status_refresh_requested` with the id `linkedin.status_refresh:<workspaceId>:<event id>`, the workspace the delivery's run's: a second delivery starts none. Their replay histories are in `workflows/__histories__/`.

`linkedin_refresh_status` `{ workspaceId, accountId }`: the provider's status for an account with a reference, stored, the event when it crosses into `connected` or `disconnected`, and a `status_check` row in the action log; an account the provider no longer knows is `disconnected`. `workflows/decrypt.ts` `withDecryptedRef(context, accountId, fn)` opens the reference for `fn` and zeroes it after; the lint's `decrypt-in-worker-only` keeps `workflows/` out of the api.

`linkedin_read_post_engagers` `{ workspaceId, accountId, postUrl, cursor?, limit, rawKey }` (alpha-p8-020, signals' reader): one page of the post's engagers, newest first, through the opened reference, written to the files port at `rawKey` (under `raw/`, so the workspace's prefix and the 72-hour lifecycle) as `{ engagers }` (`engagersFile`), answered as `{ key, count, nextCursor }`: the engagers never cross the workflow's history. A disconnected account or an unknown post answers `{ refused }` with the code; other errors fail the attempt (`linkedin_rate_limited` retried after its `retryAfterSec`). Each call writes a `read_engagers` row in the action log. The caller reserves and settles the read; this activity does not.

`linkedin_read_profile` `{ workspaceId, accountId, requestKey, rawKey }` (alpha-p8-030, the engager read's twin): the profile whose URL the request file at `requestKey` holds (`profileRequestFile`, `{ profileUrl }`), read through the opened reference and written at `rawKey` (`profileFile`, `fetchedAt` in ISO), answered as `{ key }`; both files under `raw/`, so no URL crosses the history. `{ refused }` as above, and `linkedin_provider_error` on the third attempt (`PROFILE_READ_ATTEMPTS`, `workflows/constants.ts`; the two before fail and are retried), so that the run skips a profile the provider cannot read; a rate limit still fails the attempt. A `read_profile` row in the action log, with no object. The caller reserves `read_profile` and settles it.

## Settings

`LINKEDIN_DAILY_READ_CAP_MAX` (250, 1 to 1,000; `config.ts`, the `modules/linkedin` block of `deploy/.env.example`): the highest daily read cap `PATCH /accounts/{id}` takes. Lowering it changes no account's cap, only the next change. The adapter is `PROVIDER_LINKEDIN` (`fake` or `unipile`, providers' block), the return address the api's `APP_PUBLIC_ORIGIN` (`WEB_DEV_ORIGIN` on a laptop), the key `APP_MASTER_KEY`. On Unipile, `UNIPILE_NOTIFY_URL` is the public URL of the webhook route.

## Decided here

- Connect is a `whytide:own-runs` route without `@Idempotent()`: the provider call must sit outside any run, and own-runs does not combine with `@Idempotent()`. It is idempotent in the domain instead: one row per user and workspace, upserted; a repeat replaces the pending link.
- One account per user and workspace (`(workspace_id, owner_user_id)` unique). The reference's hash is SHA-256 of `<provider>:<reference>`, unique per workspace.
- A user's disconnect clears the reference and the hash; a webhook's keeps them, so a reconnect at the vendor pairs again.
- `linkedin.manage` is Owner and Admin, with no check of whose account it is: in alpha every member is an Owner.
- Events `linkedin.sender_account_connected` and `linkedin.sender_account_disconnected`, `{ sender_account_id }`, the platform's `module.event_name` form.
- The read quota (alpha-p7-040): a refusal is an answer, not a throw, so the caller's run keeps its log row and its workflow waits for `retryAt`; reserveReads takes a `kind` (and an `objectRef`) for that row. All or none: no partial grant. A reservation is a row of its own (`sender_quota_reservations`); the day's counters change in the same run. The sweep covers the day being reserved: a reservation of an earlier day holds nothing of today's cap. A commit counts every read made, after the hour or above the reservation too: they happened, and the cap guards the account, not the caller. An account not `connected`, a restricted one included once its status says so, is refused with `linkedin_account_disconnected` and logged.
- Refresh status (alpha-p10-130) is a route that writes an event through the outbox, and the module's own subscriber in the worker starts the run: the api holds no Temporal client (platform README "Workflows"). The screen polls the account for its new status rather than waiting on the run. The hourly refresh reads no tenant table across workspaces: its global activity takes the workspaces' ids from tenancy, and each workspace's accounts are listed and refreshed in that workspace's run.
- The screen loads the account and the usage in the browser, for the kit's loading and error states with a retry in place.
- `quota_day` is `text` `YYYY-MM-DD` with a CHECK: the schema lint takes no `@db.Date`. The window is `[start, end)` in local minutes.
- The daily read cap (fix-read-cap) is the owner's to set, a whole number from 1 to `LINKEDIN_DAILY_READ_CAP_MAX`, 250 by default; a new account's cap stays 100.
- The screen on the design system (ui-tailwind), with no change of behaviour, request or key but the header's description (`linkedin.page.description`): the empty state is the connect card headed by its sentence, rather than the kit's empty state above the card; the card's Disconnect is a secondary button, its confirmation the danger one; the account card's facts and the working hours' two times follow the card's width (container queries), as the card's column does not follow the screen's. The days stay the kit's chip input.

## Open questions

- Pairing on Unipile: its new account's `account.connected` carries no `providerRef`, so a pending account cannot be paired yet; the sandbox check settles it (a header on the notify, the notify confirmed through `GET /accounts/{id}`, or `Account.name`).
- Whether the hash should be keyed (an HMAC under the master key) rather than a plain SHA-256.
- Engager-list pages count one read each in alpha; the vendor's own accounting may say otherwise.
- Whether Refresh status needs a limit of its own: each press asks the provider once, under the api's limit per workspace (`RATE_LIMIT_WORKSPACE_PER_MIN`) only.
