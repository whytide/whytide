# discovery: runbook

- **Settings**: `IMPORT_MAX_ROWS` (default 5,000; at most 50,000) and `IMPORT_MAX_BYTES` (default 5 MiB; at most the files port's 25 MiB), in the `modules/discovery` block of `deploy/.env.example`. The api reads them at start. The route's body limit is twice `IMPORT_MAX_BYTES`. An upload with a valid row also needs contacts' `HASH_SALT` (core/modules/contacts/README.md "Settings").
- **Logs**: each upload and run has the api's request line, `api: request`, with `route` `/v1/workspaces/:workspaceId/discovery/imports…`, the status and `workspace_id`. A store or database failure is a 500 with `api: request failed`. The run itself is the worker's: the delivery of `discovery.import_run_requested`, then the activities `discovery_import_rows` and `discovery_import_failed` of the workflow `discovery.import_run:<workspace_id>:<job_id>`, a failed attempt with its code (`worker.activity.failures` in the metrics).
- **Events**: `discovery.import_run_requested` and `discovery.people_imported` rows in `outbox`, delivered by the worker; a dead one is replayed with the platform's `replayDeadLetter`.
- **Failure modes**:
  - `import_bad_encoding`: the file was saved in another encoding (Excel's default "CSV"); save it as "CSV UTF-8".
  - `import_unsupported_type` for a file that looks like CSV: an unclosed quote, or a row with more or fewer cells than the header.
  - A 500 at the upload with `files_*` codes in the log: the files port's MinIO or S3 store (core/packages/providers/files/README.md).
  - A 500 `hash_salt_missing` at an upload with a valid row: contacts' `HASH_SALT` is not set. Nothing is stored. The worker needs it too: without it, a run fails with that code.
  - A failed run: the job is `failed` with `failure.chunk` and `failure.code` (`import_failed` for an error without a code); the worker's log has each attempt's failure. The people of the chunks before it are kept, with their leads and events. The tester uploads the file again: its rows already imported count as `updated`.
- **A job left running** (the screen's hint after ten minutes): a worker that does not run, a crash, or a failure the job could not be told of. Its committed chunks and counts stay.
  1. The worker: is it up (core/apps/worker/README.md "Health")? The event waits in `outbox` until one delivers it: `SELECT delivered_at, attempts, last_error FROM outbox WHERE event_name = 'discovery.import_run_requested' AND payload->>'jobId' = '<job_id>';` as the owner. Undelivered, it goes once a worker runs; dead, replay it.
  2. Temporal: the workflow `discovery.import_run:<workspace_id>:<job_id>`, in Temporal's web UI or with `temporal workflow describe --workflow-id <id>`. Running, its activity's attempts and last failure say where it is: a large file takes minutes ("Speed"), and an attempt lost with its worker is retried within a minute, after the last committed chunk. Closed while the job is still `running`: the job's last write failed (the worker's log).
  3. Nothing left to end it: end the job by hand, as the owner, so that the screen shows it ended: `UPDATE import_jobs SET status = 'failed', finished_at = now(), counts = coalesce(counts, '{"created":0,"updated":0,"skippedDuplicate":0,"skippedErased":0,"errors":0}') || jsonb_build_object('failure', jsonb_build_object('chunk', coalesce((counts->>'chunks')::int, 0) + 1, 'code', 'import_failed')) WHERE id = '<job_id>' AND status = 'running';`. The tester uploads the file again.
- **Speed**: a chunk of 500 rows goes through contacts' batched commands (alpha-p10-080) in about ten queries, where a row took six before. On the 4-core development laptop at a load average of 11 to 14, 5,000 rows took 2.9 seconds in the worker's tests (`discovery-import.test.ts`, which wants the best of three under 30), against 74 to 112 seconds row by row.
