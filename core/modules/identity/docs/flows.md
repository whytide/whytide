# identity: flows

- **A workspace route** (`/v1/workspaces/{id or slug}/…`): the api host's principal guard reads the session; its workspace guard calls `workspaceResolver`, which calls tenancy's `resolveMembership({ userId, workspaceIdOrSlug })`: the user's own memberships, an indexed query, and their workspaces for a slug, on every request, never cached. A membership puts `workspaceId`, `membershipId` and `role` on the principal; then the workspace's rate limit, `can()` for the route's `@Permission`, and the handler inside `withTenant` for that workspace (core/apps/api/docs/request-path.md). No membership is 403 `forbidden`.
- **An invite** (`pnpm invite`): a slug resolved by tenancy's `findWorkspaceBySlug`, the workspace checked by `findWorkspace`, then one `INSERT … ON CONFLICT DO NOTHING` in a run of the workspace; no row back is `invite_exists`. With no `--workspace`, no workspace with the slug and no organization at all (`hasOrganization`), the user of the email is made (`upsertUser`), then the organization, the workspace and the Owner membership (`bootstrapOrganization`), before the invite.
- **A tenant** (`pnpm tenant:create`, `pnpm workspace:create`): the organization looked up by tenancy's `findOrganizationBySlug` (or `findOrganization` for an id), the admin by `findUserByEmail`, then `upsertUser`, then `bootstrapOrganization` or `createWorkspace`, one run in the new workspace; then, outside any run, the mail through the app-mail port.
- **Signing in** through the screens: `/sign-in` → `POST /v1/sign-in` (202, the link asked for after the answer) → `/sign-in/sent` → the mailed link → `/sign-in/confirm` → its button's POST → `next` or `/`, which sends the member to their first workspace.
- **Asking for a link**: the authentication port calls `allowSignIn(email)`: the email's pending invites across workspaces, then, when there is none, the user (`findUserByEmail`) and their memberships. Nothing is written; false is 403 `auth_invite_required`.
- **The first sign-in**, when a link is followed: `users.findOrCreateByEmail(email)` reads the pending invites and the user, creates the user (`upsertUser`) when there is none, then, for each invite, oldest first, `addMember` with its role and `accepted_at` in a run of its workspace. A second sign-in finds the user and no pending invite: nothing is written.
