# onboarding

The workspace's one Company Knowledge record: what the company sells, to whom, its customers' pain points, its proof points, its competitors and its tone, with the website it comes from. The tester reads and edits it on the screen at `/w/{ws}/company`; the website fetch (alpha-p4-020) and the drafter (alpha-p4-030) fill it, also from the company's documents through the script `pnpm knowledge:draft` (knowledge-draft); the writer and the own-employee filter read it. Every content field remembers who wrote it last, an AI draft or a person, so that the drafter can leave a person's edit alone (alpha-p4-030).

- **Owns:** `company_knowledge`, `website_pages` and `company_documents` in `core/packages/db/prisma/schema/onboarding.prisma` ([docs/data.md](docs/data.md)), the Draft's workflow under `workflows/`, the drafter under `agents/draft-company-knowledge/`, the screen under `ui/` and the script under `cli/`.
- **Public interface:** `index.ts`, below.
- **Depends on:** `platform` (its egress client among the rest), `db`, `ai` (the drafter's task, `callAgent`); the workflow on `@temporalio/workflow` and `@temporalio/activity`; the screen on `@whytide/ui`, `@whytide/web` (its api client), `next-intl` and `react`; the script on `tenancy` (`findWorkspaceBySlug`) and `unpdf` (a PDF's text).
- **Reviewers:** the owners of this module.

## Public interface

| | |
|---|---|
| `readCompanyKnowledge(workspaceId)` | the `CompanyKnowledge` record, as `GET` answers it, in the caller's tenant run (`withTenant`): the drafter's and the writer's read; the first read creates it empty; another workspace than the run's is `tenant_mismatch` |
| `getCompanyDomain()` | the run's company domain, the host of `sourceUrl` without a leading `www.` (`acme.test`), or `null` without a website: the own-employee filter's (alpha-p8) |
| `api` | the routes below |
| `events` | `onboarding.company_knowledge_updated` `{ workspaceId, version }`, on every save that changes the record; `onboarding.draft_requested` `{ workspaceId, companyKnowledgeId, draftRunId }`, on every Draft |

The registries: `ids` (`ck`, `page`, `cdoc`, `drun`), `errors` (`company_knowledge_invalid_url`, 400; `company_knowledge_no_website` and `company_knowledge_no_draft`, 409; `draft_agent_not_loaded`, 500; `fetch_failed`, a run's code, never an answer; each with its key in `messages/en.json`; the drafter's run codes `ai_failed` and `draft_failed` are not registered, their keys are the screen's), `permissions` (`company_knowledge.read`: Owner, Admin, Member; `company_knowledge.write`: Owner, Admin; kept, not evaluated, in alpha), `events` and `settings` (`ONBOARDING_FETCH_MAX_PAGES`, 1 to 10, 5 by default; `AI_MODEL_ONBOARDING_DRAFT_COMPANY_KNOWLEDGE`, the drafter's model, the LLM port's first when empty). The types `CompanyKnowledge`, `ContentField`, `FetchStatus`, `FieldSource` and `ProofPoint` come with them.

## Routes

The api host mounts them under `/v1/workspaces/{ws}/onboarding`; their requests are in `api-calls/alpha-p10-090-onboarding.http`, one per route. Each answers the record with `pages`, those the last fetch read, in its order: `{ url, title, status, fetchedAt }`.

| Route | Permission | Does |
|---|---|---|
| `GET /v1/workspaces/{ws}/onboarding/company-knowledge` | `company_knowledge.read` | the record; the first read creates it empty, `fetchStatus` `none`, version 1 |
| `PUT /v1/workspaces/{ws}/onboarding/company-knowledge` | `company_knowledge.write` | saves the website and every content field (a full replacement) and answers the saved record |
| `POST /v1/workspaces/{ws}/onboarding/company-knowledge/draft` | `company_knowledge.write` | `@Idempotent()`, 202: drafts from the saved website, `fetchStatus` `fetching` (below); without a website 409 `company_knowledge_no_website` |
| `POST …/company-knowledge/draft/accept` | `company_knowledge.write` | `@Idempotent()`, body `{ replaceEdited?: boolean }`: accepts the pending draft ("The drafter"); without one 409 `company_knowledge_no_draft` |
| `POST …/company-knowledge/draft/discard` | `company_knowledge.write` | `@Idempotent()`: drops the pending draft, every field kept; without one 409 `company_knowledge_no_draft` |

A length or a count off the limits is the host's 400 `validation_failed`, `details.fields` naming each path (`longDescription`, `products`, `products.3`). A website or a proof point's page that is not an absolute `http` or `https` URL without a user name or password (a proof point may also cite a document, `document:<name>`, "The documents") is 400 `company_knowledge_invalid_url`, `details.fields` naming each (`sourceUrl`, `proofPoints.1.sourceUrl`), never the value; nothing is written.

## The record

- `sourceUrl` (2,048 characters; empty or `null` for none), `oneLiner` (200), `longDescription` (2,000), `tone` (500); `products`, `painPoints`, `featuresBenefits` and `competitors`, 20 items of 1 to 200 characters each; `proofPoints`, 20 of `{ text, sourceUrl? }`, a text of 1 to 500 characters. The limits are `LIMITS` in `domain/fields.ts`.
- Stored trimmed, each list without duplicates (a proof point by its text), in the order given.
- `fetchStatus` (`none`, `fetching`, `fetched`, `drafted`, `failed`), `fetchedAt` and `fetchError` belong to the Draft's run, below; a save never moves them. `draftRunId`, the latest Draft's run, is never answered.
- `pendingDraft`: the drafter's draft, `{ model, promptVersion, decisionRecordId, fields }`, each field's value with `sourceUrl` and `quote` (`schemas/draft-company-knowledge.ts`), until it is accepted or discarded, or a new Draft starts; `null` otherwise.
- `fieldSources`: per content field, `{ kind: "ai_draft" | "human", at, sourceUrl? }`, who wrote it last. A save marks each content field whose value changed `human`, a list's order included; the others keep theirs.
- `version` is 1 when created and moves by one with every save that changes a field, the website included; the event carries it. A save that changes nothing writes nothing and publishes nothing.

## The website fetch

A Draft (`requestDraft`, `domain/draft.ts`) locks the record, gives it a new `draftRunId` (`drun_…`), sets `fetching`, clears the error and publishes `onboarding.draft_requested` in the same transaction; a repeated key answers the first answer and publishes nothing. The worker's subscriber starts `onboarding_draft_company_knowledge` with the ids, by the id `onboarding.draft:<workspaceId>:<draftRunId>` through the platform's `startWorkflow` (`draftStart`, `events.ts`), so an event delivered twice starts one run. The workspace is the delivery's tenant run's (`currentTenant()`), never the payload's: the starter does not compare them.

The workflow's first activity, `onboarding_fetch_website` (`workflows/fetch-website.ts`, kind `provider`), reads the website through the platform's `fetchSafe` with no tenant run open: `robots.txt` first (500 KiB; a 4xx answer is no rule, another answer but a 2xx allows nothing; the `whytide` group, else `*`), then the home page, then up to `ONBOARDING_FETCH_MAX_PAGES - 1` of its same-host links, in this order: the first about, product, pricing and customers page (`domain/pages/links.ts`), then navigation links, then the rest; never a path `robots.txt` disallows. One megabyte, ten seconds and five redirects a page, sixty seconds in all, a heartbeat per page, HTML only, never inflated. The text (`domain/pages/html.ts`) keeps the title, headings (`#` per level) and paragraphs, drops scripts, styles, navigation, footers and comments, at most 50,000 characters; a page cut at either bound is `truncated`.

One tenant run then writes the outcome, only while `draftRunId` is still the run's (a later Draft supersedes it: `superseded`, nothing written): the pages replace the last run's, with `url` after redirects and `fetchedAt`, and the record becomes `fetched`; or it becomes `failed` with the code of `robots.txt` or the home page (`egress_*`), or `fetch_failed` (not a readable HTML page, or disallowed), and keeps no page. Another page that fails is left out. A site's failure is a value, never retried; a fault (the database) retries, and once the attempts are spent `onboarding_fetch_failed` marks the run `fetch_failed`.

## The drafter

Once the fetch wrote its pages, the workflow's second activity, `onboarding_draft_from_pages` (kind `ai`, `domain/drafter.ts`), drafts the record from them with the agent task `onboarding.draft-company-knowledge` ([agents/draft-company-knowledge/](agents/draft-company-knowledge/README.md)), which the worker registers at start; unregistered, the activity fails with `draft_agent_not_loaded`. One tenant run reads the pages' `url`, `title` and `text`, in the order read, then the Draft's documents ("The documents"), each text cut at 6,000 characters, while the run is the latest. `callAgent` then asks the model outside any run, the record's id as its subject: the pages in one `<pages>` data block, the answer checked against the output schema and the gates (`domain/draft-gates.ts`: every `sourceUrl` a page read, every `quote` in that page's text, case and whitespace aside, every list and text within the record's limits), retried once with the issues in a `<validation_error>` block, then `ai_failed`. The wrapper writes one decision record and one cost event per call; unchanged pages give the same input, so a second Draft reuses the decision record and asks no model. One tenant run then writes, the row locked and only while the run is the latest (else `superseded`, nothing written): the draft as `pendingDraft` and `drafted`, or `failed` with `ai_failed`. The content fields never change there. A fault past the activity's attempts (the model's port, the database) marks the run `failed`, `draft_failed`, through `onboarding_draft_failed`.

The review: an accept (`acceptDraft`, `domain/review.ts`) writes each drafted field, a text or a list with an item, whose source is not `human`, or every one with `replaceEdited`, stored as a save stores it (`applyDraft`, `domain/rules.ts`); each field that changed is marked `ai_draft` with its value's page, a list with its first item's; then the version moves and `onboarding.company_knowledge_updated` carries it, the draft cleared, in one transaction under the row lock. When no field changed, only the draft is cleared. A discard (`discardDraft`) clears the draft and nothing else.

## The script

`pnpm knowledge:draft --workspace <id or slug> [--url <https://…>] [--file <path>]... [--accept [--replace-edited]]` (`cli/draft.ts`), for an engineer: drafts a workspace's record from its website and up to five of its documents. It never calls a model. It reads the files first ("The documents"); then one tenant run saves the website with `--url` (the form's rule, the content fields unchanged) and starts the screen's Draft, `requestDraft` with the documents; the worker fetches and drafts. It reads the record every two seconds, each read its own run, until the run is `drafted` or `failed`, ten minutes at most (`WAIT`, `cli/constants.ts`), then prints the pages (address and status), the documents (name and status) and each drafted field on a line (a text's first 60 characters, a list's count), or the run's code. `--accept` then accepts the draft as the screen does (`acceptDraft`; `--replace-edited` for `replaceEdited`), while the run is still the latest; without it, the script prints the Company screen's path. Every line starts with a code and carries names, codes and field values, never a page's or a document's text. Exit codes (`EXIT`): 0 done, 1 refused before any write, 2 usage, 3 the run failed, 4 a later Draft superseded the run, 5 the wait ran out: the worker goes on and the draft shows in the Company screen ("is the worker running?" while still `fetching`), 6 `workspace_not_found`: the workspace is found first (tenancy's `findWorkspace` for an id, which has an underscore, else `findWorkspaceBySlug`), so a mistyped id writes nothing and starts no Draft. Through pnpm, any code but 0 shows as 1; the printed code says which.

## The documents

`--file`, at most five, each a `.pdf`, `.txt` or `.md` of at most 10 MB (`DOCUMENT_LIMITS`), read in the script's process before anything is written (`cli/documents.ts`): a PDF's text through `unpdf` (PDF.js; no OCR), a text file's as UTF-8, cut at 50,000 characters like a page's, never inside a character (`truncated`, else `read`). A file of another type, missing, past 10 MB, with no text (a scan), encrypted or unreadable, a sixth, or one name twice stops the script with its code and the path: `document_type_unsupported`, `document_not_found`, `document_too_large`, `document_no_text`, `document_encrypted`, `document_unreadable`, `documents_too_many`, `document_name_repeated`, `document_name_invalid` (the script's codes, printed, never an answer).

They are the documents of the record's latest Draft, in `company_documents`: `requestDraft(workspaceId, documents)` replaces them in the transaction that starts the run; a Draft from the screen gives none and so removes them. The drafter reads them after the pages, each one an entry `{ url: "document:<name>", title: <name>, text }`; a drafted value cites `document:<name>`, which the gates check like a page's address. The screen shows such a source as "Source: <name>", never as a link; an accept keeps it with its proof point, and a save takes it back.

## The screen

`/w/{ws}/company` (`ui/nav.ts`, the `company` group): `page.tsx` renders the title and what the record is for; `company-screen.tsx` reads the record in the browser through `browserApi()`, with the kit's `LoadingState` and the cards as skeletons, then on a failure its `ErrorState`, the code in words with a retry. `company-form.tsx` holds the form: the website's card, with the empty state while the record has no website and no content; the fields in four cards (the company, what it sells, who it sells to, how it sounds), two side by side from `xl`: the one-liner, the long description and the tone with their counters, the lists as chips, a badge per field ("AI draft" with a link to its page or its document's name, or "Edited"), the trigger of the kit's `Tooltip`, whose hint (`onboarding.company.source.hint`) shows on hover and on keyboard focus; then the kit's `SaveBar`, which stays in view while the form differs from the record, with "Last changed {time} by an AI draft you accepted" (or "by a person"), the time and the kind of the latest `fieldSources` entry, no line before a field was written, and Save, which PUTs every field through `browserApi()` and shows the saved record, the error under each field the api names, or another failure in words with a retry. A proof point keeps its page while its text stays; one typed on the screen has none.

Under the website's field, `website-fetch.tsx`: Draft from website (the form saved first when its website changed, a new `Idempotency-Key` per press, the same one on a retry), which asks first in the kit's `Dialog` while a draft waits for review, since a Draft drops it (Cancel keeps it); the progress while `fetching`, then while the drafter reads the pages (`fetched`), a bar for each step, asking for the record every two seconds until it ends `drafted` or `failed`. A failed read stops the asking and shows its code with a retry, which resumes it. A run `fetching` or `fetched` for more than ten minutes by the record's `updatedAt` is stuck: the asking stops, the screen says so, and Draft, which a run never disables, starts a new one ([docs/runbook.md](docs/runbook.md)). Then the pages read, by title (the address without one), each `http` or `https` page linked in a new tab with `rel="noopener noreferrer"`, "Partly read" on a cut one, "No page was read" for none; or the failure in words: one text for `egress_blocked_address` and `egress_dns_failed`, so that the screen never tells which names resolve to private addresses; the drafter's `ai_failed` and `draft_failed` under "The draft from your website failed". With a pending draft, `draft-review.tsx` shows each drafted field, the record's value ("Empty" when it has none) beside the draft's from `md`, the "Edited" badge on a person's, every drafted value with a link to its page or its document's name, "Also replace the fields I edited", Accept, whose answer replaces the form's fields, and Discard, which leaves the form as it is; a draft with no value says so, with Discard alone. A failed Accept or Discard shows its code in words with a retry, which sends the press's key and body again; none for `company_knowledge_no_draft`, nor for the Draft's `company_knowledge_no_website`. The text is `onboarding.company.*` and `onboarding.errors.*`; Save, Cancel, Try again, the loading word and the generic failure are the shared `ui.*` and `platform.error.generic`.

## Commands

`domain/commands.ts`: `getCompanyKnowledge(workspaceId)`, `saveCompanyKnowledge(fields)`, `getCompanyDomain()` and `readCompanyKnowledge(workspaceId)`, each inside the caller's tenant run, through `tenantClient`, opening none. Two first reads at once both answer the one record (`INSERT … ON CONFLICT DO NOTHING`); two saves at once are ordered by a lock on its row, so each compares with what the other committed and no version is given twice.

## Decided here

- The routes sit under the module's name, `/v1/workspaces/{ws}/onboarding/company-knowledge`; the task's `…/company-knowledge` follows it.
- The event is `onboarding.company_knowledge_updated`, the platform's `module.event_name`, for the task's `company_knowledge.updated`.
- The message keys are snake_case (`onboarding.company.one_liner`, `onboarding.company.source.ai_draft`): a key's segments are lower-case letters, digits and underscores, so the task's camelCase keys would fail the message check.
- `PUT` replaces every field, as icp's does; the version starts at 1 and moves on any change, the website included; the website is not a content field, so it has no source.
- A list's order counts as a change; whitespace around a text does not.
- Item lengths the task leaves open: 200 characters per list item, 500 per proof point, 2,048 per URL.
- A URL with a user name or a password is refused, as one the fetch would send them with.
- `getCompanyDomain()` drops a leading `www.`, so the own-employee filter compares `acme.test` with `acme.test`.
- No foreign key to `workspaces` (Prisma would need the opposite relation in `tenancy.prisma`), as icp.
- The commands run in the caller's run, so the module keeps no database client of its own.
- The workflow is `onboarding_draft_company_knowledge`, its activity `onboarding_fetch_website`: the worker takes names that start with the module's, for the task's `draft_company_knowledge` and `fetchWebsite`. The route is `…/onboarding/company-knowledge/draft`, under the module's name; the keys `onboarding.company.pages_read` and `fetch_failed`, snake_case.
- The text extraction is a small tokenizer of our own, linear in the page, so no HTML parser is a dependency.
- Only `robots.txt` and the home page fail a run; the home page disallowed is `fetch_failed`. A 5xx `robots.txt` allows nothing (RFC 9309).
- A Draft while one is fetching is allowed and supersedes it: the latest Draft wins, by one compare in the final write's transaction.
- The pages keep their text after the draft: the company's own public site, which the writer may cite.
- alpha-p4-030: the task is `onboarding.draft-company-knowledge` (the registry's names take hyphens), its activity `onboarding_draft_from_pages`, the keys snake_case (`onboarding.company.draft_ready`). The pages reach the model as one `<pages>` block of JSON `{ url, title, text }`, since the ai package writes one block per input field, for the task's `<page url="…">` blocks; each text cut at 6,000 characters; the budget 40,000 input and 6,000 output tokens, priced at no credit in alpha (the cost event records it).
- The cache's subject is the record and its input the pages' `url`, `title` and `text` only, never a time or an id, so unchanged pages reuse the decision record.
- `ai_failed` and `draft_failed` are run codes in `fetchError`, not registered errors: no route answers them, and `ai_failed` is every agent's.
- An accept marks only the fields it changed and moves the version only on a change; a new Draft clears the pending draft; the answer carries `pendingDraft` with its `decisionRecordId`.
- `fetched` is now the step between the fetch and the drafter; a record an older run left `fetched` or `fetching` is stuck after ten minutes (alpha-p10-090).
- alpha-p10-090: the record is read in the browser, so that its loading and error states show and Playwright can hold or fail the read; `page.tsx` keeps the `<title>`.
- The last-changed line reads `fieldSources`, the latest `at` and its `kind`, not `updatedAt`, which a Draft's status moves too and which names no source; the website has no source, so a change of the website alone moves no line. No migration.
- Stuck is discovery's rule on the record's time: `fetching` or `fetched`, `updatedAt` more than ten minutes before the browser's clock; a save during the run restarts it. Draft is not disabled during a run (a Draft supersedes it, alpha-p4-020), so it is enabled when the run is stuck.
- A failed read during a run stops the asking until the retry, as discovery's run does; the empty record is one with no website and no content field.
- A retry sends the failed press's `Idempotency-Key`, and the accept's body, again: the api runs a key once and stores no error (core/apps/api docs/security.md). A new press takes a new key.
- The badge's hint is a `role="tooltip"` the badge points at with `aria-describedby`, shown by `company.css` on hover and `:focus-within`, one key with a `select` on the source's kind, worded so that it never repeats its badge's word.
- The keys are snake_case (`draft_pending_confirm`, `last_changed`, `source.hint`), with `stuck`, `pages_empty` and `review.empty` beside the task's.
- knowledge-draft: the script starts the screen's Draft and waits for the worker, so it needs no model key and no route; it prints codes and names, never a text, and its refusal codes are not registered errors (no route answers them).
- `unpdf` is imported in `cli/documents.ts` alone, which only `cli/draft.ts` imports: the api and the worker never load PDF.js, which adds globals on its first call. The bytes go as `data`, a `Uint8Array` copy, never a `url`; `useWorkerFetch: false`, `useWasm: false`, `verbosity: 0`; `loadingTask.destroy()` after each file. PDF.js 6.4 has no `isEvalSupported` and runs no eval.
- A save accepts a proof point's `document:<name>` (`normalize`, `domain/rules.ts`), the smallest change that keeps an accept, and a save after it, passing: the body's schema took any string already; the website stays an `http` or `https` URL, and the screen never links a document.
- `DOCUMENT_LIMITS.text` repeats `FETCH_LIMITS.text`, since the lint keeps `cli/` from importing `workflows/`; `tests/documents.test.ts` compares them. A document's name is its file's base name: two files with one name are refused, as the table's key would.
- The documents keep their text after the Draft, like the pages, until the next Draft replaces them.
