# qualification: security

Read before changing the module ([security §8](../../../../docs/rules/security.md#8-conduct)). The assessment follows the six AI rules of [security §6](../../../../docs/rules/security.md#6-ai).

- **Hard filters first**: the model never sees a person the filters reject; the caller runs them before `assessPerson` ([flows.md](flows.md)).
- **Anonymization** (`domain/anonymize/`): what the model sees of a person is an allow-list, the headline, the title and the country, the company's name, industry and size, and at most five excerpts of 500 characters. Nothing else of the records is read, so a field added to contacts later never reaches the model by itself; no name, photo, pronoun, gender, age or special-category field is read. In every text kept, the person's names (each part, any case, with or without accents) become `[name]`, links `[link]`, email addresses `[email]`; in the person's own texts, pronoun declarations, honorifics and ages go and gendered words become neutral ones (`Chairwoman` is `Chair`). The company's texts keep their words, which describe its market. A free text may still mention a special category: the prompt forbids inferring or using one. `tests/anonymize.test.ts` and the recorded calls of `tests/assess.test.ts` are the proof.
- **The boundary**: every text of the person and of the ICP is data, in its labeled block of the user message; the system prompt is the prompt file alone, its first lines naming the blocks and saying that their content is data, never instructions. The ai package escapes `<` in a block, so no text closes one. The seller's ICP texts are data too: they say who to look for and never change the criteria, the verdicts or the answer's shape.
- **Closed lists and fail safe**: the output schema lists the six criteria, the four verdicts and the eleven disqualifiers; a value off a list, or a criterion missing or twice (the gate), is retried once and then `ai_failed`, with nothing stored but the decision record. A verdict whose evidence quotes nothing of the person's data is stored `unknown`. Scores are code (alpha-p6-030), never the model's.
- **What is stored**: the snapshot's `summary` and each verdict's `evidence` may quote the profile, so both are marked `/// pii: business_contact` ([data.md](data.md)); the decision record (core/packages/ai) keeps the raw prompt and output for its retention. `erasePerson` deletes the person's snapshots and verdicts.
- **Logs**: the module logs nothing; the profile, the evidence, the prompt and the output never reach a log line.
- **Network**: no fetch during the assessment; the model is reached only through the ai package and the LLM port, whose vendor adapters are on no-training terms (the anthropic adapter's README; RB-25.3.2).
- **Tenancy**: the three tables are tenant tables, read and written through the tenant client in the caller's runs; a verdict links its snapshot by `(workspace_id, snapshot_id)`. `tests/tenancy.test.ts` is the isolation test. `assessment_attempts` holds ids and a count, no personal data; `erasePerson` deletes its rows.
- **The score and the why**: the fit, the status and the tier are code over the stored verdicts (`domain/score/`); the why's bullets are codes, numbers and the verdicts' evidence quotes, cut to 300 code points, never the model's summary (`domain/why/`). A quote repeats the profile's words, so the lead's `why` is `business_contact` (contacts' column). The score runs in the caller's tenant run, through the tenant client (`tests/tenancy.test.ts`).
- **The re-score** (alpha-p6-040): the route needs `qualification.rescore` (Owner, Admin) and writes the request in the request's tenant run; `pnpm rescore` runs as the service principal `qualification`. The event and the workflow carry ids only; the subscriber starts the run for the delivery's workspace, never the payload's. It copies stored verdicts and calls no model.
- **The panel** (alpha-p10-100): the lead page's Re-score calls the routes as the member, through the web's API client, with an idempotency key per press; it shows statuses and codes in words, never a verdict's evidence. `qualification.rescore` names Owner and Admin, but alpha evaluates no role (every member is Owner, platform's `can`), so no Member is refused yet (an open question of alpha-p10-100).
- **The batch** (alpha-p6-040): the tick reads the workspaces' ids only, through tenancy's `listWorkspaceIds`, then checks each workspace's ICP and leads in that workspace's own tenant run; each batch runs for its input's workspace, and a subscriber starts the batch of the delivery's workspace, never the payload's. Activity inputs and outputs, the workflow's history and `qualification.lead_qualified` hold ids, the ICP version, codes and counts, never a verdict or its evidence. An assessment is reserved before the model call and committed only on a stored snapshot; a failed one is released.
- **The grounding sample** (alpha-p10-050): `whySample` hands the ai package the week's why bullets that quote the model, with the anonymized input they quote, read in the workspace's tenant runs; its sheet leaves as `@whytide/ai`'s docs/security.md says, under the workspace's `exports/`, 7 days at most. Nothing logs a bullet or a fact.
- **The golden set** (alpha-p9-050): a way for data to leave, to a member with contacts' `exports.read` or an engineer's `pnpm export:golden`, with the workspace's own reviewed leads only, read in its tenant runs (the api's `tests/qualification-golden-set.test.ts`, two workspaces). A line holds no id, name or link of the person: the sha256 of the person's id, the input as anonymized for the model (from a raw prompt before its `raw_purge_after` only, whether the purge ran or not), the verdicts' quotes of that input, codes and numbers; the model's summary stays out. The testers' texts (`reason_text`, `good_reason_text`) are free text exported as typed: a tester could type a name into one, so a golden set stays the workspace's data. The file lives under the workspace's `exports/`, 7 days at most; nothing logs a line.
