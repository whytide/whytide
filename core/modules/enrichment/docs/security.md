# enrichment: security

- **Minimum input** (RB-7.3.1): a company source gets the company's LinkedIn page, domain, name and country, each checked against the port's form; a person source the person's location text. Beside them, the run's workspace and company ids, for the source's runs of the workspace and its agent calls; company-data's lookup takes the keys only. Nothing else of the person reaches a source, and nothing of the person reaches a vendor.
- **A source's own runs:** `context.tenant` opens a run of the run's workspace only, as the worker's service principal, one transaction per call; a source reads no other workspace.
- **Data leaving the system:** each `company-data/<adapter>` call sends those company keys to a vendor the operator listed in `PROVIDER_COMPANY_DATA`, through the port's `lookupCompany`, whose input holds a company's keys and nothing about a person. The source `country-ai` (gamma-en-075) is the module's AI call: below.
- **No value in the workflow:** inputs, results, events (`enrichment.run_requested { runId }`), `sources_tried` and log lines carry ids, names, field names and codes. A source's error keeps its code, never its message, which could hold a value.
- **Personal data:** `enrichment_runs` names a person by id and holds no value; privacy's eraser deletes a person's runs. The facts are contacts', with their provenance; a member's value is never wanted, so never overwritten.
- **Global counters:** `source_usage` has no workspace and no personal column. The app reaches it outside any tenant run, through the global client inside `withoutTenant("enrichment.usage")`, and may not delete a row or count below 0.
- **Who may do what:** `enrichment.read` (the lead page's reads) and `enrichment.run` (its "Enrich now", "Find email" and "Verify again") for Owner, Admin and Member, checked by the api host on each route (gamma-en-055, gamma-en-081); a person of another workspace is 404. The Email panel's read answers the lead's address to the member, with its class and dates, never the finder or verifier that found or checked it. The read answers source classes and dates, never a provider's name (RB-7.3.2). The tick's check runs in each workspace as the service principal `enrichment`; the activities run as `service:worker` in the input's workspace.
- **Secrets:** none of this module's; the adapters' keys are the providers'. A key that is missing leaves its adapter out at start, named by its variable, never its value.
- **What a web search holds** (gamma-en-070, RB-7.3.1): the company's name in quotes and fixed words (`official website`), with the site `linkedin.com` for the page's search, nothing else: never a person's name, title or location. The query goes to the adapters of `PROVIDER_WEB_SEARCH` the operator listed, at most two searches per company in a run. The results stay inside the activity; only the chosen page and domain are kept, written to contacts with the class `web_search`. No log line, span, result or event carries the name, the query or a link: a failed search's warning names `web-search/<adapter>` and the code.
- **The website source** (gamma-en-065): it reads only the company's own site, `https://<domain>/`, through the platform's reader and `fetchSafe` (the egress rules on every hop), robots.txt first: a site whose robots.txt allows no reading of its home page is `blocked`, with no page read and no AI call, and the browser port renders only a page robots.txt allowed. Bounded: `ENRICHMENT_SITE_MAX_PAGES` pages (5), 60 seconds of fetching, 15 seconds a rendered page (the adapter's), 60,000 characters and 81,000 bytes of text to the AI. The pages are data: they reach the model in their own `<pages>` block with the company's name and the fields wanted, never anything of the lead, and the prompt says the blocks are never instructions (security §6). Every value must name a page and quote it word for word (the `grounded` gate), or the call ends `ai_failed` and nothing is written. No page is kept; the decision record keeps what `callAgent` keeps (the raw prompt 30 days), its subject the company's id. No page's address or text, and no fact, reaches the workflow, `sources_tried` or a log line.
- **What a LinkedIn page read holds** (gamma-en-060, RB-7.3.1): the company's page link only, sent through the linkedin module's `readCompany` by one of the run's workspace's accounts, inside that account's quota. The page's facts stay inside the activity; only the wanted fields are written to contacts with the class `linkedin`. No log line, span, result or event carries the link or a value.
- **What the country namer gets** (gamma-en-075, RB-7.3.1): the source `country-ai` sends the model the person's location text, cleaned, at most 200 characters, and nothing else: never the name, the profile or the company. It goes to the LLM port's model through `callAgent`, which writes a decision record and a cost event under the subject `location:<sha256 of the text>`, naming no person; the raw prompt holds the text until `AI_RAW_RETENTION_DAYS` (30) purges it. No log line, span, result, event or `sources_tried` entry carries the location: they name `country-ai`, an outcome and a code.
- **Email lookups** (gamma-en-080, send path): a finder gets the person's first name, last name and company domain only, a verifier the address only. No address in a workflow input, an activity's result, an event, `providers_tried` or a log line: the candidates go through files in the workspace's `raw/` folder, deleted at the settle. Only a verifier's `valid` makes an address an email may go to; `workEmailOf` and `addressOf` answer an active, valid one only, and a personal one only while it needs no consent (`ENRICHMENT_PERSONAL_EMAIL_EU_UK`, off by the owner's decision). One address sits on one person (a unique key). `contact_points.value` and `enrichment_cache_entries.value` are personal data, erased with the person; `email_domain_statuses` holds none.
- **LinkedIn's "Contact info"** (gamma-en-087, send path; the owner's exception of 2026-11-13, behind `LINKEDIN_CONTACT_INFO_ENABLED`, off by default): the source `linkedin-contact-info` sends only the person's id to the linkedin module's `readContactEmails`, which reads the email addresses alone, through the account the person accepted, inside its quota. Off, nothing is read. Its addresses go the way of every candidate: a raw file of 72 hours at most, a verifier, and a contact point only on `valid`; no address in a workflow input, an activity's result, an event, `providers_tried` or a log line. Off stops new reads only: nothing is deleted.
- **The free email sources** (gamma-en-085, send path): `reply` reads the lead's own inbound messages through inbox's `addressesGivenBy`, which answers addresses and never a text, and never the workspace's messages to the lead; of a message holding several addresses only the lead's own. `website` reads the company's own site as the website source does (robots.txt first, the egress rules, the same bounds), and keeps only the lead's own address as a candidate: the other addresses and the names around them stay in the activity's memory, turned into one pattern's name, and are never stored, logged or passed on. `pattern` builds guesses at the company's domain from the lead's names, none at a domain recorded catch-all. None calls a vendor but the verifiers, which get the address only; only a verifier's `valid` keeps an address. `email_domain_patterns` (gamma-rf-030; before it, `email_domain_statuses`) holds a domain, a pattern's name (a CHECK lists the names), a count and two times, no personal data. No address, name or page text reaches a workflow input, a result, an event, `providers_tried` or a log line.
- **The lead's own sources first** (gamma-en-100, send path): with no company domain, a catch-all one or the credits short, only the sources with `anyDomain` run, what the lead gave: no finder, no site read and no guess, so no vendor gets the person's names; the verifiers get the address only, and only their `valid` keeps one. A personal address follows the UK and EU switch as any. Nothing is reserved, and an address the lead gave never commits a credit. At a catch-all company domain the lead's addresses at that domain go to no verifier.
- **The lookup at find** (gamma-wr-070, send path): an address a company's page printed with a person is held on the lookup's request only while it runs (`printed_address`, personal data, emptied at every end; in no workflow input, result, event, `providers_tried` or log line). It is verified before any source is asked, sent to a verifier as the address alone, and kept only on a verifier's `valid`, at the company's own domain, on no never-contact entry and on no other person; charged as any address Whytide found. The lookup's gates are the existing ones; the switch `ENRICHMENT_LOOKUP_AT_FIND` stops new asks only.
- **A person's phone** (gamma-wr-100, send path: it changes the table the send path reads, personal data): a phone is a contact point of kind `phone`, never an address. Every reader that decides which address an email goes to, or what a verifier is sent, names the email kinds (`EMAIL_KINDS`) and answers no phone, whatever its verification or its date says (`tests/safety/phones.test.ts`); the table's CHECK keeps `verification` and `verified_at` required for the two email kinds. A number is kept only as a public page printed it with the person, cleaned by form, once on one person, and for nobody on the never-contact list; Whytide calls and messages none, and no number is sent to a vendor. The number is personal data (`contact_points.value`, erased with the person, the 30-day rule's reach); it is in no log line, span, metric label, event or workflow history, and the Email panel shows it to a member with the page, the link opening with no opener.
- **A name with no person** (gamma-wr-080, send path): the names of a picked person and the company's domain are asked of the sources that need no person (the pattern's guesses and the finders: a finder gets the first name, last name and domain, as in any lookup), the address only of a verifier. Until a verifier says `valid` the name is in memory only: in no table, request, event, `providers_tried`, file, log line, span or credit key (its key is the found company's id and the person's place in the pick). Only a `valid` address makes the person, in one tenant run that rolls back if the never-contact list or another person holds the address or the caller makes no person, so nothing is left; any other end releases the credit and leaves nothing but the domain's catch-all row, which holds no name or address. The gates are the lookup's own: no guess at a catch-all domain, nothing asked with no verifier call left or the credits short. Tests: `tests/safety/work-address-of-name.test.ts`.
