# messaging: flows

## The dossier route

`GET …/messaging/leads/{personId}/dossier`: the host checks the session, the membership and `drafts.read`, then hands the handler the tenant with no run around it (`whytide:own-runs`). `buildDossier` opens one run of the workspace for contacts' `getLead` (its `lead_not_found` becomes `dossier_lead_not_found`) and `getCompany`, onboarding's `readCompanyKnowledge` (which creates the empty record on a workspace's first read) and signals' `listEvidence`; reads the user with tenancy's `findUser` after it, outside any run; and answers `assembleDossier`'s dossier. Nothing is written but that empty record; no event is published.

## A draft requested

`POST …/messaging/leads/{personId}/drafts { channel }` (`drafts.write`, `@Idempotent()`): in the request's tenant run, `requestDraft` checks the lead with contacts' `getLead` (`dossier_lead_not_found`), writes a `drafting` row and publishes `messaging.draft_requested` (ids only: the workspace, the draft, the person, the member who asked, the replaced draft); 202 with the draft. The worker delivers the event to `events.ts`, which starts `messaging_draft_message` by the id `messaging.draft:<workspace>:<draft>`, so a second delivery starts no second run. Its activity `messaging_write_draft` (kind `ai`: three attempts of five minutes at most) calls `writeDraft`, below; past its attempts, `messaging_draft_failed` marks the draft `failed`, `write_failed`, if it is `drafting` still, and the workflow fails. The draft panel (alpha-p9-030) reads `GET …/drafts/{id}` until the draft is no longer `drafting`.

## An edit

`PATCH …/drafts/{id} { editedText }` (`drafts.write`): 409 `draft_not_editable` while the draft is `drafting`; 400 `messaging_input_invalid` (`fields: ["editedText"]`) for a text, trimmed, above the channel's hard limit (a note `LINKEDIN_NOTE_LIMIT`, a message 1,900); then `checkText` (beta-p3-020): 400 `draft_text_refused` with `details.issues` for a placeholder, a red-line phrase or a colleague's signal, and nothing changes; otherwise `edited`, with `edited_text` and `edited_at`, `text` left as the writer wrote it. The writer writes only a `drafting` draft, so nothing changes an edited one.

## A regeneration

`POST …/drafts/{id}/regenerate` (`drafts.write`, `@Idempotent()`): 409 while the draft is `drafting`; otherwise `requestDraft` with `replacesId`, a new `drafting` row of the same person and channel, and its event; 202 with it. Its writer sends the replaced draft's angle, call to action and text (the member's edit, if any) in `<replaced>`, asking for a different one. The replaced row stays as it is.

## A draft written

`writeDraft` (`domain/drafts/write.ts`), outside any run: it reads the draft in a tenant run (a draft no longer `drafting` answers its status, so a retried activity changes nothing); resolves the requester's membership with tenancy's `resolveMembership` (none: `failed`, `draft_requester_not_member`, before any call); builds the dossier as that member (no lead: `failed`, `dossier_lead_not_found`); reads the names of the lead's colleagues with contacts' `colleaguesOf`, in a run of its own; builds the blocks (`domain/drafts/blocks.ts`); calls the planner, then the writer, each through `callAgent`, which opens its own runs for the cache, the decision record and the cost event, and runs the gates on each answer. An answer with an issue is asked again with the issues, at most two regenerations in all; `ai_failed` ends the draft `failed`. The last run writes the draft once, if it is `drafting` still. Nothing is published, and nothing is logged.

## The draft panel

contacts' lead page renders `ui/draft-panel/panel.tsx` on the server in its `draft` slot, which shows its loading state meanwhile: `GET …/leads/{personId}/drafts` as the member and, when the newest draft has a plan, `GET …/leads/{personId}/dossier`; a read the api refuses is the panel's error state, whose retry reads the page again, and any other fault the slot's. In the browser, Draft is `POST …/leads/{personId}/drafts { channel }` with a new `Idempotency-Key`, then `GET …/drafts/{id}` until the draft is no longer `drafting`: every two seconds, then an eighth of its age, thirty seconds at most, and none past twenty minutes, when a note offers Check again, one more read. Save is `PATCH …/drafts/{id} { editedText }`; Regenerate is `POST …/drafts/{id}/regenerate`, polled the same way; a newer plan on another dossier hash reads the dossier once more, a loading line meanwhile. A failed request shows its code in words with a retry, which sends Draft or Regenerate again with the same key; a refused Save keeps the text. Copy writes the text to the clipboard: the member sends it on LinkedIn, and nothing is sent from the product.

## A step's draft requested

`requestStepDraft({ personId, stepExecutionId, stepKey, senderUserId, earlierDraftIds })` (`domain/drafts/step.ts`), in campaigns' tenant run (beta-p3-010): a draft of the step execution already made is answered as it is. Otherwise the input is checked (`messaging_input_invalid` for a key outside `STEP_KINDS` or more than three earlier ids) and the lead (`dossier_lead_not_found`), and one `outbound_step` row is written with its step execution and key, `createMany` skipping a duplicate: a request that lost a race to the partial key answers the winner's draft. `connect`: a `linkedin_note`, `ready`, with an empty text, and `messaging.step_draft_ready { status: "ready" }` in the same run, with no model call. `message_1`, `follow_up_1`, `follow_up_2`: a `drafting` `linkedin_message` and `messaging.draft_requested` with `userId` the sender account's owner and the `earlierDraftIds`, which starts `messaging_draft_message` as for a lead's draft.

## A step's draft written

`writeDraft` as above, with `earlierDraftIds`: in its first run, the earlier drafts are read by id, and must each be an `approved` `outbound_step` draft of the same person in the workspace, the same id counted once; any other fails the draft `earlier_draft_invalid` before the membership check and any model call. Both calls get `<step>` (`blocks.ts`): the kind of the draft's step (`first_message`, `follow_up`) and the earlier final texts (`edited_text`, else `text`), oldest first by `created_at`, empty ones left out. The last run writes the draft only while it is `drafting`, and publishes `messaging.step_draft_ready { draftId, stepExecutionId, status }` with it; a draft the sweep failed meanwhile stays `failed`, and the late answer is dropped. `messaging_draft_failed` (`markFailed`) publishes `failed` the same way.

## An approval

`approveStepDraft(draftId, { text?, stepExecutionId })` (beta-p3-020), in approvals' tenant run, so the freeze and the approval item commit together: it reads the draft (`draft_not_found`), checks that it is the step execution's `outbound_step` draft (`draft_step_mismatch`), not `drafting` (`draft_not_ready`) and not `approved` (`draft_not_editable`). The final text is `text`, else the draft's own, trimmed; `checkText` runs on it every time (`draft_text_refused` with `details.issues`), with the person's colleagues read in the same run. One conditional write on the status it read stores `edited_text` and `edited_at` when the final text is not `text`, `edited_by_user`, `edit_ratio`, `approved` and `approved_at`; a second approval meanwhile finds no row to write and is `draft_not_editable`. It answers `{ contentHash, editRatio }`. Nothing is published. Afterwards `approvedContent(draftId)` answers the frozen text and its hash; `editDraft`, `regenerateDraft`, the writer, `markFailed` and the sweep leave the row as it is.

## The sweep

`messaging_sweep`, global, every hour (schedule `messaging.sweep`): `messaging_list_workspaces` reads tenancy's `listWorkspaceIds()`, then `messaging_sweep_workspace` runs `sweepStuckDrafts()` in each workspace's run, one after the other. Every draft still `drafting` 30 minutes after `created_at`, of either kind, becomes `failed` with `{ code: "draft_stuck" }` and no text, in one conditional write; a step's draft publishes `messaging.step_draft_ready { status: "failed" }` in the same run. A workspace whose sweep failed past its attempts is counted (`unswept`) and the others go on. The panel shows a swept lead draft's failure, which Regenerate writes again.
