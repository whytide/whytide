# messaging

What a draft may say about a lead, and the draft: the dossier, built in code from the public reads of onboarding, contacts, signals and tenancy, every value a fact with an id and a source; then the writer, agents that plan and write a LinkedIn text or an email (gamma-p3-070) from it, each answer checked by gates in code against the dossier and the message policies; and a draft for each step of a sequence (beta-p3-010).

- **Owns:** `message_drafts` ([docs/data.md](docs/data.md)); the dossier and draft routes; the workflows `messaging_draft_message` and `messaging_sweep`, with its schedule `messaging.sweep`; the events `messaging.draft_requested` and `messaging.step_draft_ready`; the draft panel `ui/draft-panel/`, in the `draft` slot of contacts' lead page; the AI disclosure line's component `ui/disclosure/` ("The disclosure line"); the reply writer, the agent `messaging.write-reply`, which writes nothing of its own ("The reply writer").
- **Public interface:** `index.ts`: `api`, which the api host mounts under `/v1/workspaces/:workspaceId/messaging`; `erasePerson(personId)`, this module's step of the deletion script (core/modules/privacy): the person's drafts deleted in the caller's tenant run, `{ message_drafts: <count> }` returned, `person_not_found` for an empty id, as signals' has it; `draftSample`, the drafts' source of the weekly grounding sample (`@whytide/ai`'s README), defined as `index.ts` loads: each draft made in the week that holds the writer's text, never a member's edit, ref its id, with the facts of its lead's dossier as it is now, each sourced by its `sourceRef`, built without a sender, whom a draft does not keep; `requestStepDraft`, a sequence step's draft for campaigns, an email key's with its `mailboxId` ("The writer"); `checkText`, `approveStepDraft`, `approvedContent` and `stepDrafts`, with their types, approvals' check, approval and reads of a step's draft ("The writer", beta-p3-020), a first email's `subject` in each and an email's hash of its subject and body (gamma-p3-070); `approveStepDraftByMode`, with `ApproveStepDraftByModeInput` and `StepDraftModeApproval`, the campaign's mode's approval, which ends the text with its AI disclosure line, and `approvedContent`'s `disclosureApplied` ("The disclosure line", gamma-p4-080); `writeReply`, with `ChatMessage`, `REPLY_CHAT_MAX`, `ReplyWritten`, `ReplyFailureCode` and `WriteReplyRequest`, inbox's reply draft ("The reply writer"); the registries `errors` (`dossier_lead_not_found` and `draft_not_found`, 404; `messaging_input_invalid`, `draft_text_refused` and `draft_subject_not_allowed`, 400; `draft_not_editable`, `step_draft_not_editable`, `draft_not_ready`, `draft_step_mismatch` and `disclosure_check_failed`, 409; `writer_agent_not_loaded`, 500), `events` (`messaging.step_draft_ready`, for approvals), `ids` (`mdr`), `permissions` (`drafts.read` and `drafts.write`: Owner, Admin, Member) and `settings`. The hosts load `events.ts` and `workflows/` from the build. Inside the module: `domain/dossier/` (`buildDossier`, `assembleDossier`, `normalizeEntity`), `domain/gates/`, `domain/drafts/` (`requestDraft`, `getDraft`, `listDrafts`, `editDraft`, `regenerateDraft`, `writeDraft`), `schemas/`, and the agents `agents/plan-message/`, `agents/write-message/`, `agents/write-email/` and `agents/write-reply/`, which the worker loads (`loadAgentTasks`).
- **Depends on:** `platform`, `db` (`withTenant`), `ai` (`callAgent`, `defineGroundingSource`); contacts' `getLead`, `getCompany` and `colleaguesOf`, onboarding's `readCompanyKnowledge`, signals' `listEvidence`, tenancy's `findUser` and `resolveMembership`; `@nestjs/common` in `api/`; `providers` for the LLM fake in tests.
- **Reviewers:** the owners of this module.

## The dossier

`buildDossier(tenant, personId)` (`domain/dossier/build.ts`) reads, in one run of the tenant's workspace, contacts' lead and person (`dossier_lead_not_found` when the workspace has no lead for the person, another workspace's person included), its linked company, Company Knowledge and signals' events with their evidence; then tenancy's user outside any run. `assembleDossier(inputs)` (`assemble.ts`), pure code, builds the dossier from those reads and checks it against `dossierSchema` ([docs/concepts.md](docs/concepts.md)):

| Block | Values | From |
|---|---|---|
| `sender` | `name` | the signed-in user's display name; null for a service principal |
| `offer` | `oneLiner`, `products`, `painPoints`, `proofPoints` (their texts) | Company Knowledge |
| `lead` | `firstName`, `headline`, `title`, `location` | the person's stored business fields |
| `company` | `name`, `industry`, `sizeRange`, `country` (its English name) | the linked company; without one, the person's `companyName` and nulls |
| `whyNow` | per event, newest first: `postUrl`, `excerpt`, `comment`, `reaction`, `at` | the events and their evidence; an event without evidence is left out; a reduced row (alpha-p10-020) keeps its URL, reaction and time |

- `facts`: every value above once, `{ id, kind, value, sourceRef }`, with ids `f_1`, `f_2`, … in the table's order. `kind` is `name`, `company`, `title`, `number`, `tool`, `event`, `date`, `claim` or `quote`; only a proof point is a `claim`. `sourceRef` is `<table>/<id>/<column>`, then an item's index (`company_knowledge/ck_…/proof_points/0/text`).
- `entities`: one per kind and normalized value of the facts but the claims and quotes, `{ kind, value, factIds }` (`entities.ts`), a date as its UTC day: what the grounding gate matches a draft's entities against, after `normalizeEntity`.
- `dossierHash`: the hex SHA-256 of the canonical JSON, keys sorted at every depth, of everything else (`hash.ts`). The same inputs give the same ids and the same hash.

## The writer

`writeDraft({ draftId, userId, replacesId? }, context)` (`domain/drafts/write.ts`) writes one `drafting` draft, which `requestDraft` made; the draft workflow's activity calls it outside any run (below). It checks that `userId`, the member who asked, is a member of the workspace still (`resolveMembership`), builds the dossier as that member, and calls the agents with `callAgent`, each call with its decision record and cost event:

1. **Plan** (`messaging.plan-message`): the angle, the fact ids to use and the call to action. Its gate `facts_used`: every id is one the planner read.
2. **Write** (`messaging.write-message`): the text, from the plan. Its gates: `placeholders`, `length` (a note 1 to `LINKEDIN_NOTE_LIMIT` characters, a message 150 to 300), `grounding` (every name, company, tool, number and date of the text in the dossier), `red_lines` (false familiarity, a fake reply or forward, false urgency) and `colleague_signal` (beta-p3-020: a phrase of `COLLEAGUE_SIGNAL_PHRASES` that points at the lead's colleagues, such as "your colleague" or "someone on your team", its last word also plural, or the first and last name of another person of the lead's company, whose names contacts' `colleaguesOf` gives once per draft, in a run of its own).

An answer with an issue is asked again with the issues in its `<failures>` block, at most two regenerations per draft in all. Then the draft is `ready`, `flagged` with the issues in `flag_reasons`, or `failed` with `{ code }` (`ai_failed`, `draft_requester_not_member`, `dossier_lead_not_found`). A regeneration of a draft (`replacesId`) sends the replaced draft's angle, call to action and text in `<replaced>`, so the cache cannot answer it with the same text. The model reads the facts as `{ "f_3": "Signal Radar" }` only: no source, link, record id or hash; `<lead>`, with the lead's company, and `<why_now>`, the newest three events, are marked untrusted ([docs/security.md](docs/security.md)).

A sequence step's draft (beta-p3-010): `requestStepDraft({ personId, stepExecutionId, stepKey, senderUserId, earlierDraftIds })` (`domain/drafts/step.ts`), in the caller's tenant run, answers `{ draftId }`, the step execution's one draft: an existing one as it is, else a new `outbound_step` draft. `STEP_KINDS` (`domain/drafts/constants.ts`) says what a step key's draft is: `connect`, the connection request's note, made `ready` and empty at once, with no model call, and its `messaging.step_draft_ready`; `message_1` (`first_message`), `follow_up_1` and `follow_up_2` (`follow_up`), a `drafting` message and `messaging.draft_requested` with `userId` the sender account's owner, as whom `writeDraft` writes it, and the `earlierDraftIds` (at most `EARLIER_DRAFTS_MAX`, 6, since gamma-p3-070). `messaging_input_invalid` for another key or more ids; `dossier_lead_not_found` for a person without a lead. `writeDraft` reads those drafts by id: each must be an `approved` step's draft of the same person, else the draft is `failed`, `earlier_draft_invalid`, with no model call. Both calls get `<step>`, `{ kind, earlier: [{ stepKey, text }] }`, the earlier final texts (`edited_text`, else `text`; `text` for a draft the campaign's mode approved, whose frozen text ends with the AI disclosure line, gamma-p4-090) oldest first, empty ones left out; a lead's draft sends it empty. Prompt version 2 of both agents reads it: none, a first message as in v1; `first_message`, never as if there had been a conversation, a call or a reply; `follow_up`, built on the earlier texts without repeating or quoting them, never claiming the person answered. The last write is the writer's only while the draft is `drafting`, and publishes `messaging.step_draft_ready { draftId, stepExecutionId, status }` (`ready`, `flagged`, `failed`) with it, as `markFailed` and the sweep do.

Every text that may be sent (beta-p3-020) passes `checkText(text, { personId, channel, kind })` (`domain/gates/check-text.ts`), in the caller's tenant run, on the text trimmed: the length (a step's note 0 to `LINKEDIN_NOTE_LIMIT`, a lead's note from 1, a message 1 to 1,900), `placeholders`, `red_lines` and `colleague_signal`, but not grounding; it answers `{ ok: true }` or `{ ok: false, issues }`. The writer runs the same gates, with grounding, on each answer (`checkWrittenText`). `approveStepDraft(draftId, { text?, stepExecutionId })` (`domain/drafts/approve.ts`), in approvals' run, approves a step's draft once. The final text is `text` when given, `""` included, else the draft's own, trimmed and checked every time (400 `draft_text_refused`, `details.issues`), so a `flagged` draft is approved once its text passes and a `failed` one only with a typed text. Refusals: 404 `draft_not_found`; 409 `draft_step_mismatch` (a lead's draft, or another step's), `draft_not_ready` (`drafting`) and `draft_not_editable` (`approved`, or another approval won). It writes `edited_text` and `edited_at` when the final text is not `text`, `edited_by_user`, `edit_ratio`, then `approved` and `approved_at` under a condition on the status it read, and answers `{ contentHash, editRatio }`, the hex SHA-256 of the exact final text. `approvedContent(draftId)` answers `{ text, contentHash }` for an `approved` step's draft, else null. `stepDrafts(draftIds)` answers the workspace's step drafts of those ids, in their order, for "Up next": the final text (null when failed), its length range, the gates, the flag reasons, the plan's fact ids, `editedByUser`, `editRatio` and `approvedAt`.

Emails and the message policies (gamma-p3-070). The channel `email`: `STEP_KINDS` maps campaigns' `email_1` to `email_first`, `email_2` and `email_3` to `email_follow_up`; `requestStepDraft` takes `mailboxId`, required for an email key and refused for any other (`messaging_input_invalid`), and stores it. A lead's draft may be asked as a kind of `WRITTEN_STEP_KINDS` that fits its channel (`step_kind`), an email without one as a first email. `writeDraft` holds back every draft, on every channel, whose lead's profile is clearly in another language (`profileLanguage`, `domain/drafts/language.ts`): `failed`, `profile_not_english`, before any model call, so a member writes it by hand. An email's plan comes from the shared planner and its text from `messaging.write-email` (`agents/write-email/`): a first email's `subject` and a `body`, a follow-up's body alone, as it goes in the first email's thread; stored in `subject` and `text`. The gates after `colleague_signal`: `signal_act` on every channel (a phrase of `SIGNAL_ACT_PHRASES` that names the signal's act, "saw you liked", "your comment on", rather than its topic); for an email, `length` in words (`EMAIL_WORD_RANGE`, 50 to 120; a typed body 1 to 1,900 characters), `subject` (a first email's 1 to 6 words, 60 characters, one line, no `Re:`, `Fw:` or `Fwd:`; none on a follow-up), `links` (a first email: no address, `www.`, email address or bare domain) and `near_duplicate` (a step's email: a Jaccard similarity of 0.8 or more of word 3-shingles to another draft of the same mailbox made or approved in the last 24 hours). The text gates read the subject as the body. `checkText` takes `stepKind`, `subject`, `mailboxId` and `draftId`; `approveStepDraft(draftId, { text?, subject?, stepExecutionId })` freezes a first email's subject with its body, trimmed, `edited_subject` when it differs, and answers the hash of `{ body, subject }`'s canonical JSON; `approvedContent` answers `subject` for an email, null for a follow-up; a subject on any other draft is 400 `draft_subject_not_allowed`. `StepDraft` gains `subject`, `maxSubjectWords` and `maxSubjectCharacters`, null but for a first email.

## The workflow

`messaging.draft_requested { workspaceId, draftId, personId, userId, replacesId? }`, which `requestDraft` publishes, starts `messaging_draft_message` (`workflows/`) by the id `messaging.draft:<workspace>:<draft>` (`events.ts`): a second delivery starts no second run. Its activity `messaging_write_draft` (kind `ai`, five minutes, three attempts) calls `writeDraft` and answers `{ status }`; past its attempts, `messaging_draft_failed` marks the draft `failed`, `write_failed`, if it is `drafting` still, and the workflow fails. Its recorded histories, with the test's ids, are `workflows/__histories__/`: `pnpm -F worker test:replay` replays them.

The sweep (beta-p3-010): `messaging_sweep`, global, started hourly by the schedule `sweep` (Temporal id `messaging.sweep`), lists the workspaces (`messaging_list_workspaces`, tenancy's `listWorkspaceIds()`) and runs `messaging_sweep_workspace` in each, one after the other, as `linkedin_status_refresh` loops; it answers `{ stuck, unswept }`, a workspace whose sweep failed past its attempts counted in `unswept`. The pages (gamma-p0-085), behind `patched("sweep-pages")` (`SWEEP_PAGES_PATCH`), asked once at the run's start: the list answers `SWEEP_PAGE_SIZE` (50) workspaces after the run's cursor, in id order, with the next page's cursor (`workflows/pages.ts`); after a page that is not the last, the run continues as new with the cursor, the page's last id, and its counts so far, under the same workflow id, and the last run answers the totals. `useSweepPageSize(size)` sets the page under `APP_ENV=test` and throws in any other environment. `sweepStuckDrafts()` (`domain/drafts/sweep.ts`) fails every draft, of either kind, still `drafting` `DRAFT_STUCK_MINUTES` (30) after it was made, `draft_stuck`, with no text: a cancelled run, or one past its attempts, never leaves a draft `drafting` for good. The timeouts are `workflows/constants.ts`. The histories `messaging_draft_message_step.json` (a follow-up's run), `messaging_sweep.json` and `messaging_sweep_pages.json` (a paged chain's first run) sit beside alpha's two.

## The reply writer

inbox-reply-draft: `writeReply({ personId, userId, conversation, brief, replaced, requestId }, context)` (`domain/replies/write.ts`), which inbox's reply draft activity calls outside any run with the thread's messages, oldest first, and the member's brief, read from inbox's own tables (messaging never imports inbox). It stores nothing: inbox keeps the draft. The conversation it reads (`replyChat`, `domain/replies/chat.ts`): the latest `REPLY_CHAT_MAX` (20) messages with a text, each trimmed and cut to 2,000 characters, then the oldest left out until their UTF-8 bytes fit 24,000, the latest always kept; empty, `conversation_empty` with no call. Then `userId` a member still (`draft_requester_not_member`), the dossier as that member (`dossier_lead_not_found`), the lead's colleagues in a run of their own, and one call of `messaging.write-reply` ([agents/write-reply/README.md](agents/write-reply/README.md)) with its decision record and cost event on the person. The language is `textLanguage` of the lead's messages (of all, without one), the stopwords' heuristic `profileLanguage` uses. Its gates (`textGates`): `placeholders`, `length` (1 to 1,900), `grounding` on the dossier, the brief and the conversation (a name, number or date any of them holds is no invention; in another language than English, its numbers and dates, not its names, since the name heuristic reads English capitals), `red_lines`, `colleague_signal` and `signal_act`; not `facts_used` (no plan), `subject`, `links` or `near_duplicate`. An answer with an issue is asked again once with the issues in `<failures>`; a second is `gates_failed`, and `callAgent`'s own failure `ai_failed`. It answers `{ status: "ready", text, modelId, promptVersion, decisionRecordId }` or `{ status: "failed", code, decisionRecordId }`; the LLM port's codes are thrown, for Temporal to retry the activity. The ready text a new request replaces goes in `<replaced>`, and the request's id (`requestId`, inbox's draft id) in `<request>`: callAgent's cache keys on the input, so every new request, Try again after `gates_failed` among them, asks the model again, while a retry of the same activity finds the calls it already paid for. Open: a short message in another language may read as English to the heuristic, and its reply's capitalized words then fail grounding (a failure, never an invention); the red-line phrases are English.

## Routes

Under `/v1/workspaces/{workspaceId}/messaging`:
- `GET /leads/{personId}/dossier` (`drafts.read`): the dossier, for the lead page's debug view and the grounding sample; 404 `dossier_lead_not_found`. The schema is `schemas/dossier.ts`, the request `api-calls/alpha-p9-010-dossier.http`. The route opens its own run (`whytide:own-runs`): tenancy's read of the user refuses to run inside one.
- `POST /leads/{personId}/drafts { channel, stepKind? }` (`drafts.write`, `@Idempotent()`): 202 with a `drafting` draft, which the worker writes for the member who asked, as `stepKind` when given (one that fits the channel, none for a note, else 400 `messaging_input_invalid`); 404 `dossier_lead_not_found`. Any lead, qualified or not.
- `GET /drafts/{id}` and `GET /leads/{personId}/drafts` (newest first, `{ drafts }`), `drafts.read`: a draft is its status, plan (`angle`, `factIds`, `cta`), `text`, `editedText`, `editedAt`, model, prompt version, dossier hash, gates, regenerations and `flagReasons`, and `maxCharacters`, the channel's limit now, which an edit is held to; an email's `subject` and `editedSubject`, and `stepKind`, the kind it is written as (gamma-p3-070); 404 `draft_not_found`.
- `PATCH /drafts/{id} { editedText, editedSubject? }` (`drafts.write`): the member's own text, and a first email's subject (else 400 `draft_subject_not_allowed`), at most the channel's limit (a note `LINKEDIN_NOTE_LIMIT`, a message 1,900; else 400 `messaging_input_invalid`) and passing `checkText` (beta-p3-020; else 400 `draft_text_refused`, `details.issues`, and nothing changes), makes the draft `edited`; 409 `draft_not_editable` while it is `drafting`.
- `POST /drafts/{id}/regenerate` (`drafts.write`, `@Idempotent()`): 202 with a new `drafting` draft of the same lead and channel, written unlike this one, which is kept; 409 `draft_not_editable` while this one is `drafting`.

The schemas are `schemas/drafts.ts`, the requests `api-calls/alpha-p9-020-drafts.http` and, for an email, `api-calls/gamma-p3-070-email-drafts.http`.

Beside a sequence's step drafts (beta-p3-010): the list holds `kind = lead_draft` only, so the panel never shows a step's draft; `PATCH` and regenerate answer 409 `step_draft_not_editable` for an `outbound_step` draft, which only approvals' path changes (beta-p3-020); `GET /drafts/{id}` answers any draft, with its `kind`, an `approved` one included.

## The draft panel

`ui/draft-panel/`, in the `draft` slot of contacts' lead page (`ui/nav.ts`), reads and writes the routes above as the member, and nothing else. `panel.tsx` reads the person's drafts on the server, and the dossier when the newest has a plan, while the slot shows its loading state; a read the api refuses makes the panel its error state, with a retry that reads the page again. `drafts.tsx`, in the browser, does the rest, in a card like the lead page's others:
- the sentence that nothing is sent from here, the channel, a segmented choice over two native radios (in forced colours the chosen one outlined), and Draft: `POST …/drafts`, then `GET /drafts/{id}` while the draft is `drafting`, every two seconds at first, then an eighth of its age, thirty seconds at most; past twenty minutes, longer than the writer's three attempts, a note says the writer may have stopped, with Check again, which reads it once. Draft and Regenerate are disabled meanwhile;
- the newest draft (`draft.tsx`): its mark, a badge; its text as the person will read it, a message's bubble under the channel's name, which shimmers while the writer runs, with a counter and a meter against `maxCharacters`, a message's with the range it aims for (150 to 300, `domain/gates/range.ts`), Copy for a `ready` or `edited` one (the clipboard, then a toast, a live region), Edit and Save (`PATCH`; above the limit the counter turns to the danger colour and Save is disabled), and Regenerate, at the row's inline end, whose new draft goes on top;
- its plan, the angle, the call to action and the facts it cites, each with its source worded from the reference's table and column, never the reference, which holds record ids; while the browser reads them, a loading line; a draft written on another dossier than today's shows no facts but a note that it is stale, which Regenerate writes again;
- its gates, passed or failed with their issues, which belong to the generated text, as an edited draft says, beside the plan where the panel is 36rem wide or more (a container query, as the slot's width is the page's), under it otherwise; a flagged draft's reasons in a warm box, and a failed one's code in words in a danger one;
- every draft of the person, newest first, on a timeline, with its channel, time and mark, and its model and prompt version while it is hovered, the hint itself too, or its time has the focus; with none, the empty state.

Every string is a `messaging.draft.*` key, a gate's issue a `messaging.gate.*` one (`ui/gates.ts`); an api error is its code in words, in ui's error state, whose retry sends Draft or Regenerate again with its Idempotency-Key, or the read again; a refused Save keeps the text, and Save.

## Decided here

- `buildDossier(tenant, personId)` opens its own run, rather than reading in the caller's: tenancy's `findUser` reads the global `users` table, which no code inside a run may (`nested_run`). Hence the own-runs route; the writer's activity (alpha-p9-020) calls it outside a run too.
- The 100 ms criterion is timed on the pure assembly in a unit test: the request's time on a loaded laptop would flake.
- The kinds: the sender's name, the first name, the location and the country are `name`; the company's name and industry `company`; the headline and title `title`; the size range `number`; products `tool`; a post's URL and the reaction `event`; the event's time `date`; the one-liner, pain points, excerpts and comments `quote`.
- Every event is listed, not the brief's top three: the writer reads the newest three (alpha-p9-020). A value is trimmed; an empty one is null and no fact.
- `company.country` is the code's English name (Node's ICU, as contacts reads countries), so that the writer and the gate compare words.
