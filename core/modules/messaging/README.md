# messaging

What a draft may say about a lead, and the draft: the dossier, built in code from the public reads of onboarding, contacts, signals and tenancy, every value a fact with an id and a source; then the writer, two agents that plan and write a first LinkedIn message from it, each answer checked by gates in code against the dossier and nothing else.

- **Owns:** `message_drafts` ([docs/data.md](docs/data.md)); the dossier and draft routes; the workflow `messaging_draft_message`; the event `messaging.draft_requested`; the draft panel `ui/draft-panel/`, in the `draft` slot of contacts' lead page.
- **Public interface:** `index.ts`: `api`, which the api host mounts under `/v1/workspaces/:workspaceId/messaging`; `erasePerson(personId)`, this module's step of the deletion script (core/modules/privacy): the person's drafts deleted in the caller's tenant run, `{ message_drafts: <count> }` returned, `person_not_found` for an empty id, as signals' has it; `draftSample`, the drafts' source of the weekly grounding sample (`@whytide/ai`'s README), defined as `index.ts` loads: each draft made in the week that holds the writer's text, never a member's edit, ref its id, with the facts of its lead's dossier as it is now, each sourced by its `sourceRef`, built without a sender, whom a draft does not keep; the registries `errors` (`dossier_lead_not_found` and `draft_not_found`, 404; `messaging_input_invalid`, 400; `draft_not_editable`, 409; `writer_agent_not_loaded`, 500), `ids` (`mdr`), `permissions` (`drafts.read` and `drafts.write`: Owner, Admin, Member) and `settings`. The hosts load `events.ts` and `workflows/` from the build. Inside the module: `domain/dossier/` (`buildDossier`, `assembleDossier`, `normalizeEntity`), `domain/gates/`, `domain/drafts/` (`requestDraft`, `getDraft`, `listDrafts`, `editDraft`, `regenerateDraft`, `writeDraft`), `schemas/`, and the agents `agents/plan-message/` and `agents/write-message/`, which the worker loads (`loadAgentTasks`).
- **Depends on:** `platform`, `db` (`withTenant`), `ai` (`callAgent`, `defineGroundingSource`); contacts' `getLead` and `getCompany`, onboarding's `readCompanyKnowledge`, signals' `listEvidence`, tenancy's `findUser` and `resolveMembership`; `@nestjs/common` in `api/`; `providers` for the LLM fake in tests.
- **Reviewers:** the owners of this module.

## The dossier

`buildDossier(tenant, personId)` (`domain/dossier/build.ts`) reads, in one run of the tenant's workspace, contacts' lead and person (`dossier_lead_not_found` when the workspace has no lead for the person, another workspace's person included), its linked company, Company Knowledge and signals' events with their evidence; then tenancy's user outside any run. `assembleDossier(inputs)` (`assemble.ts`), pure code, builds the dossier from those reads and checks it against `dossierSchema` ([docs/concepts.md](docs/concepts.md)):

| Block | Values | From |
|---|---|---|
| `sender` | `name` | the signed-in user's display name; null for a service principal |
| `offer` | `oneLiner`, `products`, `painPoints`, `proofPoints` (their texts) | Company Knowledge |
| `lead` | `firstName`, `headline`, `title`, `location` | the person's stored business fields |
| `company` | `name`, `industry`, `sizeRange`, `country` (its English name) | the linked company; without one, the person's `companyName` and nulls |
| `whyNow` | per event, newest first: `postUrl`, `excerpt`, `comment`, `reaction`, `at` | the events and their evidence; an event without evidence is left out; a reduced row (alpha-p10-020) keeps its URL, reaction and time |

- `facts`: every value above once, `{ id, kind, value, sourceRef }`, with ids `f_1`, `f_2`, … in the table's order. `kind` is `name`, `company`, `title`, `number`, `tool`, `event`, `date`, `claim` or `quote`; only a proof point is a `claim`. `sourceRef` is `<table>/<id>/<column>`, then an item's index (`company_knowledge/ck_…/proof_points/0/text`).
- `entities`: one per kind and normalized value of the facts but the claims and quotes, `{ kind, value, factIds }` (`entities.ts`), a date as its UTC day: what the grounding gate matches a draft's entities against, after `normalizeEntity`.
- `dossierHash`: the hex SHA-256 of the canonical JSON, keys sorted at every depth, of everything else (`hash.ts`). The same inputs give the same ids and the same hash.

## The writer

`writeDraft({ draftId, userId, replacesId? }, context)` (`domain/drafts/write.ts`) writes one `drafting` draft, which `requestDraft` made; the draft workflow's activity calls it outside any run (below). It checks that `userId`, the member who asked, is a member of the workspace still (`resolveMembership`), builds the dossier as that member, and calls the agents with `callAgent`, each call with its decision record and cost event:

1. **Plan** (`messaging.plan-message`): the angle, the fact ids to use and the call to action. Its gate `facts_used`: every id is one the planner read.
2. **Write** (`messaging.write-message`): the text, from the plan. Its gates: `placeholders`, `length` (a note 1 to `LINKEDIN_NOTE_LIMIT` characters, a message 150 to 300), `grounding` (every name, company, tool, number and date of the text in the dossier) and `red_lines` (false familiarity, a fake reply or forward, false urgency).

An answer with an issue is asked again with the issues in its `<failures>` block, at most two regenerations per draft in all. Then the draft is `ready`, `flagged` with the issues in `flag_reasons`, or `failed` with `{ code }` (`ai_failed`, `draft_requester_not_member`, `dossier_lead_not_found`). A regeneration of a draft (`replacesId`) sends the replaced draft's angle, call to action and text in `<replaced>`, so the cache cannot answer it with the same text. The model reads the facts as `{ "f_3": "Signal Radar" }` only: no source, link, record id or hash; `<lead>`, with the lead's company, and `<why_now>`, the newest three events, are marked untrusted ([docs/security.md](docs/security.md)).

## The workflow

`messaging.draft_requested { workspaceId, draftId, personId, userId, replacesId? }`, which `requestDraft` publishes, starts `messaging_draft_message` (`workflows/`) by the id `messaging.draft:<workspace>:<draft>` (`events.ts`): a second delivery starts no second run. Its activity `messaging_write_draft` (kind `ai`, five minutes, three attempts) calls `writeDraft` and answers `{ status }`; past its attempts, `messaging_draft_failed` marks the draft `failed`, `write_failed`, if it is `drafting` still, and the workflow fails. Its recorded histories, with the test's ids, are `workflows/__histories__/`: `pnpm -F worker test:replay` replays them.

## Settings

`LINKEDIN_NOTE_LIMIT` (default 200, 1 to 300): a note's most characters. `AI_MODEL_MESSAGING_PLAN_MESSAGE` and `AI_MODEL_MESSAGING_WRITE_MESSAGE`: the two agents' models; unset, the LLM port's first. The block is in `deploy/.env.example`.

## Routes

Under `/v1/workspaces/{workspaceId}/messaging`:
- `GET /leads/{personId}/dossier` (`drafts.read`): the dossier, for the lead page's debug view and the grounding sample; 404 `dossier_lead_not_found`. The schema is `schemas/dossier.ts`, the request `api-calls/alpha-p9-010-dossier.http`. The route opens its own run (`whytide:own-runs`): tenancy's read of the user refuses to run inside one.
- `POST /leads/{personId}/drafts { channel }` (`drafts.write`, `@Idempotent()`): 202 with a `drafting` draft, which the worker writes for the member who asked; 404 `dossier_lead_not_found`. Any lead, qualified or not.
- `GET /drafts/{id}` and `GET /leads/{personId}/drafts` (newest first, `{ drafts }`), `drafts.read`: a draft is its status, plan (`angle`, `factIds`, `cta`), `text`, `editedText`, `editedAt`, model, prompt version, dossier hash, gates, regenerations and `flagReasons`, and `maxCharacters`, the channel's limit now, which an edit is held to; 404 `draft_not_found`.
- `PATCH /drafts/{id} { editedText }` (`drafts.write`): the member's own text, at most the channel's limit (a note `LINKEDIN_NOTE_LIMIT`, a message 1,900; else 400 `messaging_input_invalid`), makes the draft `edited`; 409 `draft_not_editable` while it is `drafting`.
- `POST /drafts/{id}/regenerate` (`drafts.write`, `@Idempotent()`): 202 with a new `drafting` draft of the same lead and channel, written unlike this one, which is kept; 409 `draft_not_editable` while this one is `drafting`.

The schemas are `schemas/drafts.ts`, the requests `api-calls/alpha-p9-020-drafts.http`.

## The draft panel

`ui/draft-panel/`, in the `draft` slot of contacts' lead page (`ui/nav.ts`), reads and writes the routes above as the member, and nothing else. `panel.tsx` reads the person's drafts on the server, and the dossier when the newest has a plan, while the slot shows its loading state; a read the api refuses makes the panel its error state, with a retry that reads the page again. `drafts.tsx`, in the browser, does the rest, in a card like the lead page's others:
- the sentence that nothing is sent from here, the channel, a segmented choice over two native radios (in forced colours the chosen one outlined), and Draft: `POST …/drafts`, then `GET /drafts/{id}` while the draft is `drafting`, every two seconds at first, then an eighth of its age, thirty seconds at most; past twenty minutes, longer than the writer's three attempts, a note says the writer may have stopped, with Check again, which reads it once. Draft and Regenerate are disabled meanwhile;
- the newest draft (`draft.tsx`): its mark, a badge; its text as the person will read it, a message's bubble under the channel's name, which shimmers while the writer runs, with a counter and a meter against `maxCharacters`, a message's with the range it aims for (150 to 300, `domain/gates/range.ts`), Copy for a `ready` or `edited` one (the clipboard, then a toast, a live region), Edit and Save (`PATCH`; above the limit the counter turns to the danger colour and Save is disabled), and Regenerate, at the row's inline end, whose new draft goes on top;
- its plan, the angle, the call to action and the facts it cites, each with its source worded from the reference's table and column, never the reference, which holds record ids; while the browser reads them, a loading line; a draft written on another dossier than today's shows no facts but a note that it is stale, which Regenerate writes again;
- its gates, passed or failed with their issues, which belong to the generated text, as an edited draft says, beside the plan where the panel is 36rem wide or more (a container query, as the slot's width is the page's), under it otherwise; a flagged draft's reasons in a warm box, and a failed one's code in words in a danger one;
- every draft of the person, newest first, on a timeline, with its channel, time and mark, and its model and prompt version while it is hovered, the hint itself too, or its time has the focus; with none, the empty state.

Every string is a `messaging.draft.*` key, a gate's issue a `messaging.gate.*` one (`ui/gates.ts`); an api error is its code in words, in ui's error state, whose retry sends Draft or Regenerate again with its Idempotency-Key, or the read again; a refused Save keeps the text, and Save.

## Decided here

- `buildDossier(tenant, personId)` opens its own run, rather than reading in the caller's: tenancy's `findUser` reads the global `users` table, which no code inside a run may (`nested_run`). Hence the own-runs route; the writer's activity (alpha-p9-020) calls it outside a run too.
- The 100 ms criterion is timed on the pure assembly in a unit test: the request's time on a loaded laptop would flake.
- The kinds: the sender's name, the first name, the location and the country are `name`; the company's name and industry `company`; the headline and title `title`; the size range `number`; products `tool`; a post's URL and the reaction `event`; the event's time `date`; the one-liner, pain points, excerpts and comments `quote`.
- Every event is listed, not the brief's top three: the writer reads the newest three (alpha-p9-020). A value is trimmed; an empty one is null and no fact.
- `company.country` is the code's English name (Node's ICU, as contacts reads countries), so that the writer and the gate compare words.
- The api host references the module in its tsconfig and loads its build by path, with no dev dependency: messaging depends on onboarding, whose screen depends on the web, which depends on the api.
- The writer (alpha-p9-020): two calls, so two decision records and two cost events per draft; the draft's `decision_record_id`, model and prompt version are the write's, and the plan call's record id is in `plan`, beside its answer. The agents are not priced in credits in alpha (`maxCostCredits: 0`); the cost event records each call, and `checkAgentPrices` finds `fake/fake-model` and the configured models in `COST_PRICES_JSON` as for every task.
- `<failures>` holds one list of issues per earlier answer of the step: each regeneration's input differs, so the cache (task, person, input hash, model, prompt version) never answers it with the failed text. The cache's answer stays as it is (alpha-p9-020's review): a second fresh draft of an unchanged dossier, or a second Regenerate of the same row, gets the earlier text again; Regenerate of the newest row gives a new one. `<replaced>` is null for a first draft only: a draft replaced without a plan or a text sends its nulls, so no regeneration's input is a first draft's.
- `facts_used` checks a plan's ids against the blocks the planner read, not the whole dossier: a post's link and an older event are no fact it can cite.
- Grounding is code, no model: dates (ISO days, "October 2", "2 Oct", a month, a weekday), numbers (digits) and runs of capitalized words, a sentence's common first word left out, are found as whole words after `normalizeEntity`: a name in the entities or a claim's or quote's text, never a link's or a date's; a number in a number entity (the size range) or a claim only, so an event's month or a post's id grounds no figure; a date on a dossier date's day, or as a name is. A run is grounded whole or word by word ("Ines and Sam"); a possessive ends it ("Acme's Head of Data" is Acme, then Head of Data). It misses a name written in lower case and a number in words, and a word that starts a sentence and is in no list is taken for a name: a false flag, rather than a false pass. `LinkedIn`, `I` and a trade's acronyms (`B2B`, `CRM`, `VP`) are never names.
- A length is the text's UTF-16 units, as a textarea counts them, after trimming. A note may be 1 to `LINKEDIN_NOTE_LIMIT` characters; a message is regenerated outside 150 to 300.
- The lead's company (name, industry, size, country, from its LinkedIn page or the profile) is in `<lead>`, untrusted, not in `<dossier>` (alpha-p9-020's review). The prompts' v1 changed in place, as no draft had run on them: part 1 had no route or workflow.
- An edit is trimmed and checked against the channel's hard limit only, not the gates: the member's text is theirs. Any draft but a `drafting` one can be edited or regenerated, a `flagged` or `failed` one included; `draft_not_editable` refuses both while the writer runs.
- The workflow's input carries `personId`, as the task names it; `writeDraft` reads the draft's own. `write_failed` marks a draft whose writer failed past its attempts, a fault rather than a result.
- The evals: ten synthetic leads, each a case of both agents (twenty cases), short enough for this part's size; the writer has twenty since alpha-p10-050.
- `writer_agent_not_loaded`, not `draft_agent_not_loaded`: onboarding has that code, and codes are global. The failure codes in `flag_reasons` are no registered error: the draft panel (alpha-p9-030) words them.
- The draft panel (alpha-p9-030): the counter's limit is the draft's `maxCharacters`, from the api, which alone reads `LINKEDIN_NOTE_LIMIT`. Copy is for a `ready` or `edited` draft; Edit for any written draft with a text, a `flagged` one included, as the route allows. A plan's facts are shown from the dossier whose hash the draft has, read once by the page and again by the browser only for a newer draft's hash; on another dossier the panel says the draft is stale (alpha-p10-140) rather than show today's values under the draft's ids.
- The panel's keys are snake_case, as the message check wants: `messaging.draft.nothing_sent`, not the task's `nothingSent`. Beyond the task's list: `cancel`, `channel.label`, `copy_failed`, `failure.*` (four), `gate.*` (five), `gate_result`, `gates_generated`, `source.*` (seven) and `text`.
- The panel's states (alpha-p10-140): its loading state is the slot's, contacts', while `panel.tsx` reads; a read the api refuses is the panel's own error state, under its title, so the page and the other slots stand; any other fault is the slot's. The e2e api fails a read for a test with the cookie `e2e_fail`, as `e2e_hold` holds one (core/apps/api/tests/e2e-hold.ts).
- The poll's wait grows with the draft's age, on the browser's clock, and stops at twenty minutes: a run of three five-minute attempts has ended by then, and a later draft is one Check again or a reload reads. A browser clock ahead of the server's stops it sooner. The stop is set after the render, so the server's HTML and the browser's agree. Draft and Regenerate stay disabled on a stopped draft, as the route refuses Regenerate while it is `drafting`.
- The stale note replaces alpha-p9-030's facts-changed note, so the panel has one; a message's range is `MESSAGE_RANGE`, which the length gate and the counter share. The model hint is a tooltip on the time, which the keyboard reaches, as onboarding's sources are.
- alpha-p10-140's keys: the task's `empty`, `error`, `loading`, `range`, `stale` (in place of `facts_changed`) and `model_info` (its `modelInfo`), and beyond its list `check` and `stuck`.
- The panel on the design system (ui-tailwind): Tailwind's classes and `@whytide/ui`'s parts in place of `draft-panel.css`, with no change of behaviour, request or key. The message is drawn as the person will read it, a bubble, rather than as a field; the channel is a segmented control over the native radios, so the arrow keys and the radios' names stay; the shimmering lines while the writer runs are `WRITING_LINES` (`ui/draft-panel/constants.ts`).
