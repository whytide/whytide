# contacts: security

Read before changing the module ([security §8](../../../../docs/rules/security.md#8-conduct)): `persons` and `person_hashes` hold personal data, and `leads.why` and the two texts of `review_decisions`, which may quote the profile.

- **Personal data**: business profile fields only ([security §2](../../../../docs/rules/security.md#2-personal-data)): no column for an email, a phone, a photo, pronouns, gender, age or a special category, and `tests/schema.test.ts` fails on one. Each value carries its provenance.
- **Hashes, never rows**: a rejected candidate or an erased person is an HMAC-SHA-256 under `HASH_SALT`, never a row. The salt is a secret (`# secret`), never in a file or a log; tests set a fixed test salt. A hash is pseudonymous, since whoever holds the salt and a URL can match it, so it is classed `personal`.
- **Isolation**: every query runs in the caller's tenant run through `tenantClient`; `tests/tenancy.test.ts` registers the five tables in the two-workspace harness and checks every public command with `assertScoped`. A person exists once per workspace, never across. A person's company and a lead's person are foreign keys on `(workspace_id, id)`, so the database refuses a link across workspaces, which the same test proves; the commands still load the row through the tenant client first, for a clean `*_not_found`. The batched commands' two `INSERT … ON CONFLICT` are Prisma's tagged `$queryRaw`, every value a bound parameter, the run's workspace id written into each row and in the conflict's key; `tests/batch.test.ts` writes one URL in two workspaces and finds two persons.
- **Logs**: the platform's PII registry (`piiKeys`) holds the key of every column not classed `none`, so a log line with a person object is redacted; `tests/schema.test.ts` keeps `domain/fields.ts` and the registry in step. An error names the fields at fault, never a value.
- **Who may do what**: `contacts.read` for the person routes, `leads.read` for the lead routes, every role; `contacts.write` is declared for the writes to come; `reviews.write` and `reviews.read` for the review routes, `exports.read` for the leads CSV and qualification's golden set, Owner, Admin and Member. The routes never answer a provider's member id. Alpha evaluates no role (the platform's `can`): every member may export.
- **Append-only decisions**: no route or command updates or deletes a review decision, and the database refuses `app` an UPDATE (`tests/review.test.ts`); only `erasePerson` deletes them. `contacts.lead_reviewed` carries the ids and the decision, never a text.
- **What leaves**: the routes, to a member of the workspace; a lead's cursor holds its fit score, creation time or review status and its person id, nothing the page does not show. The list's address holds the view's codes only (status, tier, sort, review), never a person's value. The lead page links the person's URL normalized to `https://linkedin.com/in/<slug>` and nothing else, so no other scheme or host reaches an `href`. The list links a signal source's `url`, which the commands take as an https URL only, in a new tab with `rel="noreferrer"`; that URL, a post's, names its author, as signals' copies do, and the column `sources` keeps its class `none` until the platform's PII registry holds its key (an open question of fix-lead-source-post). The Export's file lives in the tab under a blob URL for 40 seconds. No network call, no AI call.
- **The leads CSV** (alpha-p9-050), a way for data to leave: the workspace's own leads, read in runs of the request's workspace, to a member with `exports.read`, never stored. Its columns are the list's business fields, the lead's decision and the latest review with the tester's words; a column that reads a field `domain/fields.ts` classes `personal` is never written. Every cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return starts with an apostrophe (`domain/export/csv.ts`), so a spreadsheet shows it and never runs it. No log line or span carries a cell.
