# contacts: security

Read before changing the module ([security §8](../../../../docs/rules/security.md#8-conduct)): `persons`, `person_hashes`, `person_email_hashes` and `suppression_entries` hold personal data, and `leads.why` and the two texts of `review_decisions`, which may quote the profile.

- **Personal data**: business profile fields only ([security §2](../../../../docs/rules/security.md#2-personal-data)): no column for an email, a phone, a photo, pronouns, gender, age or a special category, and `tests/schema.test.ts` fails on one, but for the one it names: `suppression_entries.email`, the address a member blocked, classed `personal`, which erasure empties (gamma-rf-040). Each value carries its provenance.
- **Hashes, never rows**: a rejected candidate or an erased person is an HMAC-SHA-256 under `HASH_SALT`, never a row. The salt is a secret (`# secret`), never in a file or a log; tests set a fixed test salt. A hash is pseudonymous, since whoever holds the salt and a URL can match it, so it is classed `personal`.
- **Isolation**: every query runs in the caller's tenant run through `tenantClient`; `tests/tenancy.test.ts` registers the ten tables in the two-workspace harness and checks every public command with `assertScoped`. A person exists once per workspace, never across. A person's company and a lead's person are foreign keys on `(workspace_id, id)`, so the database refuses a link across workspaces, which the same test proves; the commands still load the row through the tenant client first, for a clean `*_not_found`. The batched commands' two `INSERT … ON CONFLICT` are Prisma's tagged `$queryRaw`, every value a bound parameter, the run's workspace id written into each row and in the conflict's key; `tests/batch.test.ts` writes one URL in two workspaces and finds two persons.
- **Logs**: the platform's PII registry (`piiKeys`) holds the key of every column not classed `none`, so a log line with a person object is redacted; `tests/schema.test.ts` keeps `domain/fields.ts` and the registry in step. An error names the fields at fault, never a value.
- **Who may do what**: `contacts.read` for the person routes, `leads.read` for the lead routes, every role; `contacts.write`, every role's, for a member's edit of a lead's profile fields (lead-fields-edit) and a lead added by hand (lead-manual-create), whose source names the member by user id; `reviews.write` and `reviews.read` for the review routes, `suppression.read` and `suppression.write` for the never-contact list and every addition to it, `leads.approve` for Approve (beta-p2-030), Owner, Admin and Member; `exports.read` for the leads CSV and qualification's golden set, Owner and Admin only; `suppression.remove` for what lifts an exclusion, the DELETE of an entry and gamma-p2-045's list removal, Owner and Admin (gamma-p2-040). The platform's `can` checks the member's role on every request (gamma-p6-010), so a Member's export or removal is 403 `forbidden` (the api's `tests/roles.test.ts`), and the screen hides Remove from a Member. A Member still adds to the never-contact list, departing on purpose from F18 §4, where a Member only views suppression: an addition can only stop sends and no entry is ever deleted, so a Member who hears "stop contacting me" records it at once, while a lift lets sends start again and is the owner's, with Admin beside them. The routes never answer a provider's member id.
- **Append-only decisions**: no route or command updates or deletes a review decision, and the database refuses `app` an UPDATE (`tests/review.test.ts`); only `erasePerson` deletes them. `contacts.lead_reviewed` carries the ids and the decision, never a text. The status changes (beta-p2-030) are kept the same way: no UPDATE for `app` (`tests/outreach.test.ts`), deleted by `erasePerson` only; `contacts.lead_approved` carries two ids.
- **What leaves**: the routes, to a member of the workspace; a lead's cursor holds its fit score, creation time or review status and its person id, nothing the page does not show. The list's address holds the view's codes only (status, tier, sort, review, outreach), never a person's value. The lead page links the person's URL normalized to `https://linkedin.com/in/<slug>` and nothing else, so no other scheme or host reaches an `href`. The list links a signal source's `url`, which the commands take as an https URL only, in a new tab with `rel="noreferrer"`; that URL, a post's, names its author, as signals' copies do, and the column `sources` keeps its class `none` until the platform's PII registry holds its key (an open question of fix-lead-source-post). The Export's file lives in the tab under a blob URL for 40 seconds. No network call, no AI call.
- **The leads CSV** (alpha-p9-050), a way for data to leave: the workspace's own leads, read in runs of the request's workspace, to a member with `exports.read`, never stored. Its columns are the list's business fields, the lead's decision and the latest review with the tester's words; a column that reads a field `domain/fields.ts` classes `personal` is never written. Every cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return starts with an apostrophe (`domain/export/csv.ts`), so a spreadsheet shows it and never runs it. No log line or span carries a cell.
- **Suppression** (beta-p2-010), the gate every outbound path asks:
  - Hashes only in the match: `suppressionOf` and `suppressedAt` compare the person's profile hash, their address hashes (gamma-rf-040) and their company's hashes with the entries' `hash`, never a raw value, so an entry holds after erasure has emptied its `linkedin_url` or its `email`. The routes never answer a hash.
  - No cache: each call reads the person, their company and the entries in the caller's run, so an entry added a moment before is seen by the next check (architecture §7.6).
  - Fail closed: an id of no person of the workspace, or one off the id rules, answers suppressed (`person_not_found`), never allowed.
  - An opt-out stays, on every channel: the command refuses its removal (409 `suppression_not_removable`) and an opt-out on one channel (`contacts_input_invalid`), and the CHECKs `suppression_entries_opt_out_kept` and `suppression_entries_opt_out_every_channel` refuse a direct update of its `removed_at` or its `channel`. `app` holds no DELETE on the table (gamma-p2-040, `tests/tenancy.test.ts`): no entry is ever deleted.
  - A read with no channel counts every entry, so a caller that passes none fails toward refusing; a read on a channel counts that channel's entries and every channel's (gamma-p2-040).
  - `contacts.suppression_added` carries the entry's id, layer and channel, never a value. The list answers a member the entries' URLs, domains and addresses, and the name of the person or company of the workspace each names, an address's the person who holds its hash.
  - Approve (beta-p2-030) asks the check as a new enrollment in its run and answers a refusal's reason, a code (`person_suppressed`); an entry moves the leads it holds to `suppressed` in its own transaction, so the two commit together.
- **A person without a LinkedIn profile** (gamma-rf-050): `upsertPersonFromSource` takes an address beside the URL and keeps its HMAC only, as `recordPersonEmail` does; a person exists once per workspace by their keys ([security §1](../../../../docs/rules/security.md#1-red-lines)), and an address and a URL that name two persons are `person_conflict`, nothing written, never a merge. Their never-contact entries are on their address hashes with no address (`email` null), so the list shows their name and no address. Their erasure (`erasePerson`, privacy's `--email`) writes their address hashes as `erased`, and its `hash`, which privacy's log keeps, is the first address's. The commands and the routes answer no address; an error names the field (`profile.email`, `address`), never the value.
- **Email addresses** (gamma-rf-040): contacts keeps the HMAC of each address a person holds (`person_email_hashes`), never the address, which stays enrichment's (`contact_points`); contacts never imports enrichment. One address is one person's: the key is `(workspace_id, hash)`, `app` holds no UPDATE on the table (`tests/tenancy.test.ts`), so a hash never moves to another person, and `recordPersonEmail` writes nothing for an address another person holds or an erased person left (`other_person`). `erasePerson` deletes the person's rows, counted, writes each hash as `erased` with the URL's (not on the 30-day rule's path), and empties the address of the entries on them, which keep their hash and still match. The foreign key to `persons` restricts a delete, so an erasure and a record of the same person at once end in an error (a key violation or a detected deadlock), never a hash without its person.
- **An exclusion list's file** (gamma-p2-045), the module's one upload, read as discovery's import is read ([discovery: security](../../discovery/docs/security.md)): outside the request's run (`whytide:own-runs`), in the workspace the host's guard resolved, never one the file names. `api/multipart.ts` takes `multipart/form-data` with one part, the file, named `*.csv`, read with busboy as it arrives, and counts the body's bytes against twice `EXCLUSIONS_IMPORT_MAX_BYTES`, the whole within two minutes; a field or a second part is refused. `domain/exclusions/csv.ts` refuses a ZIP signature (an .xlsx), a NUL byte and what is not UTF-8 before csv-parse sees a byte, parses with no cast, `on_record`, `raw` or `info`, records of 64 KiB at most, and stops at the first byte or row past a limit, which ends the parser and the request's reading, the answer closing the connection. A cell is never evaluated: one that starts with `=`, `+`, `-` or `@` is an invalid row, as is an email address or a URL with a path. The file is not stored; the answer, the logs, the errors and the event hold record numbers, codes, counts and ids, never a cell; the list keeps the file's name. One run writes the list, its entries and the leads they move, all or nothing, so a refused or failed file leaves no list and no entry. The companies' read is a tagged `$queryRaw`, the domains a bound array, `workspace_id` written out. `app` holds no DELETE on `exclusion_lists`; a list is removed as its entries are, by `removed_at`. No network call.
- **Shared companies** (gamma-rf-010), the module's one read across organizations:
  - Shared: a company's facts, keys and vendors' ids from a class in `CONTACTS_SHARED_FACT_SOURCES` (`open_data` and `website` by default; `web_search` and `data_vendor` allowed, a vendor's terms the owner's to check) go to `companies`, which every organization reads. It has no name column and none naming a workspace, an organization, a user or a run, and no person data (`tests/schema.test.ts`).
  - Never shared: a value read through a customer's LinkedIn account (`linkedin`), an import's, a member's or the AI's (`ai_inferred`). The code routes by the stamp's class, and the CHECK `companies_field_provenance_source` refuses any other class whatever the code does (`tests/companies.test.ts`, with the owner's client).
  - The key that makes a shared company never leaves its organization: it is stored there with no stamp, whatever class brought it, and `refreshCompany` copies a key down from the shared company only when it carries a stamp there, a shared class's; the organization's own workspaces copy it from the group's row (`tests/tenancy.test.ts`, "the key that made a shared company never leaves its organization").
  - The group's row (`group_companies`) has no `workspace_id`, so the tenant client does not scope it: every query names the run's sharing group (tenancy's `sharingGroupOf()`), never an id a caller gives, and only `domain/companies.ts` and `domain/companies/` name the two tables (`tests/schema.test.ts` reads the sources). `tests/tenancy.test.ts` reads both ways across two organizations.
  - Keys reach a workspace only by a write to its own row (the link, `upsertCompany`, `refreshCompany`), and suppression reads that row alone, so the never-contact check and the email lookup read the same keys.
  - Nothing is deleted: `app` holds no DELETE on the two tables. A one-person company's facts that were shared before its headcount was known stay shared; from then on its facts go to the group's row.
