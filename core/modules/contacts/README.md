# contacts

The people and companies of a workspace ([architecture §7.3](../../../docs/architecture.md#73-signals-people-and-leads)): a person exists once per workspace, by its normalized LinkedIn URL, with business profile fields only, each carrying where it came from and when; a company it may belong to; the salted hashes that are all that is left of a rejected candidate or an erased person; and each person's one lead, where it came from, what qualification decided, the tester's review decisions, and its outreach status with each change to it (beta-p2-030). Imports (alpha-p5-040) and signals (alpha-p8-030) write people through `upsertPersonFromSource` and leads through `createLeadForPerson`, or a chunk of each through `upsertPersonsFromSource` and `createLeadsForPersons` (alpha-p10-080); qualification (alpha-p6-040) fills the lead.

- **Owns:** `persons`, `workspace_companies`, `person_hashes`, `leads`, `review_decisions`, `suppression_entries` and `lead_status_changes`, and the global `companies` and `group_companies` (gamma-rf-010, "Shared companies"), in `core/packages/db/prisma/schema/contacts.prisma` ([docs/data.md](docs/data.md)), the person, lead, review, Approve, export and never-contact routes, and the lead list and lead page screens with the lead page's slots and its review panel.
- **Public interface:** `index.ts`, below.
- **Depends on:** `platform`, `db`; `@nestjs/common` in `api/` only; `@whytide/ui`, `next` (its `notFound`), `next-intl` and `react` in `ui/`, which the web host compiles.
- **Reviewers:** the owners of this module; five tables hold personal data ([docs/security.md](docs/security.md)).

## Routes

A member's session and `contacts.read`; the schemas are `schemas/persons.ts`, the requests `api-calls/alpha-p5-010-persons-and-companies.http`.
- `GET /v1/workspaces/{workspaceId}/contacts/persons?limit&cursor`: `{ persons, nextCursor }`, newest first, `limit` 1 to 100 (50); `cursor` is the `nextCursor` of the page before.
- `GET /v1/workspaces/{workspaceId}/contacts/persons/{id}`: the business fields and `provenance`, `{ field: { source, provider, at } }`; 404 `person_not_found`. A provider's member id is never answered.

The lead routes need `leads.read`; the schemas are `schemas/leads.ts`, the requests `api-calls/alpha-p5-020-leads.http`.
- `GET /v1/workspaces/{workspaceId}/contacts/leads?source&status&tier&review&outreach&sort&limit&cursor`: `{ leads, nextCursor }`, each lead's fields (`outreachStatus` and `outreachReason` among them, beta-p2-030) with `person`, its name, title, company, `companyId` and URL, and `reviewReasonCode`, the latest decision's code when it is Not a fit; `sort` `fit` (the default), `newest` or `unreviewed_first`, `limit` 1 to 100 (50); 400 `contacts_input_invalid` for a cursor that is not the page before's in the same sort, `validation_failed` for an `outreach` off the list. `source`, a source's `ref` (an import job's id, a signal source's id), keeps the leads whose `sources` hold an entry of it, any kind, with every filter, sort and cursor as without it (csv-import-sources: `sources @> [{ ref }]`, a bound parameter; no index, a workspace's leads are few); a ref of letters, digits and `_`, 64 at most, else `validation_failed`, here and on the three routes below; its requests in `api-calls/csv-import-sources-view.http`. The unreviewed-first requests, this and the neighbours', are in `api-calls/alpha-p10-080-contacts-polish.http`.
- `GET /v1/workspaces/{workspaceId}/contacts/leads/counts?source`: `{ counts }`, how many of the workspace's leads, or of the leads of `source`, are in each of the six statuses, every status named, from one grouped query (alpha-p6-050; its request in `api-calls/alpha-p6-050-lead-list.http`).
- `GET /v1/workspaces/{workspaceId}/contacts/leads/{personId}`: the lead's fields with `person`, as the person route answers it, and `suppression` (beta-p2-020): null while the person may be contacted, else `{ reason }`, `opted_out`, `never_contact_person` or `never_contact_company`, the first that applies (`suppressionOf` with `newEnrollment: false`, so a recent touch is none); 404 `lead_not_found`, also for another workspace's person.
- `GET /v1/workspaces/{workspaceId}/contacts/leads/{personId}/neighbours?source&status&tier&review&outreach&sort`: `{ previous, next }`, as `leadNeighbours` answers them, for the lead page (alpha-p6-060; its request in `api-calls/alpha-p6-060-lead-page.http`); 404 `lead_not_found`, also for another workspace's person.

Approve (beta-p2-030) needs `leads.approve`, its changes `leads.read`; the schemas are `schemas/leads.ts`, the requests `api-calls/beta-p2-030-approve-and-status.http`.
- `POST /v1/workspaces/{workspaceId}/contacts/leads/{personId}/approve`, with an `Idempotency-Key`: 200 `{ outreachStatus: "approved" }`, the lead approved and `contacts.lead_approved` published, again from `approved` with no second change; the same key again answers the same with `Idempotent-Replayed: true` and runs nothing. 409 `lead_in_outreach` from `in_campaign`, `replied` or `finished`, or from `suppressed` after a campaign; 409 `person_suppressed` with `details.reason`, the check's for a new enrollment, `recently_contacted` included, with `details.days`, the `CONTACTS_RECENT_TOUCH_DAYS` configured; 404 `lead_not_found`, also for another workspace's person; 400 `idempotency_key_required` without a key.
- `GET /v1/workspaces/{workspaceId}/contacts/leads/{personId}/status-changes`: `{ changes }`, the hundred newest, newest first, each `id`, `personId`, `fromStatus`, `toStatus`, `templateId`, `reason`, `actorType`, `actorId` and `createdAt`; 404 `lead_not_found`.

A member's edit of the lead's person (lead-fields-edit) needs `contacts.write`, every role's; the schema is `schemas/leads.ts`, the request `api-calls/lead-fields-edit.http`, the test the api host's `tests/contacts-lead-fields.test.ts`.
- `PATCH /v1/workspaces/{workspaceId}/contacts/leads/{personId} { firstName?, lastName?, headline?, title?, companyName?, locationText? }`: 200 and the lead as `GET …/leads/{personId}` answers it. Each value is trimmed and within the LinkedIn port's limit (`PERSON_FIELD_MAX`: 100 for a name, 300 for the others); an empty one clears the field, but the first name. ## Settings

`HASH_SALT`, in the `modules/contacts` block of `deploy/.env.example`, a secret: the key of the hashes, 32 characters or more. A host starts without it, and the first command that hashes fails with `hash_salt_missing` (500). Keep it for good: under another key no earlier hash matches, erased people's included.

`EXCLUSIONS_IMPORT_MAX_ROWS` (5,000; 1 to 10,000) and `EXCLUSIONS_IMPORT_MAX_BYTES` (1 MiB, 1,048,576; at most 5 MiB), in the same block (gamma-p2-045): the data rows and the bytes an exclusion list's file may hold; the next one stops the reading. The request's body may hold twice the bytes, so a file a little over is told so.

`CONTACTS_RECENT_TOUCH_DAYS` (90, an integer of 1 or more with no maximum; `settings.ts`'s `touchSettings`, the default `RECENT_TOUCH_DAYS` in `domain/suppression/constants.ts`), in the same block (env-settings-a): a person contacted less than this many days ago is refused a new enrollment (`recently_contacted`), Approve included, whose refusal answers the days for the lead page. **A send-safety case covers it (the worker's `tests/safety/withdrawal.test.ts`): raising it is safe; lowering it lets the same person be contacted again sooner.** Unset or empty, 90; a value that is not an integer of 1 or more stops the api's and the worker's start with `config_invalid` naming it. It is read once, as the module loads: **a changed value needs an api and worker restart**. `tests/settings.test.ts` sets 120 and tries the values off its range.

`CONTACTS_SHARED_FACT_SOURCES`, in the same block (gamma-rf-010): the source classes whose company facts go to the shared company, which every organization reads, comma-separated, of `open_data`, `website`, `web_search` and `data_vendor`; `open_data,website` when unset, none when empty. Any other class, or one twice, stops the host at start; `linkedin`, `import`, `member` and `ai_inferred` are never shared ("Shared companies").

## Decided here

- `hashOf` is HMAC-SHA-256 keyed by `HASH_SALT`, rather than SHA-256 over the salt and the value: the standard keyed hash, with no ambiguity where the two meet. Its input names its kind, `url:<normalized URL>` or `pid:<provider id>` (alpha-p5-020), so the two never share a hash; erased hashes live for good, so the format is fixed from the first row.
- One hash row per value and workspace: a later rejection adds its reasons and keeps the first expiry; `erased` replaces a `rejected_candidate` and never expires (the CHECK `person_hashes_expiry`).
- `location_country` is read here from `location_text`: its last comma-separated part, or the whole, by the English country names of Node's ICU and a few other spellings (`domain/countries.ts`); no new dependency.
- The profile also takes a full `name`, split into first and last when neither is given, for imports.
- Persons link their company, and leads their person, by `(workspace_id, id)` (alpha-p5-020): the database refuses a link across workspaces. The company key restricts a delete, since `SET NULL` would empty `workspace_id` too; no command deletes a company.
- A lead (alpha-p5-020) is keyed on its person and created `pending`. `applyQualification` replaces the whole decision, so no score, tier or reason outlives the status it came with; `newest` sorts by the lead's `created_at`, kept to the millisecond so that the cursor matches the row exactly; a list without `status` shows every status.
- `why` holds up to three `{ key, params }` bullets (alpha-p6-030's shape) and is classed `business_contact`, since its values may quote the profile: the log redaction and the workflow-input lint treat it as the profile's fields.
- The lead list (alpha-p6-050) shows a decided lead's `updated_at` under Qualified, since `leads` has no time of qualification; that header sorts by `newest`, the api's `created_at`. A why bullet's words come from its key at run time (`useKeyText` of `@whytide/ui`), as an error code's do: the module that writes the key owns its message, and a key missing from the bundle shows nothing. An `ai_failed` lead's reason is `contacts.leads.reason.ai_failed`, a select over callAgent's reasons (`invalid`, `empty`, `length`, `content-filter`, `gates`); any other shows the plain sentence. The page names the document with React's `<title>`, since the generated route re-exports the page's default alone and a `metadata` export would not reach Next.js.
- The lead page (alpha-p6-060) keeps the list's view in its URL rather than in the browser's storage: a link to a lead opens the same neighbours for anyone, and the way back finds the list as it was left, its page aside. Without a view in the URL, the page takes the list's first one, qualified leads by fit, for the neighbours and the way back. The neighbours are two reads of one row each, by the list's own order and cursor, rather than a page of the list around the lead.
- The lead page's slots are names in `ui/lead/slots.ts`, which the route generator reads, rather than a registry at run time: a panel in an unknown slot fails the build, and the page imports no module of the panels. The panels render on the server, so that a panel reads its own module's api as the member.
- Review decisions (alpha-p9-040) are append-only in the database too: `app` has no UPDATE on `review_decisions`, and their key to the lead restricts a delete, so `erasePerson` deletes them first, by person. The lead's `review_status` and `reviewed_at` are set by a raw update that leaves `updated_at`, the list's time of qualification, and never lets an earlier decision replace a later one. The event is `contacts.lead_reviewed`, since an event's name starts with its module's. Good lead needs its text, as the task decided, a field of the other kind is `contacts_input_invalid`, and a blank text is none. The summary adds `top20.reviewed`, so that the screen can tell a final rate from a partial one; its top twenty follow the list's order, ties by descending person id.
- The leads CSV (alpha-p9-050) holds the list's columns under fixed names, not words, so that a formula or a script reads them in any language. Codes are written as the api answers them (`qualified`, `hot`, `not_a_fit`); the why bullets and a Not a fit's reason, which the list shows in words, are worded in English by the platform's messages, from the keys the lead holds, so no module is imported: a bullet by its key (qualification's), a reason by `contacts.review.code.<code>`, as the review panel says it. The order is the list's by fit, whatever its sort; the filters are the list's. The PII registry (`domain/fields.ts`) decides the columns: one that reads a `personal` field is never written (alpha's columns read none).
- The export opens a run per page of a hundred leads on the module's own `app` client (`domain/store.ts`, `whytide:own-runs`), rather than the request's run, which a slow download would hold past its five seconds. The Export button reads the file through the api's client, rather than a link, as every screen reads the api, and names it as the answer's `Content-Disposition` does.
- `latestReviews({ week })` keeps a lead in the week of its latest decision only, so that a lead decided again later carries its newest label, once, in the golden set.
- The batched commands (alpha-p10-080) apply the one-row commands' rules (`mergeInto`, `mergeSource`) to a chunk in memory and write it in one `INSERT … ON CONFLICT`. A person's row is updated only when its id is the one the chunk read (`WHERE persons.id = EXCLUDED.id`): a URL another run inserted meanwhile is read and merged again, three times at most. A lead's missing sources are appended within the statement, by kind and ref, so that two runs never lose each other's, and its stored ones take the label and URL the chunk brings for them.
- A lead's source carries its label and URL (fix-lead-source-post) rather than contacts reading them: signals depends on contacts, so contacts never reads signals' sources. A source arriving again with them renames its entry, so a renamed source shows its new name on its next lead; as an added source does, a rename moves `updated_at`. The list shows Imported for an import, whatever it carries, a label without a URL as text, and the source with the latest `at` first.
- Unreviewed first (alpha-p10-080) orders by `review_status`, none first, then the enum's order (Good lead, Not a fit), then as `fit` does; its cursor holds the status and the fit. The Review column is no sort header, the Sort select asks for it, so the headers keep their Tab order.
- The list writes its view with `history.pushState`, which Next.js's router takes in: a change renders nothing on the server, and `useSearchParams` sees Back and Forward, on which the list reads the view again. The list listens to `popstate` too: after a reload, Next.js 16.4 drops a second Back pressed while it still reads the first, its search params keeping the old view as the address moves.
- The lead page reads the lead before its loading state shows, so that the person's name titles the document from the server's first bytes: React leaves a title inside a Suspense fallback out of the server's page.
- The lead page's not-found state is the page's own rather than `notFound()`: a module adds no `not-found.tsx` to the host's routes, and the state keeps the way back to the list's view.
- Export keeps the file's blob URL for 40 seconds, FileSaver.js's delay, rather than revoking it on the next tick, before Firefox or Safari may have read it.
- The never-contact list (beta-p2-010) has `layer` in its active key, which the data model's key has not, so that a blocked person can also opt out and removing the block leaves the opt-out in force. The key is a partial unique index the migration writes, and an add is `INSERT … ON CONFLICT DO NOTHING` on it followed by a read of the active entry, so two runs adding one entry at once keep one row and publish one event.
- No entry on a member id: every person has a required `linkedin_url`, and a raw member id would need a PII registry key the platform does not have. A company is matched by its domain and its page as they are now: `suppressedAt` reads the person's company of now, since no history of companies is kept.
- A check never fails open: an unknown person, or an id off the rules, is the answer `person_not_found` rather than an error; `lastTouchAt` and `recordTouch`, which a caller cannot act on, throw it. `recordTouch` is one `GREATEST` update that leaves `updated_at`, the profile's time, as the review status does.
- `erasePerson` empties the URL of the person's entries without counting them, so the deletion script's counts keep their shape; the entries, on the profile's hash, still match the person imported again.
- The outreach status (beta-p2-030) is `outreach_status` and `outreach_reason`, not the data model's `status` and `status_reason`: `leads.status_reason` is qualification's, and `status` the list's and the CSV's qualification filter. A raw update writes it, as the review status's, so the Qualified date (`updated_at`) stays; `outreach_reason` is set on every change, null for none, and the lead answers it beside `outreachStatus`. The change's key to the lead restricts a delete, as a decision's does, so `erasePerson` and the e2e seed route delete the changes first; the script's counts leave them out and keep their shape. Two CHECKs: a user's change names its user and the system's none (`lead_status_changes_actor`), and a change changes the status (`lead_status_changes_change`).
- Approve checks the status before the never-contact list, so a lead in outreach answers `lead_in_outreach` whatever the list says. From `suppressed` it needs the check's allow and no change to `in_campaign` on record, read from the changes, so a person is enrolled once at most; removing an entry leaves the lead `suppressed` until then. The actor and `approvedBy` are the run's principal, a user, or the system for a service. Again from `approved`, it publishes again and records nothing.
- An entry moves the leads it holds to `suppressed` on every add, an existing entry's too, in its own transaction and in person-id order, so two adds lock leads in one order; the reason is the check's word, the actor the entry's creator, else the system.
- The lead page reads linkedin's accounts with the neighbours through the web's API client, and a failed read fails the page as theirs does; the list's row menu offers Approve without that read, since campaigns ends an enrollment without a sender with `no_sender`. The suppressed message takes the days from the refusal's `details.days`, the setting's, never a number of the screen's; without them a recent touch reads as the check's generic refusal. The `outreach` slot is the list's last.
- Approve shares the never-contact blocks' row menu and toast (beta-p2-020), first in the menu, rather than a column of its own. A block marks the rows it holds `suppressed` until the list's next read, and the lead page shows the status of its latest read over Approve's answer, so a block's `router.refresh()` shows Blocked. The header leaves out the outreach badge when it would say Blocked beside the never-contact badge.

Lifting an entry is its own action, `suppression.remove`, the Owner's and Admin's (gamma-p2-040), since a lift lets sends start again.
- The lead's audience (gamma-p5-055) is `leads.icp_id_scored`, an ICP's id in a plain column with no key to icp's table, since contacts imports nothing of icp. No backfill: null is a decision made before audiences, the default audience's, which only a read with `isDefault` takes. `leadsPendingQualification` refuses `isDefault` without `icpId`, which would read every audience's leads, and `icpId` without `icpVersion`, which names no version to compare, rather than guess. `applyQualification` takes `icpId` without its version too, as it takes every field on its own. The lead routes answer `icpIdScored` with the lead's other fields, and `schemas/leads.ts` names it.

A read with no channel counts every entry, the strictest answer, so the callers that pass none (enrolling, Approve, the lead page, and campaigns until gamma-p2-050) refuse whoever has any entry. The stops on every channel decide before `recently_contacted` and before an entry on one channel, so an answer on `all` means every channel is closed. The answer carries `channel` only when the caller asked with one: a caller without one keeps the answer it had, which campaigns' gate stores and the worker's safety case compares.

The relationship is not in the active key: a domain excluded as a customer and then as a competitor answers the first entry.

- An entry on one channel moves no lead to `suppressed`: the other channel stays open, and the check refuses the stopped channel all the same.
- `suppressionsOf` is four reads whatever the count: the persons with `last_touch_at`, their address hashes (gamma-rf-040; none for a batch with no person), their companies, then the active entries on their hashes; `suppressionOf` is its batch of one, so the two never differ.
- A member's value (lead-fields-edit) is the source class `member` in `field_provenance`, which `mergeFields` never lets a source's value replace, however late, so a correction outlives the next fetch, a batched one too; only another member's edit changes it. A cleared field keeps the stamp without a value, so no source fills it again. Save sends only the fields changed and the command stamps only a changed value, so a field the member did not touch keeps its source. The edit locks the person's row, so two edits queue; a source's merge reads without that lock (as before), so a fetch writing at the very moment of an edit may still write over it.
- The edit's rules are the command's (`editPersonInput`), not the route's body schema, which only names the six fields: a refusal is then `contacts_input_invalid`, worded on the field at fault. The edit re-scores nothing: it is no source, and a new judgement is the member's call, through Re-score.
- A lead added by hand (lead-manual-create) is the source kind `manual`, its `ref` the member's user id, without a label or URL: the list says Added manually, the export `manual`, signals' panel Added manually. Qualification reads no source kind, so only those three name it.

- An empty optional field is left out, not cleared as Edit clears it: the dialog never empties a source's value, and a field left empty takes no stamp, so a later fetch fills it. The URL of a new person takes the `member` stamp: the member typed it.
- The person's row is locked (`FOR UPDATE`) before the erased and lead checks, so two adds of one URL queue and the second is `lead_exists`, and an erasure under way is waited for, then refused. Two adds of a new URL at once both find no row: the second fails on the unique URL (500), and Add again answers `lead_exists` (docs/runbook.md). An import that writes the person's lead meanwhile takes no lock; `createLeadForPerson` then answers `created: false`, and the add rolls back, `lead_exists`.

- The body schema requires the URL alone; a first name left out is the command's `contacts_input_invalid` naming `firstName`, so the dialog shows it under the field, as Edit's refusals show.
- title-check-ai: the decisions a rule qualification retired are qualification's to name; contacts selects them by its own columns, `hard_filter_reason` and `current_score_snapshot_id`, with the decisions at an older version and of the same audience, and never reads qualification's tables. The migration `contacts_title_hashes_reset` deletes, once, the `rejected_candidate` hashes whose only reason is `title_mismatch`, which no filter writes anymore: those persons are processed when they engage again. A hash with another reason beside it stays, as an erased one does; on a database without such rows it deletes none. A hash the previous release writes before its worker stops is not deleted: it expires after its 90 days.
- An exclusion list (gamma-p2-045) is one import, all or nothing: the list, its entries and the leads they move are one run. Its timeout is `IMPORT_RUN_TIMEOUT_MS`, 60 s, not a request's 5 s: 10,000 rows took 4.6 s with no lead to move and 13.2 s with 1,000 leads to move on a loaded laptop (2026-11-13), and the leads a file moves have no bound but the workspace's, so the maximum stays 10,000.

A duplicate stays with its entry; since review-gaps the list records it (`exclusion_list_domains`), so removing the entry's list moves the entry under it.

- `csv` is the import's source alone: `ENTRY_SOURCES` keeps an add by hand and an opt-out off it, and the CHECK `suppression_entries_csv_list` ties a `csv` entry to its list and only a `csv` entry to one. No Idempotency-Key on the upload: it spends no credit and calls no provider, and the same file again is a list of duplicates.
- A list's name is the file's name; no `name` column is read (an open question). A row's number is its record's, as discovery's reader counts: an empty line is no record.
- 2026-11-13, review-gaps: every domain a list names is a row of `exclusion_list_domains` (the list, the domain's hash as the entries hold it), written in the import's run, one statement per chunk before the entries': its duplicates are recorded too, held by an active entry or twice in the file. A removal moves each of the list's active entries whose hash another active list names under the earliest created of them, taking its relationship, with no event (the leads are suppressed already), and removes only the rest; both are set-based statements, not a query per entry. The migration fills the table from each `csv` entry's hash with its list, removed ones included, so a list imported before keeps the domains it added; its duplicates were never stored, so such a list still lifts, on its removal, a domain only its duplicate named.
- A hand add (`addSuppression`, `manual`) that meets an active `csv` entry takes it over: `source` `manual`, no list, `created_by` the adder, the rest as stored (its relationship and `created_at` too), so the CHECK `suppression_entries_csv_list` holds and no list's removal touches it again; `created: false` and no event, as for any existing entry. A hand removal (`removeSuppression`) still lifts an entry whatever list names its domain: a person's explicit act, which a later import of the domain undoes with a new entry.
- Concurrency: an import and a removal take the workspace's transaction-scoped advisory lock first (`EXCLUSIONS_LOCK`, `pg_advisory_xact_lock`), so a removal never decides "no other list names it" while an import that named the domain is uncommitted, nor an import counts a duplicate of an entry a removal is lifting; the lock ends with the run, a rolled-back one included. A hand add's takeover takes no advisory lock, so it never waits up to a minute behind an import: it is one update of the entry's row conditional on an active `csv` entry, and the removal's updates are conditional on the row too, so whichever writes the row first wins and the other, once it commits, reads it as committed: a takeover after a removal lifted the entry matches nothing and writes a new entry, and a removal after a takeover skips it. A removal waiting on an import waits in its own run (`REMOVAL_RUN_TIMEOUT_MS`, 75 s: the import's 60 s and 15 s for itself), not the request's 5 s, then removes with the import's list in sight; past it the run is rolled back whole and the route answers 500.
- gamma-rf-010, the shared companies ("Shared companies"): the CHECK on `companies.field_provenance` lists the four classes that may be shared rather than the four that never are, so a new class is refused until someone allows it. An empty `CONTACTS_SHARED_FACT_SOURCES` shares nothing and an unset one is the default, although the platform reads an empty value as unset: the setting reads its own value. A workspace tenancy has no row for (a test's made-up id) has no sharing group, and its companies read and write their own columns as before.

Linking a row therefore locks the shared company's row, as any write to its layers does.

The script links one row per tenant run, so a run holds one company's locks. A run that links several new companies (signals' chunk) holds their key locks until it ends, so two such runs meeting the same companies in opposite orders deadlock and Postgres ends one, which its activity retries.
- gamma-rf-040, a block on an email address: an `email` entry is the person's own, matched by `hashOf("email", address)` of the address trimmed and in lower case, nothing else folded, so `jane+news@` and `j.ane@` are other addresses than `jane@`. `normalizeEmail` checks a shape, not RFC 5322: letters, digits and `_'+-` in dot-separated runs, `@`, a host of two labels or more whose last starts with a letter, 254 characters at most; a quoted local part, an IP host or a non-ASCII letter is no address (`suppression_target_invalid`).

Its key `(workspace_id, hash)` keeps an address on one person, and `app` holds no UPDATE on it, so a hash never moves; the erasure deletes the rows.

It answers `suppressed` on an entry on every channel or on `email`, never on `linkedin` alone, since an address is kept for email. A hash that meets an older entry on every channel moves the lead with no event; the gate's own check exits the enrollment at the person's next step.

- The column test's no-email rule names one exception, `suppression_entries.email`, which must be classed `personal`: the list shows the address a member typed, as it shows a profile's URL, and erasure empties it.
- The erasure's counts gain `person_email_hashes`, first among contacts', so privacy's log has one more key; the entries' addresses are emptied uncounted, as their URLs are.
- `@whytide/contacts/testing` exports `addSuppression` for enrichment's tests, so the command stays the routes' only in the public index.
- gamma-rf-050, a person without a LinkedIn profile: `persons.linkedin_url` is nullable, and a person has a URL, an address's hash or both, kept in code: `upsertPersonFromSource` is the one command that creates a person, in one run with their key, and refuses neither. `PersonProfile` is a union, so the compiler asks a caller for one key at least. - A conflict writes nothing: the address is recorded before the update, and a person the call itself created is deleted before `person_conflict` is thrown, so the caller's run commits no half. An address the person already holds is not recorded again. `recordEmailHash` is `recordPersonEmail`'s write without its input checks, so the upsert records a hash it computed once.

## Enrichment's hold

gamma-en-040. A new lead waits a while before its first judgement, so that enrichment can fill its company's fields and its country first. The hold is contacts' own: with enrichment absent or off, a lead waits the setting at most and is then judged as before.

- **The setting:** `CONTACTS_ENRICHMENT_HOLD_MINUTES`, in the `modules/contacts` block of `deploy/.env.example`: an integer from 0 to 1,440, 60 by default; 0 is no hold. Tests set it with `useEnrichmentHold(minutes)` of `@whytide/contacts/testing` (`undefined` goes back to the setting).
- **The hold:** `leads.enrichment_hold_until`, now plus the setting, written by the write that creates the lead: `createLeadForPerson`, `createLeadsForPersons` and so `createLeadByMember`. A lead that exists keeps its hold; leads created before the migration have none and are judged as before (no backfill).
- **The wait:** `leadsPendingQualification` leaves out a `pending` lead held past now, so qualification's batch and its tick's `hasWork` do too (`domain/hold.ts`, `notHeld`). Only a first judgement waits: `applyQualification` ends the hold, so a decided lead, a member's new assessment and the re-score never meet one.
- **Enrichment's side:** `leadsHeldForEnrichment({ limit })` reads the held leads, oldest first, and `releaseEnrichmentHold(personIds)` ends their hold once enrichment is done, whatever its outcome; a lead nobody releases is judged once its hold ends.
- **Provenance:** enrichment's values carry their source class (`open_data`, `data_vendor`, `web_search`, `ai_inferred`) and the adapter's name as the provider; the lead page shows the class in words (`contacts.provenance.source.*`), never the provider's name (RB-7.3.2). A member's value outranks every source's, as before.
- **Decided here:** the hold's index is a partial one on `(workspace_id, enrichment_hold_until)`, held leads only, written in the migration; the reader orders by `created_at`, the leads' age, not by the hold's end, which a changed setting can reorder. The release keeps `updated_at`, the list's time of qualification, as the review and outreach statuses do. The provider's name and icp's country list are copies (providers' `ADAPTER_NAME`, icp's `COUNTRIES`), since contacts depends on neither; `tests/provenance.test.ts` reads both files and keeps the copies equal. The lead route's answer leaves the hold out.

## The place list

gamma-en-075. A location such as "Boston, MA" or "Greater Munich Metropolitan Area" gets its country from a list of places shipped with the module; what the list cannot tell, enrichment's `country-ai` asks the AI (core/modules/enrichment README "Sources").

- **The list:** `data/places.tsv.gz`, about 420 KB: GeoNames' 34,215 places of 15,000 people or more, each with its name, its ASCII name, its country, its first-level division and its population, and the 3,865 divisions with their codes and names. Its first line names the source and the download date. It loads once per process, when `countryOf` is first called (`domain/places.ts`), from the module's folder, whether the sources or `dist/` run.
- **The reading** (`domain/countries.ts`): the text is cleaned ("Greater" at the start; "Metropolitan Region", "Metropolitan Area", "Metro Area", "Bay Area", "Area" or "Region" at the end), then its comma-separated parts are read from the last to the first. A country's name (or its code, in capitals) and a division's name (or a US state's or Canadian province's two-letter code, a fixed table) are the regions a part may be; an earlier part is looked for only within them. A city's name ends the reading with the country of the largest place of that name within them, unless a place of that name in another country has more than a tenth of its people (`CITY_RIVAL_SHARE`): then none. The regions left give the country when they lie in one country. A part naming nothing, or only "Remote", "EMEA" and the like (`NO_PLACE_WORDS`), is passed over. So "Boston, MA" and "Atlanta, Georgia" are US, "Toronto, ON" CA, "Lyon" FR; "Cambridge" (GB and US) and "Georgia" alone (a country and a US state) stay empty.
- **When:** at a person's creation and whenever a source or a member brings a new location, as before; the country keeps the location's provenance. A source's location the list cannot read keeps the country recorded for the same text (enrichment's, for one), and empties it for a new text.
- **The build:** `pnpm -F contacts places:build <folder> [--date YYYY-MM-DD] [--out <file>]` (`scripts/places-build.ts`) reads `cities15000.txt`, `admin1CodesASCII.txt` and `countryInfo.txt` from the folder, and nothing else, makes no network call, keeps the places and divisions of the countries `countryInfo.txt` lists, and writes the list, the same bytes for the same files. The date is `--date`, else the day the newest file was written. The files come from <https://download.geonames.org/export/dump/>, downloaded by hand, once, with the owner's go; the list is committed as a generated file, and rebuilt only when someone downloads newer files.
- **The backfill:** `pnpm -F contacts countries:backfill [--workspace <id>]` (`cli/countries-backfill.ts`) fills `location_country` for the persons with a location and no country whose location the list can read now, in one workspace or every one, 500 per tenant run (`BACKFILL_BATCH`), with the location's provenance; a country a member set or cleared stays. It prints one line of counts: filled, unread, kept and read.
- **The credit:** the list is GeoNames' data (<https://www.geonames.org/>), under the Creative Commons Attribution 4.0 licence (CC BY 4.0), credited in the repository's `NOTICE.md`.
- **Testing:** `usePlaces(text)` of `@whytide/contacts/testing` reads a list's text in place of the file (`undefined` reads the file again). `tests/countries.test.ts` (the rules, the task's cases on the committed list, a lead's country at once, a recorded country kept), `tests/places-build.test.ts` (the build on three tiny files, under Node's permission model: no network, no other read) and `tests/countries-backfill.test.ts`.
- **Decided here:** two-letter codes count only in capitals ("MA", not "ma"); "Metropolitan Region" joins the dropped words, LinkedIn's for Paris; the no-place words are contacts', so that "Asia", a town in the list, gives no country, and enrichment reads them through `namesNoPlace`; a country name that is also another country's division ("Georgia") is ambiguous on its own; countryInfo.txt only says which countries' places are kept. The backfill lists every workspace through tenancy's `listWorkspaceIds`, a new dependency of the module on `@whytide/tenancy`.

## Shared companies

gamma-rf-010. A company's facts are kept once: every workspace reads what open sources say about it, and an organization's workspaces share what its own accounts and vendors found. The workspace's row keeps the name and the keys, which suppression reads; the facts sit in two layers above it ([docs/concepts.md](docs/concepts.md) "A company's three layers").

- **The layers:** `companies`, the shared company, global, one per LinkedIn page or domain; `group_companies`, the sharing group's row of it, keyed by `(sharing_group_id, company_id)`. The sharing group is tenancy's `sharingGroupOf()`, the run's organization today. Only `domain/companies.ts` and `domain/companies/` name the two tables (`tests/schema.test.ts` reads the sources).
- **The link:** a row links once, to the shared company with its page, else with its domain, made when there is none (`INSERT … ON CONFLICT DO NOTHING`, then read) with that one key and no stamp. At the link, each fact, key and vendor's id the row holds goes where a write with its stamp would put it, with its stamp, the link's key to the group's row, as the shared company holds it already; the row's columns stay as they are. `upsertCompany` and `refreshCompany` link the rows they meet, the script the others.
- **Writes** (`upsertCompany`): a fact, and the vendor's id, goes to the shared company when its stamp's class is in `CONTACTS_SHARED_FACT_SOURCES`, else to the group's row; each layer merges as `mergeFields` does. A key the row gains goes to the shared company when a shared class brought it, the shared company has none and no other holds it, else to the group's row. A one-person company (a headcount of 1, a size whose upper bound is 1, or a company that reads so already) keeps everything on the group's row.
- **Reads** (`getCompany`): the row's id, name and keys; each fact from the layer whose stamp wins, with that stamp; the vendors' ids merged, the group's first. A row not linked reads its own columns.
- **`refreshCompany`:** links the row, then copies down each key it lacks, the group's, else the shared company's when it carries a stamp there (never the key that made it, which has none), unless another company of the workspace holds it. Enrichment's run and lookup start with it, so a workspace asks no source for a fact the instance has.
- **Locks,** always in this order: the workspace's row (`FOR UPDATE`); the link's key locks (`pg_advisory_xact_lock`, the page's, then the domain's); the shared company's row (`FOR UPDATE`), before either layer is written; an offered key's lock, only tried.
- **The script:** `pnpm -F contacts companies:link [--workspace <id>]` (`cli/companies-link.ts`) links every row that has no link, in one workspace or in every one, 500 ids per read (`LINK_BATCH`) and one tenant run per row; safe to run again. It prints one line of counts: linked, without a key, without a group, read. Run it once after the deploy (deploy/README.md).
- **Testing:** `useSharedFactSources(classes)` of `@whytide/contacts/testing` sets the classes for the process (`undefined` goes back to the setting). `tests/companies.test.ts` (the link, the routing, the one-person rule, the race, the CHECK), `tests/tenancy.test.ts` (across organizations, two workspaces of one organization, no DELETE), `tests/schema.test.ts` (the columns, the sources), `tests/companies-link.test.ts` and the worker's `tests/enrichment-run.test.ts`.
