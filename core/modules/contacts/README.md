# contacts

The people and companies of a workspace ([architecture §7.3](../../../docs/architecture.md#73-signals-people-and-leads)): a person exists once per workspace, by its normalized LinkedIn URL, with business profile fields only, each carrying where it came from and when; a company it may belong to; the salted hashes that are all that is left of a rejected candidate or an erased person; and each person's one lead, where it came from, what qualification decided and the tester's review decisions. Imports (alpha-p5-040) and signals (alpha-p8-030) write people through `upsertPersonFromSource` and leads through `createLeadForPerson`, or a chunk of each through `upsertPersonsFromSource` and `createLeadsForPersons` (alpha-p10-080); qualification (alpha-p6-040) fills the lead.

- **Owns:** `persons`, `workspace_companies`, `person_hashes`, `leads` and `review_decisions` in `core/packages/db/prisma/schema/contacts.prisma` ([docs/data.md](docs/data.md)), the person, lead, review and export routes, and the lead list and lead page screens with the lead page's slots and its review panel.
- **Public interface:** `index.ts`, below.
- **Depends on:** `platform`, `db`; `@nestjs/common` in `api/` only; `@whytide/ui`, `next` (its `notFound`), `next-intl` and `react` in `ui/`, which the web host compiles.
- **Reviewers:** the owners of this module; four tables hold personal data ([docs/security.md](docs/security.md)).

## Public interface

Every command and query runs inside the caller's tenant run and opens none: it reads and writes through `tenantClient`, in a route's request run or an import's or a signal's own (core/packages/db README "The tenant transaction and the scoped client").

| | |
|---|---|
| `upsertPersonFromSource({ source, provider, profile })` | `{ person, created }`: the person with the profile's normalized URL, created or merged field by field ([docs/concepts.md](docs/concepts.md)); `source` is `linkedin`, `import` or `website`, `provider` is `unipile`, `csv` or `null`; `linkedin_url_invalid` (400); `person_erased` (409) when the URL or the provider id has an erased hash, and nothing is written |
| `upsertPersonsFromSource(inputs)` | an answer per input, in their order: `{ person, created }` as `upsertPersonFromSource` answers, or `{ code }` where it would throw (`contacts_input_invalid`, `linkedin_url_invalid`, `person_erased`), that input writing nothing; one query of the erased hashes, one of the stored persons and one `INSERT … ON CONFLICT` for the chunk. Inputs with one URL merge in their order, and each answers the person as the call leaves it; a person another run creates with a URL meanwhile is read and merged again |
| `getPerson(personId)` | the person, or `person_not_found` (404) |
| `listPersons({ limit, cursor? })` | a page, newest first: `{ persons, nextCursor }` |
| `findPersonByLinkedinUrl(url)` | the person with the URL once normalized, or null: the deletion script's lookup; `linkedin_url_invalid` (400) |
| `erasePerson(personId)` | deletes the person, its lead and its review decisions and writes an `erased` hash of its URL and of each provider id: the deletion script's last step (alpha-p10-030); `{ counts, hash }`, the rows deleted by table and the URL's hash, which the script logs |
| `upsertCompany({ source, provider, company })` | `{ company, created }`: the company with the page (`linkedin.com/company/<slug>`) or the domain, merged as a person is |
| `getCompany(companyId)` | the company, or `company_not_found` (404): what qualification's assessment reads (alpha-p6-020) |
| `linkPersonToCompany({ personId, companyId })` | the person with its `companyId` set; `company_not_found` (404) |
| `recordHash({ linkedinUrl \| providerId, kind, dropReasons? })` | a `rejected_candidate` hash for 90 days, its drop-reason codes counted, or an `erased` one for good |
| `isHashed({ linkedinUrls })`, `isHashed({ providerIds })` | one query for the list: a map of each input, as given, to `rejected_candidate` or `erased`; an input with no live hash, or a URL that does not normalize, is absent |
| `createLeadForPerson({ personId, source: { kind, ref, at?, label?, url? } })` | `{ lead, created }`: the person's one lead, `pending`, labeled with its first source's kind (`imported` or `signal`); a later source is appended to `sources` once per kind and `ref` (the import job's or the signal source's id), the label and `firstSourceAt` kept. A source (`LeadSource`, `{ kind, ref, at, label?, url? }`) may carry, from the module that adds it, `label`, its name as that module shows it, trimmed, 200 characters at most, and `url`, an https URL that parses, 2048 at most (signals: the source's label and post); the same kind and `ref` again takes the label and URL it brings, each where given, keeping its place and `at`; an entry stored before has neither. A label or URL off its rule is `contacts_input_invalid` naming it, and nothing is written; `person_not_found` (404) |
| `createLeadsForPersons(inputs)` | `{ lead, created }` per input, as `createLeadForPerson` answers, in one `INSERT … ON CONFLICT`: a lead the person has gets each source it lacks, and the label and URL brought for one it has, within the statement, so no other run's source is lost, and only the first input of a new lead is `created`; `contacts_input_invalid` or `person_not_found` (404) for the whole call, which then writes nothing |
| `applyQualification({ personId, status, fitScore?, confidence?, tier?, why?, snapshotId?, icpVersion?, reason? })` | the lead after one update that replaces the previous decision: a value not given is emptied; `reason`, a code, is `hardFilterReason` for `hard_filtered` and `statusReason` otherwise; a status off the list is `contacts_input_invalid`; `lead_not_found` (404) |
| `listLeads({ status?, tier?, review?, sort, limit, cursor? })` | `{ leads, nextCursor }`, each lead with its `person`; `review: "unreviewed"` keeps the leads without a decision: by descending fit (no score last), newest first, or unreviewed first (`sort`: `fit`, `newest`, `unreviewed_first`: the leads without a decision, then Good lead, then Not a fit, each by descending fit), ties by person id; the cursor is opaque, a malformed one `contacts_input_invalid` |
| `getLead(personId)` | the lead with its `person`; `lead_not_found` (404) |
| `leadNeighbours({ personId, status?, tier?, review?, sort })` | `{ previous, next }`: the person ids of the leads just before and just after this one in `listLeads`' order for that view, `null` at either end; the lead itself need not be in the view; `lead_not_found` (404) |
| `leadsPendingQualification({ limit, icpVersion? })` | up to `limit` (1 to 500) `pending` leads, with `icpVersion` also those decided at an older ICP version, oldest first: what the qualification batch reads (alpha-p6-040) |
| `latestReviews({ week? })` | each reviewed lead's latest decision, by person id: `{ personId, decision, reasonCode, reasonText, goodReasonText, snapshotId, decidedAt }`; with `week`, an ISO week, only the leads whose latest decision was made in it; `contacts_input_invalid` naming `week` for a week the year does not have. What qualification's golden set reads (alpha-p9-050) |
| `purgeExpiredHashes()` | deletes the workspace's expired `rejected_candidate` hashes and returns the count; a worker schedule calls it later |
| `normalizeLinkedinUrl(url)` | `https://linkedin.com/in/<slug>`, lowercased, without `www.`, query, fragment or trailing slash; `null` for anything else |
| `countryOf(location)` | the ISO 3166-1 alpha-2 code of the country a location text names, or `null`, as `location_country` is read (signals' country filter, alpha-p8-030) |
| `fields` | the PII class of every column ([docs/data.md](docs/data.md)) |

An input off the rules is `contacts_input_invalid` (400, `details.fields`, never a value). The registries: `ids` (`per`, `wco`, `phash`, `rvd`; a lead's key is its person's), `errors`, `permissions` (`contacts.read`, `contacts.write`, `leads.read`, every role; `reviews.read`, `reviews.write` and `exports.read`, the leads CSV's and qualification's golden set's, Owner, Admin and Member), `events` (`contacts.lead_reviewed { workspaceId, personId, decision }`) and `settings`. `api` is the NestJS module the api host mounts under `/v1/workspaces/:workspaceId/contacts`.

## Routes

A member's session and `contacts.read`; the schemas are `schemas/persons.ts`, the requests `api-calls/alpha-p5-010-persons-and-companies.http`.
- `GET /v1/workspaces/{workspaceId}/contacts/persons?limit&cursor`: `{ persons, nextCursor }`, newest first, `limit` 1 to 100 (50); `cursor` is the `nextCursor` of the page before.
- `GET /v1/workspaces/{workspaceId}/contacts/persons/{id}`: the business fields and `provenance`, `{ field: { source, provider, at } }`; 404 `person_not_found`. A provider's member id is never answered.

The lead routes need `leads.read`; the schemas are `schemas/leads.ts`, the requests `api-calls/alpha-p5-020-leads.http`.
- `GET /v1/workspaces/{workspaceId}/contacts/leads?status&tier&review&sort&limit&cursor`: `{ leads, nextCursor }`, each lead's fields with `person`, its name, title, company and URL, and `reviewReasonCode`, the latest decision's code when it is Not a fit; `sort` `fit` (the default), `newest` or `unreviewed_first`, `limit` 1 to 100 (50); 400 `contacts_input_invalid` for a cursor that is not the page before's in the same sort. The unreviewed-first requests, this and the neighbours', are in `api-calls/alpha-p10-080-contacts-polish.http`.
- `GET /v1/workspaces/{workspaceId}/contacts/leads/counts`: `{ counts }`, how many of the workspace's leads are in each of the six statuses, every status named, from one grouped query (alpha-p6-050; its request in `api-calls/alpha-p6-050-lead-list.http`).
- `GET /v1/workspaces/{workspaceId}/contacts/leads/{personId}`: the lead's fields with `person`, as the person route answers it; 404 `lead_not_found`, also for another workspace's person.
- `GET /v1/workspaces/{workspaceId}/contacts/leads/{personId}/neighbours?status&tier&review&sort`: `{ previous, next }`, as `leadNeighbours` answers them, for the lead page (alpha-p6-060; its request in `api-calls/alpha-p6-060-lead-page.http`); 404 `lead_not_found`, also for another workspace's person.

The review routes (alpha-p9-040) need `reviews.write` to decide and `reviews.read` to read; the schemas are `schemas/reviews.ts`, the requests `api-calls/alpha-p9-040-review-labels.http`. No route updates or deletes a decision.
- `POST /v1/workspaces/{workspaceId}/contacts/leads/{personId}/review { decision, reasonCode?, reasonText?, goodReasonText? }`: 201 and the decision, appended with the lead's snapshot, fit and tier of now and made the lead's `review_status`, `contacts.lead_reviewed` published; 400 `review_reason_required` for Not a fit without a code, `review_text_required` for `other` without `reasonText` or Good lead without `goodReasonText`; 404 `lead_not_found`.
- `GET /v1/workspaces/{workspaceId}/contacts/leads/{personId}/reviews`: `{ reviews }`, the hundred newest, newest first; 404 `lead_not_found`.
- `GET /v1/workspaces/{workspaceId}/contacts/reviews/summary?week`: `{ decided, goodLeads, notAFit, top20: { count, goodLeads, reviewed, rate }, byReason }` for an ISO week (`2026-W43`, UTC), as [docs/concepts.md](docs/concepts.md) "The weekly rate" defines it; 400 `contacts_input_invalid` naming `week` for a week the year does not have.

The export (alpha-p9-050) needs `exports.read`; the schema is `schemas/exports.ts`, the request `api-calls/alpha-p9-050-exports.http`.
- `GET /v1/workspaces/{workspaceId}/contacts/exports/leads.csv?status&tier&review`: the leads of the list's view (every lead without a filter) by descending fit, ties by person id, as a file: `text/csv; charset=utf-8`, UTF-8 with a byte-order mark, `attachment; filename="leads-<UTC date>.csv"`, written as each hundred leads are read; 400 `validation_failed` for a filter off its list. The columns, in order: `first_name`, `last_name`, `headline`, `title`, `company`, `location`, `fit`, `tier`, `confidence`, `status`, `review` (the latest decision), `review_reason` (a Not a fit's code in English), `review_text` (the tester's words), `source`, `why` (the bullets in English, one a line) and `linkedin_url`. A cell starting with `=`, `+`, `-`, `@`, a tab or a carriage return starts with an apostrophe ([docs/security.md](docs/security.md)).

## Screens

`ui/nav.ts` puts the lead list in the navigation's Leads group and declares the lead page (core/apps/web/docs/screens.md); their text is `contacts.leads.*` and `contacts.lead.*`.
- `/w/{workspace}/leads` (`ui/leads/`): `page.tsx` reads the counts per status and the first twenty leads of the URL's view (qualified leads by fit without one), as the member, while `contacts.leads.loading` and a skeleton of the table show (`skeleton.tsx`); `list.tsx`, in the browser, filters by status (`qualified` first), tier and review (Unreviewed only, off at first), sorts by fit, newest or unreviewed first (the Sort select; the Fit and Qualified headers too) and pages by the api's cursor, Previous and Next, the last request winning. A filter or sort change goes into the address first, `?status=…&tier=…&sort=…&review=…` (`ui/leads/query.ts`), so that a reload, Back and Forward return to the view; a filter change shows the loading state in place of the table, a sort or a page keeps the table, busy. A failed read is `contacts.leads.error`, its code in words and Try again. The header holds the counts, a pill per status, the view's own marked and `aria-current` (`contacts.leads.counts_label`), and Export; the filters and the sort sit in one bar above the table. A row shows the person's initial, then the name (the LinkedIn URL when the person has none) with the title at the company under it, the tier's icon and word, the fit and its bar, the confidence's icon and word, the source (the most recent by `at`: a signal source's label, linked to its `url` in a new tab with `rel="noreferrer"`, or, without a label, Signal linked to the source's runs, `/w/{workspace}/sources?runs=<ref>`, where its post is; Imported; then +N, the others named on hover and for a screen reader), the time of the last decision, the first why bullet in its key's words, or the reason of an `ai_failed` lead, and the latest review decision, a Not a fit's reason on hover and for a screen reader; the name links to the lead page with the view in its query. An empty view says why: no lead yet, with links to `/w/{workspace}/sources` and `/w/{workspace}/import`; none in this status and tier; none left to review. Export (alpha-p9-050) downloads the CSV of the filters set, through the api's client, keeps the file's address for 40 seconds, and shows a failure's code in words with Try again.
- `/w/{workspace}/leads/{personId}` (`ui/lead/`, alpha-p6-060): `page.tsx` reads the lead, whose name titles the document, then, while `contacts.lead.loading` shows, qualification's snapshot (`GET …/qualification/leads/{personId}/snapshot`, none until one is scored) and the neighbours in the query's view, as the member; another workspace's person, or one without a lead, is the page's not-found state (`states.tsx`: `contacts.lead.not_found`, why, and the way back to the list's view), and nothing more is read. `header.tsx` shows the way back to the list and to the previous and next lead in that view, then the header: the person's initial and name, the title at the company, the tier, the status unless qualified, the fit and its bar, the location and where the name came from, with the `actions` slot at its end; the loading state shows the way back and the header too, from the lead read first. `view.tsx` shows under them, for a `needs_review` lead, the criteria the model could not judge (`contacts.lead.unknown_criterion`), then two columns on a wide screen. The first: the headline, title, company and location, each with its source and date; the LinkedIn link, in a new tab with `rel="noopener noreferrer"`, to the person's URL normalized (`normalizeLinkedinUrl`), none when it does not normalize; the why bullets; the model's summary under its label; the six verdicts with their evidence and weight behind a disclosure; the disqualifiers; the `evidence` and `draft` slots. The second: the decision (status, fit, tier, confidence, ICP version, and the time of the snapshot, or for a lead never scored the time it was decided, its `updated_at` as in the list), a hard filter's or an `ai_failed` lead's reason and the `cost` slot; the `review` slot under it. In one column, on a phone, the second comes right after the why bullets, so that the review is near. Qualification's codes are worded by its keys through `useKeyText`, read as data: a code without a key shows nothing, on the page as in the list.
- **The lead page's slots** (`ui/lead/slots.ts`): `evidence`, `draft`, `review`, `actions` and `cost`. A module adds a panel with `panels` in its `ui/nav.ts`, `{ page: "contacts.lead", slot, screen }`, its server component in `ui/<screen>/panel.tsx` with `{ workspace, personId }`; `pnpm web:routes` writes the panels into the generated route, and a slot the page does not list fails it. The panels of a slot render in the order of their modules' folders, behind the slot's boundary (`ui/lead/slot-boundary.tsx`, alpha-p8-050): the shared loading state while they render, and for a panel that throws, on the server or in the browser, `contacts.lead.slot_failed`, the code in words and Try again, which reads the page again (`router.refresh()`) and renders the slot anew; the page and the other slots stay up. Next.js's `notFound()` and `redirect()` pass the boundary.
- **The review panel** (`ui/review-panel/`, alpha-p9-040), contacts' own in the `review` slot: `panel.tsx` reads the lead's decisions on the server, as the member; `form.tsx`, in the browser, offers Good lead with its text field, or Not a fit with the fifteen reasons and the text for Other, then Confirm, and shows the answer as the latest decision and at the head of the history, with no reload. Its text is `contacts.review.*`.

## Settings

`HASH_SALT`, in the `modules/contacts` block of `deploy/.env.example`, a secret: the key of the hashes, 32 characters or more. A host starts without it, and the first command that hashes fails with `hash_salt_missing` (500). Keep it for good: under another key no earlier hash matches, erased people's included.

## Testing

`@whytide/contacts/testing`, in test files only: `useHashSalt(salt)` sets a fixed salt for the process in place of `HASH_SALT`; `useContactsClient(asRole("app"))` points the export's own runs at a test's schema. `pnpm -F @whytide/contacts test` runs the units (the CSV's cells among them), the commands end to end (`tests/persons.test.ts`, `tests/leads.test.ts`, `tests/review.test.ts`, and `tests/batch.test.ts` for the batched commands against the one-row ones), the column test and the isolation test (`test:tenancy`); the routes' tests are the api host's, `core/apps/api/tests/contacts-persons.test.ts`, `contacts-leads.test.ts`, `contacts-review.test.ts` and `contacts-exports.test.ts`, and the screens' the web's, `core/apps/web/tests/lead-list.spec.ts`, `lead-page.spec.ts`, `review-panel.spec.ts`, `export-button.spec.ts`, `contacts-states.spec.ts` (every empty, loading and error state) and `contacts-url-state.spec.ts` (the view in the address), on leads the e2e api's test-only route writes through these commands.

## Decided here

- `hashOf` is HMAC-SHA-256 keyed by `HASH_SALT`, rather than SHA-256 over the salt and the value: the standard keyed hash, with no ambiguity where the two meet. Its input names its kind, `url:<normalized URL>` or `pid:<provider id>` (alpha-p5-020), so the two never share a hash; erased hashes live for good, so the format is fixed from the first row.
- One hash row per value and workspace: a later rejection adds its reasons and keeps the first expiry; `erased` replaces a `rejected_candidate` and never expires (the CHECK `person_hashes_expiry`).
- `location_country` is read here from `location_text`: its last comma-separated part, or the whole, by the English country names of Node's ICU and a few other spellings (`domain/countries.ts`); no new dependency.
- The profile also takes a full `name`, split into first and last when neither is given, for imports.
- Persons link their company, and leads their person, by `(workspace_id, id)` (alpha-p5-020): the database refuses a link across workspaces. The company key restricts a delete, since `SET NULL` would empty `workspace_id` too; no command deletes a company.
- A lead (alpha-p5-020) is keyed on its person and created `pending`. `applyQualification` replaces the whole decision, so no score, tier or reason outlives the status it came with; `newest` sorts by the lead's `created_at`, kept to the millisecond so that the cursor matches the row exactly; a list without `status` shows every status.
- `why` holds up to three `{ key, params }` bullets (alpha-p6-030's shape) and is classed `business_contact`, since its values may quote the profile: the log redaction and the workflow-input lint treat it as the profile's fields.
- The lead list (alpha-p6-050) shows a decided lead's `updated_at` under Qualified, since `leads` has no time of qualification; that header sorts by `newest`, the api's `created_at`. A why bullet's words come from its key at run time (`useKeyText` of `@whytide/ui`), as an error code's do: the module that writes the key owns its message, and a key missing from the bundle shows nothing. An `ai_failed` lead's reason is `contacts.leads.reason.ai_failed`, a select over callAgent's reasons (`invalid`, `empty`, `length`, `content-filter`, `gates`); any other shows the plain sentence. The page names the document with React's `<title>`, since the generated route re-exports the page's default alone and a `metadata` export would not reach Next.js.
- The lead page (alpha-p6-060) keeps the list's view in its URL rather than in the browser's storage: a link to a lead opens the same neighbours for anyone, and the way back finds the list as it was left, its page aside. Without a view in the URL, the page takes the list's first one, qualified leads by fit, for the neighbours and the way back. The neighbours are two reads of one row each, by the list's own order and cursor, rather than a page of the list around the lead.
- The lead page's slots are names in `ui/lead/slots.ts`, which the route generator reads, rather than a registry at run time: a panel in an unknown slot fails the build, and the page imports no module of the panels. The panels render on the server, so that a panel reads its own module's api as the member.
- Review decisions (alpha-p9-040) are append-only in the database too: `app` has no UPDATE on `review_decisions`, and their key to the lead restricts a delete, so `erasePerson` deletes them first, by person. The lead's `review_status` and `reviewed_at` are set by a raw update that leaves `updated_at`, the list's time of qualification, and never lets an earlier decision replace a later one. The event is `contacts.lead_reviewed`, since an event's name starts with its module's. Good lead needs its text, as the task decided, a field of the other kind is `contacts_input_invalid`, and a blank text is none. The summary adds `top20.reviewed`, so that the screen can tell a final rate from a partial one; its top twenty follow the list's order, ties by descending person id.
- The leads CSV (alpha-p9-050) holds the list's columns under fixed names, not words, so that a formula or a script reads them in any language. Codes are written as the api answers them (`qualified`, `hot`, `not_a_fit`); the why bullets and a Not a fit's reason, which the list shows in words, are worded in English by the platform's messages, from the keys the lead holds, so no module is imported: a bullet by its key (qualification's), a reason by `contacts.review.code.<code>`, as the review panel says it. The order is the list's by fit, whatever its sort; the filters are the list's. The PII registry (`domain/fields.ts`) decides the columns: one that reads a `personal` field is never written (alpha's columns read none).
- The export opens a run per page of a hundred leads on the module's own `app` client (`domain/store.ts`, `whytide:own-runs`), rather than the request's run, which a slow download would hold past its five seconds. The Export button reads the file through the api's client, rather than a link, as every screen reads the api, and names it as the answer's `Content-Disposition` does.
- `latestReviews({ week })` keeps a lead in the week of its latest decision only, so that a lead decided again later carries its newest label, once, in the golden set.
- The batched commands (alpha-p10-080) apply the one-row commands' rules (`mergeInto`, `mergeSource`) to a chunk in memory and write it in one `INSERT … ON CONFLICT`. A person's row is updated only when its id is the one the chunk read (`WHERE persons.id = EXCLUDED.id`): a URL another run inserted meanwhile is read and merged again, three times at most. A lead's missing sources are appended within the statement, by kind and ref, so that two runs never lose each other's, and its stored ones take the label and URL the chunk brings for them.
- A lead's source carries its label and URL (fix-lead-source-post) rather than contacts reading them: signals depends on contacts, so contacts never reads signals' sources. A source arriving again with them renames its entry, so a renamed source shows its new name on its next lead; as an added source does, a rename moves `updated_at`. The list shows Imported for an import, whatever it carries, a label without a URL as text, and the source with the latest `at` first.
- Unreviewed first (alpha-p10-080) orders by `review_status`, none first, then the enum's order (Good lead, Not a fit), then as `fit` does; its cursor holds the status and the fit. The Review column is no sort header, the Sort select asks for it, so the headers keep their Tab order.
- The list writes its view with `history.pushState`, which Next.js's router takes in: a change renders nothing on the server, and `useSearchParams` sees Back and Forward, on which the list reads the view again. The list listens to `popstate` too: after a reload, Next.js 16.4 drops a second Back pressed while it still reads the first, its search params keeping the old view as the address moves.
- The lead page reads the lead before its loading state shows, so that the person's name titles the document from the server's first bytes: React leaves a title inside a Suspense fallback out of the server's page.
- The lead page's not-found state is the page's own rather than `notFound()`: a module adds no `not-found.tsx` to the host's routes, and the state keeps the way back to the list's view.
- Export keeps the file's blob URL for 40 seconds, FileSaver.js's delay, rather than revoking it on the next tick, before Firefox or Safari may have read it.
