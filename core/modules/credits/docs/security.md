# credits: security

Read before changing the module ([security §8](../../../../docs/rules/security.md#8-conduct)); two reviews. Credits must never be granted by an api path ([architecture §10](../../../../docs/architecture.md#10-credits), [coding §7](../../../../docs/rules/coding.md#7-credits)).

- **The roles** (migrations `credits_initial` and `credits_reserve`; `test:roles` of core/packages/db proves them):
  - `app`, the api and the worker: reads the six tables; inserts `credit_usage` and updates only its `quantity`, `credits`, `status` and `settled_at`, never a row's organization or workspace; deletes nothing;
  - `billing_writer`, the seeder: reads, inserts and updates `plans`, `subscriptions`, `credit_grants` and `price_list`; deletes nothing; sees no other table;
  - `credit_balances` is written by the triggers alone, which run as the migration's owner (`SECURITY DEFINER`).
- **A usage row** leaves `reserved` once and its credits never rise (the trigger `credit_usage_settle_once`); no amount is negative (CHECKs on `credit_usage`, `plans` and `credit_grants`). So `app` cannot move or lower another organization's `reserved` or `committed`, nor take back what a commit took.
- **Reserve** locks the organization with `pg_advisory_xact_lock` in the caller's run, so two reserves never pass the check together; commit and release take the same lock first, so no order of them deadlocks. Its lease sweep is raw SQL across the organization's workspaces: it only expires their reservations past their lease. It reads the workspace's `organization_id` in the run, never an organization from the caller; `reserve` and `balance` refuse a workspace other than the run's (`tenant_mismatch`), and the routes read `currentTenant()`.
- **Prices** are written by `onStart` as `billing_writer`, from the code and `PRICE_<ACTION>`: a price changes with a restart only, like the plan; no api path writes one.
- **The seeder** runs as `billing_writer`, never as `app`, from the api's start hook: the api process holds `DATABASE_URL_BILLING_WRITER` for that moment. A one-shot seeder that keeps it out of the serving api is a deploy task.
- **`credits_seed_self_hosted`**, executable by `app` and `billing_writer`: it grants the plan's allowance for a period not granted yet, once per organization and period, to an `active` subscription only, and nothing else; it does not check that the organization exists, so a call with an unknown id makes a wallet nobody can spend.
- **The functions** are owned by the migration's owner, `credits_seed_self_hosted` included: PostgreSQL 16 and later let a role give a function to another role only when it may `SET ROLE` to it, and the owner may not to `billing_writer`. Each one's `search_path` is pinned to its schema with `pg_temp` last, so a temporary table never stands in for a credits table; `EXECUTE` is revoked from `PUBLIC`.
- **Tenants**: `credit_usage` is a tenant table in the two-workspace harness (`tests/tenancy.test.ts`). The organization-level tables are read outside any run through `withoutTenant("credits.<reason>")`, for the organization tenancy gives for the workspace, never an organization id from a request; the worker's daily pass (`credits.period`) lists every organization with a subscription and grants each through the function, as `app`.
- **The cost counter** reads under `credits.read`, in the request's run only: the workspace's usage and cost events, and qualification's, signals' and contacts' public functions, each in the same run. A person of another workspace is `lead_not_found`, never a zero, so a route never says whether an id exists elsewhere. Its answers hold ids, actions, vendors and amounts, no person's data.
- **Personal data**: none; `subject_ref` is an id.
