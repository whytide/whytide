# credits: flows

- **The api's start**: the migrations, then `onStart`: it binds the credits client, then, as `billing_writer`, the fixed plan from `.env`, `credits_seed_self_hosted` for every organization with a subscription, and the price list; the api listens after it (core/apps/api README "Start"). The worker binds the client in `onWorkerStart` before it polls.
- **A new organization**: tenancy's `bootstrapOrganization` writes `tenancy.organization_created` (`organizationId`, `workspaceId`) to the outbox in its transaction; the worker delivers it in a tenant run of the new workspace, and the handler in `events.ts` calls `credits_seed_self_hosted` as `app`: the subscription to the fixed plan, the period's grant, and through the trigger the balance. Delivery is at least once; a second one changes nothing.
- **A new period**: the worker's schedule `credits.period` starts the global workflow `credits_period` every day at 00:05 UTC; its activity, in `withoutTenant("credits.period")` as `app`, lists the organizations with a subscription and calls `credits_seed_self_hosted` for each, one call each. The function grants the period once: the first pass of the month grants it, the others nothing; an api start grants it too (README "Periods").
- **A balance**: `readBalance(workspaceId)` asks tenancy for the workspace's organization, then reads its `credit_balances` row, both outside a tenant run; `GET …/credits/balance` and `credits.balance` read the same in the caller's run.
- **The balance in the header**: each workspace page's load reads `GET …/credits/balance` on the server, as the member; each navigation reads it again from the browser (README "Screens").
- **The cost counter**, in the request's run: a week's costs sum the committed usage and the cost events created in it, then ask qualification for the leads it qualified; a lead's cost asks contacts for the lead (none: 404), sums its own usage and cost events, then asks signals for the runs that read it, divides each run's read credits by its candidates, and sums the engager credits committed for its candidates (README "The cost counter").
- **Reserving**, in the caller's tenant run: the workspace's organization, `pg_advisory_xact_lock` on the organization, the key's existing row if any, the price in the version in effect at the reserve's instant, then `expired` for the organization's reservations past their lease, the check of the balance and the insert of the row `reserved` with that version in `price_list_version`; the trigger moves the balance with each row. The lock holds until the caller's run ends, so the next reserve of the organization sees this one.
- **Committing, releasing**: the organization's lock first, as reserve takes it, then one update of the row, to `committed` with its final credits or to `released`; the trigger moves the balance.
- **A price rise** (README "Declaring a price"): a start whose declared list asks more credits of an action, or another unit, writes the list as a pending version in effect `CREDITS_PRICE_CHANGE_NOTICE_DAYS` days later (30 unset; README "Settings"), `announced_at` the start's instant, and logs `credits: a price rise is announced`. Until that date the version before stays in effect: a reserve charges it and records its version, and `GET …/credits/prices` answers the coming price as `next`. From the date, the new version is in effect. A later start with the same list writes nothing.
- **A drop**, a new action or a removal: a new version at the start's instant, in effect at once; a rise at the same start keeps its current price in it and waits in the pending version.
- **A withdrawal**: a start whose declared list no longer matches the pending version sets its `withdrawn_at`, where it is null, and logs `credits: a pending price change is withdrawn`. Setting the raised price back withdraws it and keeps the version in effect; any other change during a notice withdraws it and announces the declared list for a new notice from that start. A withdrawn version stays in `price_list` and never takes effect.
- **The credit alerts** (README "Alerts"): the schedule `credits.alerts` starts the global workflow `credits_alerts` every 15 minutes, one at a time. `credits_check_alerts`, in `withoutTenant("credits.alerts")` as `app`, reads every organization whose subscription's period holds the run's start, with the period's granted and used credits, inserts a row for each threshold reached (`ON CONFLICT DO NOTHING`), and answers by organization the highest current row whose mail has not gone and whose tries are under 3. For each, `credits_mail_alert` reads the alert with the subscription's period and the balance (an alert mailed already, or of a past period, sends nothing), asks tenancy for the organization's workspaces, opens one run per workspace for its members and keeps the Owners and Admins, each user once, a disabled one left out; it mails each through the app-mail port in their locale, outside any run, one at a time: under an advisory lock of the alert and the user, in a transaction of its own, a recipient already in `credit_alert_mails` is skipped, and one mailed is recorded right after the send, then the lock is let go. Once every recipient is recorded it sets `notified_at` on the alert and on the organization's lower rows of the period still unmailed; a failed send leaves the others to go, then fails the attempt. When the mail fails its attempts, whatever ended them, a start-to-close timeout included, the workflow counts it as failed, raises `tries` on those rows through `credits_fail_alert` and mails the next alert; the next check tries it again, mailing only the recipients not recorded (review-gaps-2).
