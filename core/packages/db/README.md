# @whytide/db

Prisma for the whole product: one schema file per module under `prisma/schema/`, one migration per merge request under `prisma/migrations/`, the database roles, a client per role and the migration runner the api calls before it listens (docs/rules/coding.md §5, docs/rules/security.md §3, docs/architecture.md §6 and §7.6). Every change here takes two reviews.

## Layout

| Path | Holds |
|---|---|
| `prisma/schema/schema.prisma` | the generator and the datasource, once; no model |
| `prisma/schema/<module>.prisma` | the module's models: `tenancy.prisma`, `credits.prisma`, …; the module owns its tables and is the only one that writes them |
| `prisma/schema/_roles.prisma` | a comment pointing at the roles migration; no model |
| `prisma/migrations/<timestamp>_<module>_<change>/migration.sql` | one migration per merge request, hand-written SQL welcome |
| `prisma.config.ts` | Prisma 7's configuration: the folders above and the owner's connection string, from `.env.local` at the repository root or the environment |
| `generated/` | the Prisma client, written by `prisma generate`, ignored by git, never committed |
| `src/` | `createDbClient`, `runMigrations`, the connection strings (`env.ts`), the Prisma CLI spawn, the schema lint, the name check, the commands |
| `index.ts` | the public interface: `createDbClient(role)`, `runMigrations()`, `databaseUrl(role)`, `DbRole`, `Prisma`, `PrismaClient` |

## Conventions, checked by the schema lint

`pnpm -F db lint` runs the structural lint, then `src/cli.ts schema-lint` on `prisma/schema/` and `src/cli.ts migrations-check` on `prisma/migrations/`. A finding prints as `path:line rule message`.

| Rule | A model… | Why |
|---|---|---|
| `table-map` | carries `@@map("<snake_case>")`: `model Person … @@map("persons")` | table names are `snake_case` (architecture §7) |
| `column-map` | maps every column whose name has an upper-case letter: `workspaceId String @map("workspace_id")`; relation fields have no column and need nothing | column names are `snake_case` |
| `timestamptz` | writes every `DateTime` as `@db.Timestamptz()` | instants are `timestamptz` in UTC (requirements 05 §2.3) |
| `id-string-no-default` | has its `@id` as a `String` with no `@default`; a composite `@@id([…])` is fine | ids are `<prefix>_<ULID>`, generated by `platform` (requirements 05 §2.2) |
| `provider-refs` | keeps vendor ids out of its columns: none named with a vendor (unipile, stripe, razorpay, hubspot) and ending in `_id`, such as `unipile_account_id` or `stripe_customer_id`, unless the table is the adapter's own, named `<vendor>_…`; a vendor's id goes to `providerRefs Json? @map("provider_refs")`, keyed by adapter name, through `setProviderRef` of `@whytide/providers` | vendor ids live in `provider_refs` or the adapter's own table, never in domain columns (architecture §9 rule 5, coding §5) |

Two more conventions the lint does not check yet: every tenant row carries `workspace_id` and sits in every unique key (security §3), and a tenant table is marked with the doc comment `/// tenant` on the line before its model, which is how alpha-p1-020 lists the tenant tables for its checks (`parseSchema()` in `src/schema-lint.ts` reads the mark).

## Migrations

- One per merge request, named `<module>_<change>` (`credits_tables`, `signals_add_source_kind`): `pnpm db:migrate:dev --name <module>_<change>` creates it from the schema and applies it to the worktree's database; the name is checked before Prisma runs. Prisma prefixes the folder with a timestamp, and `migrations-check` fails on a folder that is not `<timestamp>_<module>_<change>`.
- What Prisma cannot say (roles, policies, triggers, pgvector and full-text indexes, partitions) is hand-written SQL inside the same `migration.sql`, with a comment in the module's schema file pointing at it; `pnpm db:migrate:dev --name <name> --create-only` writes the migration without applying it, so the SQL can be added, then `pnpm db:migrate` applies it. Every statement runs as the owner, in one transaction per migration.
- Migrations run at start, expand first, and stay compatible with the previous release (architecture §7.6).
- `tests/fixtures/migrations/` holds the fixtures of `tests/migrate.test.ts`; nothing there reaches a real database.

## The roles

Two database roles from the first migration, so that a bug or a bypass in the tenant API stays bounded (security §3, architecture §6), and an owner for the schema:

| Role | Connection string | Used by | Can | Cannot |
|---|---|---|---|---|
| owner | `DATABASE_URL_OWNER` | migrations: `runMigrations()` in the api at start, `pnpm db:migrate`, `db:migrate:dev`, `db:reset`, Studio | DDL; it owns the database and every table | serve a request |
| `app` | `DATABASE_URL` | the api and the worker, `createDbClient("app")` | read and write tenant rows; read plans, subscriptions, grants, prices and balances (credits' migration `credits_initial`) | DDL; write a plan, a subscription, a grant, a price or a balance; delete a usage row; read `_prisma_migrations` |
| `billing_writer` | `DATABASE_URL_BILLING_WRITER` | the seeder, `createDbClient("billing_writer")` | read, insert and update plans, subscriptions, grants and prices (`credits_initial`) | delete them; anything else: by default it sees no table |

How the migration `20261021000000_db_roles` does it: `app` and `billing_writer` are group roles without a login, shared by every database of the cluster, created when missing (on a bare cluster the migrating role needs `CREATEROLE` for that); both may connect and see the schema `public`, which only the owner may create in; the owner's default privileges give `app` `SELECT, INSERT, UPDATE, DELETE` on every table and `USAGE, SELECT` on every sequence a later migration creates, and `billing_writer` nothing. Default privileges belong to the role that runs the migration, so every migration runs as the owner, always.

A module restricts or grants per table in its own migration, after the `CREATE TABLE` Prisma wrote:

```sql
-- credits: app reads plans and never writes them; billing_writer writes them (docs/15 §11).
REVOKE INSERT, UPDATE, DELETE ON TABLE "plans" FROM app;
GRANT SELECT, INSERT, UPDATE ON TABLE "plans" TO billing_writer;
```

The login roles come from the environment, never from a migration, which is static SQL and cannot hold a password. In development `pnpm env:create` creates three per slice (deploy/README.md): `owner_<slice>`, who owns `app_<slice>` and may create a database (`db:reset`, Prisma's shadow database), `app_<slice>` as a member of `app` and `billing_writer_<slice>` as a member of `billing_writer`, all with the stack's password, and writes the three connection strings to `.env.local`; `pnpm env:destroy` drops them. A deployment creates its login roles the same way with its own secrets (the deploy task). The decision is docs/adr/0003-roles-from-alpha.md.

The three variables are the `packages/db` block of `deploy/.env.example`, declared in `src/env.ts` through the platform's `defineConfig` as secrets (core/packages/platform/README.md, Config), each one optional there, since a process holds only the strings it uses; `pnpm env:check` compares the block with the declaration. `databaseUrl(role)` is the loud failure: a missing string names the variable and `pnpm env:create`, a malformed one names the variable and the example block, never a value.

## Commands

From the repository root; every one reads `.env.local` and takes a variable already in the environment first. `db:migrate`, `db:migrate:dev`, `db:reset`, `db:studio` and the tests import `@whytide/platform` from its `dist/`, so they need the platform built once (`pnpm build`, or `pnpm -F db typecheck`, whose `tsc -b` builds the referenced project first); `db:generate`, the lint and the checks do not.

| Command | Does |
|---|---|
| `pnpm db:migrate` | `prisma migrate deploy` as the owner: applies the pending migrations in order and prints their names; a no-op when nothing is pending; exit 1 when a migration fails, and again until `prisma migrate resolve` or `pnpm db:reset` |
| `pnpm db:migrate:dev --name <module>_<change> [--create-only]` | a migration from the schema, for a person at a terminal; asks for the name when none is given |
| `pnpm db:reset` | drops the slice's database and creates it again as the owner, then migrates; refuses while the api, the worker or Studio is connected |
| `pnpm db:studio` | Prisma Studio on the slice's database, as the owner, on localhost |
| `pnpm db:generate` | the client into `generated/`; `build`, `typecheck` and `test` run it first. Prisma regenerates the client only when what it is made from changed (the files of `prisma/schema/`, `prisma.config.ts`, the installed `prisma` and `@prisma/client`, the arguments, hashed into `generated/inputs.sha256`) or a client newer than that stamp was written by other means, one run at a time under the lock folder `generated.lock/`, and deleting `generated/` forces a new one |
| `pnpm -F db lint`, `typecheck`, `build`, `test` | the structural lint plus the schema lint and the name check; `tsc -b` into `dist/`; the tests below |

Every command runs the Prisma CLI through `prisma()` in `src/prisma-cli.ts` with `CHECKPOINT_DISABLE` set, so the CLI never phones checkpoint.prisma.io for update notices or usage data: the api starting up makes no network call beyond its database. In code: `runMigrations()` returns the names it applied and throws when one fails, so the api host calls it and does not listen on a throw (architecture §3); `createDbClient("app")` is the client the api and the worker use, `createDbClient("billing_writer")` the seeder's; the caller calls `$disconnect()`.

## The platform's stores: cost events and idempotency records

The platform declares what `recordCost` and `withIdempotency` need from a transaction as small interfaces, `CostStore` and `IdempotencyStore` (core/packages/platform/README.md, "Cost events" and "Idempotency"), and never imports this package; `costStore(tx)` and `idempotencyStore(tx)` (`src/cost-store.ts`, `src/idempotency-store.ts`, exported from `index.ts`) adapt a Prisma transaction or client to them, and a host wires the two together inside its tenant transaction:

```ts
await client.$transaction(async (tx) => {
  await recordCost(costStore(tx), { workspace_id, feature, vendor, model, units });
  return withIdempotency(idempotencyStore(tx), { workspaceId, key, requestHash }, () => handle(tx));
});
```

The tables are `prisma/schema/platform.prisma` (alpha-p1-055, migration `20261021102315_platform_costs_idempotency`): `cost_events` and `idempotency_records`, tenant tables that `app` reads and writes through the default privileges, no grant of their own; `idempotency_records.response_body` is marked `/// pii`, since it holds what an endpoint answered. `insertIdempotencyRecord` is `INSERT … ON CONFLICT DO NOTHING` (`createMany` with `skipDuplicates`), so two requests with one key at once never both store, and the loser's transaction stays usable until the platform rolls it back; a JSON `null` body is stored as `Prisma.JsonNull`; the sweep deletes by `created_at`, a range on the `(workspace_id, created_at)` index. The tests, `tests/cost.test.ts` and `tests/idempotency.test.ts`, run end to end on the `app` connection. Until alpha-p1-020's `withTestDb()` is merged (a schema per worker, what docs/rules/delivery.md §4 asks for), each creates a database of its own next to the slice's as a stopgap, `tests/scratch-database.ts` (created as the owner, migrated with the real migrations, dropped at the end), so that the file does not race `tests/migrate.test.ts`, which recreates the slice's database; then both tests move to `withTestDb()` and the helper goes. A killed run leaves `app_<slice>_cost` and `app_<slice>_idem` behind; the next run drops and recreates them. `tests/migrate.test.ts` reads the real migrations from the folder, so a task that adds one changes no expectation there.

## The outbox store

`prisma/schema/platform.prisma` holds the platform's own tables; the runtime that uses them lives in `core/packages/platform` and the stores here, because `db` depends on `platform` and never the reverse. The first is the `outbox` (migration `platform_outbox`): a tenant table of event rows that a module writes in the same transaction as its change and the worker delivers ([platform README, "Events and the outbox"](../platform/README.md#events-and-the-outbox)), with two indexes: `(workspace_id, created_at)` for a workspace's rows, and `(delivered_at, dead_at, next_attempt_at)` for the claim, which reads the due rows of every workspace and would scan the table on every poll without it.

- `outboxWriter(tx, workspaceId)` makes the `OutboxWriter` that `publish()` takes from a Prisma transaction client: `tx.outboxEntry.create` inside the caller's transaction.
- `createOutboxStore(prisma, { claimTimeoutMs? })` implements the platform's `OutboxStore` as the `app` client: `claim(limit, now, fn)` opens an interactive transaction (60 seconds by default, handlers included; the runtime reads `claimTimeoutMs` and starts no row past half of it), runs `SELECT … FROM outbox WHERE delivered_at IS NULL AND dead_at IS NULL AND next_attempt_at <= now ORDER BY created_at, id LIMIT n FOR UPDATE SKIP LOCKED` as raw SQL, the one query Prisma cannot say, and hands the rows and the marks (`delivered`, `failed`, `dead`: `updateMany` by `id` and `workspace_id`) to `fn`; `replay(ref, now)` puts a dead row of the workspace back in the queue. The claim reads every workspace's rows, as the worker's cross-tenant job; the policies of zeta will need an exception for it.
- `tests/outbox.test.ts`, end to end: events declared, published in a rolled-back and a committed transaction, delivered once in a tenant transaction (`set_config('app.workspace_id', …, true)`, the way `withTenant` sets it), retried with growing waits, dead-lettered after `OUTBOX_MAX_ATTEMPTS`, replayed, and two deliverers over twenty rows, one holding a row locked behind a barrier while the other takes the nineteen others and never that one. The files of `tests/` run at the same time under `node --test`, and `migrate.test.ts` recreates the slice's database, so this test runs on a database of its own, `app_<slice>_outbox`, from `tests/scratch-database.ts` (created and migrated as the owner, dropped at the end).

## Checks in the pipeline

Three scripts of this package carry the pipeline steps of the same name (`tools/ci/steps.json`, docs/rules/delivery.md §4); the runner finds them with `pnpm -r --if-present <step>`, so nothing central lists them. `pnpm -F db test` runs every test file, these included; the whole suite takes about half a minute.

| Script | Proves | Code |
|---|---|---|
| `db:migrate:check` (`pnpm db:migrate:check` from the root) | every migration expands first; the migrations apply from zero on a fresh database; a database at the previous release migrates forward | `src/migrate-check.ts`, `tests/migrate-check.test.ts` on fixtures |
| `test:tenancy` | every `/// tenant` model carries `workspace_id`, an index that starts with it and `workspace_id` in every unique key; a `/// pii` column sits in a tenant table; workspace B never reads workspace A's row of the fixture tenant table | `src/tenancy-check.ts`, `tests/tenancy.test.ts`, the harness below |
| `test:roles` | `app` cannot insert, update or delete in `plans`, `subscriptions`, `credit_grants`, `price_list` and `credit_balances` while it reads them, nor delete in `credit_usage`; `billing_writer` inserts and updates the first four, `price_list` only by a withdrawal (`credits_price_notice`), and deletes none; `app` inserts and reads `credit_alert_mails` and changes or deletes none (`credits_alert_mails`) | `tests/roles.test.ts` on the real tables of the migration `credits_initial` (core/modules/credits/docs/data.md) |

**Expand first.** A `DROP TABLE`, a column drop (`DROP COLUMN`, or `DROP <column>` in an `ALTER TABLE`), a column's `RENAME [COLUMN] <column> TO …` or a table's `RENAME TO …` is a contraction: the check fails on it unless the comment lines right above the statement, with no blank line between, hold `-- contract: <release> …`, naming the release that stopped using what is dropped or renamed, like `-- contract: v0.3.0 stopped reading persons.full_name` (`v0.3.0`, `V0.3.0` and `0.3.0` all name a release). One marker covers the one statement under it, the first one when two share a line. The statements come from a scanner, `src/sql-statements.ts`, that knows `--` and `/* */` comments, string literals, `$$` bodies and quoted identifiers: a drop inside one of them is text, a `;` inside one ends nothing, and the last statement needs no `;`. Not a contraction: dropping a constraint, a default, `NOT NULL`, an index or a type; renaming a constraint or an index. Not read, so not checked: `ALTER COLUMN … TYPE`, `SET NOT NULL`, `ALTER TYPE … RENAME …`, and DDL inside a `DO` block or a function body, which is a string to the scanner; write DDL as plain statements. The check is `src/expand-first.ts`; `tests/expand-first.test.ts` is its unit test.

**The previous release.** `prisma/releases/<tag>.sql` holds a release's migration set: every migration in order, each under a line `-- migration: <folder>`, written by `pnpm db:release-snapshot <tag>` when the release is tagged, never by hand. The check restores a scratch database from the newest snapshot (by version) and applies the current migrations on top; the migrations applied are the release's new ones. Before the first tag there is no snapshot, and the previous release is the migrations folder as committed at the merge base of `HEAD` with `origin/main` (`main` without a remote), or at `HEAD~1` on `main` itself, which is the task's Open question decided here; the snapshot takes over the moment the first one exists. A migration a release shipped is never edited: the database at the release has what the old text made, and the check fails when the new migrations no longer fit it. Both runs work on an empty schema, no rows: a `SET NOT NULL` over existing NULLs, a backfill or a unique index over duplicates passes here and fails on a real database; seeding synthetic rows into the restored database is a later task.

**Scratch databases.** The migration checks need a database from zero, which the delivery rules forbid for the slice's own. `db:migrate:check` creates `<database>_migrate_check` next to it, as the owner, who may create databases, and drops it at the end; `tests/migrate-check.test.ts` and `tests/migrate.test.ts` do the same with `_migrate_check_test` and `_migrate_test`. No test recreates the slice's database; `pnpm db:reset` is the person's. The check's working folder is `.tmp/<suffix>` under the package (`.tmp/migrate_check`), replaced at the start and removed at the end, so a run that died leaves nothing the next one does not replace.

**The tenancy rules**, the first part of `test:tenancy`, with their fixtures under `tests/fixtures/schema/tenancy/` (`pass/` clean, each file of `fail/` the rules its `expected.json` lists):

| Rule | A `/// tenant` model… | Why |
|---|---|---|
| `tenant-workspace-id` | has a `workspace_id` column (`workspaceId String @map("workspace_id")`), not optional | every tenant row carries one (security §3) |
| `tenant-index` | has an `@@index`, `@@unique` or `@@id` whose first field is it (`[…]` or `fields: […]`) | every query of a tenant table starts with the workspace |
| `tenant-unique` | puts it in every `@@unique` and has no `@unique` field alone; the primary key is not a unique key here, ids are `<prefix>_<ULID>` | a natural key (an email, a URL) is unique per workspace, never across |
| `pii-tenant` | a model with a `/// pii` column is marked `/// tenant`; the marker is a `///` line of its own right above the column, `/// pii`, `/// pii: <class>` or `/// pii:<class>` in any case, `//` lines between it and the column allowed | a global table holds no person data (security §1) |
| `pii-on-model` | carries `/// pii` above a column, never above the `model` line | the marker names the column a deletion script covers; on the model it names nothing |

## Register a tenant table in the isolation test

Every test that needs the database imports `@whytide/db/testing` (inside this package, `../testing/index.ts`); nothing in it is for production code, and the package index does not export it, decided here. A module's tenant table gets its two-workspace isolation test (docs/rules/coding.md §11) with one spec under the module's `tests/` and a `test:tenancy` script that runs it; the pipeline collects them with `pnpm -r --if-present test:tenancy`:

```ts
import { asRole, isolationTest, withTestDb } from "@whytide/db/testing";

withTestDb(); // once, at the top of the file

isolationTest("outbox", {
  createRow: (workspaceId) => outboxStore(asRole("app")).insert({ workspaceId /* … */ }), // the module's command
  readAs: (workspaceId) => outboxStore(asRole("app")).pending(workspaceId), // the module's public query
});
```

- `withTestDb({ fixtures })` gives the test file its own schema of the worktree's database, one per node:test worker (every test file is one), named `test_<package folder>_<test file>`, so a crashed run leaves nothing a new run does not replace. The schema starts the way the roles migration leaves `public`: `testing/test-db.ts` reads that migration's text and replays its statements that name `SCHEMA public` with the schema's name in place (`USAGE` for `app` and `billing_writer`, the owner's default privileges for `app`), then the real migrations plus the fixture migrations named (folders of `tests/fixtures/migrations/`) run into it as the owner, so every grant a migration writes holds in it too. No other migration names `SCHEMA public`: it would hold in `public` and silently not in a test schema, so `tests/roles.test.ts` fails on one; a schema-wide grant goes into a `db` task that extends the replay. Every table is emptied before each test and the schema is dropped after the last one; the test files run in parallel on the one database, and none recreates it.
- `asRole(role)` is a Prisma client connected as the role, working in that schema (`createDbClient(role, { schema })`): generated queries name the schema, raw SQL finds it first on `search_path`. It is disconnected after the last test.
- `isolationTest(table, { createRow, readAs })` registers the test: a row in workspace A and one in workspace B; B's read returns B's row and never A's, A's never B's, an empty workspace reads nothing. `readAs` is the read the module's public queries make, scoped the way they are: the query inside `withTenant({ workspaceId, principal }, (tx) => …, { client: asRole("app") })` ("The tenant transaction and the scoped client" below), which the harness takes as it is. `checkIsolation` is the same check as a promise, for a test that expects it to fail.
- `migrationSet(name, fixtures)`, `scratchDatabase(suffix)` and `sqlstate(promise)` serve the migration tests: a temporary migrations folder with its `prisma.config.ts`, a database next to the slice's, the SQLSTATE of a refused statement.
- Synthetic data comes from the platform's `synthetic(seed)` (core/packages/platform/README.md, "Testing"); a factory that inserts rows is a module's own, written on `asRole("app")`.

## The tenant transaction and the scoped client

Every query of a module runs in one workspace, through `src/tenant.ts` (alpha-p1-045; the context is the platform's, core/packages/platform/README.md "The tenant context"):

```ts
await withTenant({ workspaceId, principal }, async (tx) => {
  const rows = await tx.costEvent.findMany({ where: { feature: "qualification" } }); // this workspace's only
  await recordCost(costStore(tx), { workspace_id: workspaceId /* … */ });
});
```

- **The transaction.** `withTenant(context, fn, { client?, timeout?, maxWait? })` opens a Prisma interactive transaction on the `app` client (one `createDbClient("app")` per process by default; a test passes `asRole("app")`), runs `SELECT set_config('app.workspace_id', $1, true), set_config('app.user_id', $2, true)`, the bindable form of `SET LOCAL` (`SET` takes no parameter, and no id enters the SQL text), then `fn` in the platform's tenant context; it commits when `fn` resolves and rolls back when it throws. `app.user_id` is `principal.userId`, `service:<name>` for a worker's `servicePrincipal(name)`. Decided here, against a pg client of its own: the driver adapter holds one connection from `BEGIN` to `COMMIT`, so the settings reach every query of `fn` and are gone when the connection returns to the pool, which `tests/tenant.test.ts` checks on the same backend. It is async: a bad context or a missing connection string rejects.
- **One run at a time.** A `withTenant` or a `globalClient()` query inside a run, also through a `withoutTenant` inside it, is refused: it would hold a second connection, commit on its own and could wait on a lock its own outer run holds. A run holds its connection and its locks, so it does database work only, never a provider, model or egress call; an activity opens one run per database step. Prisma ends a run after 5 seconds (P2028) unless `timeout` says otherwise.
- **The scoped client.** The client `fn` gets, and `tenantClient` (the transaction of the `withTenant` around the caller, for code deep in a module), guard every operation, raw SQL included, and throw `no_tenant_context` outside their own run. On a tenant model, every read, update and delete gets `AND: [{ workspaceId }]` in its where and the workspace in its cursor, so the caller's own, another workspace's id included, can only narrow them; every new row gets the workspace; a row named in another workspace, or an update moving one there, is `tenant_mismatch`. Global models run as written. The generated types still ask for `workspaceId` on a create: pass `currentTenant().workspaceId`.
- **What it refuses**, as `tenant_query_refused` with `details.reason`: `relation`, a relation field of the queried model in any argument (a where at any depth of `AND`, `OR` and `NOT`, a cursor, data, upsert's `create` and `update`, `orderBy`, `select` with `_count`, `include`; the fluent API arrives as a select), since the guard scopes the queried model only: relations are declared in the schema and queried separately, until a later task scopes nested arguments; `unknown_model`; `no_workspace_column`, a marked model without the column; `unknown_operation`; `raw_unsafe`, `$queryRawUnsafe` and `$executeRawUnsafe`; `raw_settings`, a tagged query that names `app.workspace_id` or `app.user_id` in its text or as one whole value, a tripwire (Raw SQL below); `nested_run`, a `withTenant` or a `globalClient()` query inside a run, also through a `withoutTenant` inside it. A foreign-key column is not a relation field: it is written as given, and the database checks only that the referenced row exists, in any workspace; load the referenced row through the scoped client first.
- **Raw SQL.** A tagged `$queryRaw` or `$executeRaw` runs as written, in the transaction with the settings: it names `workspace_id` itself. A session-level `SET` would outlive the transaction on the pooled connection; resetting the connection on release comes with zeta's policies. The settings check is a tripwire for a careless query, not a parser: it reads the text with and without its comments, nested ones too, and without double quotes, whitespace or case. It misses E'' and U& escapes, a name built by concatenation, `RESET ALL`, which empties both settings for the rest of the run, and SQL written to get past it; Postgres refuses `DISCARD ALL` inside the transaction. It fails closed on a table alias named `app`, or ending in `app`, before `.workspace_id` or `.user_id` (`SELECT app.workspace_id FROM outbox_entries app`, `myapp.user_id`): don't alias a table `app`.
- **Tenant models.** `node src/cli.ts generate`, which every script that builds, type-checks or tests this package runs, writes `generated/tenant-models.ts` right after `prisma generate`: `prisma/schema` and its subfolders, parsed with the schema lint's parser (`src/tenant-models.ts`). A tenant model is marked `/// tenant` or has a `workspace_id` column (`@map("workspace_id")` or `@map(name: "workspace_id")`); every other model the parse saw is global; each model's relations are listed. The list is compiled with the client and never committed, and a model it does not name is refused, so one the parse misses fails closed. An unmarked model whose workspace column has another name is global: mark it, and `test:tenancy` checks its column.
- **Global tables.** Inside a run, use the run's client: it reads and writes the global models in its transaction. Outside a run, use `globalClient()` inside the platform's `withoutTenant(reason, fn)`: it runs the global models, outside a transaction, relations refused there too; a tenant model or raw SQL there is `no_tenant_context`. Inside a run, also through a `withoutTenant`, it is `nested_run`: it would wait on the run's locks and connection and miss the run's uncommitted rows.
- **Shutdown.** `disconnectTenantClient()` ends the default `app` client, for a host's shutdown; the next run opens a new one. A host calls it only once its in-flight runs have settled.
- **Limits.** A read across workspaces (the outbox claim, a user's memberships, an email's pending invites) is not the tenant client's: it takes an `app` client by name, as `createOutboxStore` does, until the narrow roles of zeta.
- **Tests.** `tests/tenant.test.ts`: end to end on the outbox table with `isolationTest`, and the refusals on a fixture schema through `scopeQuery`, the guards' pure half. A module registers each tenant table with `isolationTest`, whose `readAs` is its query inside `withTenant(…, { client: asRole("app") })`, and checks each public query with `assertScoped(() => query())` from `@whytide/db/testing`: it runs the query in a workspace's context without the transaction, where the tenant client refuses with `no_tenant_context`; any other error is rethrown, `nested_run` for a command that opens its own run or a query through the global client; it proves the query's first database call only.

## The schema mastra

The migration `ai_mastra_schema` (alpha-p1-135) creates the schema `mastra` and grants `app` `USAGE` and `CREATE` on it; `billing_writer` gets nothing there. It holds Mastra's storage, which core/packages/ai connects as `app`: Mastra creates and upgrades its own tables there when the worker makes its instance (core/packages/ai/README.md "The Mastra instance"), and no migration names a table of it; `prisma/schema/ai.prisma` points at the SQL. The migration names the schema itself, so a test schema of `withTestDb` gets no copy of it: every migrated test schema shares the one `mastra` of the worktree's database, created once.

The tenancy rules skip a model of that schema by name: `EXCLUDED_SCHEMAS` in `src/tenancy-check.ts`, matched against a model's `@@schema("…")`. The pass fixture `excluded-schema.prisma` is a tenant model of `mastra` without `workspace_id`; the fail fixture `other-schema.prisma`, the same model in another schema, is still checked.

## Tables by column

`tenantTablesWithColumn(column, dir?)` of `@whytide/db/testing` (alpha-p10-030) lists the tenant tables of `prisma/schema`, or of a fixture folder, that have the column, each with its schema file's name, the module or package that owns it: `[{ module: "contacts", table: "leads" }, …]`. A tenant table is marked `/// tenant` or has a `workspace_id` column, as for the tenant client. Privacy's `test:tenancy` reads the tables with a `person_id` this way and fails on one whose module registers no eraser (core/modules/privacy/README.md).
