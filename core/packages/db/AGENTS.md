# @whytide/db: the brief for a coding agent

1. Read `README.md`: the layout, the conventions the schema lint checks, how a migration is written and named, the three roles and which process uses which. It changes in the same merge request as the behavior.
2. The rules: [coding §5](../../../docs/rules/coding.md#5-data), [security §3](../../../docs/rules/security.md#3-tenants), [delivery](../../../docs/rules/delivery.md). This package is a security-sensitive path: two reviews on every change, and never a weakened grant.
3. A module task adds `prisma/schema/<module>.prisma` and one migration with `pnpm db:migrate:dev --name <module>_<change>`, nothing else here: a change to the client, the runner or the lint is a `db` task of its own. Hand-written SQL goes inside the migration, with a comment in the schema file pointing at it. A tenant table is marked `/// tenant`, carries `workspace_id` and gets the two-workspace isolation test.
4. Commands, from the repository root: `pnpm db:migrate`, `pnpm db:migrate:dev --name …`, `pnpm db:reset`, `pnpm db:studio`, `pnpm db:generate`; `pnpm -F db lint`, `pnpm -F db typecheck`, `pnpm -F db test` (needs the worktree's slice from `pnpm env:create`).
5. Never commit `generated/`, `dist/` or `.env.local`; the tests check the first and the last.
6. The connection strings are a config block of the platform: declared in `src/env.ts`, documented in the `packages/db` block of `deploy/.env.example`, and `pnpm env:check` keeps the two equal. A `pnpm db:*` command that needs one needs the platform built first (`pnpm build`, or `pnpm -F db typecheck`).
7. A store the platform takes through an interface (`costStore`, `idempotencyStore`) is a `src/<name>-store.ts` on `Prisma.TransactionClient`, exported from `index.ts`, with its end-to-end test under `tests/`. `tests/scratch-database.ts` (a database per test file) is a stopgap so that a file does not race `migrate.test.ts`, which recreates the slice's database: once alpha-p1-020's `withTestDb()` is merged, a database test uses that (a schema per worker, delivery §4) and the helper goes; a killed run leaves `app_<slice>_cost`, `_idem` and `_outbox` for the next run to drop.
8. The platform's own tables (`prisma/schema/platform.prisma`: the outbox, then cost events and idempotency records) get their stores in `src/` (`outbox.ts`), implementing the interfaces the platform declares; the runtime that drives them stays in `core/packages/platform`.

9. A test that needs the database starts with `withTestDb()` from `testing/` (`@whytide/db/testing` outside this package) and reaches it through `asRole(role)`; a tenant table gets `isolationTest(table, { createRow, readAs })` in a spec of its module, run by the module's `test:tenancy` script. No test recreates the slice's database: the migration checks use a scratch database next to it (README "Checks in the pipeline").
10. Module code reads and writes through the client `withTenant` hands it, or `tenantClient` below it, which scope every tenant model by `workspace_id` and refuse to run outside the run; never a relation in any argument (query each model on its own); a foreign key is written as given, so load the row it names through the scoped client first; never the unsafe raw forms or raw SQL naming the settings; a tagged raw query runs as written and names `workspace_id` itself, and a session-level `SET` would outlive the transaction. One run at a time, database work only. A global table goes through the run's client inside a run, and through `globalClient()` inside the platform's `withoutTenant(reason)` outside one; a module's tests check each public query with `assertScoped`, which proves its first database call only (README "The tenant transaction and the scoped client").
