# Security notes of @whytide/platform

## Egress: the addresses the client refuses

**The threat.** Server code fetches URLs a user chose: the website fetch of alpha, later crawlers and webhooks. A URL that points back at the machine or its network turns the server into the attacker's proxy (server-side request forgery): the cloud metadata service at `169.254.169.254` hands the instance's credentials to whoever can make the host fetch it; the stack's own services (Postgres, Redis, Temporal, MinIO, Mailpit, the admin app on its private port) answer on loopback and the Compose network to anything "inside"; a redirect from a harmless public page is the usual way in, so one check at the start is not enough. The same code runs Core and Cloud: one such hole is every installation's.

**The rules** (`http/`, alpha-p1-060) are one pure module with no network, run before a request and again on every redirect hop by the client of alpha-p1-065:

- Addresses are compared as bits (`node:net` `BlockList`), so the IPv4-mapped IPv6 spellings of an address (`::ffff:127.0.0.1`, `::ffff:7f00:1`) and a zoned link-local address are the blocked address they stand for. The decimal, octal and hexadecimal spellings of an IPv4 address (`2130706433`, `0177.0.0.1`, `0x7f.0.0.1`) are refused for two other reasons: the URL parser canonicalizes them to dotted form before `checkUrl` looks at the host, and given directly to `isBlockedAddress` they are not IP addresses, and what is not an IP address counts as blocked.
- The ranges: private (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`), loopback (`127/8`, `::1`), link-local with the metadata service (`169.254/16`, `fe80::/10`), this network and the unspecified address (`0/8`, `::/96`: a connect to `0.0.0.0` or `::` reaches loopback), carrier-grade NAT (`100.64/10`), the IETF protocol assignments (`192.0.0/24`, whole, Oracle Cloud Classic's metadata `192.0.0.192` among them), Azure's wireserver (`168.63.129.16`, reachable from every Azure VM), benchmarking (`198.18/15`, `2001:2::/48`), reserved with the limited broadcast address (`240/4`), site-local (`fec0::/10`), and the IPv6 ranges that embed an IPv4 address, NAT64 (`64:ff9b::/96`, `64:ff9b:1::/48`), 6to4 (`2002::/16`), Teredo (`2001::/32`) and IPv4-translated (`::ffff:0:0:0/96`), through which `64:ff9b::127.0.0.1` would reach a blocked IPv4 address. Multicast (`224/4`, `ff00::/8`) stays unblocked: TCP cannot connect to it.
- `checkUrl` refuses any scheme but `http` and `https` (no `file:`, `gopher:` or `ftp:` reaches the client's library), credentials in the URL (no smuggled basic authentication, no parser confusion around `@`), a host name with an empty label (`localhost..`, which the parser keeps and a deny-list would not match), `localhost` and every name under it, a literal blocked address in every notation the URL parser canonicalizes, and an explicit port other than the scheme's own, so the client cannot be aimed at an internal service on an unusual port.
- Operators deny hosts with `EGRESS_DENY_HOSTS`. `EGRESS_ALLOW_HOSTS` exists for local test servers and is empty in production: an entry opens a port of one exact host (no wildcards, no subdomains) and, when that host is itself loopback by name or a blocked literal, that address; it never vouches for what a name resolves to, so the client checks every resolved address of any other allow-listed host (`allowsBlockedAddress` is that decision).

**The client** (`fetchSafe`, `http/client.ts`, alpha-p1-065) does what the rules leave to it, and guarantees:

- **It connects only to addresses it checked.** Each hop resolves the name once and refuses the hop when any answer received is blocked (`127.0.0.1.nip.io` passes `checkUrl` and stops here); the socket's `lookup` then answers those addresses and nothing else, so a DNS rebind (a public answer for the check, a private one for the connection) has no second resolution to win, and a proxy from the environment is ignored for the same reason. An injected resolver supplies addresses only, and no option skips a check; the one exception is `allowsBlockedAddress`, an allow-listed host that is itself loopback or a blocked literal, for a local test server. `lists` only narrows the operator's: its deny-list adds to `EGRESS_DENY_HOSTS`, and its allow-list is refused in production (`egress_invalid_options`).
- **TLS is checked against the host name the caller gave**, not the address: the request keeps the URL's host name for the Host header, SNI and the certificate check, and forces `rejectUnauthorized`, so `NODE_TLS_REJECT_UNAUTHORIZED=0` cannot turn the check off.
- **Every redirect hop runs every check again** before anything connects: `checkUrl` on the resolved `Location`, then the resolution and the address check. GET only, no body, no credentials, no cookies, and a connection of its own per hop (`agent: false`), so no pooled socket is reused; a step from `https` down to `http` is refused (`egress_insecure_redirect`).
- **Size and time are bounded**: `maxBytes` on the body as received, held in one buffer that grows as bytes arrive, whatever the `Content-Length` claims, and on every byte read off the socket from the first, blank lines before the status line and 1xx heads included (2 × `maxBytes` + 64 KiB, so endless blank lines or `103 Early Hints`, or a body in one-byte chunks, cost no more than another body); it asks for `identity` and decodes nothing, so no compressed body expands past the bound. `timeoutMs` bounds the whole call, the resolution included: DNS goes through c-ares, with one retry well before the deadline and a cancel at it, so a lost query costs a retry, not the call, and a query that never answers holds no thread of libuv's pool (`getaddrinfo` held one about 20 s, and two such calls stalled every lookup of the process). Every hop settles by the deadline whatever the server does; a `101 Switching Protocols` answer, which Node closes without a response, is `egress_request_failed` at once. A bound that is not a whole number in range fails closed.
- **Of the URL, only the host leaves**: the errors carry codes, and for a failed connection Node's short code; the span carries the host, the status, the bytes, the redirects and the duration, never the path or the query; the client writes no log line. Its requests go out with tracing suppressed: the HTTP instrumentation exports no span with the URL and sends the far end no trace context, and its duration metric keeps the method, the host, the port and the status.

Limits, stated: the span and the metric name the host (a company's site in alpha, not a person's); an allow-listed loopback host connects wherever the resolver points, so `EGRESS_ALLOW_HOSTS` stays empty in production; the certificate check is as good as Node's CA store; a server that ignores `identity` sends a compressed body, which callers never inflate without a bound of their own; `/etc/hosts` is not read, so a host blocked there is not blocked for the client, and `EGRESS_DENY_HOSTS` denies it; over `https` the byte bound counts the decrypted bytes, not the TLS records around them, and a flood of session tickets, which carry none, is cut after 8 tickets with `egress_too_large`; a body with neither `Content-Length` nor chunking ends at the close, and while a reset fails it (`egress_request_failed`, `ECONNRESET`), a bare FIN without the TLS `close_notify` cannot be told from a clean close through Node, so an attacker on the path can cut such a body short unnoticed (RFC 9112 §9.8); a site can still serve hostile content within the bounds, which callers treat as data.

**Changing them** means a test for the range in IPv4, IPv6 and mapped form (`tests/egress-address.test.ts`) or for the client's behaviour (`tests/egress.test.ts`, and `tests/egress-dns.test.ts` for its resolver), two reviews ([security §8](../../../../docs/rules/security.md#8-conduct)), and this note brought up to date.

## Secrets at rest

The threat: a copy of the database or of a backup, a log line, or a flaw in the api host reaching a provider's account reference or key in clear ([security §4](../../../../docs/rules/security.md#4-secrets-and-keys); [architecture §15](../../../../docs/architecture.md#15-security), the fifth and sixth layers). What `secrets/` does about it, and where its limits are:

- **Ciphertext only.** A value is stored as a blob under the app master key: envelope encryption, a random data key per value, AES-256-GCM in both layers, the full 16-byte tag. A copy of the database holds nothing readable without the key. The value's associated data is the format version and the context, the wrap's the full header and the context, so a rotation re-wraps the data key and never touches the value.
- **One tenant's secrets.** The organization and the purpose are the associated data of both layers. A flaw that reads rows across organizations, or a row moved between them, gets blobs that fail with `secret_context_mismatch` under any other context: the blast radius of a bug is one organization's secrets, and only where the key is.
- **The worker only.** `decryptSecret` lives in the second package entry, which the lint rule `decrypt-in-worker-only` keeps to `core/apps/worker/` and a module's `workflows/` (the file that holds the unwrap, `secrets/keys.ts`, is under the same rule). The key ring the api can load carries `wrap` only; the unwrap sits behind a map private to `secrets/keys.ts` that only the worker entry reads. The api encrypts and stores; it never holds a plaintext after the write, so a flaw in the api cannot read a token back, and holding the keys does not change that.
- **Key hygiene.** The master key is 32 random bytes from `pnpm secrets:keygen`, set in the environment, never in the repository: gitleaks knows its shape (`whytide-app-master-key` in `.gitleaks.toml`). In the process it is non-enumerable in the config object and lives in the wrapper's closure; a blob names it by an HMAC-derived `key_version`, never by any part of it. The logger redacts every binary value and every key ending in `_ref`, `_token` or `_secret`, in a line's fields, a child's bindings, an error's details and a class instance's fields alike.
- **Rotation.** `APP_MASTER_KEY_PREVIOUS` decrypts what the previous key sealed while the rows' data keys are re-wrapped under the new one; the tooling that walks the rows is zeta's. A blob of a key no longer present fails with `secret_key_unavailable` and its `key_version`, so an operator sees which key is missing.

Limits, stated: the master key in the worker's environment is the trust root, so whoever reads that environment reads every secret; a cloud key service (Cloud 1) moves the wrap outside the process behind the same `wrap` and `unwrap`. GCM with a random 96-bit nonce is safe for well under 2^32 wraps per master key, which rotation keeps far away. A wrapped key that was tampered with is reported as a context mismatch, not as corruption, because the wrap's authentication covers both. Nothing here protects a plaintext once a caller holds it: callers keep it short-lived, zero the buffer and never log it.

## Tenant isolation

**The threat.** One workspace reading or changing another's rows: a query that forgets `workspace_id`, an id taken from another workspace, a relation that leads out of the workspace, a client kept past its transaction, a job that runs without a workspace, a setting left on a pooled connection for the next request ([security §3](../../../../docs/rules/security.md#3-tenants), [architecture §6](../../../../docs/architecture.md#6-tenancy-and-isolation)). Until the row-level policies of zeta, the code is the only barrier: the `app` role reads every workspace's rows.

**What the code does** (`tenant/`, and `src/tenant.ts` of core/packages/db; alpha-p1-045):

- The workspace comes into `withTenant` from the URL or a workflow's input, per transaction, never from a cache; a principal resolved for another workspace is `tenant_mismatch`. `app.workspace_id` and `app.user_id` are set with `set_config(…, true)`, as bound parameters, for the transaction only: the db test finds them empty on the same connection after it. One run at a time: a run or the global client inside a run, also through a `withoutTenant` inside it, is refused.
- The scoped client ANDs the workspace into every where and cursor of a tenant model, so the caller's own can only narrow them, and sets it on every new row; another workspace in a write is `tenant_mismatch`. It refuses what it cannot scope: a relation in any argument, a model the generated list does not name, an operation it does not know and the unsafe raw forms. Raw SQL that names the settings trips a check on its text, a tripwire, not a parser: it misses E'' and U& escapes, a name built by concatenation, `RESET ALL` and SQL written to get past it. The list is generated with the client from the schema: a model marked `/// tenant` or with a `workspace_id` column is a tenant model, any other model the parse saw is global, and one it missed is refused.
- The client throws `no_tenant_context` outside its own run, a client kept from an earlier run or a timer it left behind included. `globalClient()` reaches the global models only, relations refused, inside a logged `withoutTenant(reason)` outside any run; inside a run, the run's client reads them.

Limits, stated: a tagged raw query runs as written; a foreign-key column is written as given: the database checks only that the referenced row exists, in any workspace, so B could point a row at A's and learn that the id exists, and a module loads the referenced row through the scoped client first; a session-level `SET` outlives the transaction on the pooled connection, until the connection reset of zeta; an unmarked model whose workspace column has another name is global; a store built on a client of its own (the outbox claim) is outside the scoped client; nothing reads the settings yet. A module covers these with `isolationTest` and `assertScoped` until the policies read `app.workspace_id`.

## Telemetry and logs

**The threat.** A span or a log line carries a secret or a person's data to the collector and the log store, and from there to whoever reads them ([security §2](../../../../docs/rules/security.md#2-personal-data), [§4](../../../../docs/rules/security.md#4-secrets-and-keys)): a sign-in token in a URL's query, an email address in a vendor's or Prisma's error message, a prompt in an SDK error's fields.

**What the code does** (`telemetry/`, `logging/`):

- Spans: no `url.query`, and `url.full`, `url.original`, `http.url` and `http.target` end before their `?` or `#`, in both directions, set as the span starts (the sampler of `telemetry/`). A caller's `traceparent` that says "not sampled" is recorded all the same, so a caller cannot switch its requests' spans off.
- Logs: an error, at any depth of a line, is its type and code; under `err` an `AppError` adds its message (its code), stack, status and details, any other error its status and stack frames, never its message, in `err` or in `msg`. A cause, and each of an `AggregateError`'s errors, is its type and code. An object deeper than eight levels is written as `[too deep]`, a cycle as `[circular]`.

Limits, stated: spans keep `url.path` (a token placed in a path, inbound or outbound), `client.address`, `network.peer.address`, `user_agent.original` and `server.address`; the instrumentations' exception events and status messages carry an error's message and stack; pg's spans carry the statement text (without its values) and Redis's the command and its keys. The sampler sees only the attributes a span starts with. In a log line, a format argument (`log.error("failed %o", error)`, `%j`, `%s`) is formatted into `msg` by pino, past the serializer and the redaction: never pass an error or a person's data as one. Below three levels the keys of the PII registry are not redacted by name; there errors are reduced and binary values censored, nothing else.
