# @whytide/platform: the brief for a coding agent

Read [README.md](README.md) first: the primitives, how a module registers prefixes and error codes, the log rule, how a host starts telemetry. Then the rules, [coding](../../../docs/rules/coding.md), [security](../../../docs/rules/security.md) and [delivery](../../../docs/rules/delivery.md): a change here is a security-sensitive path and gets two reviews.

- Code: one folder per primitive with its `index.ts`; the package `index.ts` re-exports each folder, one line, sorted. Relative imports end in `.ts`: Node runs the sources, `tsc -b` writes `dist/`, which the package exports.
- Tests: under `tests/` only, with `node:test`, fixtures under `tests/fixtures/<area>/`; `tests/core.test.ts` is the end-to-end test. No test framework.
- Commands: `pnpm -F platform test`, `pnpm -F platform lint`, `pnpm -F platform typecheck`, `pnpm format`, `pnpm env:check`.
- A variable goes into `defineConfig` and the package's block of `deploy/.env.example` together; a log key into `logSchema` and `log-schema.json` together; an error code into the folder that throws it, through `defineErrors`. No new dependency outside its own merge request.
- Messages: every screen string is a key in a module's `messages/en.json`, named `module.screen.purpose`; `i18n/` is the runtime and `pnpm -F platform messages:check` proves the keys (README, "Messages and the i18n runtime").
- A permission action goes into the module's `permissions.ts` through `definePermissions([{ action, roles }], import.meta.url)`, named `<module>.<verb>`; a host asks `can(principal, action, resource?)` before a module command runs, never a handler by itself, and `can()` checks the member's role last (README, "Principal and permissions"). A new action, or a change to an action's roles, updates `core/apps/api/tests/fixtures/permission-table.txt` in the same merge request.
- Egress: a server-side fetch goes through `http/` only (the lint rule `no-raw-fetch`): `checkUrl` before a request and after every redirect, `isBlockedAddress` on every address a host resolves to; the client `fetchSafe` does both, connects only to the address it checked, and its `lists` only narrow the operator's. The ranges, the codes and the two host lists: README "Egress: what is refused" and "Egress: fetchSafe", and `docs/security.md`.
- A store the platform needs from the database (`cost/`, `idempotency/`) is a small interface declared in the folder, implemented in `core/packages/db` with Prisma and wired by a host; the platform never imports `@whytide/db`, and a test that needs the database lives in `core/packages/db/tests/`.
- Events: a module declares them in its `events.ts` with `defineEvents` (payloads carry ids only: a closed object of JSON values, and a field named in the PII registry fails registration), publishes with `publish(tx, …)` inside the transaction of the change and subscribes with `subscribe`; the worker delivers them at least once, nothing calls another module's handler, and a handler finishes well inside the claim's timeout (README, "Events and the outbox").
- Secrets: `encryptSecret` from the root; `decryptSecret` only in `secrets/worker.ts`, the entry `@whytide/platform/secrets/worker`, and the unwrap only through `unwrapperOf` in `secrets/keys.ts`; neither is re-exported from `index.ts` (the lint rule `decrypt-in-worker-only` fails on it). A test passes `loadMasterKeys({ APP_MASTER_KEY: newMasterKey() })` as the third argument; no key in a fixture or a doc.
- A write of a row a member owns asks `canWriteOwned(principal, { ownerUserId, manageAction })` in the module's domain before it writes: the row's owner, or a holder of the module's `<module>.manage` (README, "Principal and permissions", gamma-p6-015).
