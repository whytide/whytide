# unipile: the LinkedIn port's Unipile adapter

**Covers.** The sixteen methods of the [LinkedIn port](../README.md) on Unipile's REST API (`/api/v1`), with Node's `fetch` from this folder only. No SDK: `unipile-node-sdk` is ISC, outside the licence list, for a handful of calls; its entry in `tools/lint/vendor-sdks.json` stays, so that the SDK, if it is ever added, is kept in this folder too.

| Method | Unipile |
|---|---|
| `createHostedAuthLink` | `POST /hosted/accounts/link`: `type: create`, `providers: [LINKEDIN]`, our success and failure URLs, `expiresOn`, `notify_url` (`UNIPILE_NOTIFY_URL`), `name` (`<providerRef>.<token>`: the link's `providerRef`, `whytide-<uuid>`, which it answers bare, and its pairing token, "Pairing"), `single_use: true`, `disabled_options: [cookie_auth]` |
| `getAccountStatus` | `GET /accounts/{id}`: a source in `CREDENTIALS` is `credentials_required`; every source `OK` or `CONNECTING` is `connected`; anything else `error`; another provider's account `linkedin_not_found`; `memberRef`, the account's own LinkedIn member id, is its `connection_params.im.id`, null when the details give none |
| `listPostEngagers` | `GET /posts/{the id in the URL}` once for the post's `social_id`, then `GET /posts/{social_id}/reactions` and `/comments?sort_by=MOST_RECENT`, merged newest first (below) |
| `getProfile` | `GET /users/{the public identifier of /in/…}?linkedin_sections=experience&notify=false`: the current job gives `title`, `companyName`, `companyUrl` and `industry`, and `network_distance` `connected`, `FIRST_DEGREE` as for `getRelation` (absent without one); no profile view is notified |
| `parseWebhook` | the `messaging`, `users` and `account_status` webhooks behind the `Unipile-Auth` header, and the hosted-auth notify behind its pairing token ("Webhooks", "Pairing"); nothing is sent |
| `sendInvite` | `POST /users/invite`: `account_id`, `provider_id` (the `memberRef`) and `message` only when the note has text: no note, an empty one and a blank one send no `message` (`invites.ts`) |
| `withdrawInvite` | `DELETE /users/invite/sent/{invitation_id}?account_id=` |
| `listPendingInvites` | `GET /users/invite/sent?account_id=&limit=100`, a page at a time under a signed cursor ("Cursors"); a row without its id or its member's is dropped; `sentAt` is `parsed_datetime`, else the listing's time |
| `getRelation` | `GET /users/{provider_id}?account_id=&notify=false`: `network_distance` `FIRST_DEGREE` is `connected`; an `invitation` `SENT` and `PENDING` is `invitationPending` (one the member sent is not) |
| `sendMessage` | with `chatRef`, `POST /chats/{chat_id}/messages` (`account_id`, so that Unipile refuses another account's chat, and `text`); without, `POST /chats` (`account_id`, `attendees_ids` the member, `text`), whose answer gives the chat; multipart, never `linkedin[inmail]` (`messages.ts`) |
| `listRecentMessages` | without `chatRef`, the member's chats with the account, `GET /chat_attendees/{provider_id}/chats?account_id=` (none when Unipile answers 404); then each chat's `GET /chats/{chat_id}/messages?after=<since>`, every page, ten at most in one call: the ids, `is_sender` and `timestamp`, never the text, oldest first |
| `searchPosts` | `POST /linkedin/search?account_id=&limit=&cursor=`, body `{ api: "classic", category: "posts", sort_by: "date", keywords }`, `keywords` the phrase in quotes; `limit` at most 49, Unipile's cap for posts; the posts whose text holds the phrase kept (`posts.ts`) |
| `listAuthorPosts` | a member's, `GET /users/{the public identifier of /in/…}?account_id=&notify=false` for the `provider_id`; a company page's, `GET /linkedin/company/{the slug of /company/…}?account_id=` for its `id`, no lookup when the link holds the number; then `GET /users/{id}/posts?account_id=&limit=&cursor=`, with `is_company=true` for a company |
| `listOwnPosts` | `GET /accounts/{id}` for the account's own member id, `connection_params.im.id`, as `getAccountStatus` reads it (an account without one is `linkedin_provider_error`); then `GET /users/{that id}/posts?account_id=&limit=&cursor=` |
| `getCompany` | `GET /linkedin/company/{the slug or number of /company/…}?account_id=` ("Retrieve a company profile"): `employee_count`, `employee_count_range` (`from`, `to`; `to` left out when absent or below `from`), `industry[0]`, `website` (a bare host read as https), the `country` of the location with `is_headquarter` (a two-letter code kept, upper-cased; an English name mapped by company data's `countryOf`; anything else left out), `description` cut to 2,000 characters, the year `foundation_date` starts with; `companyUrl` is the link asked. A fact off its form is left out; nothing else of the answer (followers, employees, phone, permissions, funding) crosses (`company.ts`) |
| `getContactEmails` | `GET /users/{provider_id}?account_id=&notify=false`, no `linkedin_sections` ("Retrieve a profile", developer.unipile.com, read 2026-11-14): the section is the answer's top-level `contact_info`, which LinkedIn fills for a 1st-degree connection only; only `contact_info.emails` is mapped, and only when `network_distance` is `FIRST_DEGREE`: each trimmed, lower-cased, kept when it is an address, each once, the first three. A member who is not a relation, or shows no email, answers `{ emails: [] }`; the section's `phones`, `adresses`, `socials` and the `birthdate` never cross (`contact.ts`). The owner's exception of 2026-11-13, behind `LINKEDIN_CONTACT_INFO_ENABLED` ([the port's README](../README.md) "What the port will never have"). The live check confirms that the plain profile carries the section; until then this is the documented shape |

The three post routes are Unipile's reference as read on 2026-10-30 (developer.unipile.com); neither posts route takes a date ("Known differences").

**Cursors** (`cursor.ts`). A cursor handed out is its state as base64url JSON, a dot, and the HMAC-SHA-256 of the method's name and that JSON under `UNIPILE_CURSOR_SECRET`: the vendor's cursor, with the post (`listPostEngagers`) or the account (`listPendingInvites`) it belongs to. A post read's cursor holds the vendor's cursor of the page being read, how many of its items are done, the vendor's page size and, for an author, its vendor id; its HMAC also covers what it is bound to and does not carry: the account and the phrase (`searchPosts`), the account and the author's link (`listAuthorPosts`), the account (`listOwnPosts`). A cursor this key did not sign for the method, forged, unsigned or another method's, and one of another post, account, phrase or author, is `linkedin_input_invalid`, with nothing sent. A vendor cursor long enough to take ours past the port's 2,048 characters is `linkedin_provider_error` with `reason: "cursor_too_long"`.

**Post links.** `listPostEngagers` reads the six forms signals accepts (`post-url.ts` of its `post_engagers` source, the patterns copied in `constants.ts`): `/posts/<slug>-<kind>-<id>-<code>` (the slug's last `-<kind>-<id>-`) and `/feed/update/urn:li:<kind>:<id>` (each colon plain or `%3A`), `<kind>` `activity`, `share` or `ugcPost`. It asks Unipile for an activity by its number, as before, since a run's cursor keeps it; for a share as `urn:li:share:<id>`, its number being a 404 there; for a ugcPost as `urn:li:ugcPost:<id>`. Any other link is `linkedin_not_found`, with nothing sent. A post read's `postUrl` is `/feed/update/urn:li:<kind>:<id>`, from the item's `social_id`, never its `share_url`, which may carry tracking parameters; its author's link is `/in/<public identifier>` or `/company/<public identifier>`, the vendor id when there is none.

**Vendor and terms.** Unipile, under the account the key belongs to: the owner's in development and on Whytide Cloud, an operator's own on a self-hosted Core. Hosted authentication only: the user connects their own account on Unipile's hosted page, the link hides its cookie option (`cookie_auth`), and no password, cookie or second factor reaches us. The reads are the plan's: a post's engagers, business profile fields and, since gamma, posts (a phrase's, an author's, the account's own), inside the daily cap and the working hours of alpha-p7-040. Unipile advises about 100 profiles per account and day, and 100 a day for the other routes; past LinkedIn's limits it answers 429 or 500 ([provider limits](https://developer.unipile.com/docs/provider-limits-and-restrictions)). Data processing and retention terms: to be read in the account's agreement; where it is kept: not recorded yet.

**Variables** (`deploy/.env.example`); `requires` names the first three and the cursor secret, and `create()` refuses to start without them (`config_invalid`, naming the variable):

| Variable | |
|---|---|
| `UNIPILE_BASE_URL` | the account's API address, `https://apiN.unipile.com:PORT`, from Unipile's dashboard; https only |
| `UNIPILE_API_KEY` (secret) | sent as `X-API-KEY`; read once when the adapter starts, never logged |
| `UNIPILE_WEBHOOK_SECRET` (secret) | at least 32 characters (`openssl rand -hex 32`), the `Unipile-Auth` header of the webhooks below and the key of the pairing tokens ("Pairing") |
| `UNIPILE_NOTIFY_URL` | the public URL of `POST /v1/linkedin/webhooks/unipile` (alpha-p7-030); `createHostedAuthLink` fails with `config_invalid` without it |
| `UNIPILE_CURSOR_SECRET` (secret) | at least 32 characters (`openssl rand -hex 32`), the key cursors are signed with ("Cursors"); not the webhook secret, so that rotating that one fails no run in flight |

Rotating the key: create a key in Unipile's dashboard, set it, restart the api and the worker, then revoke the old key. Rotating the secret: set the new value on the three webhooks (or register new ones and delete the old), set `UNIPILE_WEBHOOK_SECRET`, restart; meanwhile webhooks are refused (401) and Unipile retries each five times. The notifies of links made before the restart are refused too, their tokens being the old secret's: a user connecting then connects again. Rotating the cursor secret: set it and restart; a run in flight then fails once on its old cursor (`linkedin_input_invalid`).

**Webhooks.** Three sources, registered once per Unipile account, each with the `Unipile-Auth` header and against `UNIPILE_NOTIFY_URL`, the public address of `POST /v1/linkedin/webhooks/unipile`: `messaging` for `message_received`, `users` for `new_relation`, and `account_status` with every one of its events, since its default leaves out `ok`, `connecting` and `stopped`. `pnpm unipile:webhooks register` does it from the env file (`deploy/scripts/unipile-webhooks.ts`, [deploy/docs/runbook.md](../../../../../deploy/docs/runbook.md) "LinkedIn webhooks"): it replaces the webhooks named `whytide-<source>`, never another, and `check`, `list` and `remove` go with it. The raw API's shape, for reference, from a shell where the four variables are set, so that neither the key nor the secret is typed or shows in the process list:

```sh
register() { # $1 the source, $2 its events as a JSON array
  printf '{"source":"%s","name":"whytide-%s","request_url":"%s","format":"json","events":%s,"headers":[{"key":"Unipile-Auth","value":"%s"}]}' \
    "$1" "$1" "$UNIPILE_NOTIFY_URL" "$2" "$UNIPILE_WEBHOOK_SECRET" |
    curl --fail-with-body --silent --show-error "$UNIPILE_BASE_URL/api/v1/webhooks" \
      --header @<(printf 'X-API-KEY: %s\n' "$UNIPILE_API_KEY") \
      --header 'content-type: application/json' --data-binary @-
}
register messaging '["message_received"]'
register users '["new_relation"]'
register account_status '["ok","reconnected","creation_success","sync_success","credentials","error","stopped","deleted","connecting","creation_fail","permissions"]'
```

`listed` lists them, through `GET /api/v1/webhooks`, filtered to each webhook's id, name and URL (Unipile's list gives no source; the name says it). That answer may hold each webhook's headers, `UNIPILE_WEBHOOK_SECRET` among them, so it is never printed whole:

```sh
listed() { # each webhook's id, name and URL, never its headers
  curl --fail-with-body --silent --show-error "$UNIPILE_BASE_URL/api/v1/webhooks" \
    --header @<(printf 'X-API-KEY: %s\n' "$UNIPILE_API_KEY") | grep -oE '"(id|name|request_url)": *"[^"]*"'
}
```

An account registered under alpha deletes its `account_status` webhook first (`DELETE /api/v1/webhooks/{id}`, the id from `listed`), which named four events only, unless it is named `whytide-account_status`, which `register` replaces.

`parseWebhook` (`webhooks.ts`) looks at the header first. With `Unipile-Auth`, it compares it with the secret before it reads the body, in constant time (both hashed with SHA-256, so the length does not leak): a wrong one is `linkedin_webhook_invalid` with `reason: "secret"`, whatever the body. Without it, the request is the hosted-auth notify or nothing: `reason: "token"` unless its pairing token verifies ("Pairing"). `JSON.parse` never runs on a body with neither proof. A verified body off the documented shape is `reason: "body"`. The details are `method` and `reason`, never the body. Then:

| Source and event | Port event |
|---|---|
| `messaging`, `message_received` | `message.received`: `eventKey` and `messageRef` its `message_id`, `chatRef` its `chat_id`, `senderMemberRef` the sender's `attendee_provider_id`, `attendeeMemberRefs` the attendees', `text` its `message` (empty for an attachment alone), `sentAt` its `timestamp`; `fromAccount` true only when the sender's id is the account's own, `account_info.user_id`, and false when either is missing |
| `users`, `new_relation` | `invite.accepted`: `memberRef` its `user_provider_id`, `eventKey` `new_relation:<account_id>:<user_provider_id>`, the event having no id; no `occurredAt`, the event having no time |
| `account_status`: `OK`, `RECONNECTED`, `CREATION_SUCCESS`, `SYNC_SUCCESS` | `account.connected`, without `providerRef` |
| `account_status`: `CREDENTIALS` | `account.credentials_required` |
| `account_status`: any other, `ERROR`, `STOPPED`, `DELETED`, `CONNECTING`, `CREATION_FAIL`, `PERMISSIONS`, one Unipile adds later or none | `account.disconnected`, never `ignored`: an account pauses on any status that is not OK (docs/07 §5.7) and comes back at the next `OK` |
| any other event of a verified source: a reaction, a read receipt, an edit | `ignored` |
| the hosted-auth notify, `{ status, account_id, name }`, without the header | `account.connected` with the account and the link's `providerRef` ("Pairing") |

A message without the sender's id takes the chat's one attendee other than the account as its sender; with neither, it is `reason: "body"`, refused rather than `ignored`, so that no reply is acknowledged as nothing. A message the account sent itself, from LinkedIn or through Unipile, comes as `message_received` too, told apart by the two ids; with either missing it reads as inbound, which may hold a sequence: the safe side. A reply's `senderMemberRef`, an acceptance's `memberRef` and a profile's `providerMemberRef` are all the member's LinkedIn provider id, so that a reply matches its invitation before any chat exists.

**Pairing.** `createHostedAuthLink` makes each link with `name` `<providerRef>.<token>`, the token being the HMAC-SHA-256 of the providerRef under `UNIPILE_WEBHOOK_SECRET`, in base64url: 43 characters, 88 with the providerRef (Unipile documents no limit). It still answers the bare `providerRef`, which linkedin keeps as the link's `provider_link_ref`. When an account connects through the link, Unipile posts the notify to `notify_url` with the name and no header or signature, so the token is the notify's one proof: `parseWebhook` finds the one link name in the raw text and checks its token in constant time before the body is parsed, then answers `account.connected { providerAccountRef, providerRef }` for a notify of `CREATION_SUCCESS` or `RECONNECTED` that carries that same name. A wrong token, none, another providerRef's or another secret's, or two names are `reason: "token"`, the account id never read; the right token in another body is `reason: "body"`. The token proves the link, not the account id beside it: the name travels between Unipile and Whytide only, over HTTPS, for a single-use link that lives 30 minutes. Rotating `UNIPILE_WEBHOOK_SECRET` refuses the notifies of links made before ("Variables"). The notify carries no member id: linkedin reads it through `getAccountStatus` once the account is paired.

**Network.** One HTTPS request per call, a few for a call that pages or looks a chat up, from the process that makes it (the api for links and webhooks, the worker for reads and sends), to `UNIPILE_BASE_URL` only, JSON or, on the chat routes, multipart, with `fetch` rather than the egress client, as docs/rules/security.md §5 allows inside a vendor adapter; 30 seconds at most, redirects never followed (`redirect: "manual"`), so that the key never follows one: a 3xx is `linkedin_provider_error` with its `status` and `reason: "redirect"`, its `Location` neither logged nor kept. A request that fails before any answer is `reason: "unreachable"` with the network error's code when Node gives one in that short upper-case form (`code`: `ECONNREFUSED`, `ECONNRESET`, `UND_ERR_SOCKET`), never its message; past the 30 seconds `reason: "timeout"`. An answer is read up to `MAX_ANSWER_BYTES` (1 MiB, `constants.ts`): a longer one, its length declared or not, is `reason: "answer_too_large"`, never parsed. Out go the key, the account id, a post's id, a profile's public identifier or a company's slug, a search's phrase, for a link our return URLs, `UNIPILE_NOTIFY_URL` and its name, for a send a member's id, a chat's and a note's or a message's text; back come the hosted URL, the account's sources, a post's reactions and comments with their authors' public fields, posts with their text and their authors' public fields, a profile with its contact info (of which `getContactEmails` keeps the emails alone, and `getProfile` nothing), invitations with their notes, messages with their text: only the port's business fields leave this folder. Nothing here logs or opens a span, and `fetch` is not instrumented (the platform's telemetry turns undici off).

**Provider refs.** None stored here. The account id is the port's `providerAccountRef`, which alpha-p7-030 keeps encrypted; a link's `providerRef` is the `name` Unipile echoes, before its pairing token ("Pairing").

**Known differences.**
- A reaction has no date at Unipile: its `engagedAt` is the start of the listing, carried by the cursor, and its `dateKnown` false, so a post's reactions come back on every listing above the comments written before it; a comment's `engagedAt` is its `date`, `dateKnown` true, or the listing's start when that does not parse, `dateKnown` false.
- Every reaction kind is `like`; reposts and replies to comments are not read. An engager the port cannot hold, an out-of-network member with no profile URL, is dropped.
- Unipile takes no idempotency key: the port's is dropped, and the one-send guarantee is the caller's ([../README.md](../README.md) "Sending"). A send answered without its ids, which Unipile's reference allows, is `linkedin_provider_error` (`reason: "no id in the answer"`): no ref is made up.
- An invitation accepted shows in `getRelation` only once LinkedIn and Unipile have synced it, and a message sent in `listRecentMessages` the same way: the acceptance lag (docs/07 §5.3). A member in no chat Unipile knows of has no messages, so a chat started but not yet synced reads as none.
- A 5xx may hide one of LinkedIn's limits (Unipile's provider limits): the adapter reports it as `linkedin_provider_error` and never retries; the caller pauses.
- `chatRef` is taken as given: `sendMessage` sends `account_id` with it, but `listRecentMessages` reads the chat's messages without checking the member, as the fake does.
- A 429's wait is the Retry-After header's, as in alpha; the `retry_after` of its body is not read.
- Neither posts route filters by date. The adapter reads Unipile's pages newest first, keeps the posts at or after `postedSince`, and ends the read at the vendor page whose last dated post, a repost aside, is before it, so a pinned older post at the top of an author's page ends nothing. One call loads `MAX_LOADS` (10) vendor pages at most; past them it answers what it has, with a cursor.
- The search asks for the phrase in quotes, LinkedIn's exact phrase, which Unipile does not document; the adapter keeps only the posts whose text holds the phrase, as whole words in any case and spacing, and passes over the rest, never logged. A vendor page of posts is at most 49 there, one below the port's 50.
- A repost is passed over in every read, as are a search hit that is not a `POST` and an item whose author the port cannot hold, a member without an id. The excerpt is the post's `text` cut by `postExcerpt`, empty without text; a missing name or headline is empty.
- A read's first call sets the vendor's page size, its `limit` (49 at most for the search), which the cursor keeps: a later call's `limit` caps the page it answers. A page that ends inside a vendor page resumes by reading that vendor page again, so a post published or deleted in between shifts it: a post can come back twice or be missed, as an engager can.
- A link also expires at Unipile's daily restart, whatever `expiresAt` says.
- An accepted invitation reaches the `users` webhook only when Unipile next reads the account's relations, at random times, up to 8 hours after the acceptance: the acceptance lag (docs/07 §5.3). An invitation sent with a note shows sooner, its acceptance opening a chat whose first message comes through `messaging`.
- Unipile stops the message webhooks while an account is not `OK` and gives up on a delivery after five retries, so a reply can be missed: the chat read before each message catches it (beta-p1-050), not the webhook. No webhook comes for the messages older than a first connect.
- The shapes are the documentation's as read on 2026-10-22, for the send side and the webhooks on 2026-10-29, and for the post reads on 2026-10-30 (developer.unipile.com): the comment's date format, the error types, the notify's headers and whether every message event carries `account_info.user_id` are to be verified on the sandbox.

**Errors.** A vendor's answer becomes one of the port's codes with `details.method`, its `status` and its short error `type`, never its body:

| Unipile | Port code |
|---|---|
| 429 | `linkedin_rate_limited`, `retryAfterSec` from Retry-After (60 without it) |
| 404 | `linkedin_not_found` (for `listRecentMessages`' lookup: no messages) |
| `errors/account_restricted`, `errors/checkpoint_error`, `errors/expired_credentials`, `errors/disconnected_account`, at any status | `linkedin_account_disconnected`, `reason` `restricted`, `checkpoint`, `credentials_required`, `disconnected` |
| 422 `errors/cannot_resend_yet`, `cannot_resend_within_24hrs`, `limit_exceeded`, `connection_limit_reached` | `linkedin_limit_reached` |
| 422 `errors/already_invited_recently`, `already_connected`, `no_connection_with_recipient`; `cannot_invite_attendee`, `invalid_recipient`, `blocked_recipient`, `user_unreachable` | `linkedin_send_refused`, `reason` `already_invited`, `already_connected`, `not_connected`; `recipient_unavailable` |
| any other status or type, a 5xx, a redirect, a timeout, an unreachable host, an answer too large or off the documented shape | `linkedin_provider_error`, with `{ status, type }`, `{ status, reason }` or `{ reason, code }`; never retried here |

**Sandbox.** In the environment, not `.env.local`: the four required variables and `UNIPILE_NOTIFY_URL`; then connect a LinkedIn account by hand in the sandbox, and name a post it can read, `UNIPILE_TEST_POST_URL`, with at least five engagers (the suite reads it over three pages), and a profile, `UNIPILE_TEST_PROFILE_URL`. For the post reads, a phrase, `UNIPILE_TEST_POSTS_PHRASE`, and an author's page, `UNIPILE_TEST_AUTHOR_URL` (a member's `/in/…` or a company's `/company/…`): with both, the post cases read the account's search, the author's posts and its own over the last seven days, a source of fewer than five posts or more than three pages of 50 skipping its case. `pnpm -F providers test:contract` then runs the live suite, the account `UNIPILE_TEST_ACCOUNT_ID` names or the first connected one; without a `UNIPILE_TEST_*` variable the suite is skipped, so that the adapter's own variables never reach the network alone. These variables are the tests' only: they stay out of `deploy/.env*.example`.

**Live sends.** The send cases run only with all three of `UNIPILE_TEST_ACCOUNT_ID` (the sender), `UNIPILE_TEST_RECIPIENT_PROVIDER_ID` (the `provider_id` of a second account the owner controls) and `UNIPILE_LIVE_SENDS=1`, and never under `APP_ENV=production`, where the suite refuses to start (`tests/live.ts`). They never pick an account or a recipient. One run sends at most one invitation, to the recipient while the two are not connected, withdrawn at once, even when its case fails midway, and one message, while they are; so one run sends the one or the other, and each needs its own run.

**Tests.** `tests/company.test.ts` runs `getCompany` offline on `tests/fixtures/company-profile.json` and its variants: the mapped facts only, the headquarters' country by code or name, a bare website, a long description, missing facts, and the 404, disconnected and off-shape answers as the port's codes with nothing of the body. `tests/contract.test.ts` is the port's suite on the sandbox, skipped without the variables; `../../tests/safety/unipile-no-live-send.test.ts` holds its gate to account, through a local counter that every request of the suite goes to. `tests/mapping.test.ts` runs offline on the synthetic fixtures of `tests/fixtures/`, one per method's success and per error answer, served on 127.0.0.1: the profile without its contact info, a 1st-degree connection's contact emails alone and none for anyone else (gamma-en-087), the merge with its cursor and without the authors' contact data, the id asked for each form of post link, the link and the status with its member id, every webhook, status and notify fixture, the six send-side methods, the three post reads over their pages (a search over two vendor pages, a member's, a company's and the account's own posts), the excerpt's cut, `dateKnown`, each error answer, the size limit, the cursors and the config checks; and the log check, which runs every method in a child process (`tests/logged-calls.ts`) and finds no key, secret, cursor, pairing token or vendor body in any line it writes, nor a phrase, an excerpt, a name or a headline in a line or a metric label. The event cases of the contract suite run offline there too, on the world of `tests/live.ts`, which builds Unipile's events signed with the secret, and has no `account.status` to give (Unipile's statuses map to the three kinds above). `../../tests/safety/unipile-webhook-verify.test.ts` holds the verification to account: a wrong header or token is refused before `JSON.parse` runs, and no status is `ignored`.
