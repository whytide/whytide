# The s3 adapter of the files port

**Covers** every method of the [files port](../README.md) on an S3-compatible store through `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner`, path-style: in development MinIO from the shared stack, the slice's bucket, which `pnpm env:create` creates. A `Readable` body is read into memory before `PutObject`, which needs the length, 25 MiB at most (`FILE_MAX_BYTES`): alpha's imports are 5 MB at most; larger files need multipart uploads (`@aws-sdk/lib-storage`, a new dependency). `presignDownload` checks the file with `HeadObject`, then signs a `GetObject` answered with `Content-Disposition: attachment`, so a browser saves the file and never renders it, for a day at most until a caller needs more. A presigned URL shows whoever holds it the endpoint, the bucket, the whole key with the workspace id, and the access key id, never the secret. Never a public-read bucket or object.

**Vendor and terms**: none in alpha. MinIO runs as a container of our own stack; no file leaves the host. A hosted store gets its terms here when one is chosen.

**Variables** (`deploy/.env.example`, the files sub-block): `S3_ENDPOINT`, the store's URL; `S3_BUCKET`; `S3_ACCESS_KEY`; `S3_SECRET_KEY`, a secret. `pnpm env:create` fills all four for the slice. Each is required when the adapter starts, `config_invalid` naming the missing ones, and the credentials and the region go to the client, so the SDK never walks its credential chain (`AWS_*` variables, `~/.aws`, the cloud metadata address), and the FIPS and dual-stack endpoints are pinned off, so `AWS_USE_FIPS_ENDPOINT` or a profile's `use_fips_endpoint`, which a custom endpoint refuses, changes nothing. No `requires`: the suite runs against the stack and is never skipped. In development every slice uses MinIO's root user: the stack listens on localhost only and holds synthetic data, and a user per slice needs MinIO's admin API, which `env.sh` cannot reach without `mc`. In production the user is limited to the bucket: `s3:GetObject`, `s3:PutObject`, `s3:PutObjectTagging`, `s3:DeleteObject`, `s3:ListBucket`, `s3:GetLifecycleConfiguration`, `s3:PutLifecycleConfiguration`.

**Provider refs**: none; the keys are ours.

**Lifecycle**: before a process's first `put` under a hinted prefix the adapter reads the bucket's rules and, unless its own are there unchanged, writes them back, the others kept, with one rule per hint, `whytide-lifecycle-raw`, `-exports`, `-imports`, each expiring the files tagged `whytide-lifecycle=<prefix>`; `put` sets the tag. A failed write fails that `put` only: a file elsewhere goes through, and the next hinted `put` tries again. The others go back through the SDK's lifecycle model, so a foreign rule must fit it, or the operator adds our three rules by hand: MinIO's `DelMarkerExpiration` and `ExpiredObjectAllVersions` are lost on the round trip. A store answering `NotImplemented` keeps `raw/` forever, so it needs a cleanup job of its own.

**Known differences**: S3 counts whole days and expires a file at the midnight UTC after it is that many days old, so up to a day late; a hint being a maximum, the adapter sets a day less, rounded down (72 hours is 2 days, 7 days 6, 30 days 29), and a file lives between the hint minus a day and the hint, plus the store's delay, since it deletes in the background. MinIO keeps a file as a folder on disk, so a key can be a file and a folder at once (`raw/p.json` and `raw/p.json/q.json`), and its `list` hides the inner file while the outer one exists; S3 and the fake list both. The region is MinIO's default, `us-east-1`, which MinIO ignores unless configured with one; another store's region needs a variable. The SDK's default checksums stay on: MinIO accepts them; a store that refuses them needs `requestChecksumCalculation: "WHEN_REQUIRED"`.
